前面几篇文章介绍了进程、线程、协程，以及 Python Web 服务器如何使用 WSGI 和 ASGI 运行应用。

现在我们已经知道，同步 Web 服务可以通过多进程、多线程处理并发请求，异步 Web 服务则可以利用事件循环，让大量等待 I/O 的任务共享较少的线程。

但这里还有一个问题：既然同步和异步都能处理并发请求，为什么很多人会认为异步框架性能更高？

例如，使用 Flask 编写一个查询数据库的接口，与使用 FastAPI 编写同样的接口，哪一种方式更快？如果 FastAPI 的接口使用普通的 `def`，它还算不算异步服务？如果业务代码主要执行 CPU 计算，`async def` 能不能提高吞吐量？

要回答这些问题，不能只比较框架名称，也不能仅凭某一次压测结果下结论。我们需要先研究两种执行模型对资源的占用方式，再分析吞吐量、延迟和系统瓶颈之间的关系。

## 一、同步与异步真正区别在哪里？

在 Web 开发中，一个请求通常包含两种时间。

一部分时间用于执行计算，例如验证参数、生成数据或者序列化响应。这些工作需要 CPU 实际执行指令。

另一部分时间用于等待，例如访问数据库、调用外部 API 或等待网络数据。这段时间里，程序虽然没有完成请求，但并不一定需要持续使用 CPU。

同步与异步的关键区别，在于**遇到暂时无法完成的操作时，执行资源如何被占用，以及程序如何安排其他任务继续运行**。

对于典型的同步阻塞调用，当前执行线程必须等到操作完成才能继续执行后面的代码。如果希望同时处理多个这样的请求，服务器通常需要提供多个可独立执行的 Worker 进程或线程。

对于基于事件循环的异步调用，当操作需要等待 I/O 时，当前 Task 可以暂停，事件循环安排其他就绪的 Task 执行。等待中的 Task 不需要独占一个操作系统线程。

所以，同步不等于没有并发，异步也不等于多个任务在同一时刻并行计算。同步和异步主要改变了等待期间的执行组织方式。

这一区别，决定了两种模型各自的资源成本与适用范围。

## 二、同步 Web 服务怎样处理并发请求？

首先考虑一种最简单的同步服务器：一个 Worker 进程一次只执行一个请求。

假设接口需要先计算少量数据，再同步查询数据库。如果查询耗时 200 毫秒，执行该请求的 Worker 就可能在相当长一段时间内等待数据库结果。

在它等待时，操作系统可以运行别的进程或线程，但这个同步 Worker 本身通常不能跳过当前调用，直接处理下一条请求。

因此，当多个请求同时到达时，如果当前所有 Worker 都已被占用，新请求就只能等待，或者由服务器、代理按照过载策略拒绝处理。

为了提高并发处理能力，可以增加 Worker 进程。例如，Gunicorn 的传统 `sync` Worker 一次处理一个请求。增加 Worker 数量可以让不同进程同时执行不同请求。

另一种方式是采用线程池。在 Gunicorn 的 `gthread` 模型中，一个 Worker 进程内部可以使用多个线程处理请求。线程 A 等待数据库时，线程 B 可以继续处理其他请求。

这两种方式都能实现并发，但也存在资源成本。进程需要独立的运行环境；线程需要维护线程栈、调度状态等资源。如果大量请求长期阻塞，服务器就可能需要更多工作线程来覆盖等待时间。

不过，**WSGI 并不要求服务器只能采用线程或进程实现并发**。Gevent 等协作式 Worker 也可以服务 WSGI 应用，采用自己的用户态调度机制。因此，本文讨论的“同步模型”，主要是传统的阻塞线程或阻塞 Worker 执行方式，而不是把所有 WSGI 部署都视为同一种性能模型。

## 三、异步 Web 服务怎样处理并发请求？

现在考虑 ASGI 与事件循环模型。

假设三个 HTTP 请求几乎同时到达，每个请求都需要等待数据库返回结果。

服务器可以为它们创建相应的异步执行任务。任务 A 发起非阻塞数据库请求后，在 `await` 处暂停；事件循环继续运行任务 B 和任务 C。

当某个数据库查询完成时，底层驱动与事件循环协作，让对应 Task 重新进入可执行状态。Task 恢复以后，继续处理数据并构造响应。

在这个过程中，多个任务的等待时间可以重叠，不要求每个正在等待的请求都独占一个系统线程。

这就解释了异步模型在大量 I/O 密集型连接下的主要优势：**它能够降低每个等待中任务需要长期占用的线程资源**。

但这种优势有严格的前提。

只有在操作真正支持非阻塞等待，并且任务能够及时让出执行权时，事件循环才能继续调度其他任务。

如果异步函数内部直接执行同步阻塞的数据库调用，或者长时间执行纯 Python 计算，那么它仍然可能阻塞整个事件循环线程。

另外，异步 Task 比线程轻量，不意味着它没有成本。Task 仍然需要保存执行状态、局部对象、缓冲数据和等待关系；事件循环也需要处理回调、超时和任务切换。高并发仍可能耗尽内存或下游资源。

所以，异步的主要价值不是消除资源限制，而是避免在大量等待型任务上浪费不必要的线程资源。

## 四、框架名称并不能决定执行模型

我们习惯把 Flask 称为同步框架，把 FastAPI 称为异步框架。这种说法有一定背景，但不够精确。

Flask 传统上以 WSGI 为基础，不过从 Flask 2.0 开始，它就支持使用 `async def` 编写异步视图。根据 Flask 官方文档，在典型的 WSGI 部署中，异步视图可以在自己的事件循环中运行，从而在单次请求内部并发等待多个异步 I/O 操作。

但这个请求仍然占用对应的 WSGI Worker，不能因此自动把整个服务器变成一个能够在少量线程上调度大量请求的 ASGI 服务。

另一方面，FastAPI 是 ASGI 框架，但同时支持同步和异步路径操作函数。

```python
@app.get("/sync")
def sync_endpoint():
    return {"mode": "sync"}


@app.get("/async")
async def async_endpoint():
    return {"mode": "async"}
```

FastAPI 对普通 `def` 路由函数，通常借助 Starlette 和 AnyIO，将其放在工作线程中执行，再由事件循环等待结果。对于 `async def` 路由，则可以直接在异步执行路径中运行。

这里还有一个值得注意的限制：Starlette 使用 AnyIO 的默认工作线程容量限制器。其默认容量是 40 个令牌，同步路由、同步依赖和某些文件操作可能共享这一容量。令牌限制并不是“一个 Worker 永远只有 40 个线程”的普遍定律，也不等同于 `asyncio` 默认执行器的线程数量。

Django 也同时支持同步与异步视图，并可运行在 WSGI 或 ASGI 环境中。不过，异步请求链中如果存在需要适配的同步中间件或同步组件，仍然可能产生线程占用与模式切换开销。

因此，**比较框架性能，必须同时说明应用代码、服务器类型、Worker 配置，以及实际使用的数据库或网络驱动**。

只说“Flask 对比 FastAPI”而不说明这些条件，很难得出有解释力的性能结论。

## 五、什么叫性能更好？

在比较同步与异步服务器之前，还需要明确性能指标。

最常见的是吞吐量（Throughput），即单位时间内实际完成的请求数量。常见单位是 RPS 或 QPS。

延迟（Latency）表示一个请求从发出到取得响应，经历了多长时间。这里需要说明具体测量边界，例如是否包括建立连接、代理排队和客户端接收时间。

并发量（Concurrency）表示在某一时刻正在执行或等待完成的请求数量。它不是每秒请求数，也不等于 CPU 同时执行的任务数。

在稳定系统中，它们之间有一个很有用的关系，称为 Little 定律：

**L = λ × W**

其中，L 表示系统内平均请求数量，λ 表示长期平均完成速率，W 表示请求在所定义系统边界中的平均停留时间。

如果一个稳定运行的服务平均每秒完成 100 个请求，而一个请求平均在被测系统中停留 0.2 秒，那么这个系统内的平均在途请求数约为 20。

但这个公式不能直接用来证明“增加并发量就一定提高吞吐量”。它描述的是稳定系统中的平均量关系，不是无限扩容的性能承诺。

如果增加的请求超过服务实际处理能力，排队时间就会增加。此时吞吐量可能不再显著上升，但请求延迟会继续恶化，甚至出现超时和错误。

因此，单看平均响应时间或最大 RPS，都不足以评价一个 Web 服务。

实际压测还应该关注 p95、p99 等尾部延迟，以及错误率、CPU 利用率、内存、线程数量、连接池等待时间和下游系统负载。

所谓 p95 延迟，是指在统计范围内约 95% 的请求延迟不超过该值。它能够揭示平均值容易掩盖的慢请求问题。

## 六、异步为什么可能具有更高的吞吐量？

现在可以从执行资源的角度分析两种模型的差异。

假设某个请求的主要工作是等待外部 I/O，平均需要 200 毫秒，程序自身的 CPU 计算开销很小。

如果服务器采用传统的阻塞 Worker 模型，且同时最多只能让 10 个请求处于执行中，那么在理想情况下，每 0.2 秒完成约 10 个请求，相当于每秒约 50 个请求。

这只是用于解释容量关系的简化模型，假设 I/O 时长稳定、任务持续到达，并忽略调度、协议处理和外部系统争用等成本，不是实际框架的基准测试结论。

如果提高可用线程或 Worker 的数量，就有机会让更多等待中的请求同时推进。但线程和进程数量的增长有成本。

异步模型不要求每个等待请求长期占用一个线程，因此在连接和请求数量较大、I/O 等待占比较高的情况下，往往能够以较少的线程管理更多在途任务。

不过，**在途任务数量增加，不等于下游操作真正能够以同样比例并行处理**。

如果数据库连接池只有 20 个连接，即使应用创建了 2,000 个 Task，也不意味着数据库可以同时执行 2,000 条需要独立连接的查询。

多出来的任务可能只是在等待连接池分配连接。系统瓶颈此时从工作线程数量转移到了数据库连接池，或者数据库自身的处理能力。

这就是为什么异步能够提高某些场景的服务器并发效率，但不能无限提高端到端吞吐量。

## 七、哪些场景下异步可能没有优势？

首先是 CPU 密集型任务。

如果某个请求主要执行大量 Python 计算，那么在任务运行期间，事件循环线程需要持续执行这些计算指令。

如果没有可挂起的等待操作，其他 Task 就无法及时在同一个事件循环中运行。

在传统启用 GIL 的 CPython 中，把纯 Python 计算交给线程池，也通常无法获得预期的多核并行加速。对于能够并行拆分的 CPU 任务，可以考虑多进程、支持释放 GIL 的原生扩展，或符合条件的自由线程运行环境。

其次是底层只有同步阻塞接口的情况。

假设业务代码使用同步数据库驱动，却只是把路由函数改成了 `async def`。

此时数据库调用仍然可能阻塞事件循环线程。`async` 关键字本身不会把底层阻塞操作转变为非阻塞 I/O。

对于这样的依赖，直接使用 FastAPI 的同步路由，让框架在线程池中运行它，往往比在 `async def` 中直接阻塞事件循环更合适。

再次是低并发、简单业务场景。

如果系统每天只有少量请求，数据库操作也很快，那么同步模型通常已经足够。引入异步数据库驱动、任务取消和额外的生命周期管理，未必能够带来值得付出复杂度的收益。

最后是下游系统已经成为瓶颈的情况。

如果数据库查询本身很慢，CPU 已经满载，或者外部 API 有严格的并发和速率限制，那么单纯从同步框架迁移到异步框架，通常不能消除这些限制。

框架并不是系统中唯一决定性能的组件。

## 八、用一组实验验证两种执行模型

为了避免把不同 Web 框架自身的路由、序列化和依赖处理开销混在一起，我们先在**同一个 FastAPI 应用**中比较同步路由与异步路由。

这样可以尽量固定 Web 框架、协议服务器和响应格式，只改变请求处理函数的执行方式。

创建 `main.py`：

```python
import asyncio
import time

from fastapi import FastAPI

app = FastAPI()


@app.get("/sync-io")
def sync_io():
    time.sleep(0.2)
    return {"ok": True}


@app.get("/async-io")
async def async_io():
    await asyncio.sleep(0.2)
    return {"ok": True}


@app.get("/blocked-async")
async def blocked_async():
    time.sleep(0.2)
    return {"ok": True}


@app.get("/async-cpu")
async def async_cpu():
    result = sum(i * i for i in range(2_000_000))
    return {"result": result}
```

这里设计了三种不同的 I/O 等待方式。

`/sync-io` 是同步路由，FastAPI 会把同步处理函数安排在线程中运行。`/async-io` 是正确使用异步等待的路由。`/blocked-async` 则故意在异步路由中执行同步阻塞操作，用于观察事件循环被阻塞的影响。

`/async-cpu` 不执行 I/O 等待，而是持续进行纯 Python 计算，用于观察 CPU 密集型任务对事件循环响应能力的影响。

安装并启动应用：

```bash
python -m pip install fastapi uvicorn
uvicorn main:app --host 127.0.0.1 --port 8000 --workers 1
```

接下来使用 k6 发送固定到达速率的请求。创建 `load.js`：

```javascript
import http from 'k6/http';

export const options = {
  scenarios: {
    constant_requests: {
      executor: 'constant-arrival-rate',
      rate: 50,
      timeUnit: '1s',
      duration: '30s',
      preAllocatedVUs: 100,
      maxVUs: 200,
    },
  },
};

export default function () {
  http.get(__ENV.URL);
}
```

在另一个终端依次运行：

```bash
k6 run -e URL=http://127.0.0.1:8000/sync-io load.js
k6 run -e URL=http://127.0.0.1:8000/async-io load.js
k6 run -e URL=http://127.0.0.1:8000/blocked-async load.js
```

不要同时运行这三组测试，否则它们会互相争用同一服务器的资源。

在相同条件下，通常可以预期：正确异步等待的路由不需要为每个等待中的请求占用一个工作线程；同步路由会消耗线程池容量；直接阻塞事件循环的异步路由则可能使其他请求排队，显著恶化尾部延迟。

但是，不能在没有实际执行压测的情况下给出确定的 RPS 或 p95 数值。

这组实验还有两个必须说明的限制。

首先，`asyncio.sleep()` 与 `time.sleep()` 都只是模拟等待，并不能代表真实数据库驱动在连接建立、协议交互、连接池竞争和结果解码方面的全部行为。

其次，固定速率 50 RPS 可能远低于某个测试环境的承载上限。如果三组测试都没有达到瓶颈，它们可能呈现接近的响应延迟。要观察饱和后的行为，需要逐步提高请求到达速率，并监测错误率与资源指标。

更严格的测试应该让负载发生器运行在另一台机器或独立资源环境中，同时固定 Python 版本、依赖版本、Worker 数量、CPU 资源、内存限制和连接池配置。

如果使用真实数据库，还应保证三种方案执行相同的 SQL，并控制数据量、数据库缓存、连接池与下游负载。

最后，k6 的 `http_req_duration` 有自身的测量边界，并不包含全部连接建立和 DNS 开销。解释压测数据时，必须明确使用的是哪一种延迟指标。

因此，这组实验首先用于验证执行模型，而不是直接给整个框架做性能排名。

## 九、工程上应该如何选择？

选择同步还是异步，最好先分析请求的大部分时间消耗在哪里。

如果业务主要执行同步数据库访问、少量外部调用，并且现有代码、依赖和部署体系都围绕 WSGI 建立，那么没有必要仅仅因为异步更流行就立即重写。

如果系统需要处理大量并发 I/O、长连接、流式请求或者频繁的异步网络调用，并且依赖库能够提供真正的异步接口，那么 ASGI 与异步执行模型通常更有吸引力。

但一个成熟的 Web 服务并不需要在所有地方坚持纯同步或纯异步。

FastAPI 可以使用异步路由处理非阻塞 I/O，也可以把同步阻塞操作交给工作线程；CPU 密集型工作还可以交给独立进程或者任务系统。

真正重要的是执行边界清楚。

不要在事件循环中无意地调用长时间阻塞的函数，不要让线程池数量无限增长，也不要把大量请求同时压向容量有限的数据库连接池。

同时，异步程序还需要更明确的任务取消、异常传播、超时和资源清理机制。前面第三篇讨论的这些内容，并不是额外的理论知识，而是异步服务能够可靠运行所必需的工程约束。

一个项目是否值得采用异步架构，应该由负载形态、依赖生态、维护成本与实际测试结果共同决定。

## 十、小结

回到开头的问题：异步 Web 框架是否比同步 Web 框架性能更好？

不能脱离工作负载与部署条件给出统一答案。

同步执行模型通常依靠多个进程或线程，使不同请求在阻塞等待期间仍然可以并发推进。它的优点是执行路径直接，能够自然接入大量同步库；代价是在等待型高并发场景下，可能需要更多的线程或进程资源。

基于事件循环的异步模型，则让等待中的协程任务主动让出执行权，不要求每个等待请求独占线程。它在大量非阻塞 I/O 场景下往往具有更好的资源使用效率，但对阻塞调用、任务生命周期和事件循环响应能力也提出了更高要求。

而决定整个 Web 服务吞吐量的，不只有框架执行模型。CPU、数据库、连接池、网络、序列化和外部服务，都可能先于框架成为瓶颈。

**同步与异步的真正区别，是系统如何组织等待、调度执行资源，而不是某个框架天生能比另一个框架处理更多请求。**

至此，我们从进程、线程与协程开始，依次讨论了 Python 事件循环、Task 生命周期、HTTP 请求路径、WSGI 与 ASGI 服务器接口，以及同步和异步执行模型的性能差异。

这些机制合在一起，构成了理解 Python Web 服务运行原理的一条完整主线。
