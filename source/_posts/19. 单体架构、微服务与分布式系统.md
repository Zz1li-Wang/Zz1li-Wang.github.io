前面几篇文章一直在讨论同一件事：怎样划分职责，让一项业务规则的变化尽可能停留在负责它的模块中。分层架构区分接口、业务与持久化，DDD 则进一步强调领域模型和限界上下文。

经过这些设计，一个订单系统可能已经有了相当清楚的结构。订单模块负责订单的状态和明细，库存模块管理可用数量，支付模块处理交易结果。它们各自有公开接口，也能够独立测试。

接下来，一个新的问题出现了。既然各个模块已经有了边界，是否应该让它们运行在不同的进程里？库存请求量很大时，能否只扩容库存模块？支付服务出现故障时，能否让其他功能照常工作？

从代码模块走向独立服务，表面上只是改变部署方式，实际上却改变了调用、故障和事务的性质。单体架构、微服务与分布式系统之间的关系，可以从一次普通的订单创建开始理解。

## 一、单体架构

最初的订单系统通常不需要复杂的部署。一个 FastAPI 应用接收请求，调用订单、价格和库存模块，最后通过 SQLAlchemy 把数据写进 PostgreSQL。模块可能分别放在不同目录中，但它们被构建和发布为同一个应用。这就是单体架构（Monolithic Architecture）的一种典型形式。

这里的“单体”描述的是应用的交付边界。它不要求所有逻辑写在同一个文件里，也不要求只能启动一个进程。使用多个 Uvicorn Worker，或者在负载均衡器后面部署多份相同的应用，仍然可以是单体架构。数据库也完全可以运行在另一台服务器上。

假设客户购买两件商品。订单模块先取得当前报价，库存模块检查并扣减库存，订单模块写入成交记录。如果订单和库存都存放在同一个关系数据库中，这些操作可以放在一个本地事务里完成。

下面用 SQLite 展示最关键的部分。它省略了价格、权限和 HTTP 接口，只保留库存扣减与订单写入，以便观察事务的行为。示例使用一个连接顺序执行，真实 Web 服务需要按请求管理连接和事务。

```python
import sqlite3

conn = sqlite3.connect(":memory:", isolation_level=None)
conn.executescript("""
CREATE TABLE product (
    id INTEGER PRIMARY KEY,
    stock INTEGER NOT NULL CHECK (stock >= 0)
);
CREATE TABLE orders (
    id INTEGER PRIMARY KEY,
    product_id INTEGER NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0)
);
INSERT INTO product (id, stock) VALUES (1, 5);
""")


def create_order(product_id: int, quantity: int) -> int:
    if quantity <= 0:
        raise ValueError("购买数量必须大于零")

    conn.execute("BEGIN IMMEDIATE")
    try:
        result = conn.execute(
            """UPDATE product
               SET stock = stock - ?
               WHERE id = ? AND stock >= ?""",
            (quantity, product_id, quantity),
        )
        if result.rowcount != 1:
            raise ValueError("商品不存在或库存不足")

        cursor = conn.execute(
            "INSERT INTO orders (product_id, quantity) VALUES (?, ?)",
            (product_id, quantity),
        )
        conn.execute("COMMIT")
        return cursor.lastrowid
    except Exception:
        conn.execute("ROLLBACK")
        raise


order_id = create_order(1, 2)
assert order_id == 1
assert conn.execute("SELECT stock FROM product").fetchone()[0] == 3
```

这里将 `isolation_level` 设为 `None`，关闭 `sqlite3` 的隐式事务开启行为，再通过显式 SQL 管理事务。该写法便于直接展示 `BEGIN IMMEDIATE`；从 Python 3.12 开始，`sqlite3` 同时提供并推荐使用 `autocommit` 属性管理事务模式，实际项目应结合目标 Python 版本选择并统一一种方式。

`BEGIN IMMEDIATE` 在 SQLite 中提前开始写事务；带库存条件的 `UPDATE` 使库存不足时不会继续扣减。订单插入失败，事务会回滚库存修改。两个数据变化共享一次提交或回滚的结果。

这种能力来自数据库事务，不来自单体架构这个名称。前提是相关操作确实使用同一个具备事务能力的数据库及事务连接。如果单体同时调用外部支付网关，本地数据库事务同样不能撤销一笔已经执行的外部支付。

但在订单与库存共用数据库的阶段，本地事务确实提供了一种很有价值的便利：应用可以在一个确定的提交边界里维护相关业务事实。拆分服务时，我们首先要弄清自己即将失去的是哪些便利。

## 二、模块化单体：模块边界先于部署边界

随着需求增加，单体也可能变得难以维护。不过，代码复杂和部署复杂并不总是来自同一个问题。

如果订单模块直接修改库存 ORM 对象，支付模块又依赖订单内部的状态字段，那么模块虽然分在不同目录，业务决定仍然散落在各处。再增加更多进程，并不会改变这种依赖；原来的直接访问甚至可能变成更昂贵的远程访问。

因此，可以先在同一个应用内部建立较严格的业务边界。订单模块通过库存模块公开的 `reserve()` 或 `decrease_stock()` 能力操作库存；库存数据由库存模块维护；订单只保存自身需要的库存处理结果，而不掌握库存表的内部结构。这种组织方式通常称为模块化单体（Modular Monolith）。

模块化单体仍然作为一个应用构建和发布。它允许模块之间使用普通函数调用，也能够在确有需要时使用同一数据库的本地事务。它的价值在于把代码结构与部署方式暂时分开考虑，让团队有机会在较低成本下修正业务边界。

这种边界也可以接受实际检验。比如更改 VIP 优惠的计算规则，订单创建用例可能需要重新验证结果，但库存模块不应为此修改自己的实现；把订单写入方式从普通插入改为批量写入，也不应影响库存的预留规则。若每次修改都必须跨越几个模块寻找同一条业务规则，说明部署之前还有结构问题需要解决。

数据查询是较难处理的地方。后台报表可能要同时读取订单、库存和支付信息，直接跨表 JOIN 通常最方便。模块化单体可以为这类只读场景设置专门的查询路径，同时限制其他模块随意更新不属于自己的表。若未来要独立拆分数据库，这些跨模块查询也必须重新设计数据来源；把所有 JOIN 都藏到 Repository 后面，并不会让它们自动消失。

业务边界并非一开始就能准确判断。订单、库存与支付这些名称看起来很明确，但实际需求可能让我们发现，“库存预留”属于独立的库存职责，“已发货数量”却属于履约过程；商品目录的价格与订单成交价也有不同的生命周期。把这些概念先在代码里理清，通常比直接把目录变成网络服务更容易调整。

当然，单体有自己的交付约束。即使只修改库存模块，通常也要构建和发布整个应用。某项计算密集型工作可能需要额外资源，而增加完整应用实例未必划算。多个团队在同一个发布周期里协调，成本也可能逐渐增加。

这些压力可能推动我们独立部署某项业务能力。但拆分的理由最好足够具体：哪个模块的负载与其他模块显著不同，哪个团队需要独立发布，哪种故障需要隔离。代码行数增加或目录数量增多，本身并不能给出答案。

## 三、微服务：从模块调用到服务调用

假设库存能力已形成稳定的边界，团队决定把它部署成独立的库存服务。订单仍由订单服务处理，库存服务单独运行、发布和扩容。

原来一次 `inventory.reserve(order_id, sku, quantity)` 函数调用，现在可能变成发送 HTTP 请求或 gRPC 调用。库存服务接收请求，使用自己的事务检查并预留库存，再把结果返回给订单服务。即使两个服务都部署在同一台机器上，只要它们通过进程间通信协作，就已经引入了独立进程的故障和通信问题。

这也说明了微服务架构（Microservices Architecture）与分布式系统（Distributed System）的区别。微服务描述应用如何围绕业务能力划分可独立交付的服务；分布式系统研究多个独立计算节点通过通信共同工作时的行为。微服务通常具有分布式特征，但分布式系统还包括数据库集群、消息代理集群等，并不局限于微服务。单体应用连接远程数据库，也需要面对某些分布式故障。

把一个业务模块变成服务，还意味着数据所有权必须更加明确。订单服务如果仍然直接更新库存表，库存服务就无法保证自己的规则总是得到执行。更合理的安排，是库存服务独占库存数据的写入责任，由它决定预留何时成功、何时失败。

独立部署未必要求每个服务都拥有一台独立数据库服务器。不同服务可以暂时使用同一个 PostgreSQL 实例，但应当有可识别的数据所有权、访问约束与演化责任。否则，代码已经拆开，数据库仍然把它们紧紧绑在一起。

这种变化使服务可以独立演进，也使服务之间必须通过稳定的通信契约相互理解。请求字段、错误语义、超时行为与版本兼容，开始成为业务设计的一部分。

进程内接口也不能不加调整就直接改成远程接口。过去订单模块可能反复调用 `get_stock()`、`get_reserved()`、`update_reserved()`，每次函数调用的成本很低；拆分后这些操作会产生多次网络往返，而且中间任意一步都可能失败。库存服务更适合提供一个具有完整业务语义的 `reserve(order_id, sku, quantity)`，由它自己检查条件并提交事务。这既减少网络交互，也让库存不变量仍由库存所有者维护。

同样，服务拆分以后不宜要求调用方知道库存数据库怎样锁行、订单怎样生成预留记录。外部契约描述请求预留的业务意图、可接受的结果与错误，内部实现可以随着服务单独演进。这时第一篇的信息隐藏已经不只是一种代码组织技巧，它还决定远程协议能够保持多长时间的稳定。

## 四、一次超时后的不确定性

订单服务向库存服务请求预留两件商品。库存服务收到请求，在数据库里成功预留，并提交事务。就在它返回响应之前，连接断开了。

订单服务观察到的是超时，却无法仅凭这个超时判断库存是否已被占用。请求可能没有抵达，也可能已经成功执行，只是成功响应丢失。远程调用和本地函数调用的关键差异，便体现在这种结果不确定性上。

例如，使用 HTTPX 发送库存请求时，可以明确设置超时，并传入稳定的业务请求标识：

```python
import httpx


async def reserve_stock(
    client: httpx.AsyncClient,
    order_id: str,
    sku: str,
    quantity: int,
) -> dict:
    response = await client.post(
        "http://inventory.internal/reservations",
        json={
            "order_id": order_id,
            "sku": sku,
            "quantity": quantity,
        },
        headers={"Idempotency-Key": f"stock:{order_id}"},
        timeout=httpx.Timeout(5.0, connect=1.0),
    )
    response.raise_for_status()
    return response.json()
```

这里只展示客户端协议，假设库存服务已经提供对应接口。HTTPX 的连接、读取、写入和连接池超时有各自的含义；它们不能一概视为整笔业务操作的总执行时限。调用方捕获超时时，也不能直接将结果解释为“库存不足”。

最自然的想法是重试，但这会带来第二个问题。如果第一次请求已经成功，第二次请求可能再次占用两件库存。对于产生副作用的操作，重试是否安全，取决于服务端能否识别重复请求。

幂等性（Idempotency）在这里具有明确含义：同一项逻辑操作重复提交，不应重复产生业务效果。示例中的 `Idempotency-Key` 只是把操作身份传给服务端；库存服务还必须可靠记录这个身份，并将它与参数及处理结果关联起来。

可以在库存数据库中为预留记录设置唯一的业务操作键。首次处理时，服务端在事务中完成预留与记录写入；收到相同操作键时，返回已经记录的结果，或者说明原操作仍在处理中。若相同的键对应不同商品或数量，应按契约拒绝。还需要考虑两个相同请求同时抵达的情况，因此单靠“先查询是否存在，再插入”并不足够，必须借助唯一约束和事务消除竞争窗口。

超时后能够重试，并不代表应该无条件重试。调用方需要设置整体截止时间和有限的重试预算，通常采用退避与随机抖动，避免大量请求同时重试而加剧下游故障。对于无法直接确定结果的操作，也可以通过业务操作键查询状态，再决定下一步。

还要区别技术错误与业务拒绝。库存明确返回“余量不足”，通常属于已经作出判断的业务结果，盲目重试没有意义；连接中断、读超时或服务暂时不可用，则需要结合接口契约决定是否查询或重试。一个 HTTP 500 响应也未必证明事务没有提交，特别是服务在提交后组织响应时仍可能出错。把所有非 2xx 状态都转换成同一个“预留失败”，会丢失后续恢复所需的信息。

此时，网络已经影响了订单的业务状态：订单服务可能需要区分“预留成功”“明确失败”和“结果尚未确定”。这是将函数调用改成远程调用时必须付出的设计成本。

## 五、事务的边界发生了变化

单体阶段，订单记录和库存数量可以由同一个数据库事务原子修改。拆分以后，订单服务提交自己的数据库事务，库存服务提交另一笔数据库事务。两次提交之间没有天然的共同回滚机制。

假设库存预留成功，订单服务随后写入订单失败。库存已经发生变化，订单却不存在。反过来，订单先提交成功，而库存请求失败或一直超时，系统就会留下等待处理的订单。

分布式事务协议可以在某些技术条件下协调多个事务参与者，但并不意味着随手创建两个 SQLAlchemy Session，就能获得跨数据库的原子提交。以两阶段提交为例，协调者先要求各参与者准备提交，只有参与者都确认可以提交之后，才发出最终提交指令。处于准备状态的事务可能需要保留锁和其他资源，协调者故障也会增加恢复难度。协议能够解决特定范围的原子提交问题，却必须承担相应的协调代价。在许多业务系统中，团队会改用明确的状态流程来协调这些局部事务。

比如，创建订单时先保存一个 `PENDING_STOCK` 状态，表示请求已经受理，但库存尚未确认。库存服务成功预留后，订单进入 `CONFIRMED`；库存明确拒绝后，订单进入 `REJECTED`。如果处理一直没有完成，系统需要根据超时策略发起查询、重试或者人工处理。

这里实际改变了一项业务承诺。原来客户提交订单后立即得到确定结果，现在可能先得到“处理中”，随后才知道是否成功。业务方是否允许这种延迟，应在架构设计时明确讨论。若必须即时确认库存，可能需要同步预留、事先分配库存额度或选择更紧密的部署与事务边界。异步处理不应悄悄改变产品语义。

当流程继续涉及支付，就会出现更多中间状态。库存已经预留、支付尚未完成；支付失败以后，需要释放预留；支付成功但订单确认失败，需要恢复或核对。这类跨服务、由多个本地事务组成的业务过程，常用 Saga 来组织。

Saga 可以有一个协调者保存流程状态，并依次发出预留、支付和确认命令；也可以由各参与者根据事件协作推进。无论选择哪种形式，失败后的补偿都要作为新的业务操作执行。释放库存不是撤销之前的数据库 `COMMIT`；退款也不是简单抹去一笔已经完成的支付。

补偿可能失败，也可能被重复执行，因此仍需要幂等、重试、状态记录和异常核对。Saga 的作用是把这些协调过程显式化，并不提供与单数据库事务完全相同的原子性。

## 六、消息让协作解耦，也带来新的失败窗口

如果订单提交后需要通知库存、生成报表和发送邮件，让订单服务同步等待所有下游完成，整个调用链会越来越长。某个非关键的通知服务缓慢，也可能拖慢核心交易。

消息队列提供了另一种协作方式。订单服务完成本地操作后发布事件，其他组件根据需要消费。订单不必同步等待报表和邮件处理，消费者也可以按自己的能力扩展实例数量。

但数据库提交与消息发布属于两个不同的操作。订单事务成功后，进程可能在发布消息前崩溃；如果先发消息再提交数据库，又可能出现消费者已经处理，订单却回滚的情况。消息队列没有消除这个问题。

事务性 Outbox（Transactional Outbox）把待发布消息作为一条数据库记录，与订单状态在同一个本地事务内提交。随后由独立的发布进程读取 Outbox，将消息发送到 RabbitMQ 等代理。

```python
# 以下接口为说明事务边界的示意代码
async with session.begin():
    await order_repository.save(order, session)
    await outbox_repository.add(
        event_id=event_id,
        event_type="OrderSubmitted",
        payload={"order_id": str(order.id)},
        session=session,
    )
```

关键条件是两次写入共享同一个数据库事务，而不是代码中都出现了 `session` 这个名字。Outbox 记录必须真正和订单更新一起提交或回滚。

之后的发布仍可能重复。如果发布者已经把消息发到代理，却在标记 Outbox 已发送之前崩溃，恢复后会再次发布同一条消息。消费者因而需要使用稳定的消息 ID 做幂等处理，并对同一业务对象的事件顺序作出明确约定。

尤其在同一个订单连续发生两次状态变化时，不能仅凭消息进入队列的先后，就推断所有消费者一定按相同顺序完成处理。多个发布进程、多个消费者、失败重试和重新投递都可能改变观察到的顺序。需要顺序语义的业务，可以在事件里携带聚合版本，并在消费端检查预期版本，或者利用消息分区和单键有序处理机制降低乱序风险。具体方案仍要结合消息系统的交付保证验证。

Outbox 解决数据库更新和待发布消息之间的原子持久化；Saga 管理跨服务业务过程的步骤与补偿。它们经常配合使用，但所解决的问题不同。

在这个阶段，事件也需要清楚的语义。“订单已提交”可以是一个已经成立的领域事实；“请预留库存”则是希望另一个服务执行的命令。对于尚未完成库存处理的订单，如果直接发布“订单已确认”，下游就可能依据错误的业务事实工作。事件命名、产生时机以及事件版本，都会影响系统的正确性。

## 七、分布式一致性中的几种不同要求

在讨论上述问题时，经常会出现“强一致性”和“最终一致性”。如果不说明要求针对哪项数据、哪种操作，这些词的意义就很有限。

库存服务必须保证，成功预留的数量不会超过它管理的可用库存。这是一条需要在库存所有者内部立即维护的业务不变量。通常可以依靠条件更新、唯一约束和数据库事务保证。

与此同时，订单服务中的状态可能暂时停留在 `PENDING_STOCK`，即使库存预留事实上已经完成。只要系统能可靠接收结果，并在业务允许的时间内更新订单状态，这种跨服务的短暂差异可以接受。

两种要求能够同时存在。单个服务内部维护强约束，多个服务之间允许有明确边界的异步状态传播，是很常见的设计。但所谓最终一致性必须包含使状态收敛的机制：可靠记录、重复投递、幂等消费、失败重试、超时核对，以及不能自动恢复时的人工处置。仅仅把数据更新交给消息队列，并不会保证它最终正确。

还可以进一步规定用户能够观察到什么。客户刚提交订单后立即查询详情，是否至少应看到自己的新订单？后台统计允许晚几秒更新吗？库存预留结果未确认时，页面是否必须明确显示处理中？这些是读取一致性和业务可见性要求。它们应当在接口契约里表达清楚，不能只用一句“系统最终一致”概括。

CAP 定理也经常在这里被引用。它研究的是特定分布式数据系统在发生网络分区时，线性一致性和严格定义下的可用性之间无法同时满足的约束。这里的一致性不是数据库 ACID 中对业务约束的 C，可用性也不是服务运行时间百分比。

网络分区出现后，如果两个相互隔离的节点都对冲突写入返回成功，就难以同时向所有客户端提供单一、实时一致的值；如果为保持线性一致性而拒绝部分请求，则无法满足 CAP 所定义的所有非故障节点请求都获得响应的可用性。

这一定理帮助我们认识网络分区下的限制，却不能简单推出某个订单系统应该选择“CP 数据库”还是“AP 数据库”。真实设计还取决于操作类型、隔离级别、延迟、故障恢复和业务对陈旧数据的容忍程度。读写一个购物车与扣减最后一件库存，可能需要完全不同的保证。

## 八、独立部署的收益与代价

走到这里，微服务似乎给订单系统带来了许多额外工作。它的收益主要出现在另一侧：业务能力可以按不同节奏演进、发布和扩容，团队也能够围绕清楚的数据与服务边界承担责任。

例如，报表计算特别耗费 CPU，就可以独立部署报表 Worker，并根据任务量扩容。库存服务面对突发请求时，可以单独增加处理实例，而无需每次复制整个 Web 应用。

不过，这两种收益都需要具体分析。单体也可以把报表任务放到独立进程，或通过任务队列调度，而不必把所有业务逻辑拆成微服务。库存吞吐如果受限于同一行数据库记录上的竞争，增加服务实例也未必提高处理能力。

独立进程在一定程度上隔离了进程崩溃，却没有自动隔离业务故障。如果订单服务在一次请求中连续等待库存、价格、支付三个下游，任何一个服务持续超时，都可能耗尽上游连接和并发资源，形成级联故障。超时、限流、并发隔离与熔断需要按照调用的重要性配置；关键的库存确认不能通过伪造成功来降级，非关键的通知则可以延后处理。

部署独立性同样需要配套条件。库存接口更改字段后，旧订单服务是否还能调用？数据库迁移是否允许旧版本继续运行？服务升级失败能否回滚？如果每次发布仍要求所有服务统一停机、统一升级，那么物理上的拆分并没有带来多少交付自由。

跨进程调用还让问题定位变得困难。一笔订单可能先经过 HTTP 网关，再调用库存服务，之后由消息消费者处理支付和通知。单个进程的异常栈无法还原整个过程，需要通过关联的业务操作 ID、Trace ID、结构化日志、指标和分布式追踪恢复执行路径。服务发现、配置管理、密钥管理与发布流水线也成为长期成本。

这些成本可以通过日常问题具体感受到。一次接口延迟升高，究竟是在应用中排队、等待数据库锁、建立下游连接，还是消费队列发生积压？一次订单长时间停留在处理中，是消息尚未发布、库存处理失败，还是订单更新事件丢失？如果没有跨服务的关联标识与可观测数据，排查往往需要人工在几个系统之间对时间和日志。拆分服务以前，可以先评估团队是否具备这类运行能力。

微服务的价值，必须与这些成本放在一起判断。团队规模、业务边界的稳定程度和基础设施能力，往往比系统有多少张表更重要。

## 九、架构演进并没有固定终点

当一个单体开始让开发和交付变得困难时，最稳妥的第一步通常是查清困难来自哪里。如果订单和库存相互访问内部数据，应先整理业务边界；如果主要瓶颈是慢查询，应该先分析执行计划与索引；如果报表占满 CPU，可以先把计算任务隔离出来。

只有当某个模块已经具备清楚的数据所有权、公开契约和相对独立的变化节奏时，才有充分理由考虑把它迁移成服务。迁移过程中可以逐步让新请求进入新服务，避免一次性重写整个应用。这种渐进替换思路通常被称为绞杀者模式（Strangler Fig Pattern）。

真正棘手的往往是数据迁移。原单体和新服务不能长期无约束地同时修改同一项权威业务数据。需要确定切换期间由谁负责写入，旧调用路径如何迁移，历史数据怎样校验，新旧协议在过渡阶段怎样兼容，以及失败时怎样恢复。

如果拆分后发现两个服务始终要同步发布、频繁进行细粒度远程调用，或者共享数据无法形成稳定的所有权，重新合并也可能是合理选择。微服务并非单体之后的必经阶段，更不构成软件架构成熟度的评分标准。

从本专题的第一篇到现在，我们讨论的仍然是职责、边界和变化传播。最初的边界位于函数和模块之间，后来扩展到领域模型和聚合，再到进程、网络与数据所有权。边界越强，局部自治的机会通常越大，但跨过边界的协作也会越昂贵。

单体能够利用简单的本地调用和事务，微服务能够换取独立交付与资源隔离。选择哪一种，需要回到真实的业务要求：哪些决定应当共同维护，哪些变化确实需要独立发布，哪些一致性约束必须立即成立，以及团队准备付出多少长期运营成本。

架构设计的结果未必是越来越多的服务。一个边界清楚、能够持续演化的模块化单体，同样可以是一套成熟的系统。
