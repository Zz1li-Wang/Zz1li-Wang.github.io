我们已经可以把大语言模型接入应用，通过一次 API 请求获得回答。但如果要求它查询实时订单、核对库存，再提交一份业务报告，单次文本生成就不够了。模型可以解释如何查询订单，却无法单靠参数权重知道数据库此刻的记录，更不能凭一句自然语言就完成一次经过授权的业务写入。

应用需要在模型与真实系统之间建立协作机制。先提供查询能力，再把查询结果反馈给模型；如果任务尚未结束，继续判断下一步操作。这类系统通常被称为 Agent。为了理解 Agent，最好先弄清楚模型、工具和外部控制程序各自负责什么。

## 一、语言模型的执行边界

从推理接口的角度看，大语言模型接收一段上下文，并在其训练得到的参数和当前输入条件下生成输出。上下文可能包含用户消息、系统指令、历史记录、工具定义和工具结果。模型内部可以进行复杂的信息处理，但对外呈现的仍是由接口规定的输出内容。

模型参数中蕴含的知识有时间边界，也不能直接提供受权限控制的实时业务状态。即便用户说“帮我查订单 123”，模型也只有在运行环境提供订单查询结果以后，才能依据最新记录作出可靠判断。更重要的是，生成了“已经修改库存”这几个字，不会自动改变 PostgreSQL 中的值。

这里可以区分三个层次。模型负责根据上下文预测或产生回答以及可能的行动建议；应用运行时负责组织输入、接收模型输出并决定如何继续；工具负责读取外部信息或者执行具体动作。它们之间的联系通常表现为一轮或多轮请求，而不是模型直接获得操作系统的任意权限。

这种划分还影响正确性的归属。模型回答中的业务结论需要事实来源；工具返回的数据可能错误或者过时；业务写入必须接受权限检查和事务约束。即使模型正确识别了用户意图，实际执行也要由受控代码保证。

如果进一步追问模型为什么可以输出“调用工具”的指令，还需要区分生成过程与 API 协议。基础自回归语言模型通常基于已有 Token 的条件分布生成后续 Token；现代推理接口还可能结合专门训练、受约束解码和结构化响应机制，把某些输出表示成可供程序读取的工具调用项。工具选择依旧来自模型对上下文的处理，实际的外部副作用仍由宿主执行器完成。不同模型供应商对结构化输出的实现细节各不相同，不能把某一个 API 返回对象当成所有模型内部相同的算法机制。

由此出现一条贯穿 Agent 系统的证据链。模型可以根据工具描述决定“应该查库存”，应用执行器证明“实际调用了指定库存工具”，库存服务返回“查询时刻读到的库存数量”，模型再据此形成“当前库存是否足够”的结论。每一环的证据类型都不同：工具调用意图来自模型响应，执行事实来自运行记录，业务事实来自可信数据源，推断则依赖模型对数据的解释。混淆这些层次，最常见的后果就是用模型生成的完成声明代替实际工具成功记录。

一个真正可审计的 Agent，不必保存模型全部内部推理过程，却应保留可观察的调用请求、参数、经过权限检查的执行结果和交付物验收记录。遇到错误时，开发者才能判断模型选错动作、工具返回过期数据，还是应用在传输过程中丢失了结果。这也解释了为什么 Agent 质量不能只靠最终文本评分衡量。

## 二、工具调用改变了什么

最简单的扩展方式是为模型提供一个可调用的工具。例如查询某个订单状态：

```python

def get_order_status(order_id: str) -> dict:
    return {"order_id": order_id, "status": "PENDING_STOCK"}
```

这段代码可以读取或模拟业务数据，但模型不会因为函数存在就知道怎样调用它。应用还要给模型提供函数名称、用途和参数结构。模型看到相关上下文后，可以输出一个结构化调用请求，表示它希望调用 `get_order_status` 并传入指定参数。

重要的是，**工具调用输出是一项调用意图，不是函数执行本身**。应用应检查模型选中的工具是否已注册、参数是否符合约束、当前用户是否有权使用，然后才执行实际代码。执行结果还要与原调用标识关联，反馈到模型上下文中。

如果模型返回了错误的订单编号，Schema 只能检查它是不是字符串，不能替用户判断这个编号是否属于正确业务对象。如果工具具有删除、支付或发送消息等副作用，还需要额外审批或明确的服务端授权。模型能够选择工具，与模型被授予无限执行权是两回事。

工具可以是本地函数、数据库查询、HTTP API，也可以通过 MCP 等标准协议暴露。工具部署在什么位置，不改变“模型提出请求、应用控制执行”这一基本关系。


要进一步理解 Agent，必须区分模型输出的认识状态与外部系统的实际状态。可以把一次模型调用抽象成条件分布：

\[
p_\theta(y\mid x, c, d)
\]

其中，`x` 表示任务输入，`c` 表示当前上下文，`d` 表示开发者提供的工具声明或输出约束，`y` 是模型产生的输出。推理过程可能使用内部计算、检索信息或经过专门训练的结构化输出能力，但这套表达的重点是：模型依据其收到的信息生成输出。除非系统提供外部数据通道，它无法仅靠权重读取数据库在此刻的真实状态。

假设库存数据库在 10:00 记录 `available=20`，模型在 10:01 输出“库存充足”。这只是它基于既有上下文形成的判断。10:01:01 另一个订单可能完成了扣减，因此“库存充足”既有来源时间，也存在失效条件。给 Agent 增加工具后，模型获得了新的观察渠道，但没有因此获得一个永远正确的世界状态快照。数据库查询存在隔离级别和读写竞争，网页搜索有索引延迟，缓存可能过期，这些不确定性会继续传递给模型。

更重要的是业务写入。模型发出 `reserve_stock` 调用，可以被看成提出一个动作候选；真正是否成功由库存服务的事务决定。同样一个动作，在不同的数据库状态下可能产生不同结果。模型判断“应该调用”与后端判断“允许并成功执行”是两项独立判断。

把 Agent 定义为“可以自主行动的 AI”容易产生误解。实际系统的自主性受到工具集合、权限、预算、提示约束和宿主控制流的共同限定。对某次运行，假设可用动作集合为 `A(s)`，模型可以提出 `a∈A(s)`；但运行时还要将其放进授权与参数校验函数 `P(u,s,a)` 中检查，最终可能执行、拒绝或者请求用户确认。

这里 `u` 代表真实用户与调用上下文，`s` 包括当前业务与运行状态。模型看到了 `delete_file` 工具，并不意味着 `P` 必然返回允许。把“可被模型选择”和“有权被实际执行”拆开，才是工具接入时最重要的控制原则。

这种设计还能解释为什么 Agent 不必拥有全部业务流程的最终控制权。对于订单审批，模型可以分析材料并提出建议，但审批动作必须受到审计和状态机规则约束。模型选择越自由，运行时需要验证的范围通常越广；系统不是通过给模型更多权力来自动获得可靠性。

## 三、Workflow 与 Agent 的区别

在一个固定流程中，程序可以直接规定先查询订单，再查询库存，然后生成摘要。模型只需要解释结果或者完成摘要。这是一个包含 LLM 的 Workflow，但它的步骤和转移关系主要由开发者预先确定。

如果执行顺序依赖中间结果，则可以让模型参与决策：它先判断是否需要查订单，根据订单状态决定是否查询库存，发现库存预留记录缺失以后，再决定是否需要取得补充材料。系统把模型的输出作为后续动作选择的输入，并持续重复这一过程，通常就具有了 Agent 的特征。

不过，两者之间并不存在全行业统一的硬边界。某些系统把带条件分支的工作流也称为 Agent，某些框架则要求模型具有较大的行动选择空间。比标签更有解释力的是三个问题：下一步行动由谁决定、可用动作范围有多大、执行过程由谁约束。

Agent 的自主性也是有范围的。允许模型在“查询订单”和“查询库存”之间选择，不意味着允许它随意修改数据库。允许它规划多个步骤，不意味着它必然比确定性的代码流程更可靠。可确定表达的业务规则应该尽量落实为可验证代码，而不是交给模型每次重新猜测。

## 四、最小 Agent 的运行过程

一个基础 Agent 通常要维护当前任务和一段执行上下文。应用先调用模型，如果模型返回最终回答，任务可以结束；如果返回工具调用，则执行工具，将结果追加到上下文，再调用模型。这构成一个最小的感知—决策—行动—反馈循环。

可以用下面的伪代码表达：

```python

while step < max_steps:
    response = model.generate(context, tool_definitions)
    if response.has_tool_calls:
        results = execute_allowed_tools(response.tool_calls)
        context.append(response)
        context.extend(results)
    else:
        return response.final_answer
    step += 1
raise RuntimeError("执行超过步数限制")
```

这只是控制逻辑，不是某个模型 SDK 的真实接口。具体 API 可能支持一次返回多个工具调用，也可能返回其他类型的输出项。后面几篇会逐步给出具体实现。

这里最值得注意的是循环终止。模型可能持续要求调用工具，也可能在缺少证据时给出最终回答，还可能因为参数错误反复尝试相同操作。因此，运行时要设置调用预算和终止条件，并在必要时把任务转交用户。Agent 能持续工作，并不意味着应该无限循环。

循环里的“状态”也有不同含义。聊天历史是提供给模型的信息，执行状态记录的是当前走到哪一步，外部世界状态则存在数据库或其他系统中。三者的更新速度和可靠性边界各不相同。把它们全部塞进一个消息列表，短期演示可能可行，但不适合长时间任务。


Agent 的新颖之处是让模型参与选择下一动作，但循环结构本身可以从普通反馈控制来理解。系统在某一轮观察到信息 `o_t`，根据运行状态 `s_t` 产生候选动作 `a_t`，环境执行后返回新的观测 `e_{t+1}`。随后，运行时用实际执行结果更新下一轮模型输入和自身状态。

\[
a_t = M(o_t,s_t),\qquad
(e_{t+1},s_{t+1})=T(s_t,a_t)
\]

这里 `M` 代表模型决策，`T` 代表受控的工具执行和状态转换。为了避免公式掩盖关键边界，还需要强调：`s_t` 不完全保存在模型上下文中。模型能看到的历史通常只是运行状态的投影，可能因长度限制、压缩或权限过滤而丢失信息。订单是否提交、工具是否已完成、是否取得审批等事实必须有独立记录。

如果模型这一轮返回两个工具调用，循环还面临调度策略问题。只有当两个调用互不依赖、且副作用不冲突时，才适合并发。否则，第二个工具应该等第一个结果进入上下文后再由模型决策。并行执行是一项程序决策，并不由输出数组里包含两个调用自动推出。

模型回复“我已经提交了报告”仅说明它产生了这些文字。若任务要求写入文件，应检验文件是否存在、内容是否符合约束；若任务要求审批订单，应检查真实审批记录。因而完成条件至少要区分模型宣称的完成、执行器确认的工具完成和业务验收条件满足。对于无法客观验证的研究与写作任务，还应保留证据、假设与未确定事项，不能将流畅表达误当成事实证明。

## 五、Agent 的可靠性来自哪里

工具为 Agent 接入了外部事实来源，不能保证这些事实自动正确；循环提供了多步操作能力，不能保证每一步都有意义。可靠性来自运行系统对不确定性的约束。

对于读取操作，要关注来源、时间范围和权限；对于写入操作，要关注参数验证、授权、事务和重复执行；对于模型结果，要关注证据是否充分、任务是否完成以及输出是否符合实际状态。若工具失败，可以把错误反馈给模型，但不能要求模型用文字“假装已完成”原本需要真实执行的步骤。

例如库存接口超时，订单是否已预留可能处于不确定状态。此时 Agent 应依据业务接口提供的操作 ID 查询结果，或者触发可控恢复流程。简单地再次调用扣减接口可能产生重复副作用。这些可靠性问题与传统后端系统有直接联系，只是 Agent 又增加了模型参与选择动作的不确定性。

安全边界同样应由程序建立。来自网页、文件或工具返回值的文字属于外部数据，不能因为它进入模型上下文就自动升级为更高权限的指令。提示注入的风险正源于把“供模型阅读的内容”和“要求系统遵守的控制指令”混淆。

## 六、适合使用 Agent 的条件

Agent 适合那些中间结果难以事先完全预测、需要动态选择信息来源或者多次操作才能完成的任务。模型能够根据阶段性反馈调整下一步行动，减少人为枚举全部分支的工作量。

但在步骤固定、业务约束明确的系统中，普通代码或工作流往往更可控、更容易验证，也能减少模型调用成本。订单状态从 `PENDING` 变为 `APPROVED` 的条件，应该由状态机和数据库约束判断；让模型选择是否调用“提交审批”工具，则可以是上层交互的一部分。

因此，Agent 的价值不由工具数量或模型调用轮数决定，而要看动态决策是否真的改善任务完成方式，以及应用是否有能力验证和约束这些决策。接下来我们从最基础的工具调用接口开始，观察模型的行动意图怎样变成程序可以处理的数据。


如果一项任务的步骤是确定的，普通程序可以提前编排 `query → validate → persist`，其输出路径易于测试、审计和复现。改成模型每轮都要决定下一步，会增加推理费用、等待时间和不确定性。Agent 的价值通常出现在分支众多、输入难以结构化、路径依赖临时信息的场景。例如文献调研可能需要不断根据搜索结果调整关键词，固定工作流很难事先穷举全部分支。

即便如此，也不意味着必须让模型管理每一步。系统可以让工作流负责事务、审批、执行预算和最终验收，仅让模型负责证据检索、工具选择和信息解释。由确定性编排包围开放式 Agent，是现实应用中常见且合理的组合。

比较两种方案时，应观察端到端任务完成率、人工介入次数、平均工具调用数、错误副作用、时延和可维护性，而不能只看某个模型在几个演示问题上的回答质量。系统设计的目标是稳定完成业务任务，模型调用只是完成任务的一种机制。
