上一篇文章介绍了进程、线程与协程的区别。

我们知道，操作系统通过调度线程，让多个任务共享 CPU 的执行时间。而在 Python 的 `asyncio` 中，多个协程任务可以运行在同一个线程中，通过协作式调度实现并发。

这就带来了几个问题。

协程执行到一半，为什么能够暂停？暂停以后，谁来保存它的执行状态？当网络数据到达时，程序又是怎么知道应该恢复哪个协程的？

这些问题都与 Python 的 `async/await` 机制和事件循环（Event Loop）有关。

理解它们以后，才能真正明白为什么异步程序能够在较少线程的情况下，处理大量并发 I/O 任务。

## 一、从普通函数到协程

### 1. 普通函数是如何执行的？

先看一个普通的 Python 函数。

```python
def calculate():
    print("开始计算")
    result = 1 + 2
    print("计算结束")
    return result


value = calculate()
print(value)
```

调用 `calculate()` 时，Python 开始执行函数体。

函数会沿着当前调用链运行，直到执行 `return` 返回结果，或者因为异常而退出。

调用者需要等到函数结束，才能继续执行后面的代码。

如果函数内部发生了阻塞，这个调用线程通常也会被阻塞。

例如：

```python
import time


def calculate():
    print("开始")
    time.sleep(2)
    print("结束")


calculate()
```

执行到 `time.sleep(2)` 时，当前线程会休眠大约两秒钟。

在这段时间里，这个线程不能继续执行当前调用链中的 Python 代码。

当然，操作系统仍然可以调度其他线程运行。这里所谓的阻塞，是针对当前线程而言的。

如果希望同一个线程能够在等待期间执行其他任务，就需要一种可以暂停和恢复的执行过程。

协程正是为此提供了语言层面的支持。

### 2. async def 做了什么？

Python 使用 `async def` 定义原生协程函数。

```python
async def calculate():
    print("开始计算")
    return 1 + 2


result = calculate()
print(result)
```

运行这段代码，会发现 `calculate()` 并没有打印“开始计算”。

相反，`result` 是一个协程对象。

这是协程函数与普通函数的一个重要区别。

普通函数被调用时，会立即执行函数体。

而调用 `async def` 定义的协程函数时，通常只是创建一个协程对象，并不会立即执行函数体。

这个对象保存着协程执行所需要的状态，可以在之后被驱动执行。

我们可以验证一下：

```python
import inspect


async def calculate():
    return 1 + 2


coro = calculate()

print(inspect.iscoroutine(coro))
print(inspect.getcoroutinestate(coro))

coro.close()
```

输出结果：

```text
True
CORO_CREATED
```

`CORO_CREATED` 表示协程对象已经创建，但还没有开始执行。

协程还可能处于正在运行、已经挂起或已经结束等状态。

对于已经挂起的协程，Python 需要保留它继续执行所需的状态，例如当前执行位置和局部变量等。

这样，当协程重新获得执行机会时，就可以从先前暂停的位置继续运行。

这里需要注意，协程对象并不等于线程。

一个协程可以在不同时间被驱动执行，但真正执行 Python 指令的仍然是操作系统线程。

因此，创建一个协程对象不会自动创建新的线程，也不会自动获得 CPU 执行时间。

还有一个问题：协程对象创建以后，究竟由谁来执行它？

这需要引入 `await` 和事件循环。

## 二、await 究竟做了什么？

### 1. await 不只是等待结果

先看一个简单的例子。

```python
import asyncio


async def calculate():
    print("开始计算")
    return 1 + 2


async def main():
    result = await calculate()
    print(result)


asyncio.run(main())
```

输出结果：

```text
开始计算
3
```

这里的 `await calculate()` 使协程得到执行，并取得它的返回结果。

从表面上看，`await` 与普通函数调用似乎没有太大区别。

但它们的执行语义不同。

`await` 可以等待一个支持异步等待协议的对象。在等待过程中，如果对象暂时无法产生结果，当前协程就可以暂停，把控制权交还给外层的执行机制。

等到结果准备好后，协程再恢复执行。

因此，`await` 不只是获取返回值的语法，更重要的是它允许协程在等待尚未完成的操作时挂起。

不过，不能把 `await` 直接理解成“切换到另一个任务”。

如果被等待的操作能够立即完成，当前协程就可能不需要暂停。

例如，前面的 `calculate()` 只有一次简单计算，没有任何真正需要异步等待的操作。

执行 `await calculate()` 时，可以直接完成计算并返回结果，不必让事件循环切换任务。

这说明，**`await` 提供了允许暂停的机制，但并不保证每次执行都会发生任务切换。**

### 2. 什么对象可以被 await？

在 Python 中，能够用于 `await` 表达式的对象称为可等待对象（Awaitable）。

原生协程对象就是一种可等待对象。

除此之外，`asyncio.Task` 和 `asyncio.Future` 也是常见的可等待对象。

在更底层的 Python 语言协议中，一个对象还可以通过实现 `__await__()` 方法提供可等待能力。

这个方法返回一个迭代器，用于参与协程的等待过程。

因此，`await` 的操作对象并不局限于协程函数的返回值。

这也解释了为什么有些异步库的 API 可以直接被 `await`，而有些 API 返回的是 Task 或 Future。

它们的具体实现可能不同，但都可以通过 Python 的可等待协议参与异步执行。

对于使用者而言，通常不需要自己实现 `__await__()`。

但理解这个协议有助于认识到：`async/await` 首先是一套语言机制，而 `asyncio` 是建立在这套机制之上的异步运行时库。

两者并不是同一个概念。

### 3. await 是否意味着并发？

这是使用 Python 异步编程时非常容易产生的误解。

考虑下面的代码：

```python
import asyncio
import time


async def work(name):
    print(f"{name} 开始")
    await asyncio.sleep(1)
    print(f"{name} 结束")


async def main():
    start = time.perf_counter()

    await work("A")
    await work("B")

    elapsed = time.perf_counter() - start
    print(f"总耗时: {elapsed:.2f} 秒")


asyncio.run(main())
```

程序输出通常类似：

```text
A 开始
A 结束
B 开始
B 结束
总耗时: 2.00 秒
```

虽然我们使用了两个协程，而且每个协程都包含 `await`，但它们并没有并发执行。

原因在于，`main()` 先等待 `work("A")` 完成，然后才开始执行 `work("B")`。

当 `main()` 执行：

```python
await work("A")
```

它会进入 `work("A")` 的执行过程，并等待这个协程最终返回。

即使 `work("A")` 在内部暂停，`main()` 也不能越过这个 `await`，提前执行下一行代码。

所以，`await` 并不意味着创建一个独立的并发任务。

它首先表达的是当前协程与被等待对象之间的依赖关系。

要让多个协程独立推进，我们还需要 Task。

## 三、Task 是如何实现并发的？

### 1. 为什么需要 Task？

前面已经知道，调用协程函数会创建协程对象。

但协程对象本身只是一个可执行过程的表示，并不意味着它已经被独立调度。

如果我们希望某个协程能够与其他协程并发执行，就需要把它交给调度机制管理。

在 `asyncio` 中，承担这项工作的主要对象是 Task。

Task 可以理解为由事件循环管理的协程执行任务。

它负责驱动协程执行，记录任务的完成状态，并管理协程在等待期间的挂起与恢复。

我们可以使用 `asyncio.create_task()` 创建 Task。

```python
import asyncio
import time


async def work(name):
    print(f"{name} 开始")
    await asyncio.sleep(1)
    print(f"{name} 结束")


async def main():
    start = time.perf_counter()

    task_a = asyncio.create_task(work("A"))
    task_b = asyncio.create_task(work("B"))

    await task_a
    await task_b

    elapsed = time.perf_counter() - start
    print(f"总耗时: {elapsed:.2f} 秒")


asyncio.run(main())
```

这次的输出通常类似：

```text
A 开始
B 开始
A 结束
B 结束
总耗时: 1.00 秒
```

两个任务的等待时间发生了重叠。

为什么这一次实现了并发？

因为 `asyncio.create_task()` 不只是创建协程对象，而是将协程包装为 Task，并安排它在事件循环中执行。

当任务 A 执行到异步等待操作并暂停时，事件循环就有机会执行任务 B。

当任务 B 也进入等待状态时，事件循环可以等待后续事件，而不需要让两个任务各自占用一个阻塞的操作系统线程。

等到等待条件满足，事件循环再安排相应 Task 恢复执行。

需要特别说明，`create_task()` 并不保证新任务必须等到下一次事件循环迭代才开始执行。现代 Python 还支持通过 `eager_start` 或相应任务工厂配置，让任务在创建时立即执行到首次阻塞的位置。

但这些执行时机的差异，并不改变 Task 的基本作用：管理协程的独立调度与完成状态。

### 2. 为什么最后两个 await 没有导致串行执行？

上面的代码中，我们仍然写了：

```python
await task_a
await task_b
```

为什么没有像之前一样耗费两秒？

因为两个 Task 在执行这两行代码之前，就已经被创建并安排执行。

当 `main()` 等待 `task_a` 时，`task_b` 并不会因为 `main()` 正在等待另一个 Task 而停止。

它仍然可以由事件循环调度运行。

当 `task_a` 完成后，如果 `task_b` 也已经完成，第二个 `await` 就可以直接取得结果。

因此，两个 `await` 在代码中依次出现，并不必然意味着所等待的任务依次执行。

关键在于：这些任务是否已经被独立调度。

Python 还提供了 `asyncio.gather()`，用于并发运行多个可等待对象并汇总结果。

```python
await asyncio.gather(
    work("A"),
    work("B"),
)
```

如果传入的是协程对象，`gather()` 会将它们安排为 Task 并发执行。

不过，`create_task()` 与 `gather()` 并不完全相同。它们在结果汇总、异常传播等方面还有区别。

这些内容涉及异步任务的生命周期管理，我们会在下一篇文章中详细讨论。

这里先记住一个结论：

**协程定义了可以暂停和恢复的执行过程，Task 则让这个执行过程能够被事件循环独立调度。**

至于事件循环具体如何完成调度，就需要继续往下研究。

## 四、事件循环是什么？

事件循环（Event Loop）是 `asyncio` 的核心运行机制。

它负责组织异步任务、执行回调、处理定时器以及协调网络 I/O 等事件。

对于一个典型的单线程 `asyncio` 程序，事件循环运行在一个操作系统线程中。

这个线程不需要为每个并发任务创建新的操作系统线程，而是通过事件循环，在多个 Task 之间安排执行。

### 1. 事件循环为什么叫循环？

可以把事件循环理解为一个不断运行的调度过程。

它需要知道当前有哪些任务已经可以执行，哪些任务正在等待，以及哪些等待条件已经满足。

对于典型的 `asyncio` 事件循环，其内部会维护待执行回调、定时器等调度信息，并借助操作系统的 I/O 事件机制发现网络操作是否已经具备继续执行的条件。

为了理解这个过程，我们可以用下面的伪代码表示它的基本思想。

```python
while running:
    处理已经到期的定时器()

    if 有可以执行的回调:
        执行已经就绪的回调()
    else:
        等待下一次定时器或I/O事件()

    将新完成的I/O事件转为后续执行工作()
```

这不是 CPython 事件循环内部代码的逐行还原，而是一个简化的概念模型。

实际实现还需要处理回调执行顺序、定时器精度、事件轮询和调度公平性等问题。并且，即使存在已就绪回调，事件循环也可能进行非阻塞的 I/O 轮询。

但它揭示了事件循环的基本工作方式：不断发现哪些操作已经可以推进，并执行相应的任务或回调。

这里需要注意，事件循环并不是每次都从头检查所有协程，询问它们是否已经完成。

等待中的任务通常通过 Future、回调和底层事件通知等机制建立关联。

当等待条件满足时，相关回调才会被安排执行，从而推动对应任务恢复运行。

这比持续遍历大量等待中的协程更加有效。

### 2. 事件循环会一直占用 CPU 吗？

看到 `while` 循环，可能会产生一个疑问：事件循环不停地运行，是否意味着它需要不断占用 CPU？

并不是。

如果当前没有可以立即执行的任务，事件循环可以借助操作系统提供的等待机制进入休眠，直到新的事件到达或者定时器到期。

因此，一个管理了大量网络连接的事件循环，不需要持续消耗 CPU 来检查每个连接。

例如，假设有一万个网络连接正在等待数据。

事件循环并不需要创建一万个线程，也不需要为每个连接单独编写一个无限轮询的循环。

它可以通过操作系统的 I/O 事件机制监视多个连接，并在某个连接具备读写条件时处理对应事件。

但这也意味着，事件循环的性能依赖于任务能否及时让出执行权。

如果某个 Task 长时间执行 Python 计算而不暂停，那么其他已经就绪的任务也无法及时获得执行机会。

这正是协作式调度与操作系统抢占式线程调度之间的重要区别。

## 五、Future 如何让等待中的任务恢复执行？

到这里，我们已经知道事件循环能够调度 Task。

但还有一个关键问题没有解决。

当 Task 执行到一个尚未完成的异步操作时，它可以暂停。那么事件循环如何知道这个 Task 在等待什么，又应该在什么时候恢复它？

在 `asyncio` 中，Future 是连接异步操作结果与协程调度的重要机制。

### 1. Future 表示一个尚未确定的结果

Future 可以理解为一个代表未来结果的对象。

当一个异步操作尚未完成时，Future 可以处于等待状态。

当操作完成以后，Future 可以被设置为完成，并保存操作结果或者异常。

因此，Future 不需要自己执行具体的业务计算。

它主要用于表示一个异步操作的完成状态，以及向等待这个结果的任务传递完成信息。

Task 本身也具备类似 Future 的结果与完成状态接口，但它额外承担了驱动协程执行的职责。

换句话说，Future 主要表示结果，Task 主要管理执行。

为了理解 Future 的工作方式，我们来看一个例子。

```python
import asyncio


async def main():
    loop = asyncio.get_running_loop()

    future = loop.create_future()

    loop.call_later(
        1,
        future.set_result,
        "操作完成",
    )

    print("开始等待")

    result = await future

    print(result)


asyncio.run(main())
```

输出结果：

```text
开始等待
操作完成
```

两行输出之间大约相隔一秒钟。

这里没有使用 `asyncio.sleep()`，而是直接创建 Future，并通过事件循环的定时器安排它在一秒钟之后完成。

这个例子能够帮助我们理解异步等待与恢复的具体关系。

### 2. Task 是如何等待 Future 的？

我们来分析刚才的执行过程。

程序首先通过 `asyncio.run(main())` 启动事件循环，并让事件循环运行 `main()` 对应的任务。

接着，`main()` 创建一个尚未完成的 Future。

通过 `loop.call_later()`，程序安排一个定时回调，在大约一秒钟之后调用 `future.set_result()`。

随后，代码执行到：

```python
result = await future
```

由于 Future 此时尚未完成，当前 Task 就需要暂停执行。

在典型的 `asyncio` 实现中，Task 会建立与所等待 Future 的关联，并注册用于后续恢复执行的回调。

这样，当 Future 状态发生变化时，就可以通过相应回调重新安排 Task 执行。

一秒钟之后，事件循环发现定时器已经到期，执行先前注册的回调。

这个回调调用：

```python
future.set_result("操作完成")
```

Future 由等待状态变为完成状态，并安排相关的完成回调执行。

随后，Task 的恢复逻辑被加入事件循环的待执行队列。

当事件循环再次调度这个 Task 时，它会继续驱动先前暂停的协程。

此时，`await future` 得到了结果，程序便继续执行后面的 `print(result)`。

需要注意，`set_result()` 并不是直接在当前调用栈中把等待中的 Task 运行到结束。

它会使 Future 完成，并通过事件循环的回调调度机制安排后续工作。

这一区别十分重要。

因为如果 Future 完成时就立即执行所有等待它的协程，就可能造成复杂的嵌套调用，甚至破坏事件循环原本的任务调度关系。

通过将恢复操作交给事件循环，可以把结果通知与任务继续执行分开。

### 3. 协程究竟是如何被恢复的？

从 Python 语言机制来看，协程的执行与迭代器协议有一定联系。

协程对象具有可被驱动的执行状态。运行时可以通过相应的恢复操作，让协程继续执行，并把等待结果或者异常传递回协程内部。

在 CPython 的实现中，这一过程涉及 `send()`、`throw()` 等底层接口，以及解释器维护的协程执行帧。

当协程恢复时，解释器不需要重新执行函数开头的代码，而是根据之前保存的执行状态继续运行。

因此，协程的暂停和恢复并不是操作系统线程上下文切换的简单复制。

线程上下文切换涉及操作系统对 CPU 执行状态的保存与恢复。

协程的暂停与恢复则由 Python 语言机制和运行时协作完成，保存的是协程层面的执行状态。

当然，协程最终还是运行在操作系统线程上。如果该线程被操作系统抢占，仍然会发生正常的线程调度。

这就形成了两个调度层次：操作系统调度线程，事件循环在其所属线程中调度协程任务。

## 六、事件循环如何处理网络 I/O？

到目前为止，我们主要使用 `asyncio.sleep()` 和定时器来解释任务调度。

但实际开发中，异步编程最重要的使用场景之一是网络 I/O。

例如，一个 Web 服务向数据库发送查询请求，需要等待数据库返回数据。

事件循环究竟是怎么知道网络数据已经到达的？

这涉及操作系统提供的 I/O 多路复用机制。

### 1. 为什么同步网络操作会阻塞线程？

假设程序通过 Socket 接收网络数据。

在阻塞模式下，如果程序调用 `recv()`，而接收缓冲区中暂时没有可读取的数据，调用线程就可能进入等待状态。

操作系统会在数据可用或者发生其他结束等待的条件时，让线程有机会继续执行。

对于单个连接，这种方式很直接。

但如果程序需要同时管理大量连接，就会遇到资源管理问题。

最简单的办法是为每个连接分配一个线程，让各自的线程阻塞等待网络数据。

这样可以实现并发，但大量线程需要占用栈空间、内核管理资源，并增加调度开销。

如果能让一个线程同时等待多个 Socket 的事件，就不必再让每个连接与一个线程一一对应。

这正是 I/O 多路复用希望解决的问题。

### 2. I/O 多路复用的基本原理

I/O 多路复用允许程序通过一套等待机制监视多个 I/O 对象。

当其中某个对象具备特定条件时，操作系统就可以向程序报告相应事件。

在 Linux 上，常见的机制包括 `select`、`poll` 和 `epoll`。

其他平台也提供类似能力，例如 BSD 系统中的 `kqueue`。Windows 还提供了以完成通知为核心的 IOCP 机制。

这些机制的实现细节并不完全相同，但对于异步程序而言，它们能够帮助运行时协调大量 I/O 操作，而不需要让每个操作各自阻塞一个线程。

以 Linux 上基于 `epoll` 的网络事件处理为例。

程序可以将多个 Socket 注册到事件监视机制中，并指定自己关注的事件。

例如，某个 Socket 当前是否可读，或者是否具备写入条件。

当程序需要等待网络数据时，可以通过 `epoll_wait()` 等接口等待相关事件。

这个等待调用本身可以阻塞当前线程，但它等待的是多个 I/O 对象的事件，而不是仅仅等待某一个 Socket 的数据。

因此，只有在没有其他可执行工作时，事件循环才需要进入这种等待。

一旦某些 Socket 就绪，事件循环就可以继续处理相应的回调和任务。

需要区分的是，Socket 可读并不等价于业务请求已经完整接收，更不意味着 HTTP 报文已经解析完成。

事件就绪只表示相应的 I/O 操作具备继续推进的条件，应用程序仍然需要实际读取数据、处理协议，并在必要时继续等待。

另外，`asyncio` 在不同操作系统上的底层实现也不完全相同。

在 Unix 平台，标准 `asyncio` 事件循环通常使用基于 `selectors` 的实现，可以利用适合当前平台的 I/O 就绪通知机制。

在 Windows 上，默认事件循环实现则使用基于 IOCP 的 `ProactorEventLoop`。

因此，不能把所有异步 I/O 都理解为通过 `epoll` 实现。

### 3. 从网络事件到协程恢复

现在可以把前面介绍的 Task、Future 和事件循环联系起来。

假设一个协程正在等待从网络连接中读取数据：

```python
data = await reader.read(1024)
```

这里的 `reader` 可以是 `asyncio` 提供的异步流读取对象。

如果内部已经缓存了足够的数据，读取操作就可能直接返回。

如果暂时没有数据，异步读取逻辑就需要建立等待关系，让当前协程暂停。

对于基于 Socket 就绪通知的实现，底层事件循环会关注相应 Socket 的可读事件。

当网络数据到达，操作系统使 Socket 具备读取条件后，事件循环便可以安排对应的 I/O 处理逻辑。

实际的数据读取和缓冲区更新完成后，相关等待对象就可能被标记为完成，使先前暂停的 Task 重新获得执行机会。

于是，协程从 `await reader.read(1024)` 处恢复，取得读取结果，继续处理业务逻辑。

从整体上看，这个过程形成了一条相对完整的执行链路。

协程发起异步读取，发现暂时没有结果，于是暂停。

事件循环负责协调底层 I/O 等待。

操作系统在条件满足时报告事件。

异步运行时处理事件并使等待结果就绪。

事件循环重新调度对应 Task。

Task 恢复协程执行。

这里最重要的是，等待网络数据的过程中，程序不需要让这个协程独占一个操作系统线程。

同一个事件循环线程可以先处理其他已经就绪的任务。

当然，并不是所有 I/O 操作都天然支持这种工作模式。

例如，普通磁盘文件的读写，并不总能直接通过网络 Socket 使用的 I/O 就绪通知方式实现异步操作。

在 Python 中，一些看起来是异步接口的文件操作，实际上可能通过线程池执行同步文件读写，再将结果交回事件循环。

所以，异步接口并不必然意味着底层完全没有使用线程。

真正需要关心的是：调用方是否会阻塞事件循环线程，以及底层运行时如何组织等待和结果通知。

## 七、asyncio.run() 做了什么？

我们一直通过下面的代码启动异步程序：

```python
asyncio.run(main())
```

现在可以进一步理解它的作用。

`asyncio.run()` 是运行 `asyncio` 程序的高级入口。

它负责建立事件循环的运行环境，执行传入的可等待对象，并在运行结束后处理相关的清理工作。

对于传入的协程，运行时会通过 Task 等机制驱动它执行。

当主任务内部创建其他 Task 时，这些任务也可以被同一个事件循环调度。

事件循环会持续处理已经就绪的任务、定时器和 I/O 事件，直到运行入口所等待的操作完成，并进入后续的清理过程。

最后，`asyncio.run()` 会负责关闭所管理的事件循环，并处理异步生成器和默认执行器等资源的收尾工作。

因此，在普通的独立 Python 脚本中，通常不需要手动创建和关闭事件循环。

但是，`asyncio.run()` 不能在当前线程已经存在正在运行的 `asyncio` 事件循环时再次调用。

这也是为什么在某些异步运行环境中，不能直接在协程内部调用 `asyncio.run()`。

对于 FastAPI 这样的异步 Web 应用，事件循环通常由 ASGI 服务器管理。

请求处理函数不需要自行调用 `asyncio.run()`，而是由服务器将异步调用纳入已有的事件循环。

我们还可以通过下面的代码取得当前正在运行的事件循环：

```python
import asyncio


async def main():
    loop = asyncio.get_running_loop()
    print(loop)


asyncio.run(main())
```

`get_running_loop()` 取得的是当前操作系统线程中正在运行的事件循环。

如果当前线程不存在运行中的事件循环，这个函数就会抛出 `RuntimeError`。

这再次说明，事件循环不是独立于线程之外运行的特殊 CPU 执行实体。

它本身也是由某个操作系统线程执行的程序逻辑。

## 八、为什么 async def 不一定意味着异步？

前面已经解释过，协程需要在适当的时候暂停，事件循环才能调度其他任务。

但在实际开发中，我们经常看到一些函数虽然使用了 `async def`，内部却执行大量同步阻塞代码。

例如：

```python
import asyncio
import time


async def blocking():
    print("阻塞任务开始")
    time.sleep(2)
    print("阻塞任务结束")


async def other():
    print("其他任务开始")
    await asyncio.sleep(1)
    print("其他任务结束")


async def main():
    await asyncio.gather(
        blocking(),
        other(),
    )


asyncio.run(main())
```

这里的两个任务虽然都被安排并发执行，但 `blocking()` 调用了同步的 `time.sleep(2)`。

它会阻塞事件循环所在的线程。

因此，如果事件循环先执行 `blocking()`，就必须等到同步休眠结束，才能继续执行其他 Task。

在默认的任务调度配置下，通常会先打印：

```text
阻塞任务开始
阻塞任务结束
其他任务开始
其他任务结束
```

总运行时间大约为三秒。

而如果将 `time.sleep(2)` 改成：

```python
await asyncio.sleep(2)
```

两个任务就可以让各自的等待时间重叠，整体耗时通常接近两秒。

这正是同步阻塞与异步等待的重要区别。

### 1. 为什么不能自动把同步函数变成异步函数？

因为 `async def` 改变的是函数的调用和执行语义，而不是函数内部所有操作的底层实现。

一个普通的同步阻塞函数，并不会因为被放进协程函数中，就自动获得非阻塞能力。

如果底层数据库驱动采用同步阻塞方式，那么外层函数即使使用了 `async def`，数据库调用仍然可能阻塞当前线程。

这也解释了为什么 Python 生态中经常会同时存在同步客户端和异步客户端。

异步客户端不仅仅是增加了 `async` 关键字，还需要在 I/O 等待、连接管理和结果通知等方面，与异步运行时进行协作。

### 2. 如何处理无法避免的同步阻塞操作？

如果必须在异步程序中调用同步阻塞函数，一种常见办法是将它交给线程执行。

Python 提供了 `asyncio.to_thread()`。

```python
import asyncio
import time


def blocking_operation():
    time.sleep(2)
    return "执行完成"


async def main():
    result = await asyncio.to_thread(
        blocking_operation
    )

    print(result)


asyncio.run(main())
```

这里的 `blocking_operation()` 仍然是普通同步函数。

但它会被安排到独立的工作线程中执行，而不是直接阻塞事件循环所在的线程。

事件循环线程可以继续处理其他任务，并在工作线程返回结果后恢复等待中的协程。

不过，这并不意味着同步函数真的被转换成了非阻塞函数。

它仍然以阻塞方式执行，只是阻塞发生在另一个线程中。

另外，在启用 GIL 的传统 CPython 中，线程池并不能自动让纯 Python CPU 密集型计算获得多核并行能力。

对于 CPU 密集型任务，可能需要考虑进程池或者其他支持真正并行计算的执行机制。

因此，异步编程的核心不是消除所有等待，而是让等待发生在合适的位置，不要无谓地阻塞需要继续处理其他任务的执行线程。

## 九、异步机制与 Web 服务有什么关系？

现在，我们已经能够把 Python 的异步执行过程串联起来。

一个典型的异步 Web 服务在启动以后，服务器会建立用于处理网络请求的运行环境，并运行事件循环。

当新的请求到达时，服务器接收网络数据，解析协议，并把请求交给对应的应用处理逻辑。

如果请求处理函数是异步函数，那么它可以通过协程的方式执行。

例如，一个接口需要查询数据库：

```python
@app.get("/users/{user_id}")
async def get_user(user_id: int):
    user = await repository.get_user(user_id)
    return user
```

这里假设 `repository.get_user()` 是一个真正使用异步数据库驱动的查询方法。

当数据库结果暂时不可用时，当前请求对应的协程可以暂停执行。

事件循环不必在这个请求上同步等待，而是可以继续处理其他已经就绪的请求任务。

当数据库响应返回后，底层异步运行时通过相应的 I/O 通知和等待结果机制，让之前的请求任务恢复执行。

随后，程序取得查询结果，继续生成 HTTP 响应。

从客户端的角度看，请求仍然遵循正常的发送、处理和响应过程。

异步编程改变的是服务器内部等待与执行的组织方式，而不是 HTTP 协议本身。

不过，异步服务器也有自己的处理能力上限。

如果请求处理逻辑包含大量 CPU 计算，就会持续占用事件循环线程，影响其他请求的响应时间。

如果数据库连接池已经耗尽，或者下游数据库自身处理能力不足，那么即使事件循环能够管理大量并发 Task，也不能消除这些资源瓶颈。

因此，异步编程并不意味着服务器可以无限处理并发请求。

它主要减少的是大量 I/O 等待任务与操作系统线程一一对应所产生的资源成本，让服务器能够更有效地组织并发等待。

至于一个 HTTP 请求具体怎样进入 Python Web 应用、路由如何匹配，以及 ASGI 服务器怎样调用异步接口，我们会在后续文章中继续讨论。

## 十、小结

回到文章开头提出的问题：Python 如何在一个线程中管理多个协程，并在等待时切换执行？

现在已经可以给出比较完整的解释。

`async def` 让我们能够定义协程函数。调用协程函数会创建协程对象，这个对象具有可以被驱动执行、暂停和恢复的能力。

`await` 使协程能够等待另一个可等待对象。当结果尚未准备好时，协程可以暂停执行。

Task 负责管理协程的独立调度，而 Future 等对象可以表示尚未完成的异步结果，并建立等待任务与结果完成事件之间的关系。

事件循环则负责执行就绪任务和回调，协调定时器与底层 I/O 事件，并在等待条件满足后安排相应任务继续运行。

因此，**Python 异步编程的核心并不是让代码同时运行在多个 CPU 上，而是让一个任务在无法继续执行时，把执行机会交给其他已经具备运行条件的任务。**

对于大量 I/O 密集型工作，这种执行方式可以减少线程资源占用，并提高系统组织并发请求的能力。

但它仍然依赖任务主动到达可以暂停的位置，也不能消除 CPU、网络和数据库本身的性能限制。

理解了协程、Task、Future 和事件循环之间的关系以后，下一步自然会遇到新的问题。

一个 Task 创建以后，应该由谁管理它的生命周期？如果任务执行失败，异常应该如何传播？如果请求已经取消，尚未完成的异步操作应该怎样停止？

这些问题将是下一篇《异步任务调度、取消与异常处理》的主要内容。
