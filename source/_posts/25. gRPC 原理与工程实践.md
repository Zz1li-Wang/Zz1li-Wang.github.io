上一节把 RPC 拆成了接口契约、客户端代理、消息编码、网络传输、服务端分发与结果返回。手工实现这些功能并不复杂，困难在于让不同语言、不同版本和不同部署环境中的程序长期遵守同一套约定。

本篇使用 gRPC 把这条调用链落实成可运行的程序。我们继续使用订单服务预留库存的场景，以 Python 实现客户端和服务端，同时观察 Protobuf、HTTP/2、Channel、Stub、Deadline 和错误状态分别承担什么职责。

## 一、gRPC 由哪些部分组成

gRPC 是一套开源远程过程调用框架。常见的使用方式是用 Protocol Buffers 描述服务和消息，通过代码生成器创建多语言的数据类型与调用接口，再由 gRPC 运行时负责请求发送、方法分发、状态管理等工作。

在标准的 gRPC over HTTP/2 场景中，调用方创建 Channel，并通过由 `.proto` 生成的 Stub 发起 RPC。Stub 把请求交给运行时，运行时按照 HTTP/2 和 gRPC 消息格式发送数据。服务端运行时根据方法路径找到已注册的 Servicer，再调用业务实现。

需要分清其中三个概念。Protobuf 定义结构化消息及二进制编码；HTTP/2 提供连接内的 Stream、帧、流量控制和首部等传输能力；gRPC 在这些基础上定义方法调用语义、消息封装、状态码、Metadata 和客户端服务端 API。使用 Protobuf 本身不会自动得到 RPC，也不是所有 RPC 框架都必须使用 gRPC。

通常一次 Unary RPC 会映射到一个 HTTP/2 Stream。gRPC 常使用 HTTP `POST`，方法路径采用 `/包名.服务名/方法名` 的形式。请求及响应消息有自己的长度前缀封装：1 字节压缩标记和 4 字节大端消息长度，之后才是实际序列化的消息内容。这个长度指向的是 gRPC 消息数据长度；HTTP/2 自身还有 DATA 帧的分段机制，两者不是同一层的边界。

HTTP/2 的一个 Stream 可以包含多条 gRPC 消息，这为流式 RPC 提供基础。响应的最终 gRPC 状态通常由 HTTP/2 Trailers 中的 `grpc-status` 表示。即使传输层使用 HTTP 状态码 200，业务 RPC 也可能以非 OK 的 gRPC 状态结束，因此不能只检查 HTTP 状态码判断调用成功。

## 二、先定义服务契约

创建一个独立目录，在其中编写 `inventory.proto`：

```proto
syntax = "proto3";

package inventory.v1;

service Inventory {
  rpc Reserve(ReserveRequest) returns (ReserveReply);
}

message ReserveRequest {
  string order_id = 1;
  string sku = 2;
  int32 quantity = 3;
}

message ReserveReply {
  bool accepted = 1;
  string reservation_id = 2;
  string reason = 3;
}
```

`package` 用于组织 Protobuf 中的符号名称。`service` 描述可被远程调用的服务，`rpc` 表示其方法。`ReserveRequest` 和 `ReserveReply` 则分别定义请求和响应的数据结构。方法签名里明确标出了输入和输出类型，生成工具据此创建客户端方法及服务端接口。

`quantity` 使用 `int32` 说明它是一个有符号整数，但字段类型本身并不禁止零或负数，所以服务端仍需要校验。`order_id` 和 `sku` 虽然都是字符串，却承载不同业务语义，不应因为类型相同而互换字段编号。

这些消息中的字段编号必须保持稳定。新增字段一般具有良好的二进制兼容性，但不能随意重用已经删除的字段编号。proto3 的普通标量字段在没有显式存在性跟踪时，读取未设置值通常得到默认值。例如未提供 `quantity` 的请求可能读到 `0`。如果业务必须区分“没有填写”和“明确填写零”，需要采用支持显式存在性的字段设计，并在代码中验证。

## 三、生成 Python 代码

使用虚拟环境安装必要依赖：

```bash
python -m pip install grpcio grpcio-tools
```

在 `inventory.proto` 所在目录执行：

```bash
python -m grpc_tools.protoc -I . --python_out=. --grpc_python_out=. inventory.proto
```

执行成功后会出现 `inventory_pb2.py` 和 `inventory_pb2_grpc.py`。前者提供由 Protobuf 消息定义生成的 Python 类型与编码能力；后者提供 `InventoryStub`、`InventoryServicer` 和服务注册函数等 gRPC 代码。

`_pb2.py` 的命名是 Python Protobuf 生成代码的历史惯例，并不表示 `.proto` 使用了 proto2 语法。实际语法仍由文件中的 `syntax = "proto3"` 决定。

生成结果应与运行时使用兼容的版本。不同版本的工具生成代码可能要求特定的 Protobuf 或 gRPC 运行时版本，因此团队需要在依赖文件和构建流程中固定兼容的版本范围，并由 CI 统一执行生成，而不是把生成文件视为可以随意手改的普通源代码。

## 四、实现异步服务端

下面编写 `server.py`。为了把注意力放在 gRPC 的调用流程上，示例把库存放在进程内的字典中，并使用 `asyncio.Lock` 防止同一事件循环内的协程同时更新库存。这样做便于演示，但不具备持久化和跨进程并发一致性，稍后会专门说明这个限制。

```python
import asyncio
import grpc

import inventory_pb2 as pb2
import inventory_pb2_grpc as pb2_grpc


class InventoryService(pb2_grpc.InventoryServicer):
    def __init__(self):
        self.stock = {"sku-1": 5}
        self.lock = asyncio.Lock()
        self.next_id = 1

    async def Reserve(self, request, context):
        if not request.order_id or not request.sku or request.quantity <= 0:
            await context.abort(
                grpc.StatusCode.INVALID_ARGUMENT,
                "order_id、sku 不能为空，quantity 必须大于零",
            )

        async with self.lock:
            current = self.stock.get(request.sku)
            if current is None:
                return pb2.ReserveReply(accepted=False, reason="SKU_NOT_FOUND")
            if current < request.quantity:
                return pb2.ReserveReply(accepted=False, reason="INSUFFICIENT_STOCK")

            self.stock[request.sku] = current - request.quantity
            reservation_id = f"R-{self.next_id}"
            self.next_id += 1

        return pb2.ReserveReply(
            accepted=True,
            reservation_id=reservation_id,
        )


async def main():
    server = grpc.aio.server()
    pb2_grpc.add_InventoryServicer_to_server(InventoryService(), server)
    server.add_insecure_port("127.0.0.1:50051")
    await server.start()
    print("gRPC 库存服务监听 127.0.0.1:50051")
    await server.wait_for_termination()


if __name__ == "__main__":
    asyncio.run(main())
```

`InventoryService` 继承生成的 Servicer 基类，并实现同名 `Reserve` 方法。注册函数把这个实现绑定到服务端，之后请求可以由 gRPC 运行时分发到它。这里使用 `grpc.aio.server()` 创建异步服务端，业务方法可以通过 `async def` 编写。在实际项目中，数据库访问应使用适当的异步驱动，CPU 密集计算和阻塞 I/O 则需要避免长期占用事件循环。

`context.abort()` 会结束当前 RPC 并向调用方返回相应状态。库存不足在此示例中作为合法业务结果写进 `ReserveReply`，而参数格式错误使用 `INVALID_ARGUMENT`。这种区分不是由 gRPC 强制规定，而是接口契约的设计选择，需要客户端共同遵守。

服务端监听 `127.0.0.1`，仅用于本机实验。`add_insecure_port()` 创建没有传输层加密的监听端点；跨机器部署时应使用合适的 TLS 凭证、服务端身份验证和必要的客户端认证。不能把本机演示用的非加密连接直接视为生产环境默认方案。

## 五、实现客户端并观察结果

编写 `client.py`：

```python
import asyncio
import grpc

import inventory_pb2 as pb2
import inventory_pb2_grpc as pb2_grpc


async def main():
    async with grpc.aio.insecure_channel("127.0.0.1:50051") as channel:
        stub = pb2_grpc.InventoryStub(channel)
        try:
            reply = await stub.Reserve(
                pb2.ReserveRequest(
                    order_id="order-1", sku="sku-1", quantity=2
                ),
                timeout=3.0,
            )
        except grpc.aio.AioRpcError as exc:
            print(f"RPC 错误：{exc.code().name}，{exc.details()}")
            return

        print(reply)


if __name__ == "__main__":
    asyncio.run(main())
```

打开两个终端，先运行 `python server.py`，再运行 `python client.py`。客户端预期获得包含 `accepted: true` 和 `reservation_id` 的结果。服务端进程没有重启的情况下，再次运行客户端，会产生另一笔预留，并继续扣减库存。

`InventoryStub` 是生成的客户端代理。它封装了方法路径、消息序列化和反序列化行为；客户端无需手动拼装 HTTP/2 帧。`Channel` 则是调用远程服务的长期通信抽象，内部可以管理连接及相关状态。一个 Channel 不应简单理解为单条永远不变的 TCP 连接，它与实际连接和子通道的关系还受到解析器、负载均衡策略等配置影响。

这里的 `timeout=3.0` 为调用设置允许等待的时间。超出时，客户端可能收到 `DEADLINE_EXCEEDED`。但服务端可能已经执行了库存扣减，这一点会在后文的幂等与故障恢复部分继续讨论。当前示例的字典无法识别重复的业务操作标识，因此同一个订单再次发送请求会重复扣减；这正好说明 gRPC 的调用成功机制与业务幂等是两件不同的事。

## 六、HTTP/2、多路复用与流量控制

HTTP/2 允许在一个连接中建立多个 Stream，每个 Stream 有自己的标识，DATA 帧可以在连接上交错传输。gRPC 的多个调用因此能够复用底层连接，避免让每个请求都依赖单独的 TCP 连接。

多路复用并不等于无限并发。HTTP/2 连接可以协商允许的并发 Stream 上限，服务端也有自身的线程、协程、内存和数据库连接限制。如果负载超过处理能力，请求仍然需要等待或者失败。

HTTP/2 同时具有连接级和 Stream 级流量控制。发送方需要受到接收方允许接收的数据量约束，避免连续写入占满接收端资源。gRPC 的流式接口建立在这种机制上，但“启用了流量控制”不意味着应用可以完全忽略消费速度。消息生成速度过快、应用层队列无界、单条消息过大，都可能带来内存与延迟问题。

还有一种常见误解：HTTP/2 多路复用能够彻底避免队头阻塞。HTTP/2 在应用协议层消除了 HTTP/1.1 同一连接上响应顺序约束带来的某些阻塞，但它通常仍运行在 TCP 上。TCP 的有序交付意味着某段较早的字节丢失时，后续已收到的字节可能暂时不能交给上层，因此不同 Stream 仍可能被共同影响。

## 七、四种 RPC 调用形式

gRPC 提供 Unary、Server Streaming、Client Streaming 和 Bidirectional Streaming 四种主要调用形式。前面实现的是 Unary：一个请求对应一个响应。

服务端流可以用于从服务端持续返回任务进度、状态变化或者分页式数据。客户端流适合连续上传一批数据，最后由服务端给出汇总结果。双向流允许双方独立发送消息，例如长连接上的交互式通信，并不要求发送与接收严格交替。

在 `.proto` 中，使用 `stream` 关键字声明相应方向的流：

```proto
service TaskService {
  rpc WatchProgress(WatchRequest) returns (stream ProgressEvent);
  rpc Upload(stream UploadChunk) returns (UploadResult);
  rpc Chat(stream ChatMessage) returns (stream ChatMessage);
}
```

这只是流式方法的声明示例，相应消息定义和实现被省略，不属于前面可直接运行的库存服务代码。流式接口还需要明确终止条件、半关闭、消息顺序、取消及超时处理。

需要注意，流式 RPC 是一条调用内部的连续消息交换，不承担持久消息队列的职责。客户端断线后，gRPC 不会凭空恢复服务端应用先前发过的全部业务事件。要求断点续传时，需要应用层序号、持久化日志或其他可重放的数据来源。

## 八、Metadata、Deadline 与 Status

业务通信不仅包含方法参数，还常常需要身份信息、Trace ID 和调用链上下文。gRPC 使用 Metadata 传递与 RPC 相关的键值信息。它基于 HTTP/2 首部机制，适合承载调用元数据，但不应把大量业务数据塞进去，也不能把客户端任意提供的身份字段视为已经验证的权限。

客户端可以在调用时附带 Metadata：

```python
reply = await stub.Reserve(
    pb2.ReserveRequest(order_id="order-2", sku="sku-1", quantity=1),
    timeout=3.0,
    metadata=(("x-request-id", "req-123"),),
)
```

对于身份认证，生产环境仍应通过 TLS、令牌验证、访问控制等手段建立安全边界。Metadata 是传递信息的通道，不负责证明信息本身可信。

Deadline 表达调用方愿意等待到什么时候。服务端可以感知当前调用的剩余时间和取消状态，决定是否继续后续工作。假设订单服务只有两秒预算，却已经耗掉一秒半，之后再调用库存服务时，不能重新给予库存服务一个不受约束的五秒等待期。剩余预算需要合理传递到下游；不同语言的 gRPC 实现对截止时间自动传播的支持和默认行为可能不同，不能假定 Python 客户端所有链式调用都会自动继承。

状态码提供统一的失败分类。例如 `INVALID_ARGUMENT` 表示参数不符合接口要求；`UNAVAILABLE` 常用于服务暂时不可用；`DEADLINE_EXCEEDED` 表示调用超过期限；`RESOURCE_EXHAUSTED` 可表达资源限制；`INTERNAL` 表示服务端内部错误。这些状态只能提供技术层面的线索，业务端仍需根据方法是否有副作用以及操作是否幂等决定下一步。

取消也值得单独理解。客户端不再等待结果，或者 gRPC 通知服务端调用已取消，并不保证之前的数据库写入被撤销。真正的业务取消可能需要独立的操作状态和补偿逻辑。依靠网络调用的取消机制来回滚已经提交的事务，无法得到可靠保证。

## 九、从示例走向真实服务

当前示例已经把 gRPC 的基本调用链连接起来，但它还没有达到生产可靠性的要求。首先，库存状态只存在于进程内存，服务重启后就会丢失；多个服务进程也无法共享 `asyncio.Lock`，因此需要把库存写入数据库，并利用数据库事务与并发控制维持库存约束。

其次，示例没有幂等处理。请求超时后重试会再次扣减库存，需要以稳定操作标识、唯一约束和事务保存处理结果。再次，外部网络应该使用 TLS 和适当认证，服务端还需要监控请求速率、延迟分位数、状态码分布以及连接行为。

最后是接口演化。`.proto` 文件最好纳入版本控制，协议变更需要审查字段兼容性和业务语义，生成代码统一由构建流程维护。部署新旧服务版本时，应确保调用方与被调用方存在可工作的兼容窗口。仅仅把包名改成 `v2` 不能代替迁移方案，版本编号应与实际不兼容边界对应。

gRPC 在这里解决的是远程调用协议与开发工具问题。接下来，当一个库存服务从单实例扩展为多个实例时，客户端该怎样找到它们、选中哪个实例、识别失效实例，就进入服务发现和负载均衡的范围。
