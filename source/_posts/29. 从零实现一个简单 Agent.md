前面三篇已经建立了 Agent 的最小结构：模型接收上下文，可能提出工具调用；程序验证并执行工具；工具结果回到上下文，模型继续判断是否需要下一步。现在可以把这套过程写成一个真正可运行的 Python 程序。

本篇暂时不引入 LangChain、LangGraph 或现成 Agent SDK。我们直接使用 OpenAI Python SDK 的 Responses API，保留最关键的循环控制代码。这样做的目的，是让模型交互和工具执行的责任一目了然。后面介绍工具注册和 MCP 时，再逐步替换程序中的固定工具分发逻辑。

## 一、准备运行环境

创建项目并安装依赖：

```bash
uv init minimal-agent
cd minimal-agent
uv add openai
```

运行示例需要配置 `OPENAI_API_KEY`，同时把 `OPENAI_MODEL` 设置为账户能够访问、支持 Responses API 函数调用的模型。例如在 Bash 中：

```bash
export OPENAI_API_KEY='你的 API Key'
export OPENAI_MODEL='你有权限使用的模型 ID'
```

API Key 不应写入源文件，也不要提交到 Git。这个程序会调用真实模型 API，产生相应费用；库存数据则只存在于示例内存中，不会修改实际订单系统。程序使用同步客户端，使整个执行过程更容易观察。

我们提供两个只读工具，一个查询订单，一个查询库存。模拟数据固定在程序中，模型必须通过工具才能获得这些字段的事实来源。

## 二、先实现受控工具

```python

ORDERS = {
    "O-100": {"sku": "SKU-1", "quantity": 2, "status": "WAITING_STOCK"}
}
STOCK = {"SKU-1": 5}


def get_order(order_id: str) -> dict:
    order = ORDERS.get(order_id)
    if order is None:
        return {"found": False, "order_id": order_id}
    return {"found": True, "order_id": order_id, **order}


def get_stock(sku: str) -> dict:
    if sku not in STOCK:
        return {"found": False, "sku": sku}
    return {"found": True, "sku": sku, "available": STOCK[sku]}
```

这些函数没有模型依赖。它们是普通 Python 业务能力，可以单独进行单元测试。把工具实现保持为可独立调用的函数，有助于后来把模型层、执行器和业务服务拆开。

然后声明模型可见的工具 Schema：

```python

TOOLS = [
    {
        "type": "function", "name": "get_order",
        "description": "按订单号查询订单基本信息，只读。",
        "parameters": {
            "type": "object",
            "properties": {"order_id": {"type": "string"}},
            "required": ["order_id"], "additionalProperties": False,
        },
        "strict": True,
    },
    {
        "type": "function", "name": "get_stock",
        "description": "按 SKU 查询可用库存，只读。",
        "parameters": {
            "type": "object",
            "properties": {"sku": {"type": "string"}},
            "required": ["sku"], "additionalProperties": False,
        },
        "strict": True,
    },
]
```

工具定义和执行代码分别维护，避免把模型生成的工具名称直接用于动态访问 Python 全局变量。之后我们会建立一份明确的注册表，只有注册表中的工具才能被执行。


这次练习不要求模型完成任意开放式任务，只验证一个有限问题：“根据订单信息和库存信息，解释当前库存是否足以覆盖这笔订单的需求。”因此程序只需要两个只读工具。这样的控制范围是刻意选择的：若一开始就引入写库、邮件发送和浏览器操作，执行副作用与模型循环交织，反而不容易判断哪一个机制出了问题。

我们期望通过两类测试验证程序。确定性测试直接调用 `get_order`、`get_stock` 和工具执行器，检验参数、未知工具和业务字段；模型集成测试则观察模型是否能够在可用工具中做出合适选择，正确关联结果，最终基于证据生成回答。第一类可以稳定复现，第二类会受到模型版本、采样行为和上下文影响，因此不能把单次输出当成永久保证。

还应明确任务的实际验收：订单不存在时不得编造；库存为零时不得声称充足；没有运行过库存预留事务，就不得输出“已预留成功”。这些条件中，前两项可以通过模拟数据测试；最后一项反映业务动作与查询结论之间的边界。

## 三、编写 Agent Loop

将上述代码和下面的内容一起保存为 `agent.py`：

```python

import json
import os
from openai import OpenAI

HANDLERS = {"get_order": get_order, "get_stock": get_stock}
ARG_NAMES = {"get_order": "order_id", "get_stock": "sku"}


def execute_tool(name: str, raw_arguments: str) -> dict:
    if name not in HANDLERS:
        return {"ok": False, "error": "UNKNOWN_TOOL"}
    try:
        arguments = json.loads(raw_arguments)
    except json.JSONDecodeError:
        return {"ok": False, "error": "INVALID_JSON"}
    key = ARG_NAMES[name]
    if (not isinstance(arguments, dict) or set(arguments) != {key}
            or not isinstance(arguments[key], str)
            or not arguments[key].strip()):
        return {"ok": False, "error": "INVALID_ARGUMENTS"}
    return {"ok": True, "data": HANDLERS[name](arguments[key])}


def run_agent(task: str, max_steps: int = 6) -> str:
    client = OpenAI()
    model = os.environ["OPENAI_MODEL"]
    history = [
        {"role": "developer", "content": (
            "你是订单查询助手。只依据工具结果报告订单和库存情况；"
            "没有事实依据时明确说不知道，不执行任何写入。")},
        {"role": "user", "content": task},
    ]

    for step in range(max_steps):
        response = client.responses.create(
            model=model, input=history, tools=TOOLS,
            parallel_tool_calls=False,
        )
        if response.status != "completed":
            raise RuntimeError(f"模型响应未完成：{response.status}")

        history.extend(response.output)
        calls = [item for item in response.output
                 if item.type == "function_call"]
        if not calls:
            if not response.output_text:
                raise RuntimeError("模型没有可交付的文本输出")
            return response.output_text

        for call in calls:
            result = execute_tool(call.name, call.arguments)
            print(f"第 {step + 1} 轮工具：{call.name}，结果：{result}")
            history.append({
                "type": "function_call_output",
                "call_id": call.call_id,
                "output": json.dumps(result, ensure_ascii=False),
            })

    raise RuntimeError(f"达到最大模型调用轮数：{max_steps}")


if __name__ == "__main__":
    print(run_agent("查询订单 O-100，并判断现有库存数量是否足够覆盖该订单"))
```

这段示例最重要的部分并不是 `while` 或 `for`，而是历史记录怎样增长。每轮模型输出项被原样追加到 `history`，如果出现工具调用，就为每个调用附上使用相同 `call_id` 的结果项。下一轮模型因此能够知道先前提出了什么调用，以及外部执行器返回了什么。

`parallel_tool_calls=False` 将单轮可返回的函数调用数量限制为零或一个，方便演示顺序控制。虽然当前代码仍使用循环处理多个调用，但没有自行推断并行执行的安全性。`max_steps` 防止模型持续调用工具而不结束；超过限制就报告运行失败，而不是伪造一个已经完成的答案。


从实现结构看，Agent 至少依赖三个端口：模型端口接受上下文与工具声明并返回输出项；执行器端口接受工具调用并返回受控结果；历史记录负责保存本轮模型输出与相关工具反馈。若将这三者都硬编码在一段 `while` 中，虽然能跑通，却难以在不产生 API 费用的情况下测试协议处理。

可以先让 `run_agent` 接受一个注入的模型客户端，再为执行器保留纯函数接口。测试时提供一个会按指定顺序返回 `function_call` 和最终 `message` 的假客户端，从而验证运行时是否使用原始 `call_id` 回填结果。模型行为测试再单独连接真实接口。这样可以避免把模型产生随机不同调用顺序误判成程序错误。

Responses API 中的输出可能不只有 `function_call`。在进行后续请求时，应该保留 API 要求的输出项及其顺序。在本文采用的 `history.extend(response.output)` 模式下，SDK 会把类型化输出项继续作为上下文的一部分；若使用 `previous_response_id`，则会依赖服务端保存的响应关联机制，两种方式的状态与隐私权衡不同。不能只抽取模型的可见文本重新发起下一轮，因为这可能丢失调用身份及其他必要上下文。

## 四、运行与检查

执行：

```bash
uv run python agent.py
```

模型可能先查询订单，再查询库存，然后解释结果；也可能根据提示选择其他顺序，或者在证据不足时直接回答。模型的具体输出是非确定性的，不应该把某一次工具调用顺序当作协议保证。

程序的期望业务事实很清楚：订单 `O-100` 需要两件 `SKU-1`，模拟库存中有五件。若模型正确查询两个工具，可以得到当前模拟库存数量足以覆盖订单数量这一判断。但这不等于真实业务中的库存已经被预留，也不等于可以保证并发条件下最终扣减成功，因为代码没有执行预留事务。

可以故意将 `ORDERS` 中的订单删掉，再运行程序，观察模型是否诚实报告订单不存在。也可以将库存改为 1，看模型能否据此更新结论。测试目标是验证工具结果确实影响模型输出，而不是只看它是否生成了一段流畅文字。


先把上面的完整代码保存为 `agent.py`，单独建立 `test_agent.py`，对不会产生外部副作用的工具进行测试：

```python
from agent import execute_tool


def test_known_tool():
    result = execute_tool('get_order', '{"order_id":"O-100"}')
    assert result['ok'] is True
    assert result['data']['sku'] == 'SKU-1'


def test_unknown_tool():
    result = execute_tool('delete_order', '{}')
    assert result == {'ok': False, 'error': 'UNKNOWN_TOOL'}


def test_bad_arguments():
    result = execute_tool('get_stock', '{"sku": 1}')
    assert result['error'] == 'INVALID_ARGUMENTS'
```

使用 `uv add --dev pytest` 和 `uv run pytest -q` 执行即可。这些测试不会调用模型，因此能稳定检查工具执行层。然后再运行真实模型集成测试，检查模型输出包含的调用类型、工具参数、结果关联、轮数上限和最终回答。

这里需要补一条工程细节：当前演示执行器假设两个 Handler 都不会抛出异常。扩展成真实网络工具后，还应捕获可预期的超时和远端错误，形成标准结果；程序自身的 Bug 不应一律吞掉并冒充正常的“工具失败”。对会发生副作用的工具，未知结果还需要在下一篇引入幂等或状态查询策略。

当 Agent 输出错误结论时，应先判断模型没有调用工具、调用了错误工具、参数错误、工具返回数据错误，还是工具结果已经正确而模型解释错误。仅打印最终回答无法识别这些故障来源。演示程序已经输出每轮工具名称和返回结果，可以进一步打印经过脱敏的 `call_id` 与轮次，比较模型提出的调用和执行器真正执行的操作。

如果模型始终没有查询库存，却对库存足够与否作出确定断言，问题位于工具选择或提示约束；如果工具返回可用数量 1，模型仍声称足以覆盖数量 2，则问题位于证据解释；如果工具本身查错了 SKU，则应修正工具参数与数据来源，而不是依赖继续调整 Prompt 掩盖问题。

## 五、这段代码做到了什么，还有什么欠缺

目前的模型循环、工具调用与反馈链已经完整，而且能够实际访问两个本地业务函数。但这是一个单进程、短时间运行的基础 Agent。它没有数据库持久化、没有真实用户权限、没有执行状态恢复，也没有对模型调用失败做重试预算和统一错误分类。

代码中的参数验证仍然是针对两个固定工具手工实现的。工具数量增加后，按名称分支和单独维护 `ARG_NAMES` 会越来越难扩展。更合适的做法是把工具元数据、Schema、处理函数和权限策略组合成注册实体，执行时通过统一分发器完成校验与调用，这就是下一篇的主题。

另一个限制是上下文。每一轮都在扩大 `history`，最终会受到上下文窗口和成本约束。这里以最多六轮作为示例边界，不打算解决长期执行中的压缩和记忆问题；这些机制应归入 Harness 的运行时设计。

如果以后让工具支持业务写入，还必须引入真正的授权、事务与幂等。当前 `execute_tool` 的错误字典只能告诉模型调用失败，无法保证多个服务之间的业务状态一致。Agent Loop 是多步骤决策的最小控制结构，不是一套自动获得生产可靠性的后端框架。


示例的 `max_steps=6` 限制的是模型请求轮数，并不保证六轮后一定有完整答案；某轮响应可能包含其他类型的输出项或在服务端未正常完成。`parallel_tool_calls=False` 用于减少一次输出包含多个调用的复杂性，但执行器仍应按实际响应逐项检查，不应将这个参数当成工具级授权或副作用保护。

该程序刻意没有引入持久化、角色权限、外部任务调度与多租户上下文，这是为了让学习对象保持清晰。如果直接把这个程序扩展成能删除文件或发送邮件的 Agent，安全性并不成立。尤其是 `get_order` 这种看似只读的工具，在真实系统中也要验证当前用户是否有权读取这笔订单，不能因为工具标注为只读就跳过授权。

完整工程化要在下一个专题处理，但基础 Agent 的验收必须已经达到：模型无法绕过工具注册表执行未声明函数；无效参数不会传入 Handler；每次工具返回都关联到正确调用；没有调用结果时模型不被允许伪造业务事实；预算耗尽时报告未完成而非宣称完成。只有这些条件得到程序和测试保证，才能继续增加工具和复杂任务。
