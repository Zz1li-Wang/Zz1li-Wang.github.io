前面已经知道，模型可以在响应中提出工具调用，应用执行后再把结果送回模型。如果任务只需要一次查询，一次模型调用和一次工具反馈就足够。但真正的任务通常没有固定步数：先查订单，再看库存，可能还需要读取供应商交期，最后才能形成结论。

把这种交互持续执行下去，就得到了 Agent Loop。它的代码外观可以只是一个 `while` 循环，设计难点却在于每一轮应当保存什么、何时允许工具运行、失败如何处理，以及怎样判断任务已经结束。

## 一、从单轮调用到持续执行

假设用户希望分析一个订单为什么迟迟没有发货。模型第一次可能选择 `get_order`；工具返回订单状态为 `WAITING_MATERIAL`。第二轮模型再选择 `get_material`；工具返回某项材料预计三天后到货。模型随后可以给出结论，也可能发现材料记录缺少供应商反馈，需要继续查询。

开发者无需事先穷举所有查询顺序。每一轮模型调用都基于当前上下文，决定接下来的输出。抽象地写，可以把模型的观察输入表示为 `o_t`，当前内部任务状态表示为 `s_t`，模型选择的行动表示为 `a_t`，环境执行后得到的反馈表示为 `e_{t+1}`。运行时随后根据结果构造下一轮状态和观察：

\[
a_t = \pi(o_t,s_t),\qquad e_{t+1}=\operatorname{Execute}(a_t),\qquad (o_{t+1},s_{t+1})=F(o_t,s_t,a_t,e_{t+1}).
\]

这里的 `\pi` 只是对模型决策机制的抽象，不能误解为模型显式维护了一个可供应用读取的稳定策略函数。`F` 则主要由应用控制：把哪些信息保存到上下文、哪些错误反馈给模型、哪些信息不能传播，都是运行时的设计决定。

循环推进一次，未必意味着调用了一次工具。模型可能直接给出最终答案，也可能一轮提出多个独立调用。运行时应以实际的输出项和状态转换为准，不能假定永远是“一个模型响应对应一个工具”。

## 二、一次迭代需要明确的状态

最小实现可以将用户指令、工具定义和历史消息组成上下文，调用模型后追加输出，再把工具结果反馈进去。但至少还有两类信息应与消息内容区分。

一类是执行控制信息，例如轮数、剩余预算、是否取消、当前等待的工具调用。它们决定系统允许继续做什么，不适合完全由模型的一段文字声明。另一类是外部业务状态，例如库存预留结果、订单审批记录和文件是否写入成功。它们应以业务系统或持久化存储为事实来源，不能只因为上下文里出现“已完成”便认为真实副作用存在。

可以在逻辑上把一次运行表示为：

```python

from dataclasses import dataclass, field

@dataclass
class RunState:
    task: str
    steps: int = 0
    status: str = "RUNNING"
    input_items: list = field(default_factory=list)
    last_error: str | None = None
```

这是演示用的内存状态，进程退出后就会丢失。正式 Harness 会进一步把模型调用、工具调用与业务操作拆成持久化实体，在保存状态时处理故障窗口。本篇先研究没有持久化时循环自身必须遵守的逻辑。

运行状态不应只存在于模型自己生成的计划文本中。模型可以输出“接下来先搜索、再计算”，但真正已执行多少步、当前调用是否成功，应由运行时依据可观察结果维护。这样才能在模型产生矛盾说明时保持可检验的执行事实。


一个能长时间维护的 Agent Loop 应将执行阶段显式化。例如 `READY` 表示可进入模型调用，`MODEL_PENDING` 表示推理请求尚在进行，`TOOL_PENDING` 表示已有待执行工具，`WAITING_APPROVAL` 表示必须等待外部批准，`COMPLETED`、`FAILED` 和 `CANCELLED` 表示终止状态。这些名字不是通用标准，但状态关系必须由应用定义。

对于模型结果，可以定义转移函数：

\[
\delta(\text{MODEL\_PENDING},\text{model response})=
\begin{cases}
\text{TOOL\_PENDING}, & \text{存在待执行调用}\\
\text{COMPLETED}, & \text{存在符合约定的最终输出}\\
\text{FAILED}, & \text{响应无效且无法恢复}
\end{cases}
\]

实际系统还必须处理一种容易遗漏的情况：本轮既没有工具调用，也没有可用的最终消息，或者响应因长度限制而不完整。不能仅凭“没有工具调用”就认定任务完成。程序需要检查 API 给出的完成状态和输出项类型，并决定继续、修复还是报告失败。

状态机能防止非法跳转。例如处于 `WAITING_APPROVAL` 时，调度器不能擅自执行下一步敏感工具；处于 `COMPLETED` 时，延迟到达的回调也不能把任务重新改成 `RUNNING`。这些约束是执行正确性的基础，而不仅是日志展示问题。

模型上下文用于向模型传递可见的信息，运行状态用于决定程序还能做什么。上下文可能经过摘要或裁剪；执行状态则必须保留足够的事实以恢复当前动作。因此，历史消息列表不应兼任完整事件日志。一次执行可维护 `run_id`、迭代号、待处理调用集合、每次调用的 `call_id`、完成结果、预算与终止原因，再把必要的片段投影成模型下一轮输入。

值得注意的是，模型可能主动建议“我已经完成全部操作”，但这不会让执行状态自动转成 `COMPLETED`。只有运行时确认模型输出完整、没有未完成工具以及必要验收条件满足，状态转换才成立。

## 三、决策、执行与反馈分开处理

一次循环可以分成两个阶段。模型阶段产生待执行的调用，执行阶段对这些调用做验证和分发。模型输出不应直接触发数据库更新，中间必须经过受控执行器。

执行器收到工具名称时先查注册表，再检查参数结构、用户权限和副作用策略。查询类工具可以立即执行；涉及删除、支付、外发内容或权限变更的工具，通常应检查是否需要审批。完成后，将标准化结果连同调用标识交回模型，使模型知道该步骤的结果。

出错时要保留失败的性质。参数验证失败可以作为一次工具错误反馈，模型可能修正参数后重试；权限不足则不能靠换一种说法绕过；服务端长时间无响应，需要根据超时和幂等规则决定是否继续。错误并不必然意味着整项任务立刻终止，但同样不能为了保持循环而无限重试。

对一次输出中的多个调用，如果彼此独立，可以考虑并发。可并发与否主要由业务依赖和副作用决定，而不是模型把它们放在同一响应里的顺序。一个工具修改库存、另一个工具读取库存，是否能并发必须明确；盲目并行容易产生错误结果。

## 四、终止条件与预算

Agent 至少需要一个明确的正常结束条件：模型返回可交付的最终回答，且没有继续等待处理的工具调用。与此同时，运行时应当支持预算终止和错误终止。预算可以包括最大模型调用轮数、总 Token 用量、累计工具调用次数、时间预算以及外部资源消耗。

例如：

```python

for step in range(max_steps):
    response = call_model(context)
    calls = extract_tool_calls(response)
    if not calls:
        return final_answer(response)
    for call in calls:
        result = validate_and_execute(call)
        append_call_result(context, call, result)
raise RuntimeError("Agent 达到最大执行轮数")
```

`max_steps` 只是最简单的防护。真实接口每一轮可能包含多个工具调用，模型输出也可能不完整，因此不能用轮数代替全部资源预算。如果调用失败后程序只把“请再试一次”送回模型，模型就可能重复同样的步骤直至耗尽预算。

正常结束还要接受任务本身的验证。生成了一段回答，不代表用户要求的文件已经写入；工具返回成功，不代表整个研究任务已经达到质量标准。对于可以客观判断的交付物，应由程序检查文件、记录或外部状态。主观任务则可能需要明确标注证据不足，或者由用户评审。


设模型同时提出 `get_order(order-1)` 与 `get_stock(sku-1)`。两项只读查询独立，执行器可以并行完成，逐一使用原始调用 ID 回填结果。如果第二项实际上依赖第一项查出的 SKU，那么模型在同一轮提出的两个调用就可能包含错误假设。这时应要求调用方事先提供确切 SKU，或者先返回订单结果再发起新一轮决策；不能用“模型一次返回两个调用”作为并行安全的证明。

对于修改操作，执行器需要更多信息。`reserve_stock` 与 `release_stock` 即使参数不同，也可能竞争同一个库存行；同时执行会让结果受调度顺序影响。可以把工具标注为 `read_only`、`writes_resource` 或更精确的资源集合，再依据业务约束串行化或拒绝冲突请求。一个开放式 Agent Loop 的执行层必须承担传统并发程序的正确性责任。

`max_steps` 很容易实现，但不能代表所有预算。一轮模型可能发起十个工具、返回几 MB 结果，也可能在没有工具的情况下消耗大量推理 Token。预算应区分模型请求次数、工具调用次数、累计时间、Token/费用、单次结果大小和外部副作用次数，并为不同类型设置合适的边界。

其中总时限要使用单调时钟计算本地耗时。一次工具调用的超时不等于整项任务的剩余预算；即便某个下游支持重试，也不应每次重试都重新获得完整的总时限。用户取消时，尚未完成的模型请求和工具请求可以尝试传播取消，但已提交的订单操作不会因此自动撤销。

验收也应是终止条件的一部分。用户要求生成报告，程序需要确认报告对象存在并符合最基本的结构约束。模型给出一段看似完成的说明，与任务交付物真实存在之间还隔着执行器和存储系统。

## 五、循环不应把不确定性藏起来

一次模型推理可能选择了错误工具。程序应该把错误限制在本轮执行，不应自动升级权限；工具返回的数据可能过长，运行时可以截断并说明截断发生；模型可能遗漏用户约束，因此重要业务限制还应落实为程序侧校验。

另一个容易忽略的问题是上下文不断增长。每轮工具结果和模型输出都追加到消息列表，长任务很快会触及上下文预算。简单地删除旧消息可能破坏工具调用与反馈之间的关联，也可能让模型遗忘未完成事项。基础 Agent 可以通过限制轮数控制规模，长时间运行的系统则需要上下文压缩、独立执行日志和恢复机制。

此外，模型输入可能包含外部工具返回的文本。这些内容可以作为事实材料，但不应指挥执行器改变权限、忽略审批或覆盖开发者设置的约束。循环越长，外部内容进入上下文的机会越多，运行时越需要持续维护信任边界。

还可以给运行循环规定几条能够通过程序检查的不变量。处于终止状态的任务不得继续产生新的外部工具调用；每一条模型工具调用必须保留唯一的调用关联 ID；工具结果进入模型上下文前，必须与对应调用匹配；任何需要审批的动作，在审批事实成立之前不得执行；预算耗尽后不能自动进入下一轮推理。这些不变量比“循环最多执行 N 次”更能刻画执行器是否正确。

模型调用本身也可能发生“响应不确定”的情况：客户端已经发送请求，网络中断，无法取得生成结果。对于没有副作用的普通模型生成，重新请求通常不会直接重复修改业务数据，但结果可能不同并产生额外费用；如果模型提供商的工具机制允许服务端直接执行托管工具，就还需要依据那种工具的副作用与恢复协议判断。重新生成的模型响应也可能包含不同的调用 ID，因而不能将推理请求重试与业务工具重试混在一个通用装饰器中。

把这些规则实现为受控状态转换之后，Agent Loop 才具有可测试的边界。可以使用模拟模型返回“两个工具调用”“不完整响应”“无可用消息”“持续相同工具调用”等序列，验证运行时如何处理，不需要每次都调用真实模型；真实模型测试再用于评估工具选择和信息解释质量。二者共同组成 Agent 的基础测试策略。

## 六、Agent Loop 与工作流引擎

工作流引擎也会反复推进步骤，并保存任务状态。两者的区别在于下一步控制权主要来自哪里。确定性工作流通常用开发者定义的状态转换条件驱动；Agent Loop 则允许模型在给定可用动作中参与选择。当然，一套系统可以同时存在两者：外层工作流负责审批与阶段转换，阶段内部再运行一个受预算约束的 Agent。

这种组合往往比把全部业务交给一个无限循环更容易维护。例如订单审批需要严格遵守状态机，而处理申请材料时又可能需要模型动态选择解析工具。确定性部分维护业务规则，模型处理文本理解和不确定信息搜索，彼此形成明确接口。

基础循环已经建立之后，下一篇可以直接用 Python 的模型 API 实现它。在具体代码中，我们将看到 `response.output`、`function_call`、`call_id` 和 `function_call_output` 怎样在多个轮次之间保持连续。


假设执行器调用外部扣款接口，外部服务已经提交成功，但 Agent 进程在记录结果前崩溃。恢复后本地只知道有一笔待处理调用，却不知道它是否已成功。此时无条件重试会引发重复扣款，跳过又可能遗漏未完成的业务。

这种问题没有仅靠 `try/except` 就能解决的通用办法。正确做法需要稳定的业务操作 ID、远端幂等或状态查询、明确的执行记录以及适当的恢复流程。在传统事务系统里，提交顺序与写前记录用于减小这种不确定性；在跨系统调用中，还要依赖业务对账。Agent Loop 多了一层模型决策，却没有免除分布式系统的基本限制。

基础篇只需明确该故障窗口，不应在这里假装已经提供完整的持久化调度器。后面的 Harness 专题会把每次模型调用与工具调用建模为有生命周期的执行记录，并讨论暂停、恢复和人工审批。这里的关键认识是：循环可以容易地重跑，副作用却未必允许重做。
