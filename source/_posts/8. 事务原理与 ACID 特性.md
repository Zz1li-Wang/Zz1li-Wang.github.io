在上一篇文章中，我们区分了数据库连接、连接池和 Session，知道执行完一条 SQL 并不代表事务已经结束。但还有一个问题没有回答：数据库究竟凭什么保证，多条已经执行过的 SQL，要么全部生效，要么全部不生效？

考虑一次账户转账。先从账户 A 扣除金额，再向账户 B 增加相同金额。如果第二条 SQL 失败，只留下第一条修改显然不行。即使两条 SQL 都成功执行，也不能立即认为操作已经安全：服务器可能在提交时断电，其他事务可能同时修改账户，应用也可能在提交成功后丢失网络响应。

这些不是同一种故障。事务要解决的是一组不同的问题：失败后如何处理部分修改，其他事务能看到什么，提交结果如何在崩溃后保留下来，以及数据怎样满足业务约束。通常用 ACID 概括它们，但理解 ACID 最有效的方法，是先看 PostgreSQL 在这些场景中实际上做了什么。本文以 PostgreSQL 18 为主要实现背景；涉及 Python 的示例使用 SQLAlchemy 2.0.x 与 `asyncpg`。

## 一、事务的边界到底在哪里

假设有两条账户记录，余额都以整数分为单位保存。最直接的转账语句如下：

```sql
BEGIN;

UPDATE accounts
SET balance_cents = balance_cents - 5000
WHERE id = 'A';

UPDATE accounts
SET balance_cents = balance_cents + 5000
WHERE id = 'B';

COMMIT;
```

`BEGIN` 启动事务块，`COMMIT` 请求提交其中的修改。如果需要放弃，可以用 `ROLLBACK` 结束事务并使本次修改不再作为已提交结果生效。这里强调“作为已提交结果生效”，而不是简单说数据库会把每次写入都按相反方向执行一遍；PostgreSQL 并不是这样实现普通事务回滚的。

PostgreSQL 中每条 SQL 都在事务上下文中执行。没有显式 `BEGIN` 时，服务端通常把单条语句作为一个隐式事务处理；客户端驱动也可能默认开启跨多条语句的事务。

因此，不能仅凭代码里是否出现 `BEGIN` 字符串判断有没有事务。上一篇提到的 SQLAlchemy `autobegin`，就是应用层对这种事务生命周期的管理。

事务与语句也不是一回事。第一条 `UPDATE` 返回成功，只意味着这条语句在当前事务里执行成功，并不意味着其效果已经提交。`flush()`、`execute()`、`commit()` 更不能混同：在 SQLAlchemy ORM 中，`flush()` 可以真实发出修改 SQL，而事务直到提交才完成。

事务在正常路径中经历开始、执行语句、提交或回滚。发生 SQL 错误时，PostgreSQL 的显式事务块通常进入失败状态，后续普通 SQL 会报 `25P02`，直到执行 `ROLLBACK` 才能重新开始正常事务。

不能以为捕获了 Python 异常，数据库事务就自动恢复了。只有建立了保存点，才可能回滚到保存点并继续外层事务；这部分留给第三篇。

这个边界还决定了一个根本事实：事务是**数据库承诺处理的一组操作**，不是 Python 代码块本身具有的魔法。把数据库修改和一次 HTTP 请求写在同一个 `try` 里，不会让远程 API 调用自动参与 PostgreSQL 的提交与回滚。

## 二、原子性：回滚为什么不一定要“反向修改数据”

原子性（Atomicity）要求事务里的数据库修改最终作为一个整体提交，或者作为一个整体放弃。它不是说每条 SQL 执行期间都没有中间状态。执行到第一条 `UPDATE` 之后，当前事务自己通常可以读到已经修改过的余额；只是其他普通事务不能把这个未提交结果当成已提交数据读取。

如果第二条 SQL 出错，数据库怎么知道第一条修改也不应算数？一种直观但并不准确的想象，是数据库记录每一步的反向操作：扣了多少就加回多少，插入了什么就删掉什么。PostgreSQL 的普通表并不主要依靠逐条执行反向 SQL 实现回滚。

PostgreSQL 使用多版本并发控制（MVCC）。更新一行时，通常会产生新的行版本，旧版本不会在更新的同一刻立即失去全部存在意义。行版本带有与事务有关的元信息，例如 `xmin`、`xmax`；数据库结合事务状态和读取者的快照，判断某个版本对当前查询是否可见。

事务标识也不是每次执行 `BEGIN` 就必须立刻取得永久 XID：事务在真正需要写入时才会分配常规事务 ID，单纯只读事务可以避免不必要的分配。

如果修改所属事务回滚，新增的行版本不会因为磁盘上已经存在就自动成为有效数据。PostgreSQL 能根据事务结果把它视为无效版本，之后再由清理机制回收不再需要的空间。因此，**逻辑回滚与物理清理可以发生在不同时间**。事务回滚不意味着磁盘页上从未出现过相关字节，也不意味着 WAL 中不会留下该事务的修改记录。

这正是原子性与日志恢复能够兼容的关键：数据文件可能已经包含未提交事务留下的物理变化，但事务可见性不会把它们错误地解释成已提交结果。PostgreSQL 还维护事务提交状态等必要信息；崩溃恢复后可以据此区分完成与未完成的事务。关于快照具体怎样判断行版本可见，将在第四篇深入讨论。

原子性也不是无条件覆盖所有 PostgreSQL 对象。`nextval()` 消耗的序列值不会因为事务回滚而重新分配，所以自增主键可能出现空洞；外部系统已经收到的消息或请求更不会因为数据库执行 `ROLLBACK` 就消失。这里的“全部或全部不生效”，需要限定在该事务所管理、支持事务语义的数据库操作范围内。

## 三、持久性：COMMIT 为什么离不开 WAL

原子性解释了失败后如何把修改判定为无效，但还没有解释另一种故障：数据库已经告诉客户端 `COMMIT` 成功，此时机器突然断电，内存中尚未写入数据文件的修改怎么办？

如果每次执行 `UPDATE` 都要求立即把相关表和索引的每个数据页安全写到磁盘，提交成本会很高。而且一次事务可能修改很多分散的数据页，数据库还必须处理写入过程中的崩溃。

PostgreSQL 采用预写式日志（Write-Ahead Logging，WAL），把“记录如何恢复修改”和“把所有修改过的数据页落盘”分开。

修改持久化表时，PostgreSQL 可能先在共享缓冲区修改数据页，并产生描述相关修改的 WAL 记录。WAL 记录按日志位置顺序组织，使用 LSN（Log Sequence Number）标识位置。

事务提交时还需要有标识其提交结果的日志信息。在通常的同步提交配置下，数据库会等待提交所需的 WAL 安全刷新到持久存储，然后才向客户端报告成功。

WAL 的核心顺序约束是：**一个被修改的数据页要写入持久化数据文件之前，与该页修改有关的 WAL 必须先可靠地刷新到持久存储**。这并不意味着数据页一定在 `COMMIT` 后才写入。

后台写进程或检查点可能在事务尚未提交时写出脏页；只要遵守 WAL-before-data 的顺序，恢复仍有足够信息判断最终有效的事务结果。

这样，提交时通常不需要立即把本次事务修改的所有表数据页都刷盘，而可以主要等待必要的 WAL 持久化。多个事务的日志也可能通过一次刷盘操作共同获得持久化保证，这为组提交（group commit）提供了基础。

它降低了频繁随机刷写表数据页的需求，但不是“WAL 没有磁盘 I/O”，也不意味着每一次提交只进行一次固定的磁盘操作。

崩溃后，PostgreSQL 根据最近的检查点及之后的 WAL 做恢复。检查点为恢复提供一个已知的持久化起点；恢复过程可以把尚未体现在数据文件中的修改重新应用到数据页，这通常称为 REDO。

恢复重做的是必要的物理修改，不等于“把 WAL 中所有操作都认定为已提交”。没有完成提交的事务，即使部分数据更改曾进入数据文件或者被 WAL 重做，仍不能作为有效的已提交事务结果出现。

这里还需要区分“写入 WAL 缓冲区”“写入操作系统页缓存”和“刷新到可靠存储”。只有后者配合正确的操作系统和存储设备行为，才能形成我们讨论的崩溃持久性。

`fsync` 等配置是否启用、硬件是否诚实执行持久化请求、存储是否发生不可恢复的损坏，都会影响保证能否成立。事务持久性也不等于有备份，更不等于已经同步复制到了另一台机器。

PostgreSQL 的 `synchronous_commit` 默认是 `on`。在没有配置同步备库时，通常意味着事务提交前等待本地 WAL 刷盘。如果显式设置为 `off`，数据库可以在 WAL 还未安全落盘时就向客户端报告提交成功；突然崩溃时，最近一部分已返回成功的事务可能丢失。

这是一种有意识地放宽持久性响应时点的性能取舍，而不是 ACID 的定义发生了变化。与之不同，直接设置 `fsync=off` 可能进一步引入严重的数据损坏风险，不能把两者当成等价优化。

普通持久化表之外还有明确例外。比如 PostgreSQL 的 `UNLOGGED` 表不提供普通持久化表的崩溃安全保证，在非正常关闭后可能被清空。因此谈“PostgreSQL 提供持久性”，必须同时说明表类型、提交模式和存储前提。

## 四、一致性：数据库不知道所有业务规则

ACID 中最容易被误解的是一致性（Consistency）。很多解释会直接说“事务保证数据从一个一致状态进入另一个一致状态”，但如果不回答“一致由谁定义”，这句话几乎没有实际意义。

仍然以转账为例，假设业务规则要求余额不得为负，且转账不能凭空创造或消灭金额。数据库能够通过 `CHECK (balance_cents >= 0)`、外键、唯一约束等机制维护已经声明的局部完整性条件；一旦执行违反这些约束的语句，数据库会拒绝不合法的结果。

有些约束可以延迟到提交时检查，因此事务进行过程中暂时不满足某些延迟约束，不必然意味着最终能提交无效数据。

但数据库不会自动理解“这两笔账户余额之和必须保持不变”。如果程序只扣减 A，却忘记增加 B，只要扣减后的值满足已定义的数据库约束，事务完全可能提交成功。此时原子性没有失效，持久性也没有失效；真正缺少的是业务不变量的实现。

因此，可以把事务一致性理解为：**在应用逻辑正确、数据库约束足够、并发控制满足前提的条件下，事务应当把满足规则的状态转换为另一个满足规则的状态**。数据库对它知道的约束负责，业务系统对没有声明在数据库中的规则负责。把一致性完全归功于数据库，反而容易掩盖程序逻辑错误。

更复杂的规则还涉及多个事务的并发。如果两个事务都先检查某项条件，然后各自修改不同记录，即使每个事务单独执行时都符合规则，并发执行也可能造成违反整体不变量的结果。

此时仅有 `BEGIN` 和 `COMMIT` 不够，还需要合适的隔离级别、约束设计或显式并发控制。这正是 ACID 的 C 和 I 不能分开孤立理解的原因。

## 五、隔离性：单个事务正确，不代表并发时仍然正确

隔离性（Isolation）解决的是多个事务同时运行时，彼此的读写应该怎样相互影响。PostgreSQL 通过 MVCC、锁和更高隔离级别下的冲突检测提供不同程度的隔离。最容易建立的直觉是，普通查询不会读取另一个事务尚未提交的行修改；但这不等于所有事务都仿佛在排队，一个结束后才轮到另一个。

PostgreSQL 默认使用 `READ COMMITTED`。在这个级别下，普通 `SELECT` 的可见快照通常以每条语句开始时为界。同一个事务连续执行两次 `SELECT`，如果中间有其他事务成功提交，前后两次查询可以得到不同结果。

它不允许脏读，但并不提供最强的可串行化保证。PostgreSQL 所称的 `SERIALIZABLE` 才要求成功提交的并发事务集合具有与某种串行执行相容的效果；当检测到无法满足这个条件时，数据库可能中止其中某个事务，应用必须能够重试。

这个区别对于理解“事务修改会同时对外可见”尤其重要：其他事务不会看到某次提交的一半结果，但在 `READ COMMITTED` 下，它的两条查询可能分别发生在提交前、提交后，因此分别看到提交前后的完整状态。这不是读取到了半个事务，而是两次语句读到了不同时间的已提交数据库状态。

所以，给一段代码加上事务边界，可以避免这一段修改只成功一部分，却不能自动解决所有并发更新问题。关于快照、行版本可见性、不可重复读和写偏斜，将在第四篇具体推导；锁和竞争策略则留给第五、第六篇。

## 六、在 SQLAlchemy 中把“完整提交”变成明确的代码边界

理解原理之后，再看实际工程如何利用事务。下面给出一个最小的异步 SQLAlchemy Core 示例。它保留了两笔账户更新，同时检查了扣款是否成功和目标账户是否存在。金额用整数分而不是浮点数保存，避免在这个例子中引入额外的舍入问题。

事先在 PostgreSQL 中创建测试表，并为两个账户写入初始余额：

```sql
CREATE TABLE IF NOT EXISTS blog_tx_accounts (
    id text PRIMARY KEY,
    balance_cents bigint NOT NULL CHECK (balance_cents >= 0)
);

INSERT INTO blog_tx_accounts (id, balance_cents)
VALUES ('A', 10000), ('B', 10000)
ON CONFLICT (id) DO NOTHING;
```

下面的 `transfer()` 使用 `engine.begin()` 定义事务范围：正常退出上下文时提交，抛出异常时回滚。我们故意留了一个失败注入参数，用来观察“第一条 UPDATE 已经成功，但整个事务仍然回滚”的情形。

```python
import asyncio
import os

from sqlalchemy import text
from sqlalchemy.ext.asyncio import create_async_engine


async def transfer(engine, sender, receiver, amount, fail=False):
    if amount <= 0 or sender == receiver:
        raise ValueError("转账参数不合法")

    async with engine.begin() as conn:
        debit = await conn.execute(
            text("""
                UPDATE blog_tx_accounts
                SET balance_cents = balance_cents - :amount
                WHERE id = :sender AND balance_cents >= :amount
                RETURNING balance_cents
            """),
            {"sender": sender, "amount": amount},
        )
        if debit.scalar_one_or_none() is None:
            raise ValueError("转出账户不存在或余额不足")

        if fail:
            raise RuntimeError("模拟扣款成功后的业务异常")

        credit = await conn.execute(
            text("""
                UPDATE blog_tx_accounts
                SET balance_cents = balance_cents + :amount
                WHERE id = :receiver
                RETURNING balance_cents
            """),
            {"receiver": receiver, "amount": amount},
        )
        if credit.scalar_one_or_none() is None:
            raise ValueError("收款账户不存在")


async def main():
    engine = create_async_engine(os.environ["DATABASE_URL"])
    try:
        try:
            await transfer(engine, "A", "B", 500, fail=True)
        except RuntimeError:
            print("已触发回滚")

        async with engine.connect() as conn:
            rows = await conn.execute(
                text("SELECT id, balance_cents "
                     "FROM blog_tx_accounts ORDER BY id")
            )
            print(rows.all())
    finally:
        await engine.dispose()


if __name__ == "__main__":
    asyncio.run(main())
```

依赖是 SQLAlchemy 2.0 与 `asyncpg`，连接地址使用 `postgresql+asyncpg://...` 格式的 `DATABASE_URL` 环境变量。运行前需要确保表中存在 A、B 两个账户。

若使用上面给定的初始值且没有其他客户端修改测试数据，异常触发后两笔余额应仍为 `10000`，而不是 A 变成 `9500`、B 仍为 `10000`。本轮审校已在 PostgreSQL 18.6、SQLAlchemy 2.0.54 与 `asyncpg` 0.32.0 上实际运行这段程序，输出为 `[('A', 10000), ('B', 10000)]`。

这里采用 `UPDATE ... WHERE balance_cents >= :amount RETURNING ...`，是为了把余额校验和扣款写在同一条 SQL 中。

它比“先 SELECT 余额，回到 Python 判断，再 UPDATE”更容易处理同一行上的并发竞争，但不能由此推广出“所有跨多行的业务约束都天然并发安全”。如果多个账户形成更复杂的修改关系，仍然需要分析锁顺序、隔离级别以及可能的事务重试。

还要注意，`engine.begin()` 只管理这条数据库连接上的事务。若把代码改写为 `AsyncSession`，同样可以使用 `async_sessionmaker.begin()` 来划定工作单元。

Repository 负责具体的数据访问，Service 应当能够控制多个相关操作共享的事务边界；在每个 Repository 内任意调用 `commit()`，会提前结束上层本来希望统一提交的事务。

## 七、最容易被忽略的提交边界：数据库成功，客户端却不知道

最后看一个比程序异常更难处理的情况。客户端发送 `COMMIT`。PostgreSQL 已经完成必要的 WAL 持久化，并确定事务提交成功，准备返回结果。恰好在这时，客户端与数据库之间的网络连接断开了。

对数据库来说，事务已提交；对客户端来说，它没有收到成功响应，因此无法仅凭这个网络异常判断事务究竟提交了没有。如果客户端直接重新执行整段业务操作，就可能重复扣款、重复插入订单或重复发放资源。

这说明事务的原子性和持久性并不等于网络调用的“恰好执行一次”。工程上需要通过请求幂等键、业务唯一约束、操作结果查询等机制处理未知提交结果。

PostgreSQL 还提供 `pg_xact_status()` 查询近期事务提交状态的能力，但这种查询受事务 ID 可用性与状态保留范围等条件限制，通常不能直接代替业务幂等设计。

跨系统副作用也存在类似的边界。数据库事务成功回滚，并不会自动撤销已经发送的邮件、调用的支付服务或已投递到外部消息队列的消息。即便它们都放在同一个 Python `try` 代码块里，也没有共同的原子提交机制。

若需要在数据库修改与消息发布之间保持一致，可以进一步讨论事务 Outbox、幂等消费者或分布式事务，但这些不是普通 PostgreSQL 本地事务自动提供的功能。

## 八、结语

事务不是把几条 SQL 包在 `BEGIN` 和 `COMMIT` 之间就自动获得所有正确性保证。PostgreSQL 借助事务状态与 MVCC，让部分修改可以在逻辑上被放弃；借助 WAL、检查点与崩溃恢复，避免把已经可靠提交的事务结果丢掉；借助约束、锁和不同的隔离级别，处理数据规则与并发执行之间的关系。

理解这些机制之后，ACID 就不再是四个需要背诵的名词。原子性回答部分失败如何处理，持久性回答提交后如何抵御崩溃，隔离性回答并发事务能相互观察到什么，而一致性要求数据库约束和应用业务逻辑共同维护既定不变量。

下一篇讨论 PostgreSQL 的 `SAVEPOINT` 与子事务：当一个大事务中只有局部操作失败时，数据库为什么能够撤销一部分修改，却保留此前已经完成的工作。
