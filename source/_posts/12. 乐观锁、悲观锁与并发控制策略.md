上一笔库存扣减刚刚完成，另一笔更新却把库存改回了旧值。上一篇已经解释，这种丢失更新并不一定是数据库没有加锁，而可能是应用拿着过时的数据作出了新的写入决定。

现在的问题更进一步：如果业务必须先读取数据、做出判断，再决定怎样修改，应该怎样保证读取期间没有被其他事务改变的前提，在写入时仍然成立？

一种办法是在读数据时就取得必要的锁，让冲突者等待；另一种办法是允许大家先读取，等到写入时再验证此前看到的数据是否已经过时。前者通常被称为悲观锁，后者通常被称为乐观锁。

它们并不是两套互不相关的数据库锁系统，而是两种不同的并发控制策略。要选择其中一种，首先得理解它们分别在什么时候处理冲突，以及处理冲突后，业务操作究竟还能不能继续。本文以 PostgreSQL 18 和 SQLAlchemy 2.0.x 为具体实现背景。

## 一、从读改写问题重新理解并发控制

假设一条库存记录包含三个字段：商品 ID、库存数量 `stock` 和版本号 `version`。初始状态为 `stock=10, version=1`。

请求 A 和 B 都读取了这条记录，然后各自根据自己的业务规则计算新状态。A 先把库存改成 9；B 随后提交自己根据旧值计算出来的结果。如果 B 的写入条件只有 `id=1`，数据库没有理由拒绝这个结果。

问题不在于数据库没有按顺序执行 SQL，而在于**应用读取时成立的前提，并不会自动延续到之后的写入时刻**。

对数据库来说，`UPDATE inventory SET stock=9 WHERE id=1` 只是要求写入常量 9。数据库无法知道它背后是否有一次已经过时的读取，也不知道调用者是否愿意覆盖别人刚刚完成的修改。

并发控制需要补上这部分缺失的信息。它可以在操作开始时阻止别人修改，也可以在操作结束前验证别人有没有修改。如果发现冲突，还必须规定由谁等待、由谁失败，以及是否应该重新作出业务判断。

这就形成了乐观控制与悲观控制之间的核心分歧：**先保留修改资格，再计算；还是先计算，到提交修改时再验证资格。**

## 二、乐观锁的核心是带条件的原子写入

乐观锁假设冲突不是每次都会发生。因此，读取阶段通常不主动取得阻止其他事务修改目标行的行锁，而是在真正写入时进行比较。

最直观的实现是在业务表中增加一个 `version` 字段。每次有效修改都更新版本号。客户端读取记录时同时得到版本，写回时把这个旧版本放进 `WHERE` 条件。

```sql
CREATE TABLE IF NOT EXISTS blog_control_inventory (
    id integer PRIMARY KEY,
    stock integer NOT NULL CHECK (stock >= 0),
    version bigint NOT NULL DEFAULT 1 CHECK (version > 0)
);

INSERT INTO blog_control_inventory (id, stock, version)
VALUES (1, 10, 1)
ON CONFLICT (id) DO UPDATE
SET stock = 10, version = 1;
```

现在两个请求都读取到版本 1。A 首先执行：

```sql
UPDATE blog_control_inventory
SET stock = 9, version = version + 1
WHERE id = 1 AND version = 1
RETURNING stock, version;
```

如果没有其他竞争，A 得到 `(9, 2)`，并在事务提交后使版本 2 成为当前有效版本。B 仍然持有之前读到的版本 1，再执行相同的条件更新，就无法匹配到版本 2。

在 PostgreSQL 的默认 `READ COMMITTED` 隔离级别下，即使 B 在 A 尚未提交时就尝试写入，它也会等待冲突更新结束。A 提交后，B 会针对当前行版本重新检查 `WHERE`；旧版本条件不成立，更新零行。

这是一种比较并交换（Compare-And-Swap，CAS）思想的数据库表达。比较和修改必须由数据库在同一条受并发控制的写入语句中完成，而不能由 Python 先查询版本、判断相等，然后再发一条没有版本条件的 `UPDATE`。

注意，`UPDATE` 返回零行仅表示本次条件没有匹配到记录。可能是版本已经改变，也可能是目标行被删除，或者其他业务条件不再满足。API 不应未经核查就把所有零行都说成“有人修改了数据”。

### 1. 为什么不能只在应用里检查版本？

假设程序先查询数据库中的 `version`，确认仍然为 1，然后准备更新。恰好在检查完成之后、更新发送之前，另一个事务提交了版本 2。

如果随后发出的更新没有把 `version=1` 放进 `WHERE`，就依然会覆盖较新的结果。这是典型的检查与使用之间的竞争窗口（TOCTOU）。

所以乐观锁能否生效，不取决于是否创建了一个名为 `version` 的字段，而取决于**版本校验与实际更新是否构成同一个原子数据库操作**。

版本号也不是必须使用整数。某些系统用不可重复的令牌或变更标识，只要能够可靠标识被读取的状态，并且每次相关修改都改变该标识，也能构成类似的比较条件。

但如果使用时间戳作为版本，必须考虑时间精度、更新时间是否一致等问题。用可重复出现的业务值作为校验条件，还可能遇到数据先从 A 变为 B、又从 B 变回 A 的情形，此时最终值相等，并不证明期间从未发生修改。单调递增的版本号通常更容易表达“在我读取之后是否有人修改过”。

## 三、乐观锁不是没有数据库锁

“乐观锁”这个名字容易让人误以为它完全不使用锁。事实上，在 PostgreSQL 中，条件 `UPDATE` 依然需要取得正常的表级锁和行级锁。两个事务如果同时修改同一行，写入阶段仍可能发生等待。

乐观策略的特点不是绕开 PostgreSQL 的锁管理器，而是**读取与业务计算阶段不预先长期占有用于排斥写入者的行锁**。其他事务可以在这段时间继续修改数据；等应用准备写入时，再让数据库判断旧条件是否还成立。

这意味着乐观锁并不是无成本的。高竞争情况下，大量请求可能完成查询和业务计算后才发现版本失效。虽然数据库保护了最终写入的一致性，但这些请求此前消耗的 CPU、数据库读取和其他资源并没有因此自动返还。

更重要的是，版本冲突不应被直接理解为“数据库故障”。版本失效有时是完全正常的业务竞争。用户编辑一份文档时，如果另一个用户已经保存了更新，系统往往应该返回冲突并让用户决定是否合并，而不是悄悄覆盖或自动重试。

对于库存扣减这种可以重新读取、重新计算的操作，适度重试可能合理。但是否允许重试，要取决于业务操作能否在新的状态下重新执行，而不是仅仅取决于数据库返回了零行。

## 四、并不是所有更新都需要单独的版本号

上一节的库存问题还有一种更简单的写法：

```sql
UPDATE blog_control_inventory
SET stock = stock - 1
WHERE id = 1 AND stock >= 1
RETURNING stock;
```

这条 SQL 同时表达了业务前提和状态转换：只有库存至少为 1，才在当前有效行版本上扣减 1。在 PostgreSQL 的 `READ COMMITTED` 下，发生同一行写入冲突时，等待者会在前一个事务提交后重新检查条件。

对于这个明确的单行不变量，不需要先 `SELECT` 到 Python 中计算，也不需要为了避免丢失更新额外设计一个版本号。数据库已经能够在单条条件更新中完成判断和修改。

但它不能完全替代版本校验。若业务操作依赖多个字段的旧值、复杂的用户输入，或者用户在页面上修改了很久以后才提交，明确的版本号可以表明整条记录自读取以来是否发生过相关变化。

是否要把所有字段都纳入一个版本，也需要按业务语义决定。两个请求修改彼此独立的字段，统一版本可能把原本可以共存的更新判为冲突；而过于细粒度的版本又可能漏掉跨字段不变量。

因此，版本控制的范围应当对应需要保持一致的业务状态，而不是机械地给所有表添加一个 `version` 字段。唯一约束、条件更新和版本检查可以组合使用，各自维护不同的不变量。

## 五、悲观锁为什么要在读取时取得锁

乐观锁允许先计算后验证，悲观锁则认为冲突可能足够重要，或者重新执行的成本足够高，值得在读取阶段先取得修改权。

PostgreSQL 中的典型写法是 `SELECT ... FOR UPDATE`：

```sql
BEGIN;

SELECT stock
FROM blog_control_inventory
WHERE id = 1
FOR UPDATE;

-- 在持有行锁的事务中完成判断与更新。
UPDATE blog_control_inventory
SET stock = stock - 1
WHERE id = 1 AND stock >= 1;

COMMIT;
```

`FOR UPDATE` 取得目标行的排他性行级锁，其他事务如果要以冲突方式锁定、更新或删除同一行，通常需要等当前事务结束。于是，“检查当前库存”和“按检查结果修改库存”可以处于同一段受保护的事务中。

这里的关键不是 SQL 里多了四个英文单词，而是**读取、业务判断和写入必须处于同一个正确管理的数据库事务中**。

如果在自动提交模式下单独执行一次 `SELECT ... FOR UPDATE`，语句结束事务也就结束，刚获得的行锁随之释放。之后再发出 `UPDATE`，并不能受到之前那次行锁的保护。

同样，程序即使执行了 `FOR UPDATE`，如果还没写入就先 `COMMIT`，再根据刚才查到的值决定下一步操作，竞争窗口依然存在。

### 1. 等待结束之后，究竟读到哪个版本？

在默认 `READ COMMITTED` 下，事务 B 执行 `SELECT ... FOR UPDATE` 时，如果事务 A 已锁住并修改同一行，B 可能等待 A 结束。A 提交后，B 会按 PostgreSQL 的并发语义处理更新后的行，并重新检查适用的查询条件。

这让 B 有机会在取得锁时基于最新的已提交状态作出决策。但这并不意味着可以把同样的预期无条件套用到 `REPEATABLE READ` 或 `SERIALIZABLE`。在这些隔离级别下，目标行被其他事务改变可能导致序列化失败，应用需要重试整个事务。

`FOR UPDATE` 还不能保证行在当前事务完成之后永远不变。它只在锁的有效期内阻止冲突操作。一旦当前事务提交，先前等待的事务仍然可以继续修改那条记录。

因此，悲观锁解决的是一段事务中的临时互斥，而不是给记录附加永久的修改所有权。

### 2. 等待、立即失败和跳过

PostgreSQL 默认会在需要时等待冲突行锁。如果业务不愿等待，可以使用 `FOR UPDATE NOWAIT`：当选中行无法立即锁定时，语句报告错误。

`FOR UPDATE SKIP LOCKED` 则会跳过无法立即锁定的行，适合多个工作者争抢任务队列的特殊场景。但它得到的是不完整的查询视角，不适合作为普通业务读取的一般性一致性保证。

此外，`NOWAIT` 和 `SKIP LOCKED` 的行为主要针对行级锁，相关语句取得的表级锁仍按正常规则处理。它们不是解决所有数据库等待的万能开关。

悲观控制还可以配置 `lock_timeout`，避免无限期等待。但等待超时只是告诉调用者本次操作没能获得资源，不能替业务决定该等待多久、是否继续重试，以及失败后向用户返回什么结果。

## 六、悲观锁的边界是被锁住的资源

如果业务规则只涉及已经存在的一条确定记录，`FOR UPDATE` 往往比较直观。但业务条件一旦涉及“某个集合中不存在记录”“总数不能超过上限”，情况就不同了。

例如，事务查询某个场次的预约数量，发现还有一个名额，于是打算插入预约。如果使用 `SELECT ... FOR UPDATE` 锁住当前已有的几条预约记录，并不能自然推出另一个事务就无法插入一条新的预约记录。

原因在于，锁住查询返回的行与锁住整个业务谓词并不是一回事。对于尚不存在的行，根本没有现成的行版本供普通 `FOR UPDATE` 锁定。只锁住已有记录，可能覆盖不了新增记录带来的竞争。

这类规则需要重新设计资源边界。可以选择锁住代表场次容量的一条父记录，并要求所有预约操作遵守同一协议；也可以通过约束、原子计数更新或者适当的可串行化事务来保护不变量。

其中，“锁父记录”之所以有效，前提是所有相关写入路径都遵守该锁定约定。如果某条后台脚本绕过锁协议直接插入，数据库不会仅凭其他事务锁住了父记录就自动阻止所有违反业务数量限制的写入。

多个资源必须同时锁定时，还需要考虑获取锁的顺序。不同事务按相反顺序取得多把锁，可能形成死锁。这里先明确风险，具体检测与处理留给第七篇。

## 七、SQLAlchemy 怎样表达两种策略

在 SQLAlchemy 中，乐观锁既可以由开发者直接组织条件 `UPDATE`，也可以使用 ORM 的版本计数能力。

例如，给映射类声明 `version_id_col`：

```python
from sqlalchemy import Integer
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column


class Base(DeclarativeBase):
    pass


class Inventory(Base):
    __tablename__ = "blog_control_inventory"

    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    stock: Mapped[int] = mapped_column(Integer, nullable=False)
    version: Mapped[int] = mapped_column(Integer, nullable=False)

    __mapper_args__ = {"version_id_col": version}
```

当 ORM 在 `Session.flush()` 中更新这个已加载的对象时，SQLAlchemy 会把原有版本加入 `UPDATE` 的条件，并生成新版本。如果没有匹配到预期的行，通常会抛出 `StaleDataError`。

但这个特性并不覆盖所有更新方式。通过 ORM 执行自定义条件批量 `UPDATE`、`DELETE`，或其他绕过单个映射对象 flush 的写入，不会自动获得同样的版本检查。假如项目里既有 ORM 对象修改，又有批量 SQL，就必须检查每条写入路径是否遵守同一版本协议。

对于悲观锁，SQLAlchemy 提供 `with_for_update()`：

```python
from sqlalchemy import select

async with session_factory.begin() as session:
    result = await session.execute(
        select(Inventory)
        .where(Inventory.id == 1)
        .with_for_update()
    )
    item = result.scalar_one()
    if item.stock < 1:
        raise ValueError("库存不足")
    item.stock -= 1
```

这里假设 `session_factory` 是已配置的 `async_sessionmaker`，并使用 PostgreSQL。正常退出事务上下文时，Session 会 flush 并提交；遇到异常则回滚。行锁在数据库事务结束时释放，而不是在 `result.scalar_one()` 返回后立即释放。

这种写法虽然直观，但仍须注意事务作用域。不要在持锁期间等待用户输入、调用慢速远程接口，或做不必要的耗时计算，否则会把与数据库无关的延迟转化为其他事务的锁等待。

另一个容易混淆的地方是：`AsyncSession` 只是 SQLAlchemy 的异步访问接口，不会让同一个 Session 自动适合并发任务共享。每个独立工作单元仍应使用自己的 Session，事务边界仍应由适当的应用层统一控制。

## 八、用一个可运行实验观察乐观冲突

前面的 SQL 已经解释版本比较。下面再用 `asyncpg` 和 SQLAlchemy 2.0 写一个完整实验，故意让两个独立 Session 读取相同版本，再让一个提交、另一个尝试基于旧版本更新。

```python
import asyncio
import os

from sqlalchemy import text
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine


async def main():
    engine = create_async_engine(os.environ["DATABASE_URL"])
    sessions = async_sessionmaker(engine, expire_on_commit=False)
    both_read = asyncio.Event()
    first_committed = asyncio.Event()

    async with engine.begin() as conn:
        await conn.execute(text("""
            CREATE TABLE IF NOT EXISTS blog_cas_demo (
                id integer PRIMARY KEY,
                value integer NOT NULL,
                version bigint NOT NULL
            )
        """))
        await conn.execute(text("""
            INSERT INTO blog_cas_demo VALUES (1, 10, 1)
            ON CONFLICT (id) DO UPDATE
            SET value = 10, version = 1
        """))

    async def second_task():
        async with sessions.begin() as session:
            old_version = await session.scalar(text(
                "SELECT version FROM blog_cas_demo WHERE id = 1"
            ))
            both_read.set()
            await first_committed.wait()
            result = await session.execute(text("""
                UPDATE blog_cas_demo
                SET value = value - 1, version = version + 1
                WHERE id = 1 AND version = :old_version
                RETURNING value
            """), {"old_version": old_version})
            print("第二次更新:", result.scalar_one_or_none())

    async def first_task():
        await both_read.wait()
        try:
            async with sessions.begin() as session:
                await session.execute(text("""
                    UPDATE blog_cas_demo
                    SET value = value - 1, version = version + 1
                    WHERE id = 1 AND version = 1
                """))
        finally:
            first_committed.set()

    try:
        await asyncio.gather(second_task(), first_task())
        async with engine.connect() as conn:
            result = await conn.execute(text(
                "SELECT value, version FROM blog_cas_demo WHERE id = 1"
            ))
            print("最终状态:", result.one())
    finally:
        await engine.dispose()


if __name__ == "__main__":
    asyncio.run(main())
```

安装 `SQLAlchemy>=2.0,<2.1` 和 `asyncpg`，并在环境变量 `DATABASE_URL` 中配置可访问的 `postgresql+asyncpg://...` 地址即可运行。示例会重置专用实验记录，不应直接连接生产数据库。

在默认 `READ COMMITTED`、正常完成提交且没有其他客户端干扰的前提下，第二个任务读取的是版本 1，但必须等待第一个任务完成提交才尝试更新，因此其 `RETURNING` 应为空，最终状态应为 `(9, 2)`。本轮审校已在 PostgreSQL 18.6、SQLAlchemy 2.0.54 与 `asyncpg` 0.32.0 上实际得到这两个结果。

`asyncio.Event` 在这里仅用于确定演示中的任务先后顺序，不是生产并发控制手段。真正防止覆盖的是 PostgreSQL 中带版本条件的原子 `UPDATE`。

注意，这个示例故意在第二个 Session 读完数据库后保留事务并等待，仅为了观察同一事务中的旧版本写入如何被拒绝。实际工程中应避免在持有数据库连接的事务里无谓地长时间等待。

## 九、冲突之后，不能把所有错误都直接重试

采用乐观锁后，程序需要面对一个新问题：写入零行怎么办？答案取决于业务语义。

对用户编辑的文章，直接返回版本冲突，让客户端加载新版本并决定如何处理，通常比后台自动覆盖更符合预期。对能够完全根据最新状态重新计算的库存扣减，则可以重新读取、重新判断，并在有限次数内重试。

但重试必须重新进行原本的业务判断。不能把上次从库存 10 推算出的“库存 9”原封不动地提交到新版本；也不能只重新发送失败的写入语句，却继续使用已经失效的决策结果。

这里还要区分几个不同的失败来源。乐观版本条件不匹配，往往是应用主动识别的业务并发冲突；PostgreSQL 的 `40001` 表示事务因序列化相关原因失败；`40P01` 表示检测到死锁；`55P03` 等锁相关错误可能与 `NOWAIT` 或锁超时有关。它们不应被统一解释为“版本冲突”。

对于 `40001`，PostgreSQL 明确要求重试完整事务，包括读取数据和决定写入内容的逻辑。死锁失败在某些条件下也可以重试，但同样应遵守有限次数、正确事务边界和退避策略。超时则还需判断系统是否过载，不能无限重试放大竞争。

更棘手的是客户端发送了 `COMMIT`，数据库可能已经提交，但网络在返回确认前断开。此时调用者不知道提交究竟成功没有，不能简单地按“未执行”再来一次。重试前应有业务幂等标识或结果查询手段，避免重复扣费、重复创建订单。

即使没有网络故障，事务中的数据库回滚也不能撤销已经发出的邮件、外部支付请求等副作用。因此，可重试事务最好将不可重复的外部效果放在数据库事务之外，并配合幂等键、Outbox 等机制设计可靠交付边界。

## 十、应该怎样选择：冲突概率并不是唯一标准

不少文章把结论简化成“读多写少用乐观锁，写多读少用悲观锁”。这可以作为非常粗略的直觉，却不足以作为工程决策依据。

首先要看业务不变量能否直接用单条 SQL 或数据库约束表达。如果能够使用原子条件更新、唯一索引等机制完成校验和修改，那么通常没有必要先引入复杂的应用层锁协议。

确实需要读改写时，再判断失败代价。乐观策略允许更多操作并发推进，但在高冲突或计算昂贵的场景中，失败后的重算会形成明显浪费。悲观策略让冲突较早表现为等待，适合事务内必须依据锁定资源连续作出多个决策、并且需要稳定修改资格的操作。

不过，悲观策略也有代价。锁会占用数据库事务资源；等待可能增加尾延迟和连接池压力；多资源锁定可能产生死锁。如果事务包含慢速外部调用，持锁成本会迅速增大。

乐观策略的主要成本则体现为冲突检测失败、重新计算、请求重试及用户合并操作。即使它不提前加行锁，实际写入时仍会参与 PostgreSQL 的锁协调，并不保证高冲突下没有等待。

业务交互方式同样重要。用户打开页面编辑十分钟，不可能合理地为此维持十分钟的数据库行锁；这类跨请求的长时操作更适合版本校验。相反，一次几十毫秒内完成的数据库内部工作单元，可以在明确事务范围内使用行锁。

对于跨行的约束，选择乐观还是悲观之前还得先确保控制范围正确。只在其中一行做版本检查，并不能自动保护整个集合的不变量；仅对查询到的已有行加悲观锁，也不一定能阻止新行插入。

因此，策略选择可以归结为一个顺序：先确定必须维持的业务规则，再找出真正发生竞争的状态，最后决定如何在数据库里原子地检查、锁定或更新这些状态。性能数据应在正确性成立后再用于调整取舍，而不是用“哪种锁更快”反过来决定业务规则。

## 十一、小结

乐观锁与悲观锁最大的区别，不是谁更加高级，而是处理竞争的时间点不同。

乐观锁让多个请求先读取和计算，在写入时通过版本或其他条件发现过期状态。它减少了读取阶段的排他锁占用，却要求应用正确处理冲突和重试。

悲观锁在需要保护的数据库操作开始时取得相应锁，使冲突者等待或失败。它让后续判断能够在受保护的事务范围内进行，却要求开发者严格控制持锁时间、锁定对象和事务边界。

无论选择哪一种，数据库都不能代替业务定义正确性。版本检查必须覆盖相关写入路径，行锁必须覆盖真正参与竞争的资源，重试也必须重新执行受旧状态影响的判断。
