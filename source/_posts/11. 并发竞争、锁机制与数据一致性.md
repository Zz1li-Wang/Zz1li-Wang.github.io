两个请求几乎同时读取一件商品的库存，得到的都是 10。它们各自判断库存充足，再把库存减去 1。两个请求都成功返回后，数据库里的库存却是 9，而不是 8。

数据库没有崩溃，也没有发生脏读。两次 `UPDATE` 都执行成功，两次事务也都正常提交。问题出在程序使用了各自先前读到的数值：数据库可以协调两条写入语句的执行顺序，却无法从 `SET stock = 9` 推断出调用方原本想表达的是“在最新库存基础上减去 1”。

要理解这种错误，需要区分三件事：并发操作在哪个位置发生竞争，数据库通过什么机制让冲突操作有序执行，以及有序执行之后的结果是否满足业务规则。上一篇的 MVCC 主要解释事务能够读到哪些版本，这一篇继续讨论写入时的相互排斥、等待和约束检查。下文讨论 PostgreSQL 18 的锁与约束语义。

## 一、竞争不是同时执行，而是结果依赖执行顺序

先建立一张用于实验的库存表。以下 SQL 均假设在专用 PostgreSQL 测试数据库执行，避免影响真实业务数据。

```sql
CREATE TABLE IF NOT EXISTS blog_lock_inventory (
    id integer PRIMARY KEY,
    stock integer NOT NULL CHECK (stock >= 0)
);

INSERT INTO blog_lock_inventory (id, stock)
VALUES (1, 10)
ON CONFLICT (id) DO UPDATE SET stock = EXCLUDED.stock;
```

分别打开两个独立的 `psql` 连接，记作会话 A、会话 B。两者都使用 PostgreSQL 默认的 `READ COMMITTED` 隔离级别。先让 A 读取库存，暂时不结束事务，再让 B 读取同一行。

```sql
-- 会话 A
BEGIN;
SELECT stock FROM blog_lock_inventory WHERE id = 1;
-- 10
```

```sql
-- 会话 B
BEGIN;
SELECT stock FROM blog_lock_inventory WHERE id = 1;
-- 10
```

假设应用程序在内存中用读取结果计算新库存，两个请求都算出了 9。随后 A 执行 `UPDATE ... SET stock = 9` 并提交，B 再执行同样的语句并提交。

```sql
-- 会话 A
UPDATE blog_lock_inventory SET stock = 9 WHERE id = 1;
COMMIT;
```

```sql
-- 会话 B
UPDATE blog_lock_inventory SET stock = 9 WHERE id = 1;
COMMIT;
```

最终库存是 9。两个事务没有同时修改同一个物理行版本，第二次写入甚至可以发生在第一次提交之后，但一次业务上的扣减效果仍然丢失了。这就是典型的**丢失更新**（lost update）场景：根据旧读取结果生成的新值，覆盖了另一个事务已经产生的更新效果。

需要把“两个事务并发”和“两个 CPU 在同一时刻执行一条指令”区分开。只要 A 和 B 的业务操作区间重叠，且各自的计算依赖旧数据，就可能产生竞争。即使数据库将实际写入逐一执行，也不代表应用计算所依据的信息仍然有效。

反过来，如果两个请求都只是读取库存，不尝试更改任何共享状态，通常不存在这种写入竞争。如果两个事务修改不同库存行，也不一定需要彼此等待。竞争的关键不是请求数量，而是它们访问的资源和操作之间是否存在不能任意交换顺序的依赖。

## 二、MVCC 为什么不能单独解决写入冲突

前文已经说明，PostgreSQL 的 MVCC 允许普通 `SELECT` 根据快照读取已经提交的行版本。事务 A 正在更新一行时，事务 B 的普通 `SELECT` 不必等到 A 提交，仍可能读取到旧版本。这能减少读写之间不必要的相互等待。

但两个事务不能因此不受约束地修改同一条逻辑记录。它们需要确定谁先取得修改权、后续修改应该基于哪个行版本继续，以及某个事务失败时应该怎样处理。PostgreSQL 除了 MVCC，还依靠锁和事务状态协调这些行为。

这里要区分两种 `UPDATE` 写法。第一种由应用在数据库外计算新值：

```sql
UPDATE blog_lock_inventory SET stock = 9 WHERE id = 1;
```

第二种则要求数据库在执行写入时，以正在处理的行版本计算新值：

```sql
UPDATE blog_lock_inventory
SET stock = stock - 1
WHERE id = 1 AND stock > 0
RETURNING stock;
```

在默认的 `READ COMMITTED` 隔离级别下，如果 A 已经更新目标行而尚未结束事务，B 的第二种 `UPDATE` 会等待。A 如果提交，B 将尝试在 A 更新后的行版本上重新检查 `WHERE`，满足条件才继续执行，并据此计算 `stock - 1`；如果 A 回滚，B 则可以基于未被 A 成功修改的版本继续。

例如初始库存为 10，两个这样的扣减先后成功，最终库存应为 8。如果初始库存为 1，第一个事务扣到 0 并提交后，第二个事务重新检查 `stock > 0` 时条件已不成立，`RETURNING` 不会返回被修改的行。这条 SQL 将“判断是否还能扣减”和“实际扣减”放在同一个写入操作中，避免了前面的旧值覆盖问题。

但这个结论有严格边界。它针对 PostgreSQL 的具体 `READ COMMITTED` 更新规则，以及能够由单条目标行更新表达的约束；不能推导出所有涉及多行、多表或外部系统的业务操作都天然正确。在 `REPEATABLE READ` 等隔离级别下，并发更新同一行还可能以 `40001` 失败，而不是像上述过程那样继续更新新版本。数据库对并发 SQL 的处理方式，始终与隔离级别和具体命令有关。

## 三、锁究竟锁住了什么

很多人把数据库锁理解为“一个事务锁住数据，其他事务必须等待”。这种说法过于宽泛。PostgreSQL 的锁具有不同的**对象、模式和持有期限**。对象可以是整张表，也可以是某个行版本所代表的记录；模式决定与其他操作是否冲突；持有期限决定冲突持续多久。

最容易误解的是表级锁。PostgreSQL 的普通 `SELECT` 会在被引用的表上取得 `ACCESS SHARE` 锁，`INSERT`、`UPDATE`、`DELETE` 通常会在目标表上取得 `ROW EXCLUSIVE` 锁。虽然名字里带着 `ROW`，`ROW EXCLUSIVE` 仍然是**表级锁模式**，并不表示它本身锁住某一行。

既然两个 `UPDATE` 都取得表级 `ROW EXCLUSIVE`，为什么不同请求还能同时更新同一张表？因为这两把锁彼此**兼容**。锁是否阻塞其他操作，不由名字是否包含 `EXCLUSIVE` 决定，而由该锁模式与另一种请求模式的冲突关系决定。`ROW EXCLUSIVE` 不会排斥另一把 `ROW EXCLUSIVE`，也不与普通查询的 `ACCESS SHARE` 冲突。

相比之下，`TRUNCATE` 和若干改变表结构的 DDL 操作需要 `ACCESS EXCLUSIVE`。这个模式会与所有表级锁模式冲突，包括普通 `SELECT` 使用的 `ACCESS SHARE`。所以“PostgreSQL 的读操作不阻塞写操作”只能在普通 MVCC 读写等前提下成立，不能被推广为任何表操作都不会互相等待。

表级锁为数据库维护表和表结构提供必要的协调，行级锁则主要解决同一行被修改或被显式锁定时的竞争。二者同时存在，承担不同职责。一次 `UPDATE` 可以持有表级 `ROW EXCLUSIVE`，又在实际修改的行上取得相应的行级锁；只有知道请求的是哪种锁，才能判断其他操作是否需要等待。

## 四、行锁并不是简单的“读锁”和“写锁”

PostgreSQL 提供四种常见的显式行级锁模式：`FOR UPDATE`、`FOR NO KEY UPDATE`、`FOR SHARE` 和 `FOR KEY SHARE`。它们不是只按“读”和“写”分成两类，而是根据允许其他事务进行什么操作来定义冲突关系。

`FOR UPDATE` 最严格。一个事务持有某行的这种锁时，其他事务不能同时取得该行的上述四种锁，也不能直接修改或删除它。`FOR NO KEY UPDATE` 稍弱：它允许其他事务对同一行持有 `FOR KEY SHARE`，因为后者主要要防止删除或修改被外键等关系依赖的键值，而并不一定要阻止无关键字段变化的更新。

`FOR SHARE` 可以被多个事务同时持有，但与更新该行的行级锁冲突。`FOR KEY SHARE` 则进一步收窄保护范围，允许不修改关键键值的普通更新。这些区别对于外键检查等操作很重要。如果所有读取都一律加最强的 `FOR UPDATE`，反而可能制造不必要的等待。

即使没有显式写出 `SELECT ... FOR UPDATE`，`UPDATE` 和 `DELETE` 也会自动取得必要的行级锁。PostgreSQL 中，`DELETE` 和修改某些具备可供外键使用的唯一索引列的 `UPDATE` 会取得相当于 `FOR UPDATE` 的行锁；其他 `UPDATE` 通常使用较弱的 `FOR NO KEY UPDATE`。具体哪些列被认定为关键列，要以 PostgreSQL 对唯一索引和外键可用性的规则为准。

还有一个反直觉的现象：**行锁不会阻止其他事务执行普通 `SELECT`。** 被锁定的行仍然可以通过 MVCC 向其他事务提供可见的旧版本；真正被阻塞的主要是想修改或以冲突模式锁定同一行的操作。这样，锁负责协调互斥的写入，快照负责确定普通读取的可见内容。

行级锁一般持有到事务结束，回滚到保存点也会释放在那个保存点之后取得的相应锁。锁的作用范围因此不只取决于某条 SQL 执行了多久，还取决于事务何时提交或回滚。如果数据库执行完 `UPDATE` 后，应用又等待远程 HTTP 接口数秒才提交，这段等待时间里行锁仍可能持续阻塞其他更新。

## 五、一条 UPDATE 在等待时究竟发生了什么

我们可以把第二节中的两次库存扣减改成确实发生行锁等待的实验。先把库存重置为 10，确保没有其他会话使用测试表。随后在会话 A 执行下列语句，但先不要提交：

```sql
BEGIN;
UPDATE blog_lock_inventory
SET stock = stock - 1
WHERE id = 1 AND stock > 0
RETURNING stock;
-- 预期：9
```

此时 A 已经取得该行的修改权，事务却尚未结束。在会话 B 执行相同操作：

```sql
BEGIN;
UPDATE blog_lock_inventory
SET stock = stock - 1
WHERE id = 1 AND stock > 0
RETURNING stock;
-- 此处等待 A 结束事务
```

B 等待的不是“SQL 被数据库忘记了”，而是某个必要的锁条件尚未满足。只有 A 提交或回滚，B 才能确定该怎样处理目标行。如果 A 提交，B 在默认 `READ COMMITTED` 下会针对已更新的行版本继续执行，预期返回 8；如果 A 回滚，B 仍可扣减初始的 10，预期返回 9。实验结束后，还需要在 B 执行 `COMMIT`。

这里有两个不同层面的次序。数据库保证两个冲突的行修改不能在不满足锁规则的情况下同时完成，但它并不规定哪个 HTTP 请求就一定先获得锁。锁获取时机受事务执行顺序和调度影响。即使一个请求先到达应用服务器，另一个请求仍可能先在数据库内获得锁。

正常的等待也不等于死锁。B 等 A，而 A 没有等 B，只要 A 最终结束事务，B 就能够继续；死锁需要形成相互等待、谁都无法先自行取得所需资源的局面。死锁的检测与排除将在第七篇单独讨论。

## 六、为什么 pg_locks 里未必能看见被锁住的那一行

从实现层看，PostgreSQL 并不是简单地为每一条被锁行都分配一个长期存在的共享内存锁对象。行级锁信息主要记录在磁盘行版本的头部，由相应的事务 ID，以及在多个事务持有兼容行锁时可能涉及的 MultiXact 信息表达。给一行加锁本身因此也可能修改页面并产生 WAL，而不只是改变一个纯内存的标志。

另一方面，PostgreSQL 需要在共享内存中的锁管理器里协调事务、关系等对象。当另一个事务发现某行已经被未结束事务锁定时，它通常需要等待**持锁事务结束**，以便知道原修改究竟提交还是回滚。因此，等待行锁的过程在 `pg_locks` 里经常表现为等待某个 `transactionid` 的锁，而不是直观的 `tuple` 锁记录。临时的元组锁请求仍可能出现，但不能据此推断每把行锁都会稳定地显示为一条 `tuple` 记录。

这也是一个重要的排障思路：不要只在 `pg_locks` 中搜索 `locktype = 'tuple'`，然后看到没有结果就断言不存在行锁竞争。更直接的做法是结合 `pg_stat_activity` 的等待状态和 `pg_blocking_pids()` 查看阻塞关系。

在前述会话 B 等待时，打开第三个独立连接执行：

```sql
SELECT
    a.pid,
    a.state,
    a.wait_event_type,
    a.wait_event,
    pg_blocking_pids(a.pid) AS blocking_pids,
    left(a.query, 100) AS query_text
FROM pg_stat_activity AS a
WHERE a.datname = current_database()
  AND a.pid <> pg_backend_pid()
ORDER BY a.pid;
```

在能够查看相应会话信息的权限前提下，预期能发现 B 正在等待锁，`pg_blocking_pids` 指向相关阻塞者。对于前面的行更新实验，`wait_event_type` 通常是 `Lock`，具体 `wait_event` 可能体现为 `transactionid`；但这不是所有行锁等待都固定具有的唯一监控表现。A 在等待客户端下一条指令时，服务端还可能显示为 `idle in transaction`，这与 A 已经把 SQL 执行完却仍持有事务锁的事实相吻合。

`pg_locks` 可以进一步帮助定位锁对象和请求模式，但 `granted = true` 只说明某项锁已经授予，并不等于存在性能问题。相同表上的大量兼容锁完全可以同时存在。排查的重点应当是**谁正在等待、等待什么、被谁阻塞、持锁事务为什么没有结束**，而不是简单统计锁数量。

## 七、唯一约束为什么能处理“先检查再插入”的竞争

行锁可以解释已经存在的行如何相互竞争。但如果目标记录根本不存在，两个事务都想“检查不存在，然后插入”，应该锁住什么？

假设一个用户在某场次只能预约一次。应用先执行 `SELECT` 检查是否存在预约，再执行 `INSERT`。两个请求可能在任何一个插入完成前都查到了“不存在”。如果把查询结果当成插入资格，就出现典型的检查与使用之间的竞争窗口（TOCTOU）。普通快照读取不能替这段业务逻辑自动预留一个尚不存在的主键或业务键。

解决这种唯一性约束时，更可靠的基础是数据库本身的唯一索引：

```sql
CREATE TABLE IF NOT EXISTS blog_lock_booking (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id bigint NOT NULL,
    event_id bigint NOT NULL,
    UNIQUE (user_id, event_id)
);
```

假设 A 和 B 都尝试插入 `(user_id=7, event_id=42)`。A 即使尚未提交，B 也不能因为自己的 MVCC 快照看不见 A 插入的行，就绕过唯一性检查。PostgreSQL 的唯一索引检查会考虑可能发生冲突的未提交行；在必要时等待相关事务结束，然后重新判断冲突是否仍然存在。如果 A 回滚，B 可以插入；如果 A 提交，B 通常会收到唯一约束错误 `23505`。

这是 MVCC 和约束检查共同工作的结果。唯一索引不是只加速一次 `SELECT`，它还是写入过程必须遵守的仲裁机制。并且检查必须与索引插入过程协调完成，不能简单拆成“先查索引，再决定是否插入”的两个无保护步骤，否则仍可能在检查与写入之间发生竞争。

如果重复预约在业务上应当被忽略，可以直接表达为：

```sql
INSERT INTO blog_lock_booking (user_id, event_id)
VALUES (7, 42)
ON CONFLICT (user_id, event_id) DO NOTHING
RETURNING id;
```

仅在实际插入成功时，这条语句才会返回新插入的 `id`。如果是被所指定冲突目标命中的唯一约束阻止，就不会插入新行。`ON CONFLICT DO UPDATE` 还可以把冲突处理变成原子化的插入或更新，但它并不意味着整段业务工作流天然幂等，也不会自动处理数据库以外的副作用。

这里也存在边界：默认的唯一约束允许多个包含 `NULL` 的键值在一般意义上不被当作相等；PostgreSQL 也提供 `NULLS NOT DISTINCT` 等不同语义。延迟唯一约束和部分唯一索引还有额外规则。因此，真正应当受保护的业务键是什么，以及约束怎样定义，仍需要由开发者准确设计。

## 八、为什么有锁、有事务，仍然不等于业务一定正确

到这里可以看到，事务、锁和约束分别处理不同类型的问题。事务决定修改共同提交还是回滚；锁协调互相冲突的数据库操作；约束拒绝某些不允许存在的数据库状态；MVCC 则决定普通查询能够读到哪些行版本。它们互相协作，但没有任何一个机制能够在不知道业务规则的情况下替应用推导全部正确性要求。

库存例子中的 `CHECK (stock >= 0)` 只能防止写入负数，不会防止两次扣减被合并成一次。因为最终库存 9 本身满足约束，数据库无法判断业务上已经成功接受了两笔订单。条件式原子更新把扣减意图直接交给数据库，才让这个约束与并发写入过程连接起来。

唯一约束适合禁止重复业务键，但不保证跨多行聚合规则。上一篇的值班医生写偏斜已经说明：两个事务修改不同行，即使都持有并正确释放各自的行锁，也可能共同破坏“至少一人值班”的跨行不变量。给已经存在的两行分别加锁，不一定覆盖所有基于集合或范围的决策；某些新插入的行甚至不属于此前查询到的结果集。

这也解释了为什么“给所有 SQL 加锁”不是可靠的通用答案。锁的目标、模式和覆盖范围必须与要维护的不变量一致。锁取得太早或持有太久会放大等待；锁住错误的行则可能丝毫不能改善正确性。对于无法被一条条件更新或数据库约束直接表达的规则，需要进一步设计并发控制方案，例如明确的行锁协议、版本条件更新，或者使用适当隔离级别并处理重试。这些策略将是第六篇的重点。

## 九、等待时间也是数据一致性机制的工程成本

锁冲突并不是数据库实现出错，而是数据库为了满足某种正确性要求而付出的协调成本。但在生产系统中，等待不会无限制地变成可接受的延迟。

一条行锁可能在几毫秒内被释放，也可能因为持锁事务执行了慢查询、等待外部服务或忘记提交而持续很久。多个请求都等待同一资源时，延迟会向应用层传播，占用连接池连接并形成请求堆积。即使数据库 CPU 不高，应用依然可能因锁等待而出现严重的尾延迟。

PostgreSQL 可以通过 `lock_timeout` 限制语句等待获取锁的时间，通过 `statement_timeout` 限制语句的执行时间。二者关注的对象不同：前者只针对等待获取锁的阶段，后者覆盖语句执行时间，包含其中的锁等待。超时并不会代替业务决定是否可以重试；特别是在显式事务块中，超时错误通常会让当前事务进入失败状态，需要按事务恢复规则处理。

`SELECT ... FOR UPDATE NOWAIT` 和 `SKIP LOCKED` 也改变锁等待行为：前者在不能立即获得目标行锁时报告错误，后者跳过当前无法锁定的行。它们对任务队列等特殊场景有价值，但 `SKIP LOCKED` 会产生不完整、非统一的读取视角，不能把它当作普通业务查询的一般性一致性保障。什么时候主动等待、什么时候快速失败、什么时候允许跳过冲突数据，取决于业务是否接受相应语义。

更根本的优化通常是缩短不必要的事务持有时间。在事务已经写入并持锁后进行长时间 HTTP 调用，就可能让与数据库无关的网络延迟直接转化为其他事务的数据库等待。把非必要的外部操作移出持锁区间，并明确统一提交边界，通常比单纯扩大连接池更接近问题根源。不过，拆分操作也可能改变原本需要的原子性，不能为了缩短锁时间随意把一个必须共同提交的业务事务拆散。

## 十、从锁机制回到并发正确性

最初的库存问题并非缺少事务，也不是 PostgreSQL 没有给 `UPDATE` 加锁，而是应用把“最新库存减一”的业务意图提前变成了“写入我曾经算出的数字”。锁可以让两个写入有序，却不能替应用识别旧数字已经过时。

真正能够解释数据一致性的，是把业务不变量与数据库执行机制对应起来：对单行计数，可用基于当前行值的条件更新；对业务键唯一性，可用唯一约束及其冲突处理；对多个事务必须协调的资源，可以分析相应的行锁、表锁及等待规则；对跨行或跨范围的整体约束，则不能想当然地认为已经锁了若干行就足够。

这篇文章解决的是 PostgreSQL 如何发现和协调数据库层面的竞争，以及这些机制能保证什么、不能保证什么。下一篇再进一步回答工程决策问题：当我们已经知道可能出现哪类竞争时，应该在什么条件下选择乐观锁、悲观锁或其他并发控制策略，怎样决定重试边界，以及它们各自的代价是什么。
