我们在 FastAPI 项目中经常看到这样的代码：

```python
async with session_factory() as session:
    user = await session.get(User, user_id)
```

它看起来是在创建一个数据库会话，然后查询一条记录。但如果此时打印 PostgreSQL 的连接数，会发现创建 `AsyncSession` 并不一定增加数据库连接；查询完成后，即使协程已经拿到了结果，连接也可能仍然被占用；直到事务结束，连接才回到池中。

为什么会这样？

原因是应用程序访问数据库时，至少涉及三个不同层面的状态：数据库连接负责通信，连接池负责分配和复用连接，ORM Session 负责维护一次业务操作中的对象与事务状态。它们的生命周期既有重叠，又不完全一致。如果把 Session 当成连接、把 SQL 执行结束当成事务结束，就很容易误判连接池耗尽的问题。

除非另有说明，本文以 PostgreSQL 18、SQLAlchemy 2.0.x、`asyncpg` 和应用直连数据库为讨论前提；连接前面存在代理池时，部分结论需要重新解释。

## 一、从一条 SQL 到 PostgreSQL 后端进程

先不考虑 ORM。一个 Python 程序想让 PostgreSQL 执行 `SELECT 1`，并不是将 SQL 字符串直接交给某个数据库函数。它需要通过驱动，使用 PostgreSQL 的前后端通信协议与服务端交互。

对于直接连接 PostgreSQL 的客户端，过程大致是这样的。客户端通过 TCP 或 Unix 域套接字建立通信通道，按实际配置进行必要的加密协商，然后发送包含数据库、用户名和协议版本等信息的启动消息。

服务端根据访问配置决定如何认证，双方可能交换多轮认证消息。认证和初始化完成后，服务端发送参数信息，并以 `ReadyForQuery` 表示已经可以接收查询。此后客户端才进入反复发送请求、读取结果的阶段。

这里没有把“建立 TCP 连接”和“完成数据库连接”视为同一件事。TCP 建连只是通信通道可用；PostgreSQL 还要完成协议初始化与认证。

建立一条可执行 SQL 的连接，需要承担网络往返、驱动初始化和服务端资源分配等成本。这些成本具体有多大，取决于网络、TLS、认证方式和运行环境，不能统一换算成某个固定毫秒数。

PostgreSQL 采用多进程架构。对于一条直接连接到服务器的常规客户端连接，服务端通常由一个独立的后端进程负责处理。后端进程不仅处理 SQL，还在连接存续期间维护一部分会话级状态，例如会话参数、临时对象以及预编译语句等。使用 `pg_backend_pid()` 可以取得正在处理当前连接的后端进程 ID。

这也说明，**一个连接不是一条 SQL，更不是一个事务。** 一条连接可以先后执行很多条 SQL，也可以经历多个事务。两次查询即使不在同一个事务中，也完全可能通过同一条连接发给同一个 PostgreSQL 后端进程。

反过来，如果一个 Web 服务每执行一次查询就重新建立连接、认证并在查询结束后断开，应用和数据库就会不断重复这些动作。

PostgreSQL 的连接数也不是一个可以无限增加的数字：每条活跃后端进程都会消耗服务器资源，数据库能够接纳的连接数量还受 `max_connections` 等设置约束。连接池首先要解决的，就是这种频繁建立连接和难以约束连接数量的问题。

## 二、为什么要区分 Engine、驱动连接与连接池

在 SQLAlchemy 中，`create_async_engine()` 返回 `AsyncEngine`。它负责把数据库 URL、PostgreSQL 方言、驱动能力与连接池整合起来，向上提供统一的数据库访问入口。它不是一条已经连接到数据库的 TCP 连接。

以 `postgresql+asyncpg://...` 为例，真正与 PostgreSQL 协议交互的是 `asyncpg` 提供的驱动能力；SQLAlchemy 在驱动之上提供自己的连接与事务抽象。

`AsyncConnection`、SQLAlchemy 管理的池内连接、驱动层的连接，以及服务端的数据库会话，是相关联但不能混为一谈的对象。

一次常见的访问路径是：`AsyncSession` 在需要数据库 I/O 时，通过所绑定的 `AsyncEngine` 获取连接资源；连接池决定提供空闲连接、创建新连接还是等待；SQLAlchemy 再借助数据库驱动将 SQL 发送给 PostgreSQL。查询完成后，结果沿着相反方向返回。

这里还有一个容易被名字误导的地方。PostgreSQL 所说的 *database session*，主要是客户端连接建立后在服务端持续存在的会话；SQLAlchemy 的 ORM `Session`，则是 Python 应用中的工作单元和状态管理对象。

一个 ORM Session 可以在两个连续事务中先后借用不同的物理连接，而一条物理连接也可以在不同时间服务于不同的 ORM Session。因此两种 Session 不是同一层概念。

这一层区分对理解连接池尤其重要。应用关闭 ORM Session，不等于立即关闭 PostgreSQL 会话。连接可能只是归还给连接池，稍后又被其他 ORM Session 使用。

## 三、连接池为什么不是一个简单的连接列表

连接池可以理解为一个负责连接资源分配的组件。它需要知道哪些连接可以复用，哪些正在被使用；当连接不足时是否允许新增；达到上限时是否让请求等待；归还时如何清理旧事务；连接失效后如何处理。

SQLAlchemy 对常见同步数据库驱动使用 `QueuePool`，在 `create_async_engine()` 的默认配置下使用适合 asyncio 的 `AsyncAdaptedQueuePool`。

两者管理容量的基本语义相似，但异步版本使用 asyncio 兼容的等待机制，不能理解成简单地在同步连接池外面加上一层 `await`。

看下面的配置：

```python
engine = create_async_engine(
    DATABASE_URL,
    pool_size=5,
    max_overflow=3,
    pool_timeout=10,
    pool_pre_ping=True,
)
```

对于这种连接池，`pool_size=5` 不是程序启动时立即连接数据库五次，而是池在需要时逐步建立连接，并允许保留最多五条用于长期复用的连接。SQLAlchemy 连接池默认采用惰性建连：初始化 Engine 和创建 Session 都不会仅因为配置了 `pool_size` 就把全部连接建好。

如果五条连接全部借出，而此时还有新的借用请求，`max_overflow=3` 允许额外创建最多三条临时连接。这样，同一时刻最多有八条连接被该池借出。溢出连接归还后，通常会被关闭，而不是永久扩充池的空闲容量。

当八条连接都被占用，第九个借用者需要等待。`pool_timeout=10` 约束的是等待连接池借出连接的最长时间，不是 SQL 查询执行超时，也不是数据库建立 TCP 连接的超时。等待超过限定时间，SQLAlchemy 会抛出连接池超时异常。

因此，连接池的容量不是“一个应用最多能处理多少 HTTP 请求”。请求可以进行鉴权、参数校验或其他操作而不访问数据库。只有真正向池借出连接且尚未归还的操作，才持续占据连接资源。数据库的查询并发能力也不能简单用连接数量代替：连接数只是资源上限的一部分，SQL 规划、磁盘 I/O、CPU 和锁等待同样会影响吞吐量。

借用和归还还要与物理连接的创建和断开严格区分。借用（checkout）是将一条可用连接交给当前使用者；归还（checkin）是交还使用权。它们通常不会触发新的 PostgreSQL 启动认证流程。只有池内没有可复用连接而允许新增，或者已有连接失效、被淘汰时，才可能发生实际的重新连接。

连接为什么不能直接归还而不做任何处理？因为下一位借用者不应继承前一位使用者未提交的事务。SQLAlchemy 默认的连接归还过程包含事务清理，通常通过回滚确保没有遗留的事务状态。

要注意，现代 SQLAlchemy 可能由 `Connection` 对象在关闭时先执行回滚，而不是每次都由池额外执行一次回滚；“归还时执行两次回滚”并不是固定规则。

回滚能清理未结束事务及其持有的事务性锁，却不等于把 PostgreSQL 会话恢复为刚建立时的状态。某些会话级参数、临时表、预编译语句或监听状态可能跨越事务而保留。SQLAlchemy 默认的 reset-on-return 并不提供对所有会话级状态的彻底清洗。

在连接复用的系统中，如果代码修改了会话级设置，就必须明确其作用范围和恢复策略。必要时可以用连接池事件定制清理，但不能想当然认为每次 checkout 都得到一条“全新会话”。

## 四、Session 的价值不只是替你执行 SQL

如果只需要执行 SQL，为什么不直接通过 `AsyncEngine.connect()` 获取 `AsyncConnection`？

实际上可以。SQLAlchemy Core 就提供了这种数据库访问方式。ORM Session 的存在，是因为把数据库记录映射成 Python 对象之后，应用需要管理的已经不仅是通信连接。

假设从数据库加载了一个 `User` 对象，随后修改了 `user.name`。Python 对象的属性发生变化，并不意味着修改操作立即变成了一条 `UPDATE`。

ORM 必须知道对象原来的状态、当前处于新增还是持久化状态、哪些属性被修改，以及应该如何将一批对象变更转换成 SQL。这是 Session 的主要职责。

SQLAlchemy ORM 使用 *identity map* 管理已经进入当前 Session 的持久化对象。对于同一个 ORM 身份（包含映射实体和主键等信息），当前 Session 原则上维护同一个 Python 对象实例。这使得重复获得同一行对应的 ORM 对象时，可以对其变化进行一致的追踪。

不过，identity map 不是一般意义上的查询结果缓存。再次执行 `select(User).where(...)` 通常仍然会向数据库发出 SELECT；只是如果查询结果对应的身份已经存在，ORM 会按其状态管理规则复用原对象。

`Session.get(User, id)` 则可能在对象已存在且未过期时直接利用 identity map，避免 SQL。两种行为不能混为一谈。

Session 还实现了 *Unit of Work*（工作单元）模式。它把待插入、修改、删除的 ORM 状态组织起来，在需要时通过 `flush()` 转换为数据库语句，并根据映射关系与依赖决定执行顺序。`flush()` 的作用是把当前积累的变更同步到数据库事务中，而不是确认事务最终成功。

在正常的事务型数据库配置下，`flush()` 发出的 `INSERT`、`UPDATE` 或 `DELETE` 已经在当前事务中执行，因此数据库可能检查约束、产生锁或返回生成的主键；但事务还没有 `COMMIT`。

如果后续回滚，这些可回滚的修改仍然会撤销。因此 `flush()` 和 `commit()` 的区别，绝不是“写入内存”和“写入数据库”：**前者可以真实执行 SQL，后者才是结束并提交当前事务的动作。**

SQLAlchemy 默认会在某些 ORM 查询前进行 autoflush，以避免查询时忽略当前 Session 尚未同步的变更；`commit()` 也会强制完成必要的 flush，即使把 `autoflush=False` 关闭，也不代表提交时可以跳过 flush。

flush 出错后，Session 还可能进入需要显式 `rollback()` 才能继续使用的状态。这些行为都说明 Session 本身是一台具有状态和约束的工作单元管理器，而不是连接池里的连接别名。

## 五、一次数据库操作中有三条不同的时间线

理解整个系统最容易出错的地方，是把创建 Session、开始事务、借用连接放在同一个时间点。实际上，SQLAlchemy 2.0 默认的 `autobegin=True` 把它们分开了。

创建 `AsyncSession` 时，通常还没有物理连接被借出，也没有活动的 ORM 事务。调用 `session.add(obj)` 可能让 Session 进入一个逻辑事务状态，但如果只改变了 Python 对象的 ORM 状态，尚未 flush 或发起 SQL，就不需要实际连接 PostgreSQL。

此时 `session.in_transaction()` 可以返回 `True`，却不能据此断言 PostgreSQL 已经开始了数据库事务。

这个逻辑事务由 SQLAlchemy 内部的 `SessionTransaction` 管理。它负责协调 Session 当前的工作边界；当真正需要数据库 I/O 时，才按需取得 SQLAlchemy Connection，并在连接层执行事务操作。

可以把它理解成两层相关但不同时起步的状态机：一层管理 ORM 操作，一层管理数据库连接上的真实事务。

当执行第一条 SQL 时，Session 通常从 Engine 的连接池借出连接，并在该连接上进入数据库事务。

这里的“进入事务”还需要区分 SQLAlchemy 的日志术语与网络协议消息：日志里的 `BEGIN (implicit)` 描述的是 SQLAlchemy 的事务边界，不保证各种驱动都实际发送了一条文本形式的 `BEGIN` SQL。数据库事务究竟通过哪类驱动调用和协议消息启动，取决于方言、驱动与连接的事务配置。

之后，SQL 执行结束并不导致当前事务结束。如果没有执行 `commit()`、`rollback()` 或关闭 Session，连接通常会继续归当前事务使用。这是为了让后续 SQL 在同一事务中执行，而不是每执行一条语句就切换到另一条连接。

因此，`await session.execute(...)` 返回，只说明这次执行已经取得相应结果，不能据此判断连接已经被归还。对于使用流式结果或服务端游标的代码，还可能存在结果未消费完毕、需要继续持有数据库资源的情况。实际释放时机必须结合结果消费方式和事务边界来判断。

在通常的、由 Engine 提供连接的单数据库场景中，`await session.commit()` 会先完成待处理的 flush，再提交正在使用的数据库事务并释放事务持有的连接；`await session.rollback()` 则回滚事务并释放相应资源。

同一个 Session 如果之后再执行 SQL，可以启动下一段逻辑事务，重新 checkout 一条连接。第二次取得的连接可能还是第一次的物理连接，也可能是另一条。

`await session.close()` 则处理的是另一个边界：它会释放 Session 当前占用的事务与连接资源，并把 ORM 对象从 Session 管理状态中移出。未结束的事务会被清理、回滚。

**关闭 Session 不等于提交事务，也不等于关闭池内物理连接。** 在 SQLAlchemy 2.0 的默认配置下，`close()` 主要相当于重置 Session，实例甚至可以再次使用；设置 `close_resets_only=False` 才会让关闭成为不可复用的终态。

工程中最好仍然为每次独立业务操作创建有明确作用域的 Session。

还存在重要的边界条件：一个 Session 可以映射到多个 Engine，也可以绑定由调用方管理的现有 Connection。那些场景下，连接的获取、提交权限和释放方式会受到绑定与事务配置影响。

上面“commit 后把连接归还池中”的描述，针对的是 Web 服务最常见的、Session 绑定 Engine 并自行管理事务的用法。

## 六、为什么明明没有执行 SQL，数据库却显示事务没有结束

PostgreSQL 的 `pg_stat_activity` 能观察服务端后端进程的活动状态。这里需要区分两个非常相似的词：`idle` 表示后端当前在等待新的客户端命令；`idle in transaction` 则表示后端已经处于事务中，但当前没有执行查询。

这与连接池的“空闲连接”不是同一个判断维度。一条已经归还给 SQLAlchemy 连接池、且事务结束的物理连接，仍然可能作为数据库会话存活，在 PostgreSQL 中显示为 `idle`。

而一条处于 `idle in transaction` 的连接，通常仍被应用的某个未结束事务占用，并不是可以直接分配给下一位借用者的空闲池连接。

为什么这值得关注？因为连接被占用的时间不是所有 SQL 执行时间的简单总和。假设一个请求查询数据库后，又调用外部 HTTP API，等待返回后才决定更新数据库并提交。只要第一次查询开启了事务且没有中途结束，那么等待 HTTP 响应的这段时间，即使数据库 CPU 完全没有在为该请求工作，连接也可能一直被借出。

长事务不只是拖慢连接池周转。根据事务具体做过什么以及所处隔离级别，它还可能延长某些锁或快照相关资源的保留时间，影响数据库清理旧版本等操作。

但这不是说每条处于 `idle in transaction` 的 SELECT 都一定阻塞其他事务；具体影响需要分析它执行过的语句、持有的锁和隔离级别。事务与 MVCC 的关系，将在本专题后续文章展开。

## 七、用实验区分“Session 存在”和“连接占用”

下面的程序不需要创建业务表，只依赖 PostgreSQL 内置的 `pg_backend_pid()` 和 `SELECT 1`。它将连接池限制为一条连接，然后让两个互不共享的 Session 竞争这条连接。代码中的两项观测分别来自 ORM 层和连接池层，能够验证它们并不是同一个状态。

安装依赖，并配置一个确实可访问的 PostgreSQL 数据库：

```bash
python -m pip install 'SQLAlchemy>=2.0,<2.1' asyncpg
export DATABASE_URL='postgresql+asyncpg://appuser:password@127.0.0.1:5432/appdb'
```

```python
import asyncio
import os

from sqlalchemy import text
from sqlalchemy.exc import TimeoutError as PoolTimeout
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine


async def main() -> None:
    engine = create_async_engine(
        os.environ["DATABASE_URL"],
        pool_size=1,
        max_overflow=0,
        pool_timeout=1,
        echo_pool="debug",
    )
    make_session = async_sessionmaker(engine, expire_on_commit=False)
    connection_borrowed = asyncio.Event()

    async def first_task() -> None:
        async with make_session() as session:
            print("创建 Session:", session.in_transaction())
            pid = await session.scalar(text("SELECT pg_backend_pid()"))
            print("执行查询后:", session.in_transaction(), pid)
            connection_borrowed.set()

            # 此时没有 SQL 在执行，但事务尚未结束。
            await asyncio.sleep(2)
            await session.rollback()
            print("回滚之后:", session.in_transaction())

    async def second_task() -> None:
        await connection_borrowed.wait()
        async with make_session() as session:
            try:
                await session.scalar(text("SELECT 1"))
            except PoolTimeout:
                print("第二个任务等待连接池超时")
                await session.rollback()

    try:
        await asyncio.gather(first_task(), second_task())
    finally:
        await engine.dispose()


if __name__ == "__main__":
    asyncio.run(main())
```

刚创建 Session 时，`in_transaction()` 应为 `False`；执行第一次查询后，它会变成 `True`。尽管第一项任务已经执行完 SELECT，它在休眠期间仍未结束事务，因此继续占用唯一的一条连接。

第二项任务此时会尝试从同一个池取得连接。在正常的调度条件下，第二项任务约等待一秒后触发连接池超时，而第一项任务两秒后才回滚并释放连接。实际打印顺序和精确耗时取决于调度，不应据此做性能基准测试。

本轮审校已在 PostgreSQL 18.6、SQLAlchemy 2.0.54 与 `asyncpg` 0.32.0 上实际运行这段程序，观察到了第二个任务等待连接池超时，以及第一个任务回滚后连接被归还。这个结果验证的是资源生命周期，不是性能数据。

`echo_pool="debug"` 会输出连接创建、checkout、checkin 等事件，可以用来观察连接资源何时被借出、何时归还。即使把 Session 生命周期改为更长，只要事务在执行完成后及时结束，连接也能提前释放。这恰好说明，不应把“Session 对象仍存在”当成“连接仍在占用”的充分条件。

如果想从数据库侧观察，可以另开一个 `psql` 会话，在第一项任务休眠期间执行：

```sql
SELECT pid, state, xact_start, query_start, state_change,
       wait_event_type, wait_event
FROM pg_stat_activity
WHERE datname = current_database()
  AND backend_type = 'client backend'
ORDER BY pid;
```

在直连 PostgreSQL、默认事务管理且具备相应可见权限的前提下，可以检查目标 PID 是否处于 `idle in transaction`，再对照 Python 侧的 checkout 日志。

注意，查询 `pg_stat_activity` 本身也会占用一个独立的数据库连接；它观察的是服务端状态，不是直接读取 SQLAlchemy 连接池内部数据。若数据库前面有代理，PID 与客户端连接的一一对应关系还需要重新审视。

## 八、如何判断连接池应该设置多大

理解了连接什么时候借出与归还，连接池容量就不必靠猜测。真正决定需求的，不是 HTTP 请求总数，而是单位时间内开始占用连接的操作量，以及每项操作平均占用连接的时间。

在一个负载大致稳定的系统中，可以借用排队论中的 Little 定律：

\[
L = \lambda W
\]

这里的 `L` 是平均同时占用的连接数，`λ` 是平均每秒开始占用连接的操作次数，`W` 是每次借出连接到归还之间的平均持续时间。这个关系讨论的是稳定系统的平均值，不提供突发流量下连接池必定不会超时的保证，也不能直接把计算结果当成最终的 `pool_size`。

它揭示了一个重要原因：**连接池的瓶颈不一定来自 SQL 慢，也可能来自 SQL 之外的连接占用时间太长。** 如果业务代码把外部网络调用、长时间计算、用户交互等待放进一个已经使用数据库连接的事务中，连接占用时间就会上升。即使每条 SQL 执行得很快，平均被占用连接数仍会增加。

容量还必须从整个部署拓扑考虑。假设一个服务部署了四个 Worker 进程，每个进程分别创建 Engine，并设置 `pool_size=5`、`max_overflow=3`。那么在没有额外代理和特别共享机制的情况下，这些池合计可能瞬时借出最多三十二条连接。

如果有多个服务实例，连接预算还要继续累加。PostgreSQL 的 `max_connections` 并不是专供这一套服务独占的额度，其他应用、数据库维护连接及预留连接都需要计入。

因此，调整 `pool_size` 的前提是观测。需要看连接借用等待时间、超时次数、池内已借出连接数、平均和尾部连接持有时间，再结合 PostgreSQL 的活跃连接、事务空闲时间和查询压力判断瓶颈。

盲目把池子调大可能缓解应用等待，却使数据库同时承受更多会话及并发 SQL；把池子调小则可能保护数据库，但让应用请求排队。这本质上是背压与数据库容量之间的取舍，而不是越大越好。

`pool_pre_ping=True` 也应放在正确的位置理解。它是在 checkout 时检查连接是否仍可用，目的是降低取到已失效连接的概率，并不是给事务提供自动恢复能力。

如果数据库在事务执行过程中断开，当前事务可能失败，应用仍需决定是否以及如何重试整个业务操作。`pool_recycle` 可以按连接存活时长在借用时触发重建，也不等于正在执行的连接会在指定秒数到达时被强行切断。

## 九、AsyncSession 为什么不能跨并发任务共享

`AsyncSession` 的名称容易给人一种错觉：既然它是异步的，同一个实例是不是可以同时执行多个查询？答案是否定的。

异步的作用是让协程在数据库 I/O 等待期间把执行机会交还事件循环。它并不会让一个有状态的事务上下文自动变成可以安全并发访问的对象。

`AsyncSession` 内部维护 identity map、待 flush 对象、当前事务、关联连接等可变状态。两个协程如果同时对同一个 Session 操作，就可能交错修改事务和 ORM 状态，产生难以预测的行为。

因此，SQLAlchemy 明确建议并发任务各使用自己的 `AsyncSession`。

可以在同一进程中共享生命周期较长的 `AsyncEngine` 和 `async_sessionmaker`，但是不能把一个正在使用的 Session 作为全局单例交给多个请求或通过 `asyncio.gather()` 并发复用。

一个需要格外注意的工程细节是：`async with make_session() as session` 只保证退出时关闭 Session，并不表示正常退出自动提交。如果业务操作需要明确的提交边界，可以使用：

```python
async with make_session.begin() as session:
    # 在这里调用多个需要共同提交的数据库操作。
    ...
```

`async_sessionmaker.begin()` 创建 Session 并管理事务：正常退出时提交，异常退出时回滚，然后关闭 Session。与此不同，`async with make_session() as session` 的核心职责只是管理 Session 的关闭。

这一区别也是 Service 与 Repository 分层时需要明确的：如果 Repository 函数各自 `commit()`，上层 Service 就很难把多个操作组织到同一个事务中。

还要避免把 Session 的作用域与 HTTP 请求作用域机械地画等号。一个请求可能需要多个独立事务，也可能包含很长的非数据库 I/O；真正应保持一致的是**业务工作单元的边界、数据库事务的边界和连接持有时间**。不能只因为请求还没有返回，就一直保持已经开始的数据库事务。

## 十、当数据库前面还有 PgBouncer

到目前为止，我们假设 SQLAlchemy 连接池直接连接 PostgreSQL。实际部署中也可能增加 PgBouncer 这样的数据库连接代理。这时就出现了两层池化：应用管理自己到 PgBouncer 的客户端连接，PgBouncer 再管理到 PostgreSQL 的服务端连接。

如果 PgBouncer 使用 Session pooling，服务端连接会在客户端连接持续期间分配给它；如果使用 Transaction pooling，服务端连接可以在事务结束后分配给另一个客户端。

此时，一条长期存在的应用侧驱动连接，不再必然对应同一条 PostgreSQL 后端连接。前文借助 `pg_backend_pid()` 观察物理连接复用的方法，在这种拓扑下必须重新解释。

更关键的是，Transaction pooling 会破坏某些依赖 PostgreSQL 会话持续性的功能假设，例如某些会话级设置、会话级 advisory lock 和特定临时表用法。

部分协议级预编译语句能否使用，还取决于 PgBouncer 版本和配置，不能简单断言“事务池一定不支持预编译语句”。这也解释了为什么连接代理并非只需要调整地址就能完全透明接入。

对大多数直接使用 SQLAlchemy 连接池的应用而言，暂时不必引入 PgBouncer。只有当实际连接规模、实例数量、数据库资源或部署拓扑提出要求时，再评估代理池是否能解决相应问题。池化的层数增加，不会改变事务本身必须被正确管理这一事实。

## 十一、结语

回到开头的问题：创建一个 `AsyncSession`，并不意味着建立了新的数据库连接；执行完一条 SQL，也不意味着连接已经归还；关闭 Session，通常也不意味着底层连接被物理断开。只有把 ORM 工作单元、数据库事务和连接池租借关系当成不同的生命周期，才能准确解释这些现象。

连接池解决的是有限通信资源的复用与分配，Session 解决的是 ORM 对象变化和事务工作单元的组织，而事务本身决定数据库操作何时真正结束。它们需要协同工作，但不能互相代替。
