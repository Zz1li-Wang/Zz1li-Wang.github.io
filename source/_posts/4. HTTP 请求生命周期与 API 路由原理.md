使用 FastAPI 编写接口时，我们通常只需要几行代码，就可以对外提供一个 HTTP API。

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/users/{user_id}")
async def get_user(user_id: int):
    return {"user_id": user_id}
```

启动服务以后，客户端访问 `/users/123`，就能得到对应的 JSON 响应。

这个过程看起来很简单。

但如果仔细想一想，就会发现其中隐藏着不少问题。

客户端发送的 HTTP 请求，究竟是怎样进入 Python 程序的？`@app.get()` 为什么能够让 URL 对应到一个 Python 函数？框架又是如何提取参数、执行函数，并将返回值转换成 HTTP 响应的？

要回答这些问题，我们需要沿着一次请求的执行路径，从网络连接开始，逐步研究它在 Web 服务器和应用框架内部经历了什么。

## 一、一次 HTTP 请求经历了什么？

先建立一个整体认识。

假设浏览器向服务器发送下面这个请求：

```http
GET /users/123 HTTP/1.1
Host: example.com
Accept: application/json
```

服务端使用 Uvicorn 运行 FastAPI 应用。

从客户端发出请求，到最终收到响应，整个过程可以粗略理解为：

客户端建立或复用网络连接，将 HTTP 请求发送给服务器。

Web 服务器接收网络数据，并按照 HTTP 协议解析请求。

随后，服务器通过约定的应用接口，将请求交给 FastAPI。

FastAPI 根据请求路径和 HTTP 方法匹配路由，再完成参数处理、依赖解析和接口函数调用。

接口执行完毕后，框架构造 HTTP 响应，交还给 Web 服务器。

最后，服务器将响应编码成符合 HTTP 协议的网络数据，发送给客户端。

这条链路中有三个需要区分的层次。

HTTP 协议规定客户端与服务端如何表达请求和响应。

Web 服务器负责网络通信、协议解析，以及将请求交给应用程序。

Web 框架则负责路由匹配、参数验证、依赖管理和具体的业务调用。

所以，FastAPI 并不是直接从网络中读取 HTTP 报文的程序。它依赖 Uvicorn 这样的 ASGI 服务器，完成底层网络协议与 Python 应用之间的衔接。

实际部署时，前面还可能存在 Nginx、API 网关或负载均衡器。它们可以先接收客户端连接，再把请求转发给 Python 服务。

为了便于理解，本文先讨论客户端直接访问 Uvicorn 的情况。

## 二、HTTP 请求究竟是什么？

HTTP 的全称是 Hypertext Transfer Protocol，即超文本传输协议。

它是一种应用层协议，定义了客户端与服务端之间交换请求和响应时所采用的语义和消息格式。

这里需要注意，HTTP 不负责规定 Python 函数应该如何执行，也不负责决定请求应该由哪个业务接口处理。

它主要关心客户端想对哪个资源执行什么操作，以及服务器如何表达处理结果。

### 1. HTTP 请求的结构

以 HTTP/1.1 为例，一个请求通常包含请求行、请求头，以及可选的请求体。

```http
POST /users HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 16

{"name":"Alice"}
```

第一行称为请求行。

其中，`POST` 是请求方法，`/users` 是请求目标，`HTTP/1.1` 表示使用的 HTTP 版本。

请求方法用于表达请求的操作语义。比如，`GET` 主要用于获取资源表示，`POST` 表示将请求内容交给目标资源进行处理。

请求头则用于携带与请求有关的附加信息。

`Host` 用于标识目标主机，`Content-Type` 表示请求体的数据格式，`Content-Length` 则表示请求体的字节长度。

空行之后是请求体。

在这个例子中，请求体包含一段 JSON 数据。

不过，并不是每个 HTTP 请求都必须包含请求体。

对于常见的 `GET` 请求，客户端通常通过 URL 路径和查询参数表达获取资源所需的信息。

需要强调的是，HTTP 请求体并不等于 JSON。

它可以是 JSON、普通文本、表单数据、文件内容，或者其他字节数据。JSON 只是 Web API 中常用的一种数据表示格式。

此外，上面的文本形式属于 HTTP/1.1 的消息语法。HTTP/2 和 HTTP/3 使用不同的二进制帧机制，不能把这种请求行格式直接当成所有 HTTP 版本的网络传输格式。

但无论底层采用什么编码方式，请求方法、目标资源、请求头和请求内容等基本语义仍然存在。

### 2. URL 如何表达资源位置？

考虑下面这个地址：

```text
https://example.com:8443/users/123?detail=true
```

其中，`https` 是协议方案，`example.com` 是主机名，`8443` 是端口，`/users/123` 是路径，`detail=true` 则是查询参数。

这些部分在请求处理过程中承担不同的作用。

主机名和端口主要用于确定请求应该发送到哪个网络服务。实际过程中，还可能涉及 DNS 查询、代理选择以及负载均衡。

路径用于标识服务端的目标资源，也是 Web 框架进行路由匹配的重要依据。

查询参数通常用于表达筛选条件、分页信息或其他操作参数。

因此，路径与查询参数并不是一回事。

例如：

```text
/users/123?detail=true
/users/123?detail=false
```

对于普通的 FastAPI 路由匹配，两次请求都会匹配到 `/users/{user_id}`。

区别在于，它们携带的查询参数不同。

框架通常先根据路径和请求方法找到处理函数，再根据函数的参数定义解析所需的查询参数。

当然，具体路由机制也可以扩展到主机名等条件。这里讨论的是 FastAPI 中最常见的基于路径和 HTTP 方法的路由。

### 3. HTTP 请求与 TCP 连接是一回事吗？

不是。

HTTP 请求是应用层的消息，TCP 连接是传输层提供的可靠字节流通信通道。

对于常见的 HTTP/1.1 部署，客户端通常通过 TCP 连接向服务器发送 HTTP 数据。

如果使用 HTTPS，还涉及 TLS 加密通信。TLS 可能由 Python Web 服务器处理，也可能提前在反向代理处终止。

但一个 HTTP 请求并不必然对应一个新的 TCP 连接。

HTTP/1.1 默认支持持久连接，一个 TCP 连接可以先后承载多个 HTTP 请求。

HTTP/2 进一步支持在同一个连接中复用多个并发请求流。

HTTP/3 则使用基于 UDP 的 QUIC，而不是 TCP。

所以，不能简单地认为客户端发送一个请求，服务器就必须创建一个连接，处理完以后再关闭连接。

**HTTP 请求的生命周期与底层网络连接的生命周期，是两个不同的概念。**

这个区别对于后面理解 ASGI 的请求作用域十分重要。

## 三、请求是如何进入 Python 程序的？

理解 HTTP 消息以后，我们继续研究它怎样进入服务端。

假设使用下面的命令启动 FastAPI：

```bash
uvicorn main:app --host 127.0.0.1 --port 8000
```

这里的 `main` 对应 Python 模块，`app` 是模块中定义的 ASGI 应用对象。

Uvicorn 启动以后，会建立网络监听机制，等待客户端连接。

### 1. Socket 与网络数据接收

对于典型的 TCP 服务，服务器需要创建监听 Socket，并绑定指定的 IP 地址和端口。

当客户端连接建立后，操作系统会为服务器提供用于该连接通信的 Socket。

客户端发送的数据首先进入操作系统的网络协议栈。

操作系统负责处理 TCP 报文、维护连接状态，并将收到的数据放入相应的接收缓冲区。

这时，数据还没有自动变成 Python 中的请求对象。

它本质上仍然是网络字节数据。

服务器程序需要通过相应的 Socket 或异步传输接口读取这些数据。

在传统同步阻塞模型中，如果线程尝试读取某个 Socket，而数据尚未到达，那么读取操作可能阻塞当前线程。

上一篇文章介绍的事件循环与 I/O 多路复用，正是为处理这类等待提供了另一种组织方式。

Uvicorn 可以借助异步事件循环管理网络连接，在数据可读时执行相应的协议处理逻辑，而不需要为每个连接长期分配一个独立的阻塞线程。

不过，Socket 可读不意味着完整的 HTTP 请求已经到达。

TCP 只负责提供有序的字节流，它不会替 HTTP 协议识别某条请求在什么位置结束。

因此，服务器还需要进行 HTTP 协议解析。

### 2. HTTP 协议解析器负责什么？

服务器读取到网络数据之后，需要根据当前 HTTP 版本的规则识别消息结构。

以 HTTP/1.1 为例，它需要识别请求方法、请求目标、请求头，以及请求体的边界。

这里的边界问题尤其重要。

假设客户端通过同一个 TCP 连接连续发送两个 HTTP 请求。

TCP 只保证字节流的传输顺序，并不保证每次 Socket 读取恰好得到一个完整的 HTTP 请求。

一次读取可能只拿到半个请求，也可能读到一个请求以及下一个请求的部分数据。

因此，协议解析器必须按照 HTTP 的消息定界规则，把连续的字节数据还原成各自独立的请求。

对于 HTTP/1.1，请求体的长度可能由 `Content-Length` 指定，也可能通过分块传输编码等机制确定。

解析器还需要处理不合法的请求语法、请求大小限制，以及其他协议层面的条件。

Uvicorn 提供了不同的 HTTP 协议实现选择，例如基于 `h11` 或 `httptools` 的实现。

这些组件负责的是 HTTP 协议层面的工作，而不是业务路由匹配。

它们不需要知道 `/users/123` 应该由 `get_user()` 函数处理。

它们只需要将解析得到的请求信息，以约定的形式交给上层应用。

这里还有一个细节。

服务器不一定要等待整个请求体全部接收完成，才能开始调用应用。

对于大文件上传、流式请求等场景，请求头解析完成后，应用就可以开始处理请求，而请求体则通过后续的异步事件逐步读取。

这种能力正是 ASGI 接口设计的一部分。

## 四、ASGI 如何连接服务器与应用？

现在，我们已经知道 Uvicorn 负责网络数据接收和 HTTP 解析。

但它怎么调用 FastAPI 呢？

最直接的办法似乎是让 Uvicorn 直接调用某个 FastAPI 内部函数。

可这样会产生一个问题：服务器与框架将高度耦合。

如果换成另一个 Web 框架，服务器就需要重新实现一套调用方式。

因此，Python Web 生态需要一套统一的服务器与应用交互接口。

ASGI（Asynchronous Server Gateway Interface）就是这样一种接口规范。

它定义了支持异步运行的服务器，应该如何与 Python Web 应用进行交互。

### 1. ASGI 应用是什么？

从接口形式来看，一个 ASGI 3 应用可以表示为：

```python
async def app(scope, receive, send):
    ...
```

这个函数接收三个参数。

`scope` 是一个字典，用于描述当前请求或连接的相关信息。

`receive` 是一个异步可调用对象，用于从服务器接收事件。

`send` 也是一个异步可调用对象，用于向服务器发送事件。

这里的事件并不是操作系统直接传入的原始网络报文，而是符合 ASGI 规范的 Python 字典。

对于 HTTP 请求，`scope` 可能包含：

```python
{
    "type": "http",
    "http_version": "1.1",
    "method": "GET",
    "scheme": "http",
    "path": "/users/123",
    "query_string": b"detail=true",
}
```

这是经过简化的示例，并不是完整的 ASGI scope。实际还会包含 ASGI 版本、请求头等规定字段。

从中可以看到，请求方法、路径等数据已经被解析出来。

应用不需要再去读取原始 TCP 字节，寻找 HTTP 请求行中的空格。

它只需要使用这些经过标准化的信息，决定如何处理请求。

### 2. receive() 与 send() 是如何工作的？

ASGI 不要求服务器在调用应用时，一次性交付完整的请求体。

应用可以通过 `receive()` 接收请求事件。

例如：

```python
{
    "type": "http.request",
    "body": b"hello",
    "more_body": False,
}
```

这个事件表示收到一部分请求体数据。

其中，`more_body` 用于说明后面是否还有请求体内容。

如果请求体比较大，服务器可以通过多次事件向应用交付数据。

应用也可以使用 `send()` 发送响应事件。

例如，先发送响应状态与响应头：

```python
await send({
    "type": "http.response.start",
    "status": 200,
    "headers": [
        (b"content-type", b"application/json"),
    ],
})
```

然后发送响应体：

```python
await send({
    "type": "http.response.body",
    "body": b'{"user_id":123}',
    "more_body": False,
})
```

通过这种接口，Web 框架并不需要亲自实现 TCP 数据发送，也不需要关心响应应该怎样转换成 HTTP/1.1 报文或其他协议版本的传输格式。

它只需要按照 ASGI 规范发送响应事件。

服务器负责将这些事件转化为实际的网络数据。

这里也能看出 ASGI 的一个重要设计特点：应用与服务器之间交换的是事件，而不是简单地让应用返回一整段响应文本。

因此，它能够支持分块请求、流式响应等需要持续交换数据的场景。

### 3. 一个连接会创建多少个 ASGI scope？

这取决于协议。

对于 HTTP，每个请求对应独立的 HTTP scope。

即使多个 HTTP/1.1 请求复用了同一条 TCP 连接，服务器仍然会为不同请求建立相应的 ASGI 调用上下文。

对于 HTTP/2，同一连接中不同的请求流，也分别具有自己的 HTTP 请求作用域。

而对于 WebSocket，scope 通常会持续存在于整个 WebSocket 连接期间。

所以，在 ASGI 中，一个 HTTP 请求的作用域不等于底层 TCP 连接的作用域。

这也说明，不能简单地把一次请求所使用的 Python Task、一个 HTTP 请求和一条 TCP 连接视为同一个对象。

它们分别处于不同层次，生命周期也不一定一致。

关于 ASGI 与传统 WSGI 的设计区别，以及 Uvicorn 内部的 Worker 和事件循环组织方式，我们会在下一篇继续研究。

这一篇先把重点放回请求进入框架之后的执行过程。

## 五、API 路由究竟是如何工作的？

现在，HTTP 请求已经通过 ASGI 接口交给 FastAPI。

接下来需要解决的问题是：框架怎样知道应该执行哪个函数？

这就是路由（Routing）的作用。

路由可以理解为一套请求匹配与分发机制。

它根据请求携带的方法、路径等信息，从已经注册的路由集合中找到对应的处理逻辑。

### 1. @app.get() 做了什么？

我们再看最开始的代码。

```python
@app.get("/users/{user_id}")
async def get_user(user_id: int):
    return {"user_id": user_id}
```

这里的 `@app.get()` 是一个 Python 装饰器。

它的主要目的并不是在收到 HTTP 请求时重新定义一个函数，而是在应用构建阶段，将这个接口注册到 FastAPI 的路由系统中。

注册过程中，框架会保存与这个路由有关的信息。

例如，请求方法是 `GET`，路径模板是 `/users/{user_id}`，对应的处理函数是 `get_user`。

FastAPI 还会分析接口函数的参数声明，以及相关的依赖和响应配置，为后续请求处理建立相应的路由处理结构。

因此，路由注册通常发生在 Python 模块导入和应用初始化阶段，而不是每次请求到达时才扫描所有被装饰的 Python 函数。

这里需要区分两个时间点。

装饰器注册路由，是应用启动和构建时发生的事情。

根据请求选择已注册的路由，则是请求处理时发生的事情。

这也是为什么新增一个接口以后，运行中的服务通常需要重新加载代码或更新应用的路由配置，才能让新路由生效。

### 2. 路由表如何匹配请求？

FastAPI 的路由机制建立在 Starlette 之上。

Starlette 的普通路由匹配具有顺序优先的特点，会按照路由表中的顺序检查请求是否符合相应规则。

假设注册了两个接口：

```python
@app.get("/users/me")
async def current_user():
    return {"name": "current"}


@app.get("/users/{user_id}")
async def get_user(user_id: int):
    return {"user_id": user_id}
```

当客户端访问：

```http
GET /users/me HTTP/1.1
```

框架会根据路由规则匹配请求。

固定路径 `/users/me` 可以直接命中第一个路由。

而 `/users/{user_id}` 是带有动态路径参数的路由，它可以匹配 `/users/123`、`/users/456` 等路径。

但动态路由也可能匹配 `/users/me`。

因此，路由注册顺序很重要。

如果先注册 `/users/{user_id}`，再注册 `/users/me`，前一个动态路由可能提前匹配 `/users/me`，使后面的固定路由没有机会被选中。

所以，在有重叠可能的情况下，通常应该将更具体的路径放在更通用的动态路径之前。

需要注意，路由匹配并不只是简单比较两个字符串是否完全相等。

动态路径需要根据路径模板识别相应的片段，并提取路径参数。

对于使用 Starlette 路径转换器的路由，路径规则本身还可能包含类型转换或匹配约束。

但在 FastAPI 的常见写法中，仅仅把处理函数的参数声明成 `int`，并不意味着路由一定会在匹配阶段拒绝所有非数字路径。

这里涉及路由匹配与参数验证的区别。

### 3. 路由匹配和参数验证不是一回事

考虑：

```python
@app.get("/users/{user_id}")
async def get_user(user_id: int):
    return {"user_id": user_id}
```

如果客户端访问：

```text
/users/123
```

框架会匹配 `/users/{user_id}`，提取路径参数 `user_id`，再根据函数的类型声明将它解析成整数。

最终，`get_user()` 接收到的 `user_id` 是 `int` 类型，而不是 URL 中的原始字符串。

如果客户端访问：

```text
/users/abc
```

在这个普通 FastAPI 路由中，路径模板仍然能够匹配。

但 `abc` 无法通过整数参数验证。

因此，框架会返回请求验证错误，默认通常是 HTTP 422，而不是把它当成路径不存在。

这说明路由匹配与参数验证虽然相互关联，却属于不同的处理步骤。

**路由匹配解决的是由哪个接口处理请求，参数验证解决的是请求提供的数据能否满足这个接口的参数要求。**

这个区别有助于解释为什么有些错误返回 404，有些错误却返回 422。

## 六、路由匹配以后发生了什么？

路由匹配成功，并不意味着框架会立刻执行接口函数。

通常还需要处理请求参数、依赖注入和中间件等机制。

这些机制共同构成了从 HTTP 请求到业务函数调用之间的执行过程。

### 1. 参数从哪里来？

FastAPI 可以从 HTTP 请求的多个位置提取参数。

路径参数来自 URL 的路径模板。

查询参数来自 URL 中 `?` 后面的查询字符串。

请求头来自 HTTP Headers。

请求体则需要根据相应内容类型和接口声明进行读取、解析与验证。

例如：

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/users/{user_id}")
async def get_user(
    user_id: int,
    detail: bool = False,
):
    return {
        "user_id": user_id,
        "detail": detail,
    }
```

当客户端访问：

```text
/users/123?detail=true
```

FastAPI 会根据路由定义和函数参数声明，提取 `user_id` 和 `detail`。

其中，`user_id` 来自路径，`detail` 来自查询字符串。

经过验证后，框架调用处理函数，传入整数 `123` 和布尔值 `True`。

如果请求体使用 Pydantic 模型声明，FastAPI 还会借助 Pydantic 对数据进行解析和验证。

因此，HTTP 请求中原本以字节、字符串等形式存在的数据，可以在进入业务函数之前转换为 Python 中的相应数据类型。

这种处理降低了业务代码直接操作原始 HTTP 报文的必要性。

### 2. 依赖注入发生在什么阶段？

FastAPI 还支持通过 `Depends()` 声明依赖。

例如：

```python
from fastapi import Depends


def get_current_user():
    return {"id": 1, "name": "Alice"}


@app.get("/profile")
async def profile(
    user: dict = Depends(get_current_user),
):
    return user
```

这里的 `get_current_user()` 不需要在路由函数内部手动调用。

FastAPI 会分析接口的依赖关系，并在执行路径操作函数之前完成依赖求解。

真实业务中，依赖可以用于获取数据库会话、验证身份、提取请求上下文等操作。

但依赖注入与路由匹配不是同一个机制。

通常需要先确定请求命中了哪个路径操作，才知道这个路径操作声明了哪些依赖，以及应该如何求解。

同时，依赖自身也可能存在子依赖，或者包含需要进一步解析的请求参数。

因此，不能把整个处理过程机械地理解为“所有参数先验证完毕，然后再统一执行依赖”。

实际上，参数提取、验证和依赖求解之间存在关联，框架会根据已构建的依赖关系进行处理。

### 3. 中间件为什么能够在接口前后执行？

除了路由和依赖，Web 框架还支持中间件（Middleware）。

中间件用于在请求进入业务处理逻辑之前，或者响应离开应用之前，执行一些通用操作。

例如，记录请求耗时：

```python
import time

from fastapi import FastAPI, Request

app = FastAPI()


@app.middleware("http")
async def record_time(request: Request, call_next):
    start = time.perf_counter()

    response = await call_next(request)

    elapsed = time.perf_counter() - start
    response.headers["X-Process-Time"] = str(elapsed)

    return response
```

这里的 `call_next(request)` 代表把请求交给后续处理链。

中间件先记录开始时间，再等待下游处理完成，最后修改响应头并返回响应。

因此，中间件通常具有一种包裹式的执行结构。

请求进入时，先经过外层中间件，再进入内部处理逻辑。

响应返回时，则沿着相反方向经过相应的中间件。

如果有多个中间件，它们就形成一个嵌套的调用关系。

但不是所有中间件都必须将请求交给后续路由。

例如，某个鉴权中间件可以在发现请求不合法时，直接返回错误响应，根本不执行后面的路由。

同样，中间件也不只是用于请求前后打印日志。

它还可以负责跨域处理、请求标识、访问控制、响应头修改等与具体业务接口无关的横切逻辑。

不过，中间件是否适合直接管理数据库事务，需要结合事务作用域、流式响应、依赖清理时机等因素判断，不能仅仅因为它位于请求外层就认为所有事务都应该放在中间件中。

## 七、接口函数是怎样执行的？

经过路由匹配和必要的请求处理以后，框架终于可以调用接口函数。

但在 FastAPI 中，接口函数又分为普通同步函数和异步函数。

例如：

```python
@app.get("/async")
async def async_endpoint():
    return {"mode": "async"}


@app.get("/sync")
def sync_endpoint():
    return {"mode": "sync"}
```

这两个接口都能够处理 HTTP 请求，但执行方式有所不同。

对于使用 `async def` 定义的路径操作函数，FastAPI 会通过异步调用方式执行它。

如果函数内部使用真正的异步 I/O 操作：

```python
user = await repository.get_user(user_id)
```

那么在等待数据库返回结果时，当前请求所对应的异步执行过程就可能暂停，让事件循环处理其他就绪任务。

对于普通 `def` 定义的路径操作函数，FastAPI 通常会通过线程池等机制执行同步函数，并异步等待其结果，避免直接在事件循环线程中执行可能阻塞的同步调用。

这也是前面几篇文章介绍的进程、线程与协程，在 Web 服务中真正产生联系的地方。

不过，还需要纠正一个常见误解。

使用 `async def` 并不代表接口一定更加高效。

如果异步函数内部直接调用同步阻塞的数据库驱动，或者长时间执行纯 Python 计算，那么仍然可能阻塞事件循环线程。

而普通同步函数虽然可以在线程池中执行，但线程池的工作线程数量也不是无限的。

因此，Web 框架能够支持异步，并不意味着每个请求都会自动变成非阻塞请求，更不意味着服务器具有无限的并发处理能力。

它只是在一定的运行机制下，为应用提供了管理并发请求的能力。

## 八、Python 对象如何变成 HTTP 响应？

当接口函数执行结束以后，程序通常会返回一个 Python 对象。

例如：

```python
return {
    "user_id": 123,
    "name": "Alice",
}
```

但客户端不能直接接收 Python 字典对象。

网络中传输的是符合协议要求的数据，而不是 Python 进程内存中的对象。

所以，框架还需要将返回值转换为 HTTP 响应。

### 1. 返回值与响应对象

FastAPI 会根据接口的返回值、响应配置和响应模型等信息，构造相应的响应。

对于普通字典，默认情况下通常会生成 JSON 响应。

如果接口声明了 `response_model`，框架还会按照模型定义处理返回数据，进行必要的验证和序列化。

因此，接口返回 Python 字典，并不意味着可以直接跳过响应处理过程。

例如，响应模型要求某个字段为整数，但实际返回了无法满足模型约束的数据，就可能导致响应验证失败。

这类错误与客户端请求参数验证失败不同。

客户端请求数据不合法，FastAPI 默认通常返回 422。

而服务端生成的响应不满足自身声明的模型，通常属于服务端程序错误，默认会导致 500 错误，而不是把责任归给客户端。

### 2. HTTP 响应的结构

对于 HTTP/1.1，一个普通响应可能长这样：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"user_id":123,"name":"Alice"}
```

第一行是状态行，其中包含 HTTP 版本、状态码和原因短语。

响应头用于描述响应内容和相关控制信息。

空行之后是响应体。

其中，`200` 表示请求处理成功，`Content-Type: application/json` 表示响应体采用 JSON 格式。

但并不是所有响应都必须包含响应体。

例如，204 状态码表示没有响应内容，而 HEAD 请求的响应也具有特殊的消息体规则。

对于流式响应，框架还可能分多次发送响应内容，而不是一次性将全部数据放入内存后再返回。

### 3. 响应什么时候真正发送给客户端？

前面介绍过 ASGI 的 `send()`。

框架通过 `http.response.start` 告诉服务器响应状态码和响应头，再通过一个或多个 `http.response.body` 事件发送响应体。

Web 服务器负责按照当前 HTTP 协议的规则，将这些信息编码并写入网络连接。

这里不能把接口函数 `return`、ASGI `send()` 返回和客户端完整收到响应当成同一个时间点。

接口函数返回，只表示业务处理产生了一个结果。

框架还可能需要进行序列化、响应包装以及其他处理。

服务器写入响应数据以后，数据仍然需要经过操作系统的发送缓冲区、网络传输和客户端接收过程。

而 ASGI `send()` 的完成，也不等于客户端应用已经读取和处理了全部响应数据。

因此，业务函数执行结束，与整个 HTTP 请求响应周期结束之间，仍然存在其他步骤。

对于流式响应，这种差别更加明显。接口可以先产生响应，再持续发送后续的数据块。

## 九、如果请求处理失败，会发生什么？

到目前为止，我们主要讨论请求成功的情况。

但实际 Web 服务还需要处理各种失败。

理解这些错误发生在请求生命周期的哪个阶段，比单纯记住 HTTP 状态码更重要。

### 1. 404、405 和 422 有什么区别？

假设服务端注册了：

```python
@app.get("/users/{user_id}")
async def get_user(user_id: int):
    return {"user_id": user_id}
```

如果请求是：

```http
GET /articles/123 HTTP/1.1
```

而应用中不存在能够匹配 `/articles/123` 的路由，那么框架通常返回 404 Not Found。

这表示请求没有找到对应的目标资源或路由处理。

如果请求改成：

```http
POST /users/123 HTTP/1.1
```

路径符合已定义的路由，但对应路由只允许 `GET`，则通常会返回 405 Method Not Allowed。

这表示目标路径存在相应处理规则，但当前 HTTP 方法不被允许。

如果请求是：

```http
GET /users/abc HTTP/1.1
```

路径模板可以匹配，但 `abc` 无法通过 `user_id: int` 的参数验证，FastAPI 默认会返回 422 Unprocessable Content。

可以看到，三个错误发生在不同的判断阶段。

404 主要涉及目标路由是否存在，405 涉及请求方法是否被支持，422 则是在路由已经匹配后，请求数据未能满足接口要求。

需要注意，这里讨论的是 FastAPI 的默认请求验证行为，422 并不是 HTTP 协议强制所有 Web 框架都必须采用的参数验证状态码。

### 2. 业务异常如何变成 HTTP 响应？

假设某个用户 ID 的格式合法，但数据库中没有对应用户。

此时路由能够匹配，参数也通过了验证，但业务层查询结果为空。

我们可以主动返回相应的 HTTP 错误：

```python
from fastapi import HTTPException


@app.get("/users/{user_id}")
async def get_user(user_id: int):
    user = await find_user(user_id)

    if user is None:
        raise HTTPException(
            status_code=404,
            detail="User not found",
        )

    return user
```

这里的 `find_user()` 表示项目中自行实现的异步查询函数。

`HTTPException` 不只是普通的内部计算错误，它携带了需要转换成 HTTP 响应的状态码和错误信息。

框架的异常处理机制可以捕获它，并生成对应的响应。

这也说明，404 不一定全部来自路由匹配失败。

业务逻辑同样可以主动返回 404，表达所请求的资源不存在。

### 3. 未处理异常会怎样？

如果接口函数抛出了没有被应用正常处理的异常，服务器通常会产生 500 Internal Server Error，表示服务端无法正常完成请求。

不过，这也有前提条件。

如果响应头和部分响应体已经发送，服务器就无法像尚未发送响应时那样，简单地重新生成一个全新的 500 响应。

此时可能需要关闭连接或终止相应的响应流。

所以，异常发生的时间点会影响服务器能够采取的处理方式。

此外，某些错误根本不会进入 FastAPI。

例如，请求报文本身违反了 HTTP 协议，服务器可能在协议解析阶段就拒绝请求。

如果前面存在反向代理，代理也可能在请求到达 Python 程序之前直接返回错误响应。

因此，并不是客户端收到的每个 HTTP 错误，都意味着 FastAPI 的某个路由函数执行失败。

## 十、如何把整个请求过程串联起来？

现在，我们重新考虑最开始的接口：

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/users/{user_id}")
async def get_user(user_id: int):
    return {"user_id": user_id}
```

假设客户端发送：

```http
GET /users/123 HTTP/1.1
Host: localhost:8000
```

如果连接尚未建立，客户端首先需要与服务器建立相应的网络连接。

连接建立以后，客户端将 HTTP 请求数据发送给服务器。

操作系统接收数据，Uvicorn 通过 Socket 和异步网络接口取得相应字节，并完成 HTTP 协议解析。

Uvicorn 随后构建这个请求对应的 ASGI scope，并通过 `receive`、`send` 等接口调用 FastAPI 应用。

请求进入 FastAPI 的处理链后，可能先经过相关中间件。

随后，路由系统根据 HTTP 方法和请求路径，匹配已经注册的 `/users/{user_id}`。

框架提取路径参数 `user_id`，验证并转换为整数，然后完成接口依赖求解。

接下来，FastAPI 调用 `get_user()`，得到：

```python
{"user_id": 123}
```

框架将结果转换为 JSON 响应，通过 ASGI 接口发送响应状态、响应头和响应体。

Uvicorn 再将相应数据写回网络连接，客户端最终接收并解析响应。

在这条路径中，Python 的异步执行机制贯穿其中，但它并没有改变 HTTP 的基本请求与响应语义。

异步改变的是服务器如何管理网络 I/O 和请求处理任务，使多个请求可以在等待期间共享执行资源。

而路由、参数验证和业务函数调用，则由 Web 框架负责组织。

## 十一、小结

回到文章开头的问题：为什么一个简单的 `@app.get()`，就能够对外提供一个 HTTP API？

因为它并不是独立完成全部工作的。

HTTP 协议定义请求与响应的语义。

操作系统提供网络通信能力。

Web 服务器负责接收数据、解析 HTTP，并将请求交给应用。

ASGI 定义服务器与 Python 异步应用之间的标准接口。

FastAPI 则通过路由、参数验证、依赖注入和响应处理机制，将一个 HTTP 请求转换成具体的 Python 函数调用，再把执行结果转换为 HTTP 响应。

其中最值得注意的是，**一次 HTTP 请求并不等于一次 TCP 连接，也不等于一个 Python 函数调用。**

它跨越了网络通信、协议解析、应用调用和业务执行等多个层次。

理解了这些边界，就更容易判断实际开发中遇到的问题究竟发生在哪里。

请求无法建立连接，通常需要先检查网络和服务器监听情况。

请求返回 404 或 405，需要检查路径与方法的匹配关系。

请求返回 422，则应该查看接口参数的声明与验证过程。

而接口响应缓慢，则可能涉及事件循环阻塞、线程池资源不足、数据库等待或者其他下游系统的瓶颈。

这些问题看起来都发生在一次 HTTP 请求中，但根本原因可能完全不同。
