前面的工具注册表能够统一管理本地 Python 函数，但实际项目里的业务能力往往分散在不同进程、语言和服务中。订单查询可能属于 Python Backend，文档搜索可能由单独的检索服务提供，文件操作还可能发生在用户电脑上。Agent 如果为每一种工具分别实现发现、调用和返回格式，接入成本会持续增加。

MCP（Model Context Protocol）提供了一套可互操作的能力交换协议。它让宿主程序用统一方式发现和访问外部工具、资源与提示，而具体业务逻辑仍由各自服务实现。本篇将从协议参与方开始，经过消息格式和版本生命周期，再使用 Python 的 FastMCP 编写 Server、Client，并把工具调用接入前面实现的 Agent。

需要特别注明版本边界：MCP 在 2026 年 7 月 28 日发布了新的 `2026-07-28` 协议修订版，移除了此前的协议级初始化握手和会话。大量旧教程仍基于 `2025-11-25` 或更早版本，介绍 `initialize`、`notifications/initialized` 和 `Mcp-Session-Id`。这些描述对旧版连接有意义，不能无条件用来解释新协议。实际 SDK 也可能为了兼容旧服务而保留这套流程。

## 一、Host、Client 与 Server 的关系

在 MCP 架构中，Host 是管理模型交互和外部能力的宿主应用，Client 是与某个 MCP Server 通信的协议客户端，Server 则负责暴露工具、资源或提示等能力。

一套 Agent 应用可以作为 Host，它内部可能管理多个 MCP Client，每个 Client 与对应 Server 建立逻辑通信关系。Host 还负责决定哪些能力可以展示给模型、哪些操作需要用户授权，以及工具返回的内容如何进入模型上下文。

这里需要区分 MCP Client 与模型客户端。调用大模型的 SDK 负责向模型服务发送推理请求；MCP Client 则负责向 MCP Server 发现或调用工具。它们都可能使用网络通信，但协议对象不同。一个 Agent 可以同时持有一个模型客户端和多个 MCP Client，再通过 Harness 把两者连接起来。

MCP Server 并不要求自己运行大模型。普通的文件系统工具服务只需验证路径并读取文件，数据库工具服务可以执行授权后的查询。反过来，某个 MCP Server 也可能自主调用模型或者内部实现更复杂的业务流程，这属于该服务的实现选择，而非 MCP 的必要条件。

## 二、Tools、Resources 与 Prompts

MCP 提供几类基础能力。Tool 是可以被调用的操作，通常具有名称、描述与输入 Schema；Resource 表示可供读取的内容或数据，用 URI 标识；Prompt 则提供服务端公开的可复用提示模板。它们使用不同的协议方法，不应统一理解成“可执行函数”。

例如库存 Server 可以提供 `get_stock(sku)` Tool，用于实时查询库存；还可以提供 `inventory://catalog` Resource，供 Host 读取库存系统的字段说明；也可以公开一份“如何核查库存异常”的 Prompt。模型是否会看到这些能力，取决于 Host 如何发现和提供它们。

在常见设计中，Tool 更适合作为模型请求的可执行能力入口；Resource 经常由宿主应用选择何时读取并放入上下文；Prompt 通常由用户或应用触发。这里描述的是典型控制方式，并不表示协议禁止其他编排方式。

工具返回结果可能含文本内容、结构化内容或其他内容块。特别是读取外部网页、文件或服务返回文本时，Host 应把它视为不可信数据，不能因为它来自 MCP Server 就允许它改变系统权限。


Host 负责与用户交互、决定可见能力、组织模型上下文和实施宿主侧权限策略。一个 Host 通常可以同时维护多个 MCP Client；各 Client 通过独立传输连接各自的 Server。Server 公开工具描述，并执行其自己的业务逻辑。一个 Server 不需要知道模型是哪一种，也不需要把外部模型 API 嵌入自己的实现。

假设订单 Server 和库存 Server 都提供 `get_status`。协议层允许它们各自使用这个名称，但 Host 把两者合并成同一模型工具集合时，就必须建立命名空间和确定路由。工具最终的真实身份由连接目标与 Server 内的工具名共同决定，仅把模型发来的 `get_status` 当作全局唯一名称会造成错调。

此外，MCP `tools/list` 得到的是 Server 所声明的能力集合，并不是对当前终端用户具有操作权限的证明。一个工具可以存在却在某次调用中因授权条件不足而拒绝；Host 与 Server 都需要在自己的信任边界内检查权限。

## 三、MCP 的消息格式与传输

MCP 的基础消息采用 JSON-RPC 2.0 风格。请求包含方法名和参数，响应通过相应的请求标识返回结果或错误。一个工具调用在逻辑上可以表示为：

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "get_stock",
    "arguments": {"sku": "SKU-1"}
  }
}
```

这段 JSON 主要用于解释 `tools/call` 的方法与参数。在 `2026-07-28` 版本中，实际请求还需要携带规定的 `_meta` 信息；通过 Streamable HTTP 发送时，也需要相应的协议版本和路由首部。不能把这个简化示例当作可直接发送的完整现代 MCP HTTP 请求。

传输方式回答消息怎样在进程之间流动。stdio 通过子进程的标准输入和标准输出交换协议消息，适合本地命令行工具与桌面应用。Streamable HTTP 适合通过 HTTP 部署远程服务，可结合 TLS、授权和基础设施路由。采用何种传输，并不改变 `tools/list`、`tools/call` 等协议能力的基本意义。

stdio 还有一个实际约束：服务端程序不要随意向标准输出打印调试信息，因为标准输出承载协议数据。日志通常应写到标准错误输出或其他日志系统。远程 HTTP 则要考虑身份认证、端点授权、Origin 校验和访问范围，不应把一个无认证的本地演示服务直接暴露到公网。

## 四、2026 年协议生命周期的变化

`2025-11-25` 等旧版本采用连接初始化流程：Client 发出 `initialize` 请求，双方协商协议版本和能力，完成初始化后再执行工具发现与调用。部分 HTTP 实现还使用 `Mcp-Session-Id` 维护协议级会话。

`2026-07-28` 将这项机制改为无协议会话的请求模型。请求自身声明协议版本和客户端能力；`server/discover` 可供客户端提前发现服务器能力，但不再是每次调用之前必须完成的握手。Streamable HTTP 中，`Mcp-Method` 以及需要时的 `Mcp-Name` 等首部为网关路由提供可见信息。

这项变化降低了协议层对黏性会话和共享会话存储的依赖，有助于普通 HTTP 基础设施处理水平扩容。但“协议无状态”不意味着业务无状态。浏览器自动化可能仍需要一个浏览器实例 ID，文件处理可能有任务 ID，库存预留则要保存操作结果。这样的业务状态应通过明确的资源标识、工具参数和后端存储维护。

协议版本与 SDK 版本必须分开。某个 SDK 可以同时支持新旧两种协议修订版；Client 可能先尝试现代发现方式，再回退到旧版握手。开发时应查阅实际安装的 SDK 文档，确认其协商规则，而不能根据“使用 FastMCP”就推断网络上必然发送某个版本的消息。


MCP 消息以 JSON-RPC 为基础，客户端请求有 `id`，服务端对该请求返回 `result` 或 JSON-RPC `error`。但工具逻辑内部也可能执行失败，此时协议仍可能成功完成 `tools/call`，而调用结果带有指示工具执行错误的字段。对 Host 来说，“RPC 请求被正确处理但库存不足”和“JSON-RPC 方法不存在或参数结构非法”属于不同的层面；连接中断则可能根本拿不到任何结果。

如果把这三类错误全部压成字符串 `ERROR` 交给模型，模型就无法可靠决定下一步。业务拒绝应有明确业务码，协议错误应保留其错误分类，网络中断需要按执行副作用重新判断是否可重试。MCP 不自动提供跨请求的业务事务与幂等语义。

在 `2026-07-28` 修订版中，请求不再先通过 `initialize` 与 `notifications/initialized` 完成独立的初始化阶段。现代请求需要携带协议版本和客户端能力信息，HTTP 传输还使用规定的协议版本与路由首部。客户端可以先调用 `server/discover` 获取服务器能力，也可以直接发送符合协议的新请求。

采用这种设计以后，不应把“协议层没有会话”解释为“工具不能有跨调用状态”。例如浏览器工具可以在创建实例时返回 `browser_id`，随后调用通过这个显式标识访问同一个浏览器状态；长任务可返回 `task_id`，以后用该 ID 查询进度。状态由业务应用明确拥有、持久化和清理，不依赖隐藏在某条连接上的协议会话。

不过新旧协议之间存在实际兼容成本。官方 SDK 和第三方 FastMCP 的版本支持不一定同步。一个新版本 SDK 可能仍默认使用旧握手模式；一个使用新协议的 Server 也不保证能让旧版 Client 无修改地连接。教程中应明确区分“规范要求”和“本示例安装的 SDK 当前默认行为”，避免将旧版代码运行成功误写为已经验证现代协议的所有特性。

## 五、用 FastMCP 实现 Server

下面以独立 `fastmcp` Python 包的 4.x 版本为例。它与官方 `mcp` Python SDK 是两个可以分别安装的项目；官方 Python SDK v2 也有自己的高层 Server API，不能直接把不同包的导入路径和版本升级说明混用。FastMCP 3.x 与 4.x 的默认协议协商行为存在差异，因此本文示例固定在 4.x 兼容范围内。

创建目录并安装：

```bash
uv init mcp-inventory
cd mcp-inventory
uv add 'fastmcp>=4,<5'
```

为了便于复现，保存下面的代码为 `server.py`：

```python

from fastmcp import FastMCP

mcp = FastMCP("Inventory Demo")
STOCK = {"SKU-1": 5, "SKU-2": 0}


@mcp.tool
def get_stock(sku: str) -> dict:
    """查询演示库存的可用数量，不修改库存。"""
    if sku not in STOCK:
        return {"found": False, "sku": sku}
    return {"found": True, "sku": sku, "available": STOCK[sku]}


@mcp.resource("inventory://catalog")
def catalog() -> str:
    """库存演示服务的数据字段说明。"""
    return "SKU 为商品编号，available 为当前模拟可用数量。"


@mcp.prompt
def check_inventory(sku: str) -> str:
    """提供库存核查提示模板。"""
    return f"查询 {sku} 的可用库存，再根据查询结果说明库存状态。"


if __name__ == "__main__":
    mcp.run(transport="stdio")
```

`@mcp.tool` 将函数作为可调用工具暴露，并依据参数与类型信息生成输入 Schema；`@mcp.resource` 将一份内容绑定到 URI；`@mcp.prompt` 公开一个可复用模板。三种装饰器声明的是 MCP 能力，而 `STOCK` 只是本地模拟数据，进程重新启动后也会重新初始化。

这里使用 stdio 运行方式，适合由 Client 启动为本地子进程。若准备远程部署，可以根据所使用 FastMCP 版本的文档配置 Streamable HTTP 传输、监听地址和认证。实际部署前应锁定依赖版本，因为独立 FastMCP 的文档可能同时包含尚未进入稳定发布的功能。

## 六、编写 Client 发现和调用工具

新增 `client.py`：

```python

import asyncio
from fastmcp import Client


async def main():
    async with Client("server.py") as client:
        tools = await client.list_tools()
        print("工具：", [tool.name for tool in tools])

        result = await client.call_tool(
            "get_stock", {"sku": "SKU-1"}
        )
        print("返回内容：", result)


if __name__ == "__main__":
    asyncio.run(main())
```

在项目目录运行 `uv run python client.py`。当前 FastMCP 的 Client 可按目标类型选择传输；传入本地 Python 脚本时，由客户端管理对应的本地进程和 stdio 连接。Client 负责协议消息发送、能力调用及响应解析，业务程序只需要使用 `list_tools()`、`call_tool()` 等接口。

这里打印整个结果对象，是因为工具返回值可能同时包含不同内容字段；应用应根据实际类型读取文本内容、结构化内容和错误状态，不应假定所有 MCP 工具都只返回一段字符串。

要验证 Server 的三种能力，可以在客户端进一步调用读取资源和获取 Prompt 的接口，具体方法签名以安装的 FastMCP 版本为准。Tool、Resource、Prompt 的对象类型不同，应用要分别决定怎样将它们提供给模型。


在开发 Tool 时，可以先验证发现和调用的语义，再验证具体传输。独立 FastMCP 的 Client 支持针对 FastMCP Server 实例的内存连接。假设前面的 `server.py` 可以正常导入，可以写一个简单测试：

```python
import asyncio
from fastmcp import Client
from server import mcp

async def verify():
    async with Client(mcp) as client:
        tools = await client.list_tools()
        names = {tool.name for tool in tools}
        assert 'get_stock' in names
        result = await client.call_tool('get_stock', {'sku': 'SKU-1'})
        assert not result.is_error
        print(result)

asyncio.run(verify())
```

该测试验证 Python Server 与 Client 之间的工具发现和调用，不证明实际的 stdio/HTTP 网络路径已经正确配置，也不证明 `2026-07-28` 全套线路协议已经经过互通测试。下一步应分别使用 stdio 和 Streamable HTTP 的部署方式进行端到端测试，再检查鉴权、错误处理以及多实例路由。

MCP Server 返回的工具定义通常有名称、描述与输入 Schema。Host 把它转换成模型提供商自己的 Function Tool 格式时，要处理模型接口支持的 Schema 子集、名称字符限制、描述长度、工具名称冲突与结果内容类型。这个适配过程不是简单地把 JSON 原样复制。

尤其是 `content` 与 `structuredContent` 等返回形式：模型接口可能期望文本或 JSON 字符串，而 MCP Tool 结果可能包含多个内容块。Host 应当根据业务约定保留结构化数据、错误状态及必要的来源标识，对二进制或大文件返回采用受控引用，不应默默丢弃有意义字段。它也必须继续校验工具参数，不能因为远端 Server 声明了 Schema 就把模型生成的参数视为可信。

## 七、怎样接入前面的 Agent

第四篇的 Agent 使用本地 `HANDLERS` 来处理模型调用。替换成 MCP 后，可以将原来的本地执行器改成一个异步工具适配器：初始化 MCP Client、获取工具列表、将每个可用 MCP 工具的名称和输入 Schema 转换成模型工具声明，然后在模型返回调用时通过 `client.call_tool()` 执行。

这个衔接过程可以写成如下伪代码：

```python

async with mcp_client:
    discovered = await mcp_client.list_tools()
    model_definitions = convert_to_model_tools(discovered)

    while within_budget():
        response = await call_model(model_definitions, history)
        if not has_tool_calls(response):
            return get_final_answer(response)

        for call in get_tool_calls(response):
            validate_call(call, discovered)
            result = await mcp_client.call_tool(call.name, call.arguments)
            history.append(to_model_tool_result(call.call_id, result))
```

这段代码是结构示意，并非完整可执行文件。实际实现需要在 `convert_to_model_tools` 中处理工具名称冲突、Schema 格式兼容及描述长度，在 `validate_call` 中执行授权和参数验证，还要将 MCP 返回的错误状态与内容块转换成模型接口接受的工具反馈格式。

如果连接多个 MCP Server，模型最终看到的工具名称应该有明确命名空间。假设订单 Server 和库存 Server 都提供 `get_status`，宿主应用可以暴露 `orders__get_status` 与 `inventory__get_status`，并维护映射关系，保证模型名称能够准确路由到具体的 MCP Client 和原始工具。

另外，Host 不应简单把所有外部工具全部发给模型。工具发现只是取得服务端能力，最终的工具可见范围还应由用户身份、任务上下文和权限策略共同确定。MCP Tool 的描述不会自动授予调用权限，服务端也必须做自己的鉴权。

前面的伪代码说明了转换关系，但仍然没有完成一项可观察的真实交互。我们可以进一步写出一个本地运行的桥接程序：启动 `server.py` 作为 MCP 子进程，发现它公开的工具，再使用 Responses API 让模型决定是否调用工具。这里的模型 Client 和 MCP Client 分别负责不同协议，宿主程序只负责在两者之间进行安全映射。

先安装模型 SDK：

```bash
uv add openai
```

保存为 `bridge_agent.py`：

```python
import asyncio
import json
import os

from fastmcp import Client as MCPClient
from fastmcp.exceptions import ToolError
from openai import AsyncOpenAI


async def main():
    llm = AsyncOpenAI()
    model = os.environ["OPENAI_MODEL"]

    async with MCPClient("server.py") as mcp:
        discovered = await mcp.list_tools()
        allowed = {tool.name: tool for tool in discovered}
        declarations = [
            {
                "type": "function",
                "name": tool.name,
                "description": tool.description or "",
                "parameters": tool.input_schema,
                "strict": False,  # 示例不假定 MCP Schema 满足模型严格模式限制
            }
            for tool in discovered
        ]
        history = [
            {"role": "developer", "content": "只依据工具结果回答库存问题。"},
            {"role": "user", "content": "查询 SKU-1 的可用库存"},
        ]

        for _ in range(6):
            response = await llm.responses.create(
                model=model,
                input=history,
                tools=declarations,
                parallel_tool_calls=False,
            )
            if response.status != "completed":
                raise RuntimeError(f"模型响应未完成: {response.status}")
            history.extend(response.output)
            calls = [x for x in response.output if x.type == "function_call"]

            if not calls:
                if not response.output_text:
                    raise RuntimeError("没有可交付的模型消息")
                print(response.output_text)
                return

            for call in calls:
                if call.name not in allowed:
                    payload = {"ok": False, "error": "UNKNOWN_TOOL"}
                else:
                    try:
                        args = json.loads(call.arguments)
                        if not isinstance(args, dict):
                            raise ValueError("工具参数必须为对象")
                        result = await mcp.call_tool(call.name, args)
                        payload = {"ok": not result.is_error, "data": result.data}
                    except (ValueError, ToolError) as exc:
                        payload = {"ok": False, "error": str(exc)}

                history.append({
                    "type": "function_call_output",
                    "call_id": call.call_id,
                    "output": json.dumps(payload, ensure_ascii=False, default=str),
                })

    raise RuntimeError("超过 Agent 的执行轮数")


if __name__ == "__main__":
    asyncio.run(main())
```

使用 `uv run python bridge_agent.py` 运行。需要提前设置 `OPENAI_API_KEY` 和可用的 `OPENAI_MODEL`。这个示例假定当前 FastMCP Client 返回的工具对象具有 `input_schema` 属性，并且用于本地 Server 的工具参数 Schema 能被目标模型接口接受。不同 SDK 版本或复杂 JSON Schema 需要单独的兼容转换，不能简单认为所有 MCP Schema 都可以无损地传给模型。

这段桥接程序解决了“模型声明的工具名如何变成一次真正 MCP 调用”的问题，但仍然只面向可信本地演示 Server。生产版至少还要加入基于用户身份的工具筛选、参数校验、授权、输出内容限制、远程认证和审计。由于只有一个 Server，此处直接使用原始工具名；一旦连接多个 Server，就要把 `(server_id, original_name)` 映射为模型可见的唯一名称。这里的 `strict=False` 只影响模型输出约束，绝不等于可以跳过执行器校验。


## 八、通信标准没有替业务建立事务

MCP 让工具发现和调用有了统一协议，却不会自动解决业务一致性。一次 `tools/call` 可以通过网络到达库存服务，如果它执行了数据库提交但响应丢失，客户端仍可能只观察到连接异常或超时。是否可以重试，取决于业务工具有没有稳定的操作标识和幂等处理，而不是取决于消息使用 JSON-RPC 还是 HTTP。

同样，MCP 工具可以输出成功状态，但 Host 应当清楚这个成功来自哪里。对纯查询而言，返回结构化数据就足以继续推理；对写入操作而言，还可能需要查询交易凭证、状态变化或外部事件。MCP 只定义协作接口，不替代 PostgreSQL 事务、服务端授权和运行时恢复机制。

远程 MCP 还引入了新的安全面。客户端需要验证服务器来源，避免任意远程服务访问本地敏感环境；服务端需要按用户或服务身份授权，避免把请求中自称的角色当成可信凭据；工具结果也可能包含恶意提示注入内容。对于文件系统、命令执行和网络请求等工具，必须进一步限制路径、主机、进程权限和资源使用。


通过 stdio 启动本地 Server 时，Host 通常对要执行的程序、环境变量和工作目录有直接控制权。远程 HTTP Server 则有独立的网络和身份边界，需要检查 HTTPS、服务端身份、访问令牌以及每个工具对目标资源的授权。开发工具如果提供便利的自动连接功能，也不能把任意来源的 Server 当作可信服务。

一个以 HTTP 暴露的工具若支持访问任意 URL，还必须考虑服务端请求伪造（SSRF）和内网地址探测；文件工具要防止目录穿越和符号链接逃逸；Shell 工具必须控制进程权限及运行资源。MCP 标准化了通信，没有替这些业务工具建立沙箱。

最后，任何 MCP Tool 返回的文本都可能包含针对模型的恶意指令。Host 要维持来源标识与指令层级，同时在工具执行器里限制敏感动作。对读取邮件、网页与文档的 Agent，提示注入是跨信任边界问题，不能仅依靠模型识别恶意文字来保证安全。

## 九、一个基础 Agent 系统到此完成

从前六篇到现在，我们已经依次建立了模型与 Agent 的职责划分、Function Calling 的数据结构、Agent Loop 的控制机制、本地最小实现、工具注册表以及 Prompt、Skill 和 Tool 的关系。MCP 则把外部能力接入从具体函数封装提升到可互操作的协议层。

这套基础系统仍然是短时间、单任务的实现。它没有可靠的任务队列，没有持久化检查点，也没有对长期上下文进行压缩与恢复。多 MCP Server 的动态管理、权限审批、工具故障恢复和执行轨迹记录也都需要额外工程设计。

这些并不是 MCP 协议本身应该包办的职责。下一专题讨论 Harness 时，我们将继续沿用相同的模型调用和工具协议，把 Agent Loop 放入可控制、可恢复和可观测的任务运行环境，而不重复发明底层通信与工具描述机制。
