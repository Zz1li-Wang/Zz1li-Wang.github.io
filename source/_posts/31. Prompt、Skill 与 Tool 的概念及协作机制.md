Agent 能够调用工具以后，开发者通常会遇到另一个问题：同一项复杂任务总要向模型解释步骤、约束和注意事项。把这些内容全部写入每一次请求的系统 Prompt，会增加上下文负担；把它们全部写成 Python 函数，又无法方便地表达需要模型阅读和判断的操作知识。

Prompt、Skill 与 Tool 因而经常一起出现。它们并不是三个同一层级的“插件类型”。Prompt 承载指令与上下文，Tool 暴露可执行能力，Skill 则把某类任务所需的说明和配套资源组织成可复用的材料。理解其区别，有助于把模型应当理解的知识和程序必须执行的操作分开。

## 一、Prompt 怎样影响模型行为

Prompt 是发送给模型的输入内容，可以包含用户目标、任务约束、上下文材料和输出格式要求。不同模型接口使用不同的消息角色或指令机制，通常会区分较高优先级的应用指令与普通用户内容。

Prompt 的作用是引导模型理解任务和输出，不是操作系统级别的强制策略。例如“不要删除文件”可以降低模型提出删除操作的概率，却无法代替执行器关闭删除权限。真正安全的做法是在工具层限制用户允许执行的动作，并在必要时要求人工确认。

还有一类常被称为 Prompt 的内容，是模板化的业务输入。例如合同审查说明、代码评审检查项或报告写作约束，可以通过模板变量生成具体任务指令。模板使提示内容可复用，但变量填充仍要避免将未经验证的外部文本提升为高优先级指令。

Prompt 不应承担所有程序逻辑。凡是可以由确定性条件验证的字段、日期和权限，最好交给代码处理。模型适合解释语义和不确定材料，程序适合执行可验证规则，两者各有边界。

## 二、Tool 提供行动能力

Tool 的特点是有一个真实执行端点。模型提出 `get_order` 调用，应用必须调用对应函数或远程服务，才能得到订单事实；模型提出 `send_email` 调用，也必须由实际邮件服务执行，才可能完成发送。

工具定义通常包括名称、参数 Schema、描述和返回数据。Schema 约束输入结构，服务端代码处理权限和副作用。Tool 可以独立于 Skill 存在：一个普通库存查询工具不需要额外的操作手册，也能被 Agent 调用。

但仅有工具也不意味着模型能可靠完成复杂任务。它可能不知道业务系统要求先查询状态才能修改，或者不知道失败时应当保留哪些证据。这部分面向模型的操作知识，可以通过 Prompt 或 Skill 提供。

## 三、Skill 组织可复用的操作知识

以 Agent Skills 的开放格式为例，一个 Skill 是含有 `SKILL.md` 的目录。该文件以 YAML Frontmatter 声明名称和描述，后面是 Markdown 指令正文。目录还可以包含脚本、参考资料和静态资源。

例如一个订单异常核查 Skill 可以采用如下结构：

```text
order-check/
├── SKILL.md
├── references/
│   └── status-codes.md
└── scripts/
    └── validate_report.py
```

`SKILL.md` 的最小内容可以写为：

```markdown
---
name: order-check
description: 核查订单交付异常。适用于订单迟延、库存缺口与交期分析。
---

先读取订单当前状态，再核对相关库存与材料信息。
区分工具返回的明确失败和暂时无法取得结果。
结论必须标出实际查询依据；缺失信息不得自行补造。
如需修改订单状态，先取得用户确认并调用已授权的业务工具。
```

这份文件提供的是“怎样完成某类任务”的操作说明，并没有声明一个新的数据库 API。即使 Skill 包含 `scripts/validate_report.py`，它也只有在运行环境允许、确实执行脚本时才会产生作用。文件内容本身不会自动获得执行权限。

规范要求 `name`、`description` 等元数据满足格式约束，还提供 `license`、`compatibility`、`metadata` 等可选字段。`allowed-tools` 在开放规范中属于实验性元数据，不应把它视为所有 Agent 实现都会强制执行的授权系统。权限仍必须由具体运行环境落实。


在 Agent 运行环境里，来自应用的高优先级指令、用户当前目标、技能说明、工具输出和外部文档通常同时存在。它们都以文本形式进入模型上下文，但不应拥有相同的控制权。特别是网页和数据库中的字符串属于任务材料，不得通过“请无视系统规则”这样的自然语言获得执行权限。

Skill 的 `SKILL.md` 也是一份内容材料。一个由可信开发者维护的 Skill 可以被宿主按预设方式加载成任务操作说明，但来自第三方仓库或用户上传的同名文件，不能只凭目录结构就获得高优先级指令地位。是否信任 Skill、是否允许执行其中脚本，应由宿主的安装、审查和权限机制决定。

再考虑一个很容易被忽略的区别：Tool 的参数 Schema 约束数据结构，Skill 的 Markdown 指令指导模型如何使用能力。前者可以在执行器中被严格校验，后者往往属于软性策略，仍有被模型误解或忽略的可能。因此，所有必须严格成立的权限与业务约束都应体现在工具实现或者宿主控制逻辑里。

## 四、为什么要按需加载 Skill

如果系统有几十种业务技能，把所有 Skill 的完整内容一次性放进模型上下文，不但浪费 Token，还会使不同技能的指令相互干扰。Agent Skills 推荐渐进式披露：启动时主要读取名称和描述，选中某个 Skill 后再读取详细说明，必要时再访问参考文件和脚本。

这一设计类似两级信息检索。第一层元数据帮助运行时判断某项任务可能用到哪些 Skill；第二层正文则给模型提供执行该任务所需的步骤、约束和额外材料。再往下才是具体参考资源，需要时加载即可。

按需加载有两个局限。首先，元数据如果不准确，相关 Skill 就可能无法被发现。其次，Skill 正文也是内容输入，可能过时、与系统当前权限不一致，甚至包含恶意指令。运行时必须清楚 Skill 的来源与信任级别，不能因为文件存放在约定目录里就无条件提升其权限。

对于用户上传的 Skill、第三方仓库或自动下载的技能，更需要限制读取路径、脚本执行和外部网络访问。Skill 本身是可复用的指令与资源集合，不是沙箱。真正的执行隔离需要由宿主程序完成。

假设希望实现一个最小 Skill 加载器，它可以只负责识别目录和读取元数据，不包含任何脚本执行能力。以 Python 3.12 和 PyYAML 为例：

```python
from pathlib import Path
import yaml


def read_skill(root: Path, name: str) -> tuple[dict, str]:
    # name 来自应用自己的候选目录，而非任意模型生成路径
    root = root.resolve()
    path = (root / name / "SKILL.md").resolve()
    if not path.is_relative_to(root) or not path.is_file():
        raise ValueError("无效的 Skill 路径")

    text = path.read_text(encoding="utf-8")
    parts = text.split("---", 2)
    if len(parts) != 3 or parts[0].strip():
        raise ValueError("缺少 YAML Frontmatter")
    metadata = yaml.safe_load(parts[1])
    if not isinstance(metadata, dict):
        raise ValueError("元数据必须是对象")
    if not isinstance(metadata.get("name"), str):
        raise ValueError("缺少 Skill 名称")
    if not isinstance(metadata.get("description"), str):
        raise ValueError("缺少 Skill 描述")
    return metadata, parts[2].strip()
```

该程序只能证明目录和文档格式在最小约束下可读取，尚未实现 Agent Skills 的完整规范校验，也没有验证内容来源。`safe_load` 避免把 YAML 当作任意 Python 对象构造指令，路径解析和目录约束减少越界读取风险，但这些措施不能使任意第三方 Skill 自动可信。后续真正激活技能时，运行时还要决定该正文以什么信任级别进入上下文，脚本是否允许执行，以及执行过程如何受限。

此外，`description` 是影响技能检索的重要元数据。一个“帮助完成所有任务”的宽泛描述几乎无法给检索器提供区分能力。更准确的描述应写清适用任务、输入材料与输出目标；而正文需要写出处理顺序、异常分支及验收标准。Skill 质量最终还需要通过实际任务的召回和执行效果验证，而不能仅检查 YAML 文件格式。

## 五、三者怎样共同完成任务

假设用户要求核查一份逾期订单。用户 Prompt 给出订单编号和目标；运行时通过 Skill 元数据判断应加载 `order-check`，再把它的核查流程送入模型上下文；模型根据当前信息选择 `get_order`、`get_stock`、`get_material_status` 等工具，执行器逐项校验并调用；工具结果返回后，模型依据 Skill 中的报告要求生成结论。

在这条协作关系中，Prompt 和 Skill 都影响模型如何理解任务，但来源和复用粒度不同。Tool 则负责与外部世界产生可观察交互。Skill 可以建议使用哪些 Tool，运行时仍必须从真实工具注册表中确定是否存在并且有权调用。

因此，不能用“给 Agent 装了一个 Skill”来证明它已经具有某种实际能力。只有当它拥有所需的工具、文件或计算环境，并且通过授权，才有可能执行对应操作。反过来，有了工具也不一定需要 Skill；固定流程中的工具完全可以由普通程序直接调用。


随着 Skill 增多，把全文全部塞进系统 Prompt 会引入相互冲突的操作说明，也会浪费上下文预算。渐进式加载通常先使用元数据，筛出候选 Skill，再读取相关 `SKILL.md` 正文，并按需要进一步读取 `references/` 下的材料或调用 `scripts/` 中的脚本。

这套过程里存在两个不同的正确率问题：检索准确率与执行准确率。某个 Skill 没有被召回，模型可能缺少完成任务所需的知识；错误 Skill 被召回，则可能把任务引向不适当的操作步骤。即便检索正确，模型也可能遗漏 Skill 中的某条约束，因此需要在可验证环节保留程序检查。工具可用性、Skill 可发现性和 Skill 的质量是三个独立维度。

Skill 还具有版本问题。用户开始任务时加载的是 v1 指令，执行中途文件被更新为 v2。对于短任务，可以将已加载内容作为当次运行快照；对于长任务，应记录引用的版本或内容散列，防止恢复时无意中把新旧指令拼在一起。这个问题和工具 Schema 更新类似，最终都指向一个结论：模型的上下文必须有可追踪来源。

`SKILL.md` 可以描述运行某个脚本，但描述本身不执行代码。宿主若允许通过 Shell Tool 执行 `scripts/validate.py`，便又引入了一个独立的权限层。脚本可能读取工作目录、访问网络、创建文件或者删除已有内容。因此，运行环境应限制工作目录、文件路径、环境变量、网络可达性和执行时间，并根据用户授权决定是否需要批准。仅仅将脚本放进名为 `scripts` 的目录不会建立沙箱。

对于第三方 Skill 的安装，应检查文件内容与依赖，固定来源版本，避免隐式自动更新；对于需要修改代码仓库的技能，还应使用版本控制和变更审查。Skill 的可复用性越高，越需要将“说明书是否可信”和“执行端是否有权限”分开管理。

## 六、Skill 与 MCP 的关系

MCP 核心协议用于交换工具、资源和提示等能力，Skill 则主要用于组织可复用的任务说明和资源。两者可以互相配合，但在核心协议中属于不同的抽象层。

一种架构可以把 Skill 文件放在 Agent 宿主应用的本地目录中，工具则通过 MCP Server 提供。另一种架构可能通过 MCP Resource 暴露某些说明文档，供宿主程序读取后构建上下文。但一个 MCP Resource 不会因为内容类似 `SKILL.md` 就自动成为宿主已安装的 Skill；是否支持技能发现、激活和脚本执行，要看宿主实现。

同样，MCP 的 `prompts` 能力与通用 Prompt 模板有关，但它并不等于 Agent Skills 标准。不同生态的“Prompt”“Skill”有各自的组织方式，讨论时应明确所指规范，避免只依据名称判断功能范围。

还要注意 `2026-07-28` 规范引入的可选 **Skills over MCP** 扩展。它允许支持该扩展的 Client 与 Server 通过 MCP 发现和传输技能材料，但这不是所有 MCP 实现都必须支持的核心能力，也不会让任意 Resource 自动成为已经安装并获得执行权限的 Skill。Host 仍需决定技能是否可信、是否激活、文件保存到哪里，以及其中的脚本能否执行。

从工程结构看，Skill 更靠近任务知识层，MCP 更靠近外部能力接入层。Harness 可以同时管理两者：决定何时加载哪份技能说明，也决定哪些 MCP 工具可见、哪些调用需要审批。这种划分有助于保持系统的职责清楚。

## 七、边界保持清楚，组合才能可靠

模型需要知道任务目标、操作规则与可用能力，但并非所有信息都应该交给它自由解释。Prompt 可以表达意图，Skill 可以复用操作知识，Tool 可以暴露受控执行端点；授权、状态验证和副作用控制必须落在真实代码和基础设施中。

下一篇进入 MCP 协议本身。我们将从 Host、Client、Server 的连接关系出发，研究它怎样声明和发现工具、如何传递参数与结果，并使用 Python 实现一个可供 Agent 接入的 MCP 工具服务。至此，这一专题关于模型、循环、工具与外部能力的关系将形成完整闭环。


可以把用户输入视为此次任务的目标，应用 Prompt 提供全局行为规范，Skill 提供任务领域的可复用操作知识，工具目录提供当前可执行的动作，执行器与业务系统负责最终授权与状态变化。MCP 核心能力可以承载工具、资源和 Prompt 的远程接入，可选的 Skills over MCP 扩展还可以标准化技能发现与传输；但协议不会自动完成 Skill 的信任判断、激活、代码执行或安全审批。

这几层没有必要强行合并为一个“能力包”。一份 Skill 可能使用多个本地或远程工具，一个 MCP Server 也可能服务许多不同 Skill。同样的 Tool 可用于不同工作流，而确定性业务流程甚至不需要模型或 Skill 就能直接调用它。将知识、协议、权限和执行拆开，才能让每一层独立升级和测试。
