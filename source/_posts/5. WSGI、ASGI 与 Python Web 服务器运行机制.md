前面几篇文章介绍了 Python 的并发机制、事件循环，以及一个 HTTP 请求从网络进入 FastAPI 的完整过程。

我们知道，FastAPI 并不直接负责监听端口和解析 HTTP 协议，而是通过 Uvicorn 这样的 Web 服务器接收请求。

不过，Python Web 开发中还有一些容易混淆的概念。

例如，Flask 通常使用 WSGI，而 FastAPI 使用 ASGI。部署 Flask 时，经常会用到 Gunicorn；部署 FastAPI 时，又会看到 Uvicorn、Gunicorn 和 UvicornWorker。

有时候，我们还会通过 `--workers 4` 启动多个 Worker。

那么，WSGI 和 ASGI 究竟是什么？Gunicorn 与 Uvicorn 有什么区别？Worker 是进程还是线程？一个 Worker 又是怎样同时处理多个 HTTP 请求的？

要理解这些问题，需要先弄清楚 Python Web 服务器与 Web 框架之间的关系。

## 一、为什么需要 WSGI？

### 1. Web 服务器与 Web 框架的职责

一个 HTTP 服务至少需要完成两类工作。

首先，程序需要建立网络监听，接收客户端发送的数据，并按照 HTTP 协议解析请求。

其次，程序需要根据请求路径和参数，执行对应的业务逻辑，生成响应。

这两类工作并不一定要由同一个组件完成。

Web 服务器主要负责网络通信、协议处理和请求调度。

Web 框架则主要负责路由、参数处理、中间件、依赖管理，以及业务函数的调用。

这样的分工很自然，但它也带来了一个问题。

如果服务器和框架由不同的开发者实现，那么它们之间应该怎样交互？

假设一个 Web 服务器提供自己的 Python 调用接口，另一个服务器又使用完全不同的接口。

那么，同一个 Web 框架就需要分别适配这些服务器。

反过来，服务器开发者为了支持多个框架，也需要为每个框架编写专门的适配代码。

随着框架和服务器数量增加，这种设计会产生大量重复工作。

为了解决这个问题，Python 社区在 2003 年提出了 WSGI。

WSGI 的全称是 Web Server Gateway Interface，即 Web 服务器网关接口。

它的目的很简单：**统一 Python Web 服务器与应用程序之间的调用方式，让符合规范的服务器和应用可以相互配合。**

2003 年的 PEP 333 最初定义了 WSGI，后来 PEP 3333 对其进行了更新，以适应 Python 3 等环境。

这里需要注意，WSGI 既不是一个 Web 服务器，也不是一个 Web 框架。

它是一套接口规范。

Gunicorn 可以实现 WSGI 服务器接口，Flask 可以提供 WSGI 应用接口，双方就能够通过这套规范进行交互。

因此，框架不需要知道服务器内部究竟怎样监听 Socket，服务器也不需要了解框架使用什么样的路由系统。

双方只需要遵守同一个调用协议。

### 2. WSGI 定义了怎样的接口？

WSGI 的核心接口非常简单。

一个 WSGI 应用是一个可调用对象，接收两个参数：

```python
def application(environ, start_response):
    ...
```

其中，`environ` 是一个字典，保存请求相关的信息。

`start_response` 是服务器提供的可调用对象，应用通过它声明响应状态和响应头。

应用最终返回一个可迭代对象，用于产生响应体的字节数据。

我们可以直接编写一个最简单的 WSGI 应用：

```python
from wsgiref.simple_server import make_server


def application(environ, start_response):
    path = environ["PATH_INFO"]

    body = f"Request path: {path}".encode("utf-8")

    start_response(
        "200 OK",
        [("Content-Type", "text/plain; charset=utf-8")],
    )

    return [body]


if __name__ == "__main__":
    with make_server("127.0.0.1", 8000, application) as server:
        server.serve_forever()
```

这里使用 Python 标准库中的 `wsgiref` 启动一个简单的 WSGI 服务器。

运行程序以后，访问：

```text
http://127.0.0.1:8000/users
```

就会得到：

```text
Request path: /users
```

整个过程可以这样理解。

服务器首先接收并解析 HTTP 请求，然后创建 `environ` 字典。

接着，服务器调用：

```python
application(environ, start_response)
```

应用从 `environ` 中读取请求信息，生成响应内容，再调用 `start_response()` 声明响应状态与响应头。

最后，应用返回响应体的可迭代对象，由服务器负责迭代并发送响应。

这里有两个细节。

首先，WSGI 的 `start_response()` 并不意味着响应头已经立即写入网络。具体发送时机仍然由服务器根据协议规范处理。

其次，应用返回的是字节串组成的可迭代对象，而不是直接返回 Python 字符串。

这种设计也允许应用通过生成器逐步产生响应数据。

不过，`wsgiref` 主要适合学习和测试 WSGI 接口，不是面向生产环境高并发部署的服务器。

### 3. WSGI 为什么采用同步接口？

WSGI 的设计与它所处的时代有关。

当时，典型的 Web 应用主要围绕 HTTP 请求与响应展开。

服务器接收一个请求，调用应用程序，然后获得相应结果。

对于这种处理模型，同步函数调用是一种容易实现、容易理解的接口形式。

WSGI 并不需要规定服务器必须使用一个进程，还是多个进程，也不要求只能使用一个线程。

它只规定服务器应该怎样调用应用，以及应用应该怎样返回响应。

因此，WSGI 的同步接口并不等于 WSGI 服务器只能串行处理所有请求。

服务器完全可以通过多个进程、多个线程或者其他并发机制，同时处理不同的 WSGI 请求。

但是，WSGI 的应用接口本身是同步调用模型。

应用通常通过 `wsgi.input` 读取请求体，通过同步函数调用和可迭代对象生成响应。

它没有提供一套像 `async/await` 那样的原生异步事件接口，让应用在同一个连接生命周期中反复接收和发送不同类型的异步事件。

这就形成了 WSGI 的一个重要边界。

它很适合传统的 HTTP 请求处理，但并不适合直接表达 WebSocket 这样的双向、长期交互的连接协议。

需要强调的是，WSGI 可以支持响应内容的逐步生成，也可以借助异步服务器或协作式运行机制提高并发能力。

所以，不能简单地认为 WSGI 不支持流式响应，或者只要使用 WSGI 就完全没有并发。

真正的限制在于它定义的应用接口及其执行语义。

## 二、ASGI 解决了什么问题？

随着 Web 应用的发展，服务器需要处理的通信模式逐渐变得复杂。

除了普通的 HTTP 请求，越来越多的应用开始使用 WebSocket、长时间保持的连接，以及需要持续发送数据的异步通信。

Python 本身也逐步建立了以 `asyncio`、`async/await` 为基础的异步编程机制。

这时，原来围绕同步 HTTP 请求与响应设计的 WSGI 接口，就不再适合直接表达所有这些运行方式。

于是，Python 社区提出了 ASGI。

ASGI 的全称是 Asynchronous Server Gateway Interface，即异步服务器网关接口。

它延续了 WSGI 分离服务器与应用的思想，但重新设计了双方之间的交互方式。

### 1. 从同步调用到异步事件

在 WSGI 中，应用接收请求环境信息和响应回调，并返回响应体的可迭代对象。

而 ASGI 3 定义的应用接口是：

```python
async def application(scope, receive, send):
    ...
```

这三个参数在上一篇文章中已经介绍过。

`scope` 描述当前协议作用域，例如 HTTP 请求或 WebSocket 连接。

`receive` 用于异步接收事件。

`send` 用于异步发送事件。

与 WSGI 相比，这种设计最重要的变化，不只是将普通函数替换成了 `async def`。

更重要的是，**服务器与应用不再局限于一次同步调用和响应迭代，而是可以在同一个协议作用域中持续交换异步事件。**

例如，对于一个 HTTP 请求，应用可以接收多个请求体事件，也可以发送多个响应体事件。

对于 WebSocket 连接，应用可以接收连接建立、客户端消息和断开连接等事件，也可以在连接存续期间多次发送消息。

因此，ASGI 不需要为不同通信模式重新设计一套完全独立的服务器调用接口。

不同协议通过各自的 `scope` 类型与事件格式表达具体语义。

这就是 ASGI 能够统一支持 HTTP、WebSocket 等协议的重要原因。

### 2. ASGI 为什么适合异步编程？

考虑一个需要查询数据库的 HTTP 请求。

在同步阻塞模型中，如果请求处理函数执行数据库查询，而数据库暂时没有返回结果，那么负责执行这段同步调用的线程通常需要等待。

如果服务器采用多线程模型，就可以让其他线程处理新的请求。

但如果服务器采用 ASGI，并且应用使用真正的异步数据库驱动，那么当前请求对应的 Task 可以在等待数据库结果时暂停。

事件循环随后可以执行其他已经就绪的请求任务。

当数据库结果准备好时，事件循环再恢复之前的 Task。

这一过程我们已经在第二篇文章中详细研究过。

因此，ASGI 与 `asyncio` 的结合，使服务器可以通过较少的操作系统线程管理大量等待 I/O 的请求。

但需要注意，ASGI 并不规定服务器内部必须使用某一种特定的事件循环实现，也不规定一个 HTTP 请求必须对应一个固定的操作系统线程。

它规定的是服务器与应用之间的异步接口。

具体怎样调度 Task、怎样实现 I/O 多路复用、是否使用线程池，属于服务器及其运行时的实现问题。

### 3. ASGI 是否完全取代了 WSGI？

没有。

WSGI 和 ASGI 主要区别在于接口模型，而不只是出现时间不同。

如果一个应用主要提供普通 HTTP API，使用大量同步数据库驱动和同步业务代码，那么 WSGI 仍然可以是一种合理选择。

如果应用需要原生异步 I/O、WebSocket 或复杂的长期连接处理，那么 ASGI 通常更加合适。

两者之间也存在兼容方案。

例如，可以通过适配层把 WSGI 应用包装为 ASGI 应用，让 ASGI 服务器运行已有的同步 Web 程序。

但这种转换并不会自动让应用内部的同步阻塞操作变成非阻塞操作。

适配层通常仍然需要借助线程等机制执行原有的同步代码。

因此，不能把使用 ASGI 服务器理解为整个应用已经完成异步化。

真正决定是否能够利用异步等待能力的，是从框架到具体 I/O 操作的执行链路是否能够正确协作。

## 三、Web 服务器启动以后做了什么？

前面讨论了 WSGI 和 ASGI，但它们都只是接口规范。

真正接收客户端连接、执行应用程序的，是具体的 Web 服务器。

以 Uvicorn 为例：

```bash
uvicorn main:app --host 127.0.0.1 --port 8000
```

这个命令启动以后，服务器究竟做了什么？

### 1. Socket 监听

Web 服务器首先需要为指定地址和端口建立监听机制。

对于典型的 TCP 服务器，底层涉及 Socket 的创建、地址绑定和监听等操作。

操作系统负责维护相应的网络连接状态。

当客户端发起连接时，操作系统的网络协议栈处理连接建立过程，服务器随后通过相应接口取得可用于通信的连接 Socket。

之后，服务器才能读取客户端发送的 HTTP 数据。

不过，服务器不会只是在 Socket 上无限读取数据，然后直接把结果作为 Python 字符串交给应用。

它还需要处理 HTTP 协议解析、连接生命周期、超时以及请求任务调度等工作。

对于异步服务器，这些工作通常与事件循环相结合。

### 2. 事件循环与网络 I/O

上一篇文章介绍过，事件循环能够借助操作系统的 I/O 事件机制，同时管理多个网络连接。

对于 Uvicorn，服务器会在相应的运行环境中建立事件循环，并使用 HTTP 协议实现处理网络数据。

在 Linux 等平台上，事件循环可以使用 `epoll` 等 I/O 就绪通知机制。

当连接有数据可读时，事件循环安排相应的协议处理回调。

服务器根据协议状态解析请求，并在适当的时候调用 ASGI 应用。

对于一个典型的 HTTP 请求，Uvicorn 可以创建相应的异步任务，执行：

```python
await app(scope, receive, send)
```

这里的 `app` 就是 FastAPI 或其他符合 ASGI 规范的应用对象。

需要注意，这段代码主要表达调用关系，并不是 Uvicorn 内部实现的逐行还原。

在实际运行时，Uvicorn 还需要管理协议状态、请求任务、连接关闭和异常处理等工作。

当应用执行异步数据库查询时，当前请求任务可能在 `await` 处暂停。事件循环随后就有机会处理其他已经就绪的网络事件或请求任务。

所以，一个事件循环线程并不需要等某个请求完全处理结束，才能开始处理下一个请求。

但这也不意味着服务器真的同时执行了多个 Python 计算任务。

在通常的单线程事件循环中，某一时刻仍然只有一个 Task 在这个线程中执行 Python 代码。多个 Task 之所以能够并发，是因为它们可以在等待 I/O 时主动暂停，让出执行机会。

因此，**异步 Web 服务器的并发能力，主要来自对 I/O 等待的有效组织，而不是单个线程突然具有了更强的计算能力。**

### 3. Web 服务器需要管理哪些资源？

除了监听端口和处理 HTTP，服务器还要解决另一个问题：应用应该在什么时候启动，又应该在什么时候关闭？

例如，一个 FastAPI 应用可能需要在启动时初始化数据库连接池、Redis 客户端或者其他外部资源。

这些资源不能简单地在每个 HTTP 请求中重新创建，否则会增加不必要的连接和初始化成本。

但也不能假设所有资源都应该在 Python 模块导入时创建。

因为模块导入、操作系统进程创建和事件循环初始化，可能发生在不同的时间。

尤其在多 Worker 环境下，每个进程拥有独立的内存和运行时状态。

如果资源与某个事件循环绑定，就应该在适当的事件循环环境中创建和释放。

ASGI 为此定义了 Lifespan 协议。

它允许服务器通过 `lifespan.startup` 和 `lifespan.shutdown` 等事件，通知应用完成启动和关闭工作。

FastAPI 提供了相应的生命周期接口：

```python
from contextlib import asynccontextmanager

from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):
    print("应用启动")

    yield

    print("应用关闭")


app = FastAPI(lifespan=lifespan)
```

`yield` 之前的代码用于启动阶段，之后的代码用于关闭阶段。

在真实项目中，可以在这里初始化数据库连接池，并在应用关闭时释放连接。

不过，这里的生命周期不应该理解为整个 Web 服务集群只有一次启动和关闭。

如果服务使用多个 Worker 进程，那么每个执行 ASGI 应用的 Worker 通常都需要运行自己的 Lifespan 初始化与清理过程。

因此，数据库连接池等资源通常也是按 Worker 分别建立的。

这一点对后面的多进程部署非常重要。

## 四、Worker 究竟是什么？

现在，我们已经知道，一个 Uvicorn 进程可以运行事件循环，并通过协程处理多个并发 HTTP 请求。

那么，为什么还需要 Worker？

因为协程解决了 I/O 等待的并发问题，却不能自动让一个事件循环线程利用多个 CPU 核心同时执行 Python 计算。

而且，如果整个 Web 服务只有一个进程，那么这个进程一旦退出，服务就无法继续处理请求。

因此，实际部署时，经常会启动多个服务进程。

这些负责执行请求处理工作的进程，通常被称为 Worker。

但需要明确：**Worker 是服务器架构中的角色名称，不是操作系统规定的一种独立执行实体。**

在不同服务器实现中，Worker 可以采用不同的执行模型。

例如，Gunicorn 的常见 Worker 是操作系统进程，但不同 Worker 类型内部又可以使用线程或协作式任务调度。

所以，不能仅凭 Worker 这个词，就推断它一定是线程或者协程。

### 1. 一个 Worker 可以处理多少请求？

假设我们启动一个最常见的单 Worker Uvicorn 服务：

```bash
uvicorn main:app --workers 1
```

此时，一个 Uvicorn Worker 进程通常运行一个主要的事件循环。

如果请求处理函数使用真正的异步 I/O，那么事件循环可以管理多个并发请求任务。

因此，一个 Worker 并不等于只能处理一个请求。

我们可以通过下面的代码验证：

```python
import asyncio
import os
import threading

from fastapi import FastAPI

app = FastAPI()


@app.get("/work")
async def work():
    pid = os.getpid()
    thread_id = threading.get_ident()

    await asyncio.sleep(2)

    return {
        "pid": pid,
        "thread_id": thread_id,
    }
```

这个接口没有执行实际的数据库操作，而是通过 `asyncio.sleep(2)` 模拟异步等待。

如果同时发送多个请求，它们的等待时间可以发生重叠。

即使这些请求由同一个 Worker 进程和同一个事件循环线程处理，整体完成时间也可能接近两秒，而不是每个请求依次等待两秒。

这说明，一个异步 Worker 的并发能力，并不是由它拥有多少个操作系统线程直接决定的。

当然，真正的数据库查询还会受到连接池大小、数据库处理能力等资源限制。

另外，应用中的同步路径操作、线程池任务和其他后台线程，也可能使一个 Worker 实际包含多个操作系统线程。

所以，一个异步 Worker 通常以事件循环处理异步请求，并不等于它绝对只有一个线程。

### 2. 多个 Worker 如何工作？

如果希望启动四个 Worker，可以执行：

```bash
uvicorn main:app --workers 4
```

Uvicorn 会启动多进程管理机制，创建四个 Worker 进程来处理请求。

这四个 Worker 是相互独立的操作系统进程。

它们拥有各自的 Python 解释器运行环境、内存空间和事件循环。

当多个客户端请求到达时，不同连接或请求会根据服务器的连接分配与调度机制，由相应 Worker 处理。

需要注意，多个 Worker 并不意味着操作系统会严格地将每四个请求平均分配给四个进程。

请求实际落在哪个 Worker，可能受到监听 Socket 的组织方式、操作系统调度、连接复用和服务器实现等因素影响。

另外，同一个 HTTP/1.1 持久连接上先后发送的请求，通常会由持有该连接的 Worker 继续处理，而不是每个请求都重新随机分配。

因此，Worker 是请求执行资源的分组单位，而不是简单的按请求轮询分配器。

### 3. 多 Worker 为什么能够利用多核？

回到第一篇介绍的进程与线程。

在传统启用 GIL 的 CPython 中，同一解释器内的多个线程无法同时执行纯 Python 字节码。

但多个独立进程可以拥有各自的解释器运行环境。

因此，如果启动四个 Worker 进程，并且计算机具有足够的可用 CPU 核心，那么这些进程可以在不同核心上并行执行 Python 代码。

这使得多 Worker 部署能够突破单个传统 CPython 解释器的 CPU 执行限制。

不过，并不意味着启动四个 Worker 就一定能够获得四倍性能。

如果服务的瓶颈是数据库连接数、外部 API 响应速度、网络带宽或者磁盘 I/O，增加 Worker 未必能够解决瓶颈。

相反，过多的 Worker 还可能增加内存占用、连接数量和进程调度成本。

因此，Worker 数量应该根据实际工作负载和部署资源确定，而不是机械地按照 CPU 核心数套用固定公式。

## 五、Gunicorn 与 Uvicorn 有什么区别？

前面一直使用 Uvicorn 启动 FastAPI。

但在很多 Python 项目中，还会遇到 Gunicorn。

例如，传统的 Flask 服务可能通过 Gunicorn 运行，而一些 FastAPI 项目则会采用 Gunicorn 配合 Uvicorn Worker 的方式。

要理解两者的关系，需要先区分进程管理和请求执行。

### 1. Gunicorn 的 Master-Worker 模型

Gunicorn 最初主要面向 WSGI 应用。

它采用经典的 Pre-fork 进程模型。

通常会有一个主进程，负责管理多个 Worker 子进程。

主进程主要负责进程生命周期管理，例如创建 Worker、处理操作系统信号、监测 Worker 退出以及执行重启等操作。

真正的客户端请求处理主要由 Worker 完成。

这种架构有一个直接的好处：进程管理与请求处理可以分开。

如果某个 Worker 异常退出，主进程可以按照相应策略重新创建 Worker。

如果需要调整处理能力，也可以改变 Worker 数量。

这里需要注意，Master 进程通常不是一个负责逐条读取 HTTP 请求，再将每条请求交给 Worker 的业务分发器。

对于典型的 Gunicorn 部署，监听 Socket 可以由主进程创建，再由 Worker 继承和使用。

多个 Worker 在操作系统提供的连接接受机制下取得客户端连接。

因此，主进程主要管理进程和监听资源，不必理解每个请求的 HTTP 路径或业务内容。

### 2. Gunicorn 的 Worker 可以采用不同执行模型

Gunicorn 的一个重要特点，是允许选择不同的 Worker 类型。

最传统的是同步 Worker。

例如：

```bash
gunicorn main:app -w 4 -k sync
```

这里需要假设 `main:app` 是一个符合 WSGI 规范的应用，而不是普通的 FastAPI ASGI 应用。

`sync` 是 Gunicorn 传统的同步 Worker 类型。

在这种模型下，一个 Worker 通常一次处理一个 HTTP 请求。

如果请求处理过程中发生同步阻塞，当前 Worker 就需要等待，不能在同一个执行流中继续处理其他请求。

如果启动四个这种 Worker，就可以让四个进程分别处理请求。

不过，这种模型仍然可以满足不少传统 Web 应用的需求。

对于大量同步数据库操作或者既有 WSGI 项目，也不一定必须改成异步框架才能正常工作。

Gunicorn 还提供了 `gthread` 等 Worker 类型。

`gthread` 可以在一个 Worker 进程中创建多个线程，由线程处理并发请求。

例如：

```bash
gunicorn main:app -w 2 -k gthread --threads 4
```

这表示启动两个 Worker 进程，每个 Worker 配置四个工作线程。

在这种配置下，服务器可以通过多个操作系统线程处理同步请求。

但线程仍然受到当前解释器实现、GIL 状态以及共享资源同步等因素影响。

Gunicorn 也支持 Gevent 等协作式并发 Worker。

它们可以通过 Greenlet 和相应的 I/O 协作机制，实现另一种形式的并发。

这里需要特别区分，Gevent 的 Greenlet 与 Python `asyncio` 中的原生协程不是同一种运行模型。

二者都可以进行协作式任务调度，但使用的运行时机制和接口不完全相同。

所以，不能简单地认为只要使用了某种异步 Worker，就一定在使用 `asyncio`。

### 3. Gunicorn 能不能直接运行 ASGI？

可以，但需要注意版本。

早期 Gunicorn 主要提供 WSGI 服务器和进程管理能力。

因此，以前部署 FastAPI 时，经常需要结合 Uvicorn Worker，让 Gunicorn 负责进程管理，让 Uvicorn 负责 ASGI 请求执行。

但 Gunicorn 后来加入了原生 ASGI 支持。

2026 年 1 月发布的 Gunicorn 24.0 首次引入原生 ASGI Worker，当时标记为 Beta。

在 2026 年 2 月发布的 Gunicorn 25.1 中，官方已将 ASGI Worker 提升为稳定功能。

因此，在支持该功能的 Gunicorn 版本中，可以直接运行：

```bash
gunicorn main:app -w 4 -k asgi
```

这里的 `main:app` 可以是 FastAPI 应用。

Gunicorn 通过自身的 ASGI Worker 实现，运行异步事件循环并调用 ASGI 应用，不再必须依赖 Uvicorn Worker 才能执行 ASGI。

所以，“Gunicorn 只能运行 WSGI，Uvicorn 才能运行 ASGI”这个说法，已经不适用于当前版本。

更准确地说，Gunicorn 是具备多种 Worker 执行模型和进程管理能力的服务器，而 Uvicorn 是专门面向 ASGI 的服务器实现。

两者的能力存在交集，但架构侧重点有所不同。

### 4. Gunicorn 配合 Uvicorn Worker 又是什么？

虽然 Gunicorn 已经具备原生 ASGI Worker，但仍然可以使用 Uvicorn Worker。

这种方式下，Gunicorn 负责管理 Worker 进程，而每个 Worker 使用 Uvicorn 的 ASGI 服务器实现处理请求。

当前建议使用独立的 `uvicorn-worker` 包：

```bash
pip install gunicorn uvicorn uvicorn-worker
```

然后运行：

```bash
gunicorn main:app \
    -w 4 \
    -k uvicorn_worker.UvicornWorker
```

需要注意，以前常见的：

```bash
gunicorn main:app \
    -w 4 \
    -k uvicorn.workers.UvicornWorker
```

虽然在一些 Uvicorn 版本中仍然可以使用，但 `uvicorn.workers` 模块已经被官方标记为弃用。

因此，新项目更适合使用独立的 `uvicorn-worker` 包，或者根据需要直接采用 Gunicorn 原生 ASGI Worker。

这几种部署方式都可以运行 ASGI 应用，但其进程管理方式、HTTP 协议实现、可配置参数和具体运行时行为未必完全相同。

选择时不能只看它们能否成功启动 FastAPI，还应该关注所需的协议功能、稳定性、资源开销和实际负载表现。

## 六、Uvicorn 自带 Worker，为什么还需要 Gunicorn？

既然 Uvicorn 可以直接通过 `--workers` 启动多个进程，为什么还要让 Gunicorn 管理它？

答案并不是 Uvicorn 无法管理进程。

实际上，Uvicorn 已经提供内置的多进程管理功能。

它可以启动多个 Worker，监测子进程状态，并在适当情况下重启退出或失去响应的 Worker。

所以，如果只是希望在一台机器上运行多个 FastAPI 进程，直接使用 Uvicorn 就能够满足很多需求。

Gunicorn 的价值更多体现在它自身的进程管理功能、Worker 类型选择、信号管理以及其他部署控制能力上。

两者都可以作为多进程 Web 服务的运行基础，但不必在每个项目中同时引入。

### 1. Uvicorn 与 Gunicorn 的进程创建方式

这两个服务器还有一个值得注意的实现区别。

Gunicorn 的经典 Master-Worker 模型采用 Pre-fork 方式。

在 Unix 系统中，主进程可以通过 `fork()` 创建 Worker 子进程。

子进程会继承父进程的一部分运行状态和资源，并利用写时复制等机制减少初始内存复制成本。

而 Uvicorn 内置的多进程管理器使用的是 `spawn` 方式。

`spawn` 会启动新的 Python 解释器进程，再根据相应配置加载应用。

因此，它不会像传统的 `fork` 模式那样直接继承父进程中已经运行的完整 Python 解释器状态。

这种方式使 Uvicorn 的多进程管理能够在 Windows 上工作，也能减少某些继承复杂运行时状态带来的问题。

不过，两种进程启动机制都有自己的成本。

`fork` 需要注意继承资源与多线程状态的安全性。

`spawn` 则往往需要重新导入模块和初始化程序环境，启动成本可能更高。

在实际 Web 服务中，我们通常不需要直接处理这些底层差异，但它们能够解释为什么同样是四个 Worker，不同服务器的启动和资源初始化行为可能有所不同。

### 2. 多个 Worker 可以监听同一个端口吗？

这是理解多进程服务器时，一个很容易产生疑惑的问题。

既然每个 Worker 都是独立进程，那么它们为什么能够共同提供同一个端口上的 HTTP 服务？

原因在于，多个进程不一定需要分别创建相互冲突的监听端口。

在典型的 Master-Worker 模型中，可以先创建监听 Socket，再让多个 Worker 使用共享或继承的监听资源。

操作系统负责处理新连接的接入，Worker 在相应机制下获得连接并执行请求处理。

具体实现还可能使用其他 Socket 共享或端口复用机制。

因此，客户端看到的仍然是同一个服务地址和端口，而底层可以有多个 Worker 进程提供处理能力。

不过，这里的并发单位需要区分清楚。

监听 Socket 主要解决新连接如何进入服务器。

建立连接以后，后续的请求通常会沿着该连接对应的协议处理机制，由拥有该连接的 Worker 继续管理。

因此，不能把多 Worker 简单理解为每收到一个 HTTP 请求，主进程就会重新选择一个 Worker。

## 七、多 Worker 部署带来了哪些新问题？

多进程能够利用更多 CPU 核心，也可以提供一定程度的故障隔离。

但它同样改变了应用的运行环境。

最重要的变化是：不同 Worker 之间默认不共享普通 Python 内存。

### 1. 全局变量不再是全局共享状态

考虑下面的代码：

```python
from fastapi import FastAPI

app = FastAPI()

counter = 0


@app.get("/counter")
async def get_counter():
    global counter

    counter += 1

    return {"counter": counter}
```

如果只运行一个 Worker，并且暂时忽略其他并发安全问题，我们可能会观察到 `counter` 随着请求不断增长。

但如果使用四个 Worker：

```bash
uvicorn main:app --workers 4
```

每个 Worker 都有自己独立的 Python 内存空间。

因此，它们也分别拥有自己的 `counter`。

某个请求可能进入 Worker A，使它的计数器增加到 5。

下一个请求却可能进入 Worker B，而 Worker B 的计数器仍然是 2。

这样，客户端就可能观察到计数结果忽大忽小。

这不是 FastAPI 的路由错误，而是多进程内存隔离的正常结果。

所以，需要跨 Worker 共享的业务状态，不能简单地依赖 Python 全局变量。

通常应该使用数据库、Redis 或其他合适的共享存储机制。

### 2. 每个 Worker 都可能建立自己的连接池

再考虑数据库连接池。

假设每个 Worker 初始化时都会创建自己的数据库连接池。

如果一个 Worker 允许最多保持 10 个数据库连接，四个 Worker 就可能同时建立最多 40 个连接。

这里的具体连接数量还取决于连接池实现、溢出连接配置和实际负载。

但基本关系是明确的：**Worker 数量增加，可能使服务器对下游数据库和缓存系统的连接需求随之增加。**

这也是为什么配置 Worker 数量时，不能只考虑 CPU 核心数。

还需要考虑数据库最大连接数、连接池配置和其他下游系统的承载能力。

否则，增加 Worker 可能提高 Web 服务接收并发请求的能力，却让数据库更早达到连接上限。

### 3. 应用启动逻辑可能执行多次

前面提到，ASGI Lifespan 通常在每个 Worker 的事件循环环境中运行。

因此，如果将某些初始化操作放在 Lifespan 中，它们可能随着 Worker 数量增加而执行多次。

创建数据库连接池通常符合这种行为。

但如果在 Lifespan 中执行数据库迁移、注册全局定时任务或者执行只能完成一次的业务初始化，就可能出现重复执行的问题。

例如，四个 Worker 同时启动时，可能都会尝试执行同一项全局任务。

因此，必须区分进程内资源初始化与整个服务系统只应执行一次的操作。

前者适合放在 Worker 生命周期中。

后者通常需要独立的部署步骤、调度机制或者分布式协调措施。

Lifespan 提供的是应用运行时的生命周期通知，而不是分布式系统中的全局唯一执行保证。

### 4. Worker 退出以后，任务会怎样？

假设某个请求通过 `asyncio.create_task()` 创建了一个后台任务。

这个 Task 属于创建它的 Worker 所在的 Python 进程和事件循环。

如果 Worker 正常关闭，服务器可以尝试协调任务取消与资源清理。

但如果进程被强制终止，或者 Worker 意外崩溃，内存中的 Task 不会自动转移到其他 Worker 继续执行。

因此，多 Worker 并不等于后台任务具有可靠性保障。

即使服务器能够自动重新启动一个新的 Worker，也不能自动恢复旧 Worker 内存中的任务执行进度。

如果任务要求可靠执行、重试或故障恢复，就需要通过持久化队列、任务状态存储等机制建立独立的任务生命周期。

这与前一篇讨论的异步任务取消和生命周期管理，实际上是同一个问题在进程层面的延伸。

## 八、实际部署时应该如何选择？

现在，我们已经理解了 WSGI、ASGI、Uvicorn、Gunicorn 和 Worker 的基本关系。

可以重新考虑几个常见的部署场景。

对于已有的 Flask 等 WSGI 应用，如果业务主要使用同步接口，那么使用 Gunicorn 的同步或线程 Worker 是一种直接的方案。

对于 FastAPI 等 ASGI 应用，可以直接使用 Uvicorn。

如果需要多进程运行，可以使用 Uvicorn 自带的 `--workers` 参数。

在 Linux 等适用的部署环境中，也可以使用 Gunicorn 管理 Uvicorn Worker，或者使用 Gunicorn 的原生 ASGI Worker。

它们不是互相依赖的必选组件，而是不同的部署组合。

另外，如果系统已经使用 Docker 或 Kubernetes，也需要考虑容器级别的进程管理和副本扩展。

例如，在 Kubernetes 中，可以使用多个 Pod 副本分担请求，而不一定要在每个容器内部启动大量 Worker。

这不是说容器内一定只能有一个 Worker，而是需要从整个部署体系考虑进程数量、内存占用、服务扩展和故障恢复。

还有一个经常被忽略的问题：Web 服务器并不一定直接暴露在公网。

实际部署时，前面可能还会有 Nginx、负载均衡器或者 API 网关。

这些组件可以负责 TLS 终止、反向代理、流量控制和连接管理。

Python Web 服务器则专注于执行 Python 应用。

所以，一套完整的部署架构中可能同时存在网络代理、服务器进程管理器、HTTP 协议实现、事件循环和 Web 应用框架。

这些组件处于不同层次，不能简单地把它们理解成可以互相替代的同一种软件。

## 九、小结

回到文章开头的问题：WSGI、ASGI 与 Python Web 服务器之间究竟是什么关系？

WSGI 和 ASGI 首先是接口规范。

它们解决的是服务器如何与 Python 应用交互的问题。

WSGI 采用同步可调用对象和响应迭代器的模型，适合传统的 HTTP 请求处理。

ASGI 则使用异步可调用对象和事件消息，使服务器与应用能够在协议作用域内持续交换数据，从而适应异步 HTTP、WebSocket 等通信方式。

Uvicorn 是面向 ASGI 的 Web 服务器，它能够利用事件循环管理网络 I/O，并通过协程组织并发请求。

Gunicorn 则提供成熟的多进程管理能力和多种 Worker 执行模型。它既能运行传统 WSGI 应用，也能在当前版本中通过原生 ASGI Worker 或 Uvicorn Worker 运行异步应用。

而 Worker 只是服务器体系中负责执行工作的运行单元。

在常见的多进程部署中，一个 Worker 对应一个独立的进程，但它内部仍然可以使用线程、事件循环和协程处理请求。

因此，最重要的不是记住 Gunicorn 和 Uvicorn 应该怎样组合，而是理解整个系统存在不同的职责边界。

**WSGI 和 ASGI 规定服务器与应用如何通信；Web 服务器负责协议处理和运行调度；Worker 决定请求在哪些执行资源中运行；Web 框架负责将请求转换成业务函数调用。**

理解了这些边界，也就能够解释为什么同一个 FastAPI 项目可以使用不同的 ASGI 服务器部署，为什么一个 Worker 可以同时处理多个异步请求，以及为什么增加 Worker 数量并不一定能提高整个系统的性能。

下一篇文章，我们将继续讨论同步与异步 Web 框架的设计及性能差异。

重点不再是服务器如何启动，而是研究同步和异步两种执行模型，究竟怎样影响请求的吞吐量、延迟、线程资源消耗以及 CPU 利用率。
