在单体应用中，订单模块调用库存模块，可能只需要执行一次普通的 Python 函数。两个模块共享进程的运行环境，函数参数可以直接传递，结果也会沿着调用栈返回。

如果库存模块被部署成独立服务，情况就不同了。订单服务需要将参数转换为可以传输的数据，通过网络发送给库存服务，再等待对方处理并返回结果。原来由 Python 运行时完成的调用过程，现在必须依靠操作系统、网络协议和服务端程序共同完成。

这也是理解 RPC、gRPC 和服务间通信的起点。我们先不讨论如何把远程调用包装得像本地函数，而是看看一次请求在网络中究竟经历了什么。

## 一、从函数调用到网络通信

在同一个 Python 进程中调用 `inventory.reserve(order_id, quantity)`，调用方和被调用方都处于同一个虚拟地址空间。执行过程由语言运行时和操作系统调度，通常不需要经过网络协议栈。

跨进程以后，即使两个服务运行在同一台机器上，也不能直接读取彼此的普通内存对象。进程需要借助进程间通信机制交换数据。Unix Domain Socket、管道、共享内存以及 TCP Socket 都可以用于进程间通信。对于可以部署在不同主机上的服务，TCP/IP 是一种常见选择。

这里需要区分三个经常并列出现、实际却处于不同层面的概念。

Socket 是操作系统向程序提供的通信接口及其对应的端点抽象。Python 的 `socket` 模块允许程序创建 Socket、建立连接、发送和接收字节。Socket 并不等于 TCP：它也可以使用 UDP，或者在支持的平台上使用 Unix Domain Socket。

TCP（Transmission Control Protocol）是传输层协议，为两个端点提供可靠、有序、双向的字节流。应用向 TCP 连接写入字节，另一端按原有次序读取这些字节，至于这些字节代表 JSON、图片还是业务命令，TCP 并不关心。

HTTP（Hypertext Transfer Protocol）则规定了请求、响应及相关语义。方法、目标资源、状态码、首部字段和消息内容属于 HTTP 的概念。HTTP/1.1 和通常使用的 HTTP/2 建立在 TCP 之上；HTTP/3 则运行在 QUIC 之上，QUIC 通常使用 UDP 作为承载。因此，不能简单地把“HTTP 使用 TCP”当作所有 HTTP 版本都成立的规则。

对于一个典型的 HTTP/1.1 服务，请求大致沿着以下路径前进：

```text
客户端业务代码
    ↓
HTTP 客户端：构造请求消息
    ↓
Socket 接口：向操作系统写入字节
    ↓
TCP：管理连接、序号、确认与重传
    ↓
IP：将数据报送往目标地址
    ↓
网络与接收端协议栈
    ↓
服务端 Socket：读取字节
    ↓
HTTP 服务器：解析请求并分发给业务代码
```

这是便于理解的逻辑路径，真实网络还可能经过 DNS 解析、代理、TLS、负载均衡器等环节。特别是 HTTPS，HTTP 消息通常先由 TLS 加密，再通过底层传输连接传递。

IP 地址用于定位网络接口，端口号用于区分同一主机上的不同通信端点。服务端监听 `127.0.0.1:8000`，表示它只在本机回环地址的这个端口上接受相应连接；监听 `0.0.0.0:8000` 则通常表示监听本机所有 IPv4 接口。后者不等于一定可以从外网访问，防火墙、路由和云平台安全规则仍可能阻止连接。

## 二、TCP 怎样建立连接

在应用发送 HTTP 请求之前，通常需要先建立一条 TCP 连接。客户端调用 `connect()`，操作系统负责完成连接建立过程；服务端则提前执行 `bind()` 和 `listen()`，等待客户端连接。

TCP 正常建立连接时使用三次握手。假设客户端选择的初始序列号是 `x`，服务端选择的是 `y`，过程可以简化为：

```text
客户端                         服务端
  |                              |
  | -------- SYN, seq=x -------> |
  |                              |
  | <--- SYN+ACK, seq=y, ack=x+1 -|
  |                              |
  | -------- ACK, ack=y+1 -----> |
  |                              |
```

SYN 用于发起连接并同步初始序列号，ACK 用于确认接收到的序列号。经过握手，双方为这条连接建立必要的传输状态，例如序列号空间、接收窗口以及协商得到的选项。图中省略了 TCP 选项及其他细节；实际实现还需要应对丢包、重复报文和异常连接建立过程。

序列号非常重要。TCP 传送的是有序字节流，接收端根据序列号识别字节在流中的位置，发现缺失或重复的数据；发送端则结合确认信息和计时机制，决定哪些数据需要重传。

TCP 的可靠性也有边界。它能够在连接正常维持并完成传输的条件下提供有序、不重复的字节流，但连接可能中途失败。TCP 确认的是传输层接收状态，不能证明服务端应用已经读取这些字节，更不能证明数据库事务已经提交。

TCP 还需要解决发送速度的问题。接收端通过接收窗口实施流量控制，避免发送端持续发送超出其缓冲能力的数据；发送端同时通过拥塞控制，调整对网络路径施加的负载。二者的约束对象不同：流量控制关注接收端处理数据的能力，拥塞控制关注网络本身的承载情况。

这里还有一个容易忽略的区别。TCP 握手成功，表示传输连接已经建立，并不表示服务端业务程序能够立即处理请求。连接可能已经进入内核的已建立连接队列，应用仍未调用 `accept()` 取出它；即使应用取出了连接，也可能正在等待线程、协程或数据库资源。

因此，“能够连接到端口”和“服务可以正常完成业务请求”是两种不同的健康状况。

## 三、TCP 为什么没有消息边界

假设客户端连续执行两次发送：

```python
sock.sendall(b"hello")
sock.sendall(b"world")
```

直觉上，服务端似乎应该先读取到 `hello`，再读取到 `world`。实际情况并没有这样的保证。它可能一次读到 `helloworld`，也可能先读到 `hel`，接着读到 `loworld`，还可能出现其他划分方式。

因为 TCP 保证的是字节的顺序，不负责保留应用每次调用 `send()` 的边界。TCP 可以根据发送缓冲、网络条件和传输实现拆分或合并数据；接收端的 `recv(1024)` 也只表示最多读取 1024 个字节，并不表示读取一条完整的业务消息。

开发中常说的“粘包”和“拆包”，通常就是应用把字节流误当成独立消息后表现出来的问题。TCP 本身没有破坏消息，因为它从未承诺替应用保存这些消息边界。

要解决这个问题，应用必须定义协议。可以采用固定长度、特殊分隔符或长度前缀。长度前缀是一种常见方式：先发送一个固定长度的整数，表示后面的消息有多少字节，接收端按这个长度继续读取。

下面使用 Python 标准库实现一个简单协议。每条消息由 4 字节的无符号大端整数和其后的 UTF-8 内容组成。示例只监听本机地址，服务端一次处理一个连接上的一条消息，目的是观察 Socket 与消息边界，不涉及并发服务架构。

将代码保存为 `tcp_demo.py`：

```python
import socket
import struct
import sys

HOST, PORT = "127.0.0.1", 9000
MAX_SIZE = 1024 * 1024


def recv_exact(sock, size):
    data = bytearray()
    while len(data) < size:
        chunk = sock.recv(size - len(data))
        if not chunk:
            raise ConnectionError("连接提前关闭，消息不完整")
        data.extend(chunk)
    return bytes(data)


def recv_message(sock):
    (size,) = struct.unpack("!I", recv_exact(sock, 4))
    if size > MAX_SIZE:
        raise ValueError("消息超过大小限制")
    return recv_exact(sock, size).decode("utf-8")


def send_message(sock, text):
    body = text.encode("utf-8")
    if len(body) > MAX_SIZE:
        raise ValueError("消息超过大小限制")
    sock.sendall(struct.pack("!I", len(body)) + body)


def serve():
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as server:
        server.bind((HOST, PORT))
        server.listen()
        print(f"监听 {HOST}:{PORT}")
        while True:
            conn, _ = server.accept()
            with conn:
                conn.settimeout(5)
                message = recv_message(conn)
                send_message(conn, f"已收到：{message}")


def request():
    with socket.create_connection((HOST, PORT), timeout=5) as conn:
        send_message(conn, "创建订单")
        print(recv_message(conn))


if __name__ == "__main__":
    if len(sys.argv) != 2 or sys.argv[1] not in {"server", "client"}:
        raise SystemExit("用法：python tcp_demo.py server|client")
    serve() if sys.argv[1] == "server" else request()
```

分别在两个终端运行：

```bash
python tcp_demo.py server
python tcp_demo.py client
```

客户端应当打印 `已收到：创建订单`。

`struct.pack("!I", len(body))` 把消息的字节长度编码成 4 字节整数。`!` 表示网络字节序（大端），`I` 表示无符号 32 位整数。这里使用 `len(body)`，而不是字符串的字符数量，是因为 UTF-8 中一个字符可能占用多个字节。

`recv_exact()` 反复调用 `recv()`，直到取得指定数量的字节。如果对端正常关闭其发送方向，且接收缓冲区已无数据，`recv()` 会返回空字节串。此时仍未取得完整消息，协议就应当将其视为消息不完整，不能拿残缺内容继续执行业务。

`sendall()` 会持续尝试发送全部给定数据，或者在出错时抛出异常。它成功返回并不是远端业务处理成功的证明。另一方面，在 `sendall()` 报错后，程序也不一定能判断对端究竟接收了多少数据。

这个示例还设置了最大消息长度，避免客户端声明一个异常大的长度，导致服务端无约束地申请内存。虽然长度前缀解决了消息边界，但生产环境还需要考虑认证、并发、整体执行时限、异常连接和资源使用等问题。它是一份传输协议的最小演示，不是一套可直接上线的 RPC 服务。

## 四、HTTP 在字节流上增加了什么

既然 TCP 只负责传输字节，HTTP 就需要规定如何识别请求、解释请求，并确定响应何时结束。

以 HTTP/1.1 为例，一条最简单的请求可以写成：

```http
GET /orders/123 HTTP/1.1
Host: example.com
Accept: application/json

```

实际传输时，请求行和各个首部字段之间使用 `\r\n`（CRLF）分隔，首部和消息体之间用一个空行分隔。这里的排版只是为了方便阅读。

服务端可能返回：

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 2

{}
```

HTTP 的请求行说明使用什么方法访问哪个目标；状态行说明处理结果；首部携带与消息有关的元信息；消息体承载具体内容。至此，服务端能够根据协议判断收到的是 HTTP 请求，再交给应用中的路由处理函数。

HTTP/1.1 对消息体边界有明确规定。如果使用 `Content-Length`，它表示内容的**字节长度**；如果使用 `Transfer-Encoding: chunked`，消息体按照分块编码规则传输。对于某些响应，消息体边界也可以由连接关闭确定，但这种方式妨碍连接复用，并且连接异常中断时可能无法区分正常结束与内容不完整。协议还有一些特殊情形，例如 HEAD 响应和 204 状态码没有响应消息体，不能仅靠 `Content-Length` 机械判断。

这与前面设计的长度前缀协议具有相同的基本目的：让接收端能够在连续的字节流中识别完整消息。区别在于 HTTP 不仅规定消息格式，还规定请求方法、响应状态、首部字段以及缓存等语义。

HTTP 也没有规定服务端必须使用 FastAPI、Django 或某一种语言。框架处理的是更上层的工作：解析 HTTP 消息，匹配路由，验证参数，调用业务代码，再将返回值转换为 HTTP 响应。在框架下面，依然是协议实现和操作系统的通信能力。

HTTPS 又增加了一层安全通信机制。在通常的 HTTPS over TCP 场景里，客户端完成 TCP 连接建立后，还需要通过 TLS 握手协商安全参数并验证服务端身份，然后才在加密通道里传递 HTTP 消息。因此，一次 HTTPS 请求可能包含域名解析、TCP 握手、TLS 握手、HTTP 发送和业务处理等多个阶段；它们不应该笼统地被称作一次“网络耗时”。

## 五、一个端口为什么可以服务多个连接

初学 Socket 时，容易把端口号理解成一条连接独占的标识。实际上，监听端口和已建立的连接属于不同层面的对象。

服务端执行 `listen()` 后，拥有一个用于接受新连接的监听 Socket。客户端发起连接，服务端通过 `accept()` 获得新的已连接 Socket。服务端的监听 Socket 仍可以继续等待其他客户端，已连接 Socket 则负责与特定客户端交换数据。

对于典型的 TCP 连接，通常可以用四个值识别它：源 IP、源端口、目标 IP、目标端口。这常被称作 TCP 四元组。例如：

```text
127.0.0.1:51001  →  127.0.0.1:8000
127.0.0.1:51002  →  127.0.0.1:8000
```

两条连接的目标地址和端口相同，客户端源端口却不同，因此操作系统能够区分它们。客户端连接时使用的源端口往往由操作系统临时分配，称为临时端口（Ephemeral Port）。

这里也能看出，服务器同时维持多少条连接，与同时执行多少项业务操作不是一个数字。一个单线程服务器可以持有多个非阻塞连接，并借助事件循环在可读写的连接之间切换；一个采用阻塞式、逐连接处理方式的服务器，即使已经建立许多连接，也可能一次只能完成一个客户端请求。

`listen()` 的等待队列同样不等于应用中的任务队列。操作系统负责管理尚待应用接受的连接，应用是否及时 `accept()`，以及接受后如何调度业务处理，是后续的并发模型问题。不同操作系统在连接等待队列和 `backlog` 参数方面的实现细节也有所不同。

## 六、短连接、长连接与连接池

如果每次请求都新建 TCP 连接，客户端需要反复承担连接建立成本。对于 HTTPS over TCP，还可能涉及 TLS 握手。连接结束后，内核也需要维护相应状态。请求量上升时，频繁创建连接会增加延迟和系统开销。

因此，HTTP/1.1 默认支持持久连接（Persistent Connection），也就是常说的 HTTP 长连接。在双方允许的情况下，同一条 TCP 连接可以承载多次 HTTP 请求与响应；使用 `Connection: close` 等机制则可以表示不再复用连接。

这里的“长连接”并不意味着连接永远不会断开。服务端可以基于空闲时间或资源压力关闭连接，代理和负载均衡器也可能有自己的空闲连接限制。客户端即使把连接留在池中，也应当能够处理下次复用时发现连接已经失效的情况。

需要进一步区分连接复用与多路复用。

HTTP/1.1 的持久连接可以连续执行多次请求。协议也定义了流水线（Pipelining），允许在收到前一个响应之前发送后续请求，但响应仍有顺序约束，实际部署中并不常用。普通 HTTP/1.1 客户端通常不会在一条连接上独立并发处理许多请求，因此经常需要通过多条连接实现并发。

HTTP/2 在一条连接内部引入多个 Stream。不同请求和响应的数据帧可以交错传输，双方依据 Stream ID 归属到正确的请求。这才是通常所说的 HTTP/2 多路复用。不过 HTTP/2 常运行在 TCP 上，如果 TCP 中较早位置的字节因丢包尚未恢复，后续字节就不能按序交付给 HTTP/2 层，多个 Stream 仍可能一起受到影响。HTTP/3 使用 QUIC，在传输层提供独立的流，以减轻这种跨流阻塞问题。

连接池解决的是另一项工程问题：怎样让多个请求共享和管理一组可复用的连接。它通常负责控制连接数量、保留空闲连接、淘汰过期连接，并在连接不足时决定等待还是报错。

以 Python 的 HTTPX 为例：

```python
import asyncio
import httpx


async def main():
    limits = httpx.Limits(
        max_connections=100,
        max_keepalive_connections=20,
        keepalive_expiry=30.0,
    )
    timeout = httpx.Timeout(
        connect=2.0, read=5.0, write=5.0, pool=1.0
    )

    async with httpx.AsyncClient(limits=limits, timeout=timeout) as client:
        response = await client.get("https://example.com/")
        print(response.status_code)


asyncio.run(main())
```

`max_connections` 限制客户端连接池允许的连接总数；`max_keepalive_connections` 限制保留的空闲可复用连接数；`keepalive_expiry` 控制空闲连接在池中可保留的时间。这些参数控制客户端的资源使用，并不能要求服务端保持连接不关闭。

四类超时也各有作用。连接超时限制建立连接所等待的时间，读取和写入超时限制相应 I/O 操作等待下一段数据进展的时间，连接池超时限制取得连接所等待的时间。它们不构成整笔业务调用的统一截止时间，更不能保证服务端在客户端超时后停止执行。

在 FastAPI 等长期运行的服务中，通常应该把 `AsyncClient` 作为可复用资源，在应用生命周期内创建并在退出时关闭。如果每处理一个请求就创建一个客户端、结束后立即关闭，那么连接池也难以发挥复用价值。不过，同一客户端应在合适的并发上下文中共享，不能脱离事件循环和生命周期随意跨线程复用。

另一个常见混淆是 TCP Keepalive 与 HTTP Keep-Alive。前者是操作系统 TCP 层可选的探测机制，用于发现部分长时间无通信的失效连接；后者通常指 HTTP 层允许复用持久连接的行为。即使 HTTP 连接可以复用，也不意味着底层已经开启 TCP Keepalive；开启 TCP Keepalive，也不表示应用会自动重新执行失败的 HTTP 请求。

## 七、连接关闭与超时后的不确定性

TCP 连接是双向的，双方各有发送方向。正常关闭时，FIN 表示一方不再发送数据，但它仍可能接收对方随后发来的数据，这称为半关闭。双方完成关闭过程后，连接才真正退出通信。RST 则用于重置连接，通常意味着当前连接无法继续按正常方式使用。

连接关闭过程包含多个 TCP 状态，例如 `FIN_WAIT_1`、`CLOSE_WAIT` 和 `TIME_WAIT`。其中 `TIME_WAIT` 通常出现在执行主动关闭的一端，主要帮助处理连接结束后的延迟报文和必要的最后确认重传。它并不是客户端专属状态，也不能看到大量 `TIME_WAIT` 就直接断定存在连接泄漏。

更困难的是网络异常中断。假设订单服务向库存服务发送预留请求，库存服务完成数据库提交后，在响应返回之前连接断开。订单服务观察到的可能是读取超时、连接重置或响应体不完整，却无法仅根据这个异常断言“库存预留失败”。

这种不确定性与 TCP 的可靠传输并不矛盾。TCP 负责尽可能可靠地交换字节，但业务是否执行、数据库是否提交、响应是否成功返回，是更高层的问题。即使客户端的 `sendall()` 成功，甚至收到对端 TCP 的确认，也仍然缺少业务处理结果的证明。

实际排查时，可以按故障发生的阶段判断问题。

连接被拒绝，通常意味着目标地址和端口没有可接受连接的监听者，或者连接被明确拒绝。连接超时可能涉及路由、防火墙、目标不可达或握手过程没有完成。已经建立连接后发生读取超时，则要进一步检查服务端是否收到请求、是否排队、是否受数据库或下游服务阻塞。连接被重置说明 TCP 连接遭到异常终止，但重置发生的具体原因仍需结合服务端和中间网络设备分析。

在 Linux 上，可以使用下面的命令观察监听端口和 TCP 连接状态：

```bash
ss -lntp
ss -tan
```

`ss -lntp` 用于查看正在监听的 TCP Socket 及可用的进程信息（部分进程信息可能需要相应权限）；`ss -tan` 可以查看包括已建立、连接建立中和关闭过程中的 TCP Socket 状态。

对于 HTTP 请求，`curl -v` 能帮助查看连接建立、TLS 协商、请求与响应首部等细节：

```bash
curl --http1.1 -v https://example.com/
```

在多服务环境里，还需要把客户端耗时、服务端日志和链路追踪联系起来。客户端报告“读取超时”，最多说明它在限定时间内没有得到预期的读取进展；它不能直接替我们判断服务端是否提交了业务事务。后续讨论 RPC 的重试与幂等时，这一点会再次成为设计的关键。

## 八、从网络连接走向远程调用

现在我们已经能把一次跨服务请求拆开理解。Socket 提供通信接口，TCP 建立连接并传送有序字节流，HTTP 定义请求、响应及其边界，连接池管理通信资源，而业务系统负责解释请求并执行操作。

在这些层次之间，每一层只保证自己协议范围内的行为。TCP 连接成功不等于 HTTP 请求成功；HTTP 客户端成功发送请求不等于服务端事务提交；业务处理成功也不保证客户端最终收到了响应。区分这些保证，是设计可靠远程调用的基础。

下一篇将沿着这条路径继续讨论 RPC。当调用方希望像执行 `inventory.reserve()` 一样使用远程服务时，框架需要完成哪些工作？函数名与参数怎样转成协议消息？序列化、网络传输、服务端方法分发和异常返回如何衔接？理解了 Socket、TCP 和 HTTP 的职责，RPC 的内部机制就有了可以落脚的基础。
