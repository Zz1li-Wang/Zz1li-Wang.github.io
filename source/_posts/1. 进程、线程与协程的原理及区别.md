在 Python 开发中，我们经常会遇到进程、线程和协程这三个概念。

例如，部署 FastAPI 服务时，可以通过多个 Worker 进程处理请求；调用同步阻塞函数时，可以使用线程池；编写异步接口时，又会使用 `async/await` 和协程。

它们似乎都在解决同一个问题：如何让程序同时执行多个任务？

但进程、线程和协程并不是同一层面的概念。

进程主要负责提供独立的运行环境，线程负责在进程内部执行程序指令，而协程则让程序能够在用户态组织多个可以暂停和恢复的任务。

要理解三者的区别，我们需要先弄清楚一个更基本的问题：计算机究竟是如何同时运行多个程序的？

## 一、并发与并行

### 1. CPU 是如何执行多个任务的？

程序运行的本质，是 CPU 不断执行机器指令的过程。

在简化的执行模型中，一个逻辑 CPU 在某个时刻执行一个线程的指令流。如果计算机只有一个逻辑 CPU，那么两个需要持续计算的线程，就无法在同一时刻真正执行。

但我们日常使用计算机时，可以一边播放音乐，一边浏览网页，还能同时下载文件。

这些程序为什么能够一起运行？

原因在于，操作系统并不要求某个程序从开始到结束一直占用 CPU，而是通过调度机制，让多个任务共享 CPU 的执行时间。

操作系统内部有一个重要的组成部分，称为调度器（Scheduler）。

调度器负责决定哪些线程可以获得 CPU，以及当前正在运行的线程是否应该被其他线程替换。

对于采用抢占式调度的操作系统，一个线程即使没有主动放弃 CPU，也可能被操作系统暂停。

例如，线程 A 正在执行计算任务。经过一段时间后，操作系统决定让线程 B 运行，于是暂停线程 A，将 CPU 分配给线程 B。

稍后，线程 A 又可能重新获得 CPU，继续执行之前没有完成的计算。

由此，多个线程就可以在一个逻辑 CPU 上交替运行。

这种机制是操作系统实现并发的重要基础。

需要注意，现代 CPU 可能通过超线程等技术，在同一个物理核心上支持多个逻辑 CPU。这里讨论的是操作系统看到的逻辑 CPU，而不是处理器内部的全部硬件执行细节。

### 2. 什么是并发与并行？

现在可以进一步理解并发（Concurrency）和并行（Parallelism）。

并发指的是多个任务在一段时间内能够交替推进，而不要求它们在同一时刻真正执行。

在单个逻辑 CPU 上，操作系统通过任务调度，就可以实现多个线程的并发运行。

并行则不同。

并行要求多个任务在同一时刻真正执行。如果计算机具有多个可用的逻辑 CPU，那么两个线程就有机会分别运行在不同的执行资源上。

![文章配图](<Pasted image 20261013233631.png>)

所以，**并发描述的是多个任务的组织与推进方式，并行描述的是多个任务是否真正同时执行。**

两者并不是互相排斥的关系。

一个程序可以具有并发能力，却没有实际发生并行计算。也可以在多个 CPU 上同时执行多个并发任务。

我们平时所说的“同时运行”，经常没有严格区分这两种情况。但在讨论程序性能时，这个区别十分重要。

如果两个任务都需要大量 CPU 计算，那么只有真正的并行执行，才有机会显著缩短它们完成计算的总时间。

如果两个任务主要是在等待网络响应，那么即使只有一个执行线程，也可能通过并发提高任务的整体处理效率。

### 3. 任务为什么能够暂停和恢复？

前面提到，操作系统可以暂停正在执行的线程，再切换到另一个线程。

但这里有一个问题：线程执行到一半被暂停，为什么下次还能从原来的位置继续执行？

因为线程的执行过程具有相应的上下文（Context）。

其中包括程序计数器、CPU 寄存器状态、栈指针等信息。

程序计数器用于记录接下来要执行的指令位置，寄存器保存当前计算所需的部分数据，栈指针则用于定位线程的调用栈。

当操作系统需要切换线程时，会保存当前线程继续执行所必需的状态，并恢复目标线程的相应状态。

这个过程称为上下文切换（Context Switch）。

上下文切换存在一定的开销。

操作系统需要执行调度和状态切换工作。如果切换发生在不同进程的线程之间，还可能涉及虚拟地址空间切换。CPU 缓存、地址转换缓存等硬件状态的利用效率也可能受到影响。

因此，线程数量越多，并不意味着程序运行得越快。

如果大量线程频繁竞争有限的 CPU 资源，就可能将相当一部分时间消耗在调度和切换上。

不过，线程切换并不总是由时间片耗尽引起的。

线程也可能因为等待某个事件而主动停止运行。不同操作系统和调度策略对时间片的使用方式也不完全相同，不能把所有线程调度都理解成固定时间片的轮流执行。

### 4. 线程的运行状态

操作系统不只是决定哪个线程运行，还需要记录线程是否具备运行条件。

为了便于理解，可以将线程的状态简化为运行中、可运行和阻塞等待三种。

运行中表示线程正在 CPU 上执行。

可运行表示线程已经具备执行条件，只是暂时没有获得 CPU。

阻塞等待表示线程正在等待某个事件，暂时无法继续执行。

假设程序向数据库发送了一条查询请求。

在使用同步阻塞数据库接口的情况下，如果查询结果尚未返回，调用线程通常需要等待。

此时线程不能继续执行依赖查询结果的代码，但 CPU 不需要陪着它一起等待。

操作系统可以让这个线程进入等待状态，转而执行其他可运行的线程。

当数据库响应到达，相关的等待条件满足后，线程可以重新进入可运行状态，等待调度器再次分配 CPU。

这里有一个非常重要的区别：

**线程处于等待状态，不等于 CPU 也处于等待状态。**

实际上，现代计算机的大量并发能力，正是建立在这种计算与等待可以分离的机制之上。

需要说明的是，上述三种状态只是用于解释调度原理的抽象模型。不同操作系统内部还可能区分多种睡眠、停止和终止状态。

理解了 CPU 调度、上下文切换和线程状态，我们就可以进一步研究进程与线程的关系。

## 二、进程是什么？

我们编写的 Python 代码通常保存在一个 `.py` 文件中，但文件本身不是进程。

当操作系统启动 Python 解释器执行代码时，需要为程序准备运行环境，包括内存地址空间、文件描述符以及其他操作系统资源。

这样一个正在运行的程序实例，就是进程（Process）。

一个 Python 文件可以被执行多次，每次执行都可以形成独立的进程。

### 1. 进程为什么需要独立的内存空间？

操作系统需要同时运行很多程序，但这些程序不应该随意访问彼此的内存。

否则，一个程序写错内存地址，就可能破坏另一个程序的数据。

为了解决这个问题，现代操作系统引入了虚拟内存机制。

每个普通用户进程通常具有独立的虚拟地址空间。

程序访问的内存地址是虚拟地址，操作系统和硬件通过页表等机制，将这些地址映射到实际的物理内存。

因此，两个进程即使使用了相同数值的虚拟地址，也不意味着它们访问的是同一块物理内存。

这就是进程内存隔离的基础。

一个进程通常可以通过自己的虚拟地址空间访问程序代码、全局数据、堆、线程栈以及映射的共享库等内容。

这里的堆（Heap）主要用于动态分配内存，栈（Stack）则与函数调用和执行状态有关。

不过，独立的虚拟地址空间不代表不同进程一定占用完全不同的物理内存。

操作系统可以让多个进程共享只读代码页面，也可以通过共享内存机制，让不同进程映射相同的物理内存。

在某些进程创建方式下，还可以通过写时复制（Copy-on-Write）减少初始内存复制的成本。

所以，更准确地说，进程提供了独立的地址空间和受操作系统控制的资源访问边界，而不是绝对不共享任何资源。

### 2. 进程与 CPU 调度是什么关系？

前面一直在讨论线程调度，现在又引入了进程。那么 CPU 执行的究竟是进程还是线程？

这需要区分资源管理与执行调度。

进程主要提供资源环境，线程则是在这个环境中实际执行指令的执行流。

一个进程至少需要有线程来执行程序，也可以包含多个线程。

当我们说“操作系统让某个进程运行”时，在现代主流操作系统的普通执行模型中，实际获得 CPU 的是这个进程中的某个线程。

因此，不能简单地认为进程和线程都是完全相同意义上的 CPU 调度单位。

以 Linux 为例，内核使用任务结构描述可被调度的执行实体，普通进程和线程在内核层面共享不少基础机制，只是资源共享关系不同。

不过，我们没有必要把进程理解成纯粹的资源容器。进程还具有生命周期、权限和资源管理等方面的语义。

### 3. 进程之间如何通信？

进程隔离提高了程序运行的独立性，但也带来了通信问题。

假设进程 A 需要把计算结果交给进程 B。

由于两个进程默认不共享普通变量，因此不能直接通过修改自己的全局变量，让另一个进程读取到结果。

它们需要使用进程间通信（IPC）机制。

常见方式包括管道、消息队列、套接字和共享内存。

不同通信方式的成本也不相同。

通过管道或消息队列传输 Python 对象时，往往需要序列化和反序列化；共享内存可以减少部分数据复制，但又需要解决并发访问和同步问题。

因此，进程隔离并不是没有代价的。

在 Python 中，可以使用 `multiprocessing` 模块创建子进程。

```python
from multiprocessing import Process
import os


def worker():
    print(f"子进程 PID: {os.getpid()}")


if __name__ == "__main__":
    print(f"主进程 PID: {os.getpid()}")

    process = Process(target=worker)
    process.start()
    process.join()
```

运行后，主进程和子进程会打印不同的进程 ID。

`start()` 用于启动子进程，`join()` 则让主进程等待子进程结束。

需要注意，`join()` 只是调用方的等待操作，并不是启动子进程的必要步骤。

`multiprocessing` 在不同操作系统和 Python 版本中可能采用不同的进程启动方式，例如 `spawn`、`fork` 和 `forkserver`，这些方式对资源继承、启动成本等方面会产生影响。

多个进程可以被操作系统分别调度。如果存在多个可用的 CPU 核心，它们就有机会真正并行执行。

这也是传统 CPython 程序利用多核处理计算密集型任务的一种常见方式。

但是，创建进程、初始化解释器，以及进程之间传递数据都需要成本。实际开发中通常会使用进程池，避免反复创建和销毁进程。

## 三、线程是什么？

进程提供了程序运行的资源环境，但如果一个程序内部需要同时完成多个任务，是否必须创建多个进程？

当然不必。

一个进程可以包含多个线程（Thread），这些线程可以共享进程的大部分资源，并独立参与操作系统的调度。

因此，线程可以理解为进程内部的执行流。

### 1. 线程共享哪些资源？

同一个进程中的线程通常共享虚拟地址空间。

这意味着多个线程可以访问相同的程序代码、全局变量、堆内存以及进程打开的文件描述符等资源。

但每个线程也需要保存自己的执行状态。

例如，每个线程都有自己的程序计数器、寄存器状态和线程栈。

为什么需要独立的线程栈？

因为不同线程可能正在执行不同的函数调用。

线程 A 可能正在调用数据库接口，线程 B 则正在计算某个数据结果。它们的函数调用链不同，自然需要分别保存各自的执行状态。

需要区分的是，线程拥有独立的调用栈，并不意味着线程中的所有局部变量都与其他线程隔离。

如果某个局部变量保存了一个共享对象的引用，那么不同线程依然可以通过这个引用访问同一个对象。

例如，两个线程都持有同一个列表对象，即使引用分别保存在各自的局部变量中，对列表内容的修改依然可能互相影响。

这也说明，线程之间的内存共享和数据隔离不能简单地通过“全局变量”与“局部变量”来判断。

真正需要关心的是：这些变量最终是否引用了同一份可变状态。

### 2. 多线程为什么会产生竞态条件？

共享内存使线程间通信变得方便，但也带来了并发安全问题。

假设两个线程同时修改一个计数器。

```python
counter += 1
```

从代码上看，这只是一条语句。

但从执行语义上分析，它需要读取当前值、计算新值，再将结果写回。

如果某种执行过程允许两个线程在这些步骤之间交错运行，就可能发生这样的情况：

两个线程都读取到旧值 10，分别计算得到 11，最后又分别写回 11。

按照预期，两个线程各增加一次，结果应该是 12，但实际结果却是 11。

这种由于多个执行流的时序不同，导致程序结果出现非预期变化的问题，称为竞态条件（Race Condition）。

上述过程用于说明竞争的原理，并不表示在每一种 Python 版本和解释器实现中，这条具体语句都必然以这样的方式发生交错。

是否会出现竞争，需要结合操作本身、解释器实现和实际调度方式判断。

为了保证共享数据的一致性，程序通常需要使用锁（Lock）、条件变量、信号量等同步机制。

线程共享资源越多，数据交换通常越方便，但需要处理的并发安全问题也可能越复杂。

### 3. 线程是如何调度的？

对于现代操作系统中的普通原生线程，调度工作主要由操作系统完成。

线程创建以后，就可能被操作系统安排到不同 CPU 上运行。

如果多个线程竞争有限的 CPU 资源，调度器会根据相应的调度策略分配执行时间。

这种调度通常具有抢占式特点。

也就是说，线程并不一定需要主动执行某条“让出 CPU”的指令，才会被切换出去。

它可能在执行过程中被操作系统暂停。

这带来了一个重要结果：多线程程序不能随意假设多个线程的实际执行顺序。

同时，线程切换并不总是比进程切换快到可以忽略成本。

同一进程的线程切换通常不需要更换整个进程的虚拟地址空间，因此在某些方面具有优势。但实际成本还取决于操作系统、硬件缓存、地址空间状态以及运行负载。

不能简单地认为线程切换始终很轻量，或者进程切换一定十分昂贵。

相比于进程，线程的主要优势是共享资源方便，并且通常具有较低的创建与管理成本。

不过，如果程序需要维护非常多的线程，就仍然需要为这些线程分配栈空间、内核管理资源，并承担调度成本。

这就为协程的出现提供了一个重要背景。

## 四、协程是什么？

现在我们已经有了进程和线程。

操作系统能够通过线程调度实现并发，那么为什么 Python 还需要协程？

这里需要回到 Web 服务中一个十分常见的场景：等待 I/O。

假设一个 Web 服务需要同时处理大量请求。

每个请求都需要访问数据库，数据库查询完成后才能生成响应。

在传统同步阻塞模型中，当线程调用数据库接口后，如果数据库尚未返回结果，当前线程通常就无法继续处理这个请求。

为了同时处理更多请求，我们可以创建多个线程。

但如果大量请求都处于等待数据库或网络响应的状态，这些线程中的绝大多数实际上并不需要持续执行 Python 代码。

此时，是否一定需要为每个等待中的任务保留一个操作系统线程？

协程提供了另一种思路。

### 1. 协程的基本思想

协程（Coroutine）是一种能够在执行过程中暂停，并在之后恢复执行的程序结构。

它的关键特点是：**任务可以在尚未执行完成时，保留当前执行状态，并在适当的时候继续执行。**

普通同步函数通常沿着当前调用链持续执行，直到返回结果或者抛出异常。

协程则允许在执行过程中遇到某些等待操作时暂停，把执行机会交给其他任务。

等到等待条件满足后，再恢复执行。

这里需要特别注意，协程本身并不等于操作系统线程。

协程不需要被操作系统当作一个独立线程来调度。在 Python 的 `asyncio` 模型中，多个协程任务通常可以运行在同一个操作系统线程中。

这意味着，程序可以使用较少的线程，管理大量处于等待状态的并发任务。

不过，协程并不负责创造额外的 CPU 计算能力。

如果一个线程只有一个可用的逻辑执行资源，那么运行在这个线程中的多个协程任务仍然需要共享相同的 CPU 执行时间。

因此，协程首先解决的是任务组织和等待调度问题，而不是多核并行计算问题。

### 2. 协程为什么能够暂停和恢复？

这是理解协程最重要的一个问题。

我们先看一段 Python 代码。

```python
import asyncio


async def worker():
    print("任务开始")
    await asyncio.sleep(1)
    print("任务结束")


asyncio.run(worker())
```

与普通函数不同，使用 `async def` 定义的是协程函数。

调用协程函数时，Python 通常不会立即执行函数体，而是创建一个协程对象。

协程对象会保留执行所需的状态，使这段代码可以在后续被驱动执行。

对于 CPython 来说，协程的执行状态与其执行帧等内部结构有关，包括当前执行位置、局部状态以及尚未完成的调用关系。

这与操作系统保存线程的寄存器、栈指针等上下文不是同一回事。

协程暂停不需要把它变成一个独立的操作系统线程，也不需要由操作系统直接为每个协程保存一套线程调度上下文。

那么，究竟是什么让协程暂停？

答案与 `await` 有关。

在上面的代码中，协程执行到：

```python
await asyncio.sleep(1)
```

此时，`asyncio.sleep(1)` 表示一个异步等待操作。

如果等待无法立即完成，协程就可以暂停执行，把控制权交回负责驱动它的调度机制。

等到相应的等待条件满足，协程可以恢复执行，并从之前尚未完成的位置继续运行。

这样，函数不需要从头开始执行，也不需要始终占用一个正在运行的操作系统线程。

不过，`await` 并不等于无条件切换任务。

如果被等待的对象能够立即产生结果，那么 `await` 可能直接得到结果，当前任务也就不需要实际挂起。

因此，真正重要的是被等待对象的行为，而不是代码中是否出现了 `await` 这个关键字。

### 3. 谁来管理这些协程？

前面我们已经知道，操作系统负责调度线程。

那么，对于运行在同一线程中的多个协程，谁来决定接下来执行哪一个？

在 Python `asyncio` 中，这项工作主要由事件循环（Event Loop）与 Task 等对象配合完成。

这里需要区分三个概念。

协程对象表示一段可以被驱动执行、能够暂停与恢复的计算过程。

Task 用于管理协程的执行，包括调度、完成状态和取消等操作。

事件循环则负责运行就绪任务、处理回调和协调异步 I/O 等事件。

当一个 Task 执行到尚未完成的异步等待操作时，它可以暂停对应的协程，让事件循环继续处理其他已经具备运行条件的任务。

当等待结果准备好以后，事件循环再安排相应任务恢复执行。

因此，在通常的单线程事件循环模型下，多个 Task 不需要各自占用一个操作系统线程。

它们通过协作式调度，共享同一个线程的执行时间。


我们来看一个完整示例。

```python
import asyncio
import time


async def worker(name):
    print(f"{name} 开始")

    await asyncio.sleep(1)

    print(f"{name} 结束")


async def main():
    start = time.perf_counter()

    await asyncio.gather(
        worker("A"),
        worker("B"),
    )

    elapsed = time.perf_counter() - start
    print(f"总耗时: {elapsed:.2f} 秒")


asyncio.run(main())
```

运行结果通常类似：

```text
A 开始
B 开始
A 结束
B 结束
总耗时: 1.00 秒
```

两个任务都包含一秒钟的等待，但整体耗时接近一秒，而不是两秒。

原因在于，任务 A 执行到 `await asyncio.sleep(1)` 后，可以暂停执行。

事件循环继续执行任务 B。

当任务 B 也进入等待状态后，事件循环可以等待定时器到期等事件，而不需要让两个任务分别占用一个线程同步休眠。

等到相应等待结束，再恢复任务的执行。

这里并没有让两段 Python 计算代码在同一个线程上真正并行执行。

两个任务只是让各自的等待时间发生了重叠。

这正是并发与并行之间的区别。

### 4. 协作式调度存在什么限制？

协程调度通常依赖任务主动到达能够暂停的位置。

如果某个协程长时间执行计算，又没有让出控制权，事件循环就很难及时执行其他任务。

例如：

```python
async def worker():
    total = 0

    for i in range(100_000_000):
        total += i

    return total
```

虽然这个函数使用了 `async def`，但它内部没有能够让出执行权的异步等待操作。

在普通的单线程事件循环中，当它开始执行这段计算时，其他 Task 就无法依靠协程调度获得及时执行的机会。

同样，如果在协程中直接使用同步阻塞操作：

```python
import time


async def worker():
    time.sleep(1)
```

`time.sleep(1)` 会阻塞当前操作系统线程。

即使这段代码被放进 `async def` 函数中，它也不会自动变成异步操作。

对于运行在同一线程中的事件循环来说，这意味着其他任务也会受到影响。

所以，协程并不是在所有场景下都比线程更高效。

它的优势主要来自对等待型任务的组织方式，而不是 `async` 语法本身。

至于 `await` 在 Python 语言层面如何工作、Task 如何保存等待关系，以及事件循环如何通过 I/O 多路复用监视网络事件，我们会在下一篇文章中继续研究。

## 五、进程、线程与协程的关系

现在我们可以把三个概念放在一起理解。

进程提供程序的资源环境和隔离边界。

线程是在进程内部执行指令、参与操作系统调度的执行流。

协程则是在程序内部能够暂停和恢复的执行过程，可以借助运行时调度机制组织并发任务。

三者并不是同一个层级的技术，也不能简单地按照出现时间理解为依次替代的关系。

一个进程可以包含多个线程。

一个线程可以在运行事件循环时，交替执行多个协程任务。

同一个进程甚至可以在不同线程中分别运行事件循环，不过单个事件循环及其相关对象通常有自己的线程使用约束。

这意味着，进程、线程和协程完全可以在同一个程序中同时存在。

它们之间最重要的差异，体现在资源边界和调度机制上。

对于普通操作系统线程，操作系统能够在程序没有主动要求切换时抢占 CPU。

对于 `asyncio` 中的协程任务，事件循环通常采用协作式调度。当前任务需要执行到能够让出控制权的位置，其他 Task 才有机会在这个事件循环线程中运行。

但这并不意味着协程运行时完全不受操作系统调度影响。

执行协程的线程仍然是操作系统线程，仍然可能被操作系统抢占。

所谓协程的协作式调度，是指同一个事件循环内部的 Task 如何交替执行，而不是说操作系统不能中断运行协程的线程。

这里实际上存在两个不同层面的调度过程。

一个是操作系统负责的线程调度，决定哪个线程获得 CPU。

另一个是程序运行时负责的协程任务调度，决定当前线程在什么时候执行哪个协程任务。

理解这两个层次，就不会再把协程切换与线程上下文切换混为一谈。

在 Web 开发中，这些机制经常结合使用。

例如，一个 Python Web 服务可以启动多个 Worker 进程，以利用多个 CPU 核心。

每个 Worker 可以运行事件循环，通过协程处理多个并发请求。

如果某个请求必须执行同步阻塞操作，还可以把这部分工作交给线程池，避免直接阻塞事件循环。

因此，进程、线程和协程不是互相竞争的三种技术，而是可以根据实际任务特点进行组合的执行机制。

## 六、Python 的 GIL 限制了什么？

讨论 Python 的进程和线程时，还有一个无法绕开的问题：GIL。

GIL 的全称是 Global Interpreter Lock，即全局解释器锁。

需要明确的是，GIL 不是操作系统对线程的限制，也不是 Python 语言规范要求所有解释器必须具有的机制。

它主要涉及 CPython 解释器的实现。

### 1. 为什么 CPython 需要 GIL？

传统 CPython 使用引用计数等机制管理对象的生命周期。

多个线程如果同时操作同一个 Python 对象，就可能涉及引用计数更新、对象内部状态修改等共享数据访问问题。

GIL 是传统 CPython 用于保护解释器内部状态的重要机制之一。

在启用 GIL 的传统 CPython 解释器中，同一个解释器内通常只有持有 GIL 的线程能够执行 Python 字节码和访问受 GIL 保护的 Python 对象。

因此，即使一个进程创建多个线程，并且计算机具有多个 CPU 核心，这些线程也无法同时执行纯 Python 字节码。

这会限制 CPU 密集型程序使用多线程实现多核并行加速的效果。

但这里需要注意，GIL 与操作系统调度并不是一回事。

操作系统仍然可以调度不同的线程。只是线程即使获得 CPU，也可能因为无法取得 GIL 而暂时不能继续执行相关 Python 代码。

因此，GIL 是解释器内部的一项执行约束，而不是操作系统停止提供并行调度能力。

### 2. 为什么多线程仍然适合 I/O 密集型任务？

因为 Python 线程并不是在所有情况下都必须持续持有 GIL。

当 CPython 执行某些阻塞 I/O 操作时，通常会释放 GIL，让其他线程有机会执行 Python 代码。

一些原生扩展也可以在不需要操作 Python 对象的计算过程中释放 GIL。

因此，即使一个 Python 进程启用了 GIL，多线程仍然可以在许多 I/O 密集型任务中实现有效并发。

如果多个线程的大部分时间都在等待外部系统，那么它们没有必要同时执行 Python 字节码，也可以通过重叠等待时间提高整体吞吐量。

这就是为什么传统 CPython 的 GIL 并没有使多线程失去实际价值。

### 3. GIL 是否会一直存在？

从 Python 3.13 开始，CPython 已经支持可选的自由线程构建（Free-threaded Build）。

在这种构建方式下，可以禁用 GIL，使多个线程有机会在不同 CPU 核心上并行执行 Python 代码。

截至 Python 3.15，自由线程仍然不是常规 CPython 构建的默认执行模式。

另外，是否能够真正禁用 GIL，还可能受到运行时配置和第三方扩展兼容性的影响。

因此，不能再笼统地说“Python 多线程无法并行执行 Python 代码”。

更准确的说法是：

在启用 GIL 的传统 CPython 解释器中，同一个解释器内的多个线程无法同时执行 Python 字节码。

对于支持并实际关闭 GIL 的自由线程构建，则不存在这一相同形式的限制。

当然，取消 GIL 并不意味着所有多线程程序都会自动获得性能提升。

线程同步、共享对象竞争、内存访问以及任务本身的计算特点，依然会影响并行效率。

还需要注意，GIL 不是通用的线程安全保证。即使解释器启用了 GIL，涉及多个步骤的共享状态操作仍然可能产生竞态条件。

## 七、应该如何选择？

了解三种机制以后，就可以根据实际任务选择不同的并发方式。

首先需要判断任务主要消耗什么资源。

如果程序的大部分时间都在执行计算，那么它属于 CPU 密集型任务。

此时，性能提升通常依赖计算效率、算法优化，以及是否能够使用多个 CPU 核心真正并行执行。

在传统 CPython 中，多进程通常是一种有效的选择。

多个进程具有独立的解释器运行环境，可以分别在不同 CPU 核心上执行 Python 计算任务，而不需要竞争同一个解释器的 GIL。

当然，如果使用能够释放 GIL 的原生计算库，或者使用兼容的自由线程构建，多线程也可能实现有效的并行计算。

如果程序的大部分时间都在等待网络、磁盘或数据库响应，那么它属于 I/O 密集型任务。

此时，主要矛盾不是 CPU 的计算能力不足，而是大量任务无法持续执行。

多线程和协程都能够改善这种情况。

多线程适合需要执行同步阻塞接口的场景，尤其是已经具有大量同步代码和依赖库的程序。

协程则更适合能够通过异步接口表达等待过程，并且需要管理大量并发 I/O 任务的场景。

但也不能因此认为协程一定比线程快。

对于并发量不高的程序，线程池可能已经能够满足需求。

如果底层依赖库只提供同步阻塞接口，强行在外层添加 `async/await`，通常也不能真正改善其阻塞行为。

另外，协程不能自动解决 CPU 密集型计算造成的事件循环阻塞问题。

如果需要在异步 Web 服务中执行耗时计算，就可能需要借助进程池、能够真正并行计算的原生库，或者把任务交给独立的工作进程。

进程也不是越多越好。

进程创建、内存占用和进程间数据传输都有成本。如果任务非常短小，或者需要频繁交换大量数据，并行执行带来的收益就可能被额外开销抵消。

所以，真正需要考虑的并不是哪一种技术更加先进，而是任务的执行特点是什么，瓶颈出现在哪里，以及引入某种并发机制以后，是否能够降低这个瓶颈带来的成本。

## 八、小结

回过头来看，进程、线程和协程分别解决了不同层次的问题。

进程提供独立的运行环境和资源隔离。

线程让同一个进程能够拥有多个执行流，并由操作系统负责调度。

协程则让程序能够管理多个可以暂停和恢复的执行过程，在适合的运行时调度机制下，使大量等待型任务共享较少的操作系统线程。

理解三者时，最容易混淆的地方是把资源管理、任务调度和并行计算当成同一个问题。

事实上，它们是相互关联但并不相同的概念。

进程隔离主要影响资源共享与故障边界，线程调度决定 CPU 如何分配给执行流，而协程调度决定应用程序如何组织可以挂起的任务。

协程并没有取代线程，也没有绕开 CPU 调度。

它只是把一部分原本可能需要多个操作系统线程才能组织的并发等待任务，交给程序内部的调度机制处理。

理解了这一点，也就理解了 Python 异步编程的基本出发点。
