前四篇从模块、分层、设计原则到具体模式，一直围绕如何安排变化展开。到了复杂业务系统，技术结构已经清楚，却仍然可能无法准确表达业务。订单服务里有创建、审核、取消、库存确认和退款等方法，代码分层整齐，但谁也说不清“订单确认”究竟指提交、库存占用还是付款完成。

这样的困难发生在代码设计之前。团队对业务概念缺少共同理解，数据库字段便成了默认的交流语言；各种状态检查散落到 Service，新的调用入口又可能绕过旧规则。继续增加 Repository 或策略类，只会让错误的业务认识以更精致的形式保存下来。

领域驱动设计（Domain-Driven Design，DDD）从这里展开。它要求开发人员和业务人员共同建立模型，再让模型指导代码边界。Eric Evans 在 2003 年的同名著作中系统阐述了这一方法。理解它，最好沿着订单业务逐步变复杂的过程走，而不是先背下一套实体、聚合和领域服务的名词。

## 一、订单表背后的业务规则

假设系统里有一张订单表，包含订单编号、客户编号、订单状态和总金额；还有一张订单明细表，记录商品、数量和成交单价。

如果只从数据存储出发，我们可以很快设计出两个 ORM 类，再给它们编写新增、查询、修改和删除接口。这样的结构表达了数据如何存储，却没有充分说明这些数据允许怎样变化。

例如，草稿订单可以增加明细；提交后的订单不允许随意改变商品和价格；订单一旦被取消，就不能再进入待发货状态；订单里的成交单价必须保留提交时的金额，商品目录后来涨价也不应该改变这笔订单的历史价格。

这些规则无法从 `orders` 表拥有一个 `status` 字段这一事实中直接推导出来。业务真正关心的是订单处于什么阶段，以及哪些操作在当前阶段合法。

如果所有代码都能直接执行 `order.status = "CONFIRMED"` 或 `order.total_cents = 100`，数据库结构虽然清楚，业务约束却可能散落在路由、Service、定时任务和消息消费者里。新增一个调用入口，很容易绕过某些检查。

这正好回到第一篇的主题：重要的设计决定应该有明确的归属。对于复杂业务，这些决定往往首先表现为规则、状态与不变量，而不只是文件间的依赖。

领域（Domain）指软件要服务的业务问题范围。订单、库存、结算、仓储等词来自业务世界；数据库、HTTP、消息队列则属于实现系统时使用的技术。

领域模型（Domain Model）是我们对业务中重要概念及其关系的有目的的抽象。它并非真实业务的完整复制，而是为了支持当前软件决策，提炼出必要的状态、行为与约束。

对订单而言，一个有意义的模型应该能够回答：何时允许提交？提交会改变什么？订单明细能否继续修改？价格由谁确定？库存不足时，订单应当处于什么状态？

于是，原来由外部代码直接修改状态的做法，可以逐渐变成调用 `order.submit()`、`order.confirm_stock()` 或 `order.reject_stock()`。这些名称表达了业务动作；对象的方法则负责检查该动作是否允许发生。

订单对象开始维护自己允许发生的业务动作。通过这种方式，规则从散落的应用流程逐渐回到真正拥有该规则的领域对象。

不过，在真正定义这些方法之前，团队还得确定“订单确认”具体指什么。不同部门如果对同一个词有不同理解，再严谨的方法也可能维护错规则。

## 二、从业务讨论形成通用语言

设想一次需求讨论，产品说“订单确认后通知仓库”。开发人员可能认为确认就是用户点击提交，仓库人员却认为确认意味着库存已经分配，财务人员可能理解为付款已完成。

如果团队直接使用一个名为 `CONFIRMED` 的状态，三个理解就会被压缩进同一个字段。等到出现“用户已经提交，但库存不足”或“库存已占用，但尚未付款”这样的情况，状态流转会越来越难解释。

问题出在建模之前：大家并没有统一“确认”的含义。

DDD 强调通用语言（Ubiquitous Language）。业务专家与开发人员应当围绕同一组经过澄清的概念交流，并让这些概念进入需求、代码、测试和接口文档。

对于本例，我们可以明确区分“草稿”“已提交、等待库存处理”“库存已确认”和“库存不足被拒绝”。如果付款属于另一套独立流程，就不应偷偷把“库存已确认”等同于“已支付”。

通用语言并不要求给所有业务词汇编写一份永不变化的字典。相反，它是在讨论业务、发现反例和修改代码的过程中逐步完善的。一个术语如果难以在真实场景中说通，就需要重新审视模型。

实践中，可以从实际操作和业务事件入手理解流程。

“客户提交订单”是一个动作；“订单已提交”是已经发生的事实；“必须至少包含一条商品明细”是允许提交的条件；“提交后不能改动成交明细”是提交后的业务约束。

这些表达比“更新订单表的 status 字段”包含更多信息，也更容易让业务人员检查是否正确。

举例来说，我们在讨论“修改订单”时，应该继续追问：修改草稿和修改已提交订单是不是同一种操作？如果客户已经提交，是否应该创建新的变更申请？一个订单被拒绝后，允许重新提交同一个订单，还是必须创建新订单？

不同答案会导向不同模型。开发人员不可能仅凭 DDD 术语得到这些答案，必须通过业务澄清取得依据。

一个团队内部可以逐渐统一订单语言，但企业软件通常涉及多个业务部门。“商品”“价格”“库存”在不同部门仍可能有不同含义，单靠制定全公司统一的数据对象往往解决不了。

## 三、子域与限界上下文

电商系统涉及商品展示、优惠定价、订单交易、库存管理、支付结算和物流履约。它们共同服务于销售业务，但拥有不同的规则。

在 DDD 中，可以把大领域继续分成若干子域（Subdomain）。子域描述的是业务问题空间。常见的分类是核心子域、支撑子域和通用子域。

核心子域通常体现企业竞争优势或业务差异化，需要投入最多的建模与业务专家协作。支撑子域为核心业务提供必要能力，但通常不直接形成差异化优势。通用子域则更接近许多组织都要解决的通用问题，适合评估成熟产品或通用方案。

这种分类是战略判断，不是给某个目录永久贴标签。对于以复杂促销能力为竞争优势的平台，定价可能属于核心子域；对于主要竞争力在物流履约的企业，精细化仓储调度可能更关键。

分类的意义在于决定哪里值得投入复杂建模，哪里应优先采用简单而成熟的方案。DDD 不要求每个子域都使用同样复杂的技术结构。

比子域更容易混淆的概念是限界上下文（Bounded Context）。

假设商品目录系统里的“商品”负责名称、图片、分类和展示价格；库存系统里的“商品”主要关联 SKU、可用数量与预留数量；订单系统里的“商品”则体现客户下单时购买的 SKU、数量和成交价。

如果尝试建立一个全系统共用的巨大 `Product` 类，它就不得不承载所有属性和变化规则。商品展示的需求可能波及库存和订单代码，反过来也是如此。

一种更自然的做法，是承认不同业务部分可以有不同的商品模型。商品目录维护自己的商品信息；库存维护库存项；订单保留订单明细及成交快照。它们通过明确的契约交换必要信息。

限界上下文划定的就是**一套特定领域模型及其语言保持一致的范围**。在这个范围内，概念的含义必须明确；跨出边界时，即使名称相同，也要检查语义是否一致。

子域与限界上下文不能直接画等号。前者属于对业务问题的划分，后者是模型和软件组织的边界。一个子域可以由多个限界上下文实现，一个上下文也可能支持不止一个子域中的需求，二者需要根据实际业务与组织条件建立映射。

以订单与商品目录为例，订单创建时可以通过一个商品价格查询接口获得当前有效报价，再把成交单价保存进自己的订单明细。商品目录后续修改展示价格，不应自动覆盖已经提交的历史订单。

这里出现了两个不同的业务事实：目录当前报价，以及订单当时接受的成交价格。它们看起来都属于“价格”，但由不同上下文负责。

上下文之间需要明确集成关系。若订单方必须使用上游目录方的数据格式，并承担转换工作，可以设置防腐层（Anti-Corruption Layer，ACL），把外部概念转换成订单方自己的模型。例如外部返回 `salePrice`、币种和税务信息，订单方将其转换为自己认可的 `Money` 和成交报价，而不让整个订单领域直接依赖外部 SDK 的字段。

DDD 的上下文映射（Context Mapping）还包括客户—供应方、共同内核（Shared Kernel）、遵奉者（Conformist）、开放主机服务（Open Host Service）等合作方式。它们描述团队和模型之间如何协调，不是一组必须全部实施的技术组件。对初学者来说，先把每个上下文的模型所有权与集成契约说明白，比记住这些名称更重要。

更需要注意的是，**限界上下文不等于微服务**。一个单体应用完全可以包含多个上下文；一个服务内部也可能意外混入几种不同模型。是否拆成独立进程，需要另外考虑部署、团队、数据一致性和运维成本。

确定上下文之后，模型才有了语义范围。下一步是判断其中的对象应该如何表达：哪些需要长期追踪身份，哪些更适合用取值描述。

## 四、实体与值对象

在一个确定的限界上下文内，模型需要进一步落实为可执行的对象与行为。这部分工作通常被归在 DDD 的战术设计之中。

先比较两个订单。它们可能属于同一个客户，购买同样的商品、数量和金额，但只要订单编号不同，就仍然是两笔不同的交易。

订单具有持续的身份。即使它从草稿变成待确认，金额和状态都发生变化，我们仍然认为它是原来的那笔订单。

这类对象称为实体（Entity）。实体的关键特征是需要追踪身份与生命周期，而不是它必须有数据库自增主键。

订单编号可以是 UUID，也可以是业务生成的订单号。如何生成身份属于设计选择。数据库主键与业务身份也不一定是同一个东西。

现在看金额。100 元人民币与另一个 100 元人民币，如果数值和币种相同，通常就可以视为等价。我们不需要像跟踪某笔订单那样跟踪每一个金额对象的身份。

这类由取值及其含义决定相等性的对象称为值对象（Value Object）。金额、日期范围、地址、坐标都可能被建模为值对象，但是否如此取决于业务语义。例如一个需要独立审核和追踪历史版本的地址记录，也可能被建模为实体。

下面使用 Python 的不可变数据类表示金额：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Money:
    cents: int
    currency: str = "CNY"

    def __post_init__(self) -> None:
        if self.cents < 0:
            raise ValueError("本例中的金额不能为负")
        if self.currency != "CNY":
            raise ValueError("本例只支持人民币")

    def __add__(self, other: "Money") -> "Money":
        if self.currency != other.currency:
            raise ValueError("不能直接相加不同币种")
        return Money(self.cents + other.cents, self.currency)

    def multiply(self, quantity: int) -> "Money":
        if quantity <= 0:
            raise ValueError("数量必须大于零")
        return Money(self.cents * quantity, self.currency)
```

`Money` 保存的不只是一个整数，还表达了金额单位和允许的运算。我们不能把人民币金额与美元金额无条件相加，也不应该允许订单行数量为负。

`frozen=True` 使数据类避免通过普通属性赋值被修改，但不能代替一切领域约束。这里将金额限制为非负，是因为例子只处理商品单价和订单总额；退款、欠款、账务分录等场景需要另外定义允许负数的金额模型或业务操作。

值对象常使用不可变设计。修改值时创建新对象，有利于理解和共享。不过，不可变性是一种有用的实现方式，不是判断实体与值对象的唯一标准。真正的区分仍是业务是否关心身份。

当然，可以直接把金额写成 `{"cents": 30000, "currency": "CNY"}`。对于短生命周期的数据传输，这完全合理。

只有当“金额的合法值、相等性和计算规则”在业务中频繁出现时，把它们建模为值对象才更有意义。这样检查逻辑可以留在一个明确的位置，调用方也不必反复记住金额单位。

DDD 不要求把每个字符串、整数都包装成类。抽象的成本仍然需要服从第三篇讨论的 KISS 与 YAGNI。

实体和值对象帮助我们表示业务概念，却还没有解决多个相关对象被一起修改时，谁维护整体规则。提交订单不能只有一张订单头表符合条件，还要确保明细与金额一致。

## 五、聚合与业务一致性

订单有自己的身份，也包含若干明细。假设订单处于草稿状态时允许增加明细，但提交后必须同时满足三个条件：明细不能为空，所有明细数量都大于零，成交总额必须等于明细小计之和。

这些条件称为业务不变量（Invariant）。所谓不变量，并不是“对象的任何字段都永远不变”，而是指在规定的有效状态下必须始终成立的业务条件。

若调用方能够直接改写订单明细，却忘记更新总额，订单就会出现不一致。若明细对象能够绕开订单状态检查自行修改，提交后的订单就可能被悄悄篡改。

我们需要一个能够控制这些修改的业务边界。

聚合（Aggregate）是一组被视为一个一致性单元的领域对象。聚合内有一个对外负责的实体，称为聚合根（Aggregate Root）。外部代码应通过聚合根访问和修改这个聚合中的业务状态，由它维护跨内部对象的约束。

对于本例，可以让 `Order` 成为聚合根。订单明细由它持有，公开接口要求通过 `order.add_line()` 添加明细、通过 `order.submit()` 提交订单，而不提供绕过这些操作直接改变内部明细的路径。

聚合根不是简单地“主表对象”。数据库有外键，也不意味着外键关联的所有记录都属于同一个聚合。判断依据是哪些规则需要在一次业务状态变更中得到共同维护。

本例的订单明细可以先建模成值对象，因为我们只关心 SKU、数量与提交时的单价，不需要单独追踪一条明细的长期身份。如果以后出现针对特定明细的部分退货或售后记录，就需要重新考虑明细身份与模型边界。

提交订单可能需要占用库存，看起来订单和库存关系非常紧密。为什么不把商品库存对象也塞进 `Order` 聚合？

因为库存并不只服务于一笔订单。同一个 SKU 的库存可能被许多订单竞争，也会受到入库、盘点和损耗影响。它有独立的生命周期和并发约束。

如果每笔订单都拥有一份可修改的库存实体，那么多个订单究竟以谁的库存为准就会成为问题。更合理的做法是让库存管理方负责“预留数量不能超过可用数量”这条规则，让订单方负责“订单能否从待处理变为已确认”这条规则。

跨聚合协作时，通常通过标识符或明确的命令与结果交互，避免把另一个聚合的内部可变对象直接纳入当前聚合。这样可以减小事务争用与模型耦合。

常见的设计建议是：**一个聚合定义一个需要强一致维护的业务边界；尽可能保持聚合小，并将跨聚合协调显式化。** 这是一条重要的建模原则，但不意味着底层数据库事务在技术上绝不能同时修改两行或两个聚合。在单数据库场景中，某些明确要求立即原子完成的业务操作，可以在一个本地事务里协调多个聚合；此时需要有意识地承担更大的锁范围与耦合成本，而不能据此把所有对象合并成一个巨型聚合。

把聚合定义落到代码上，可以更清楚地看出它和普通 ORM 数据容器的差别。下面先不涉及数据库，集中实现一个订单在内存中的有效状态与状态转换。

## 六、订单聚合的 Python 实现

理解了实体、值对象和聚合，我们可以写一个不依赖 FastAPI、SQLAlchemy 的订单模型。为避免提前引入支付和库存的复杂性，这个例子约定：客户提交订单后进入“等待库存处理”状态；库存确认成功后才变成“已确认”。因此，提交订单不代表已经成功预留库存，更不代表付款完成。

先定义订单明细与订单已提交事件：

```python
from dataclasses import dataclass
from uuid import UUID

@dataclass(frozen=True)
class OrderLine:
    sku: str
    quantity: int
    unit_price: Money

    def __post_init__(self) -> None:
        if not self.sku.strip():
            raise ValueError("SKU 不能为空")
        if self.quantity <= 0:
            raise ValueError("购买数量必须大于零")

    @property
    def subtotal(self) -> Money:
        return self.unit_price.multiply(self.quantity)

@dataclass(frozen=True)
class OrderSubmitted:
    order_id: UUID
```

然后定义订单聚合根：

```python
class Order:
    def __init__(self, order_id: UUID, customer_id: UUID):
        self.id = order_id
        self.customer_id = customer_id
        self._lines: list[OrderLine] = []
        self._status = "DRAFT"
        self._events: list[object] = []

    @property
    def status(self) -> str:
        return self._status

    @property
    def lines(self) -> tuple[OrderLine, ...]:
        return tuple(self._lines)

    @property
    def total(self) -> Money:
        total = Money(0)
        for line in self._lines:
            total = total + line.subtotal
        return total

    @property
    def events(self) -> tuple[object, ...]:
        return tuple(self._events)

    def add_line(self, line: OrderLine) -> None:
        if self._status != "DRAFT":
            raise ValueError("只有草稿订单可以修改明细")
        self._lines.append(line)

    def submit(self) -> None:
        if self._status != "DRAFT":
            raise ValueError("当前状态不允许提交")
        if not self._lines:
            raise ValueError("空订单不能提交")
        self._status = "PENDING_STOCK"
        self._events.append(OrderSubmitted(self.id))

    def confirm_stock(self) -> None:
        if self._status != "PENDING_STOCK":
            raise ValueError("当前订单不等待库存确认")
        self._status = "CONFIRMED"

    def reject_stock(self) -> None:
        if self._status != "PENDING_STOCK":
            raise ValueError("当前订单不等待库存确认")
        self._status = "REJECTED"
```

这个模型有几个值得注意的地方。

首先，外部代码不能通过 `order.lines.append(...)` 修改内部列表，因为公开属性返回的是元组。不过，Python 没有强制的模块私有访问控制，调用者仍然可以故意访问 `_lines`、`_status`。这里的边界依靠公开 API、团队约定和测试维护，不能误认为下划线会阻止所有非法操作。

其次，总额由明细计算得到，而没有再保存一份可随意改写的 `total_cents`。这样，在内存模型中不会出现“明细和总额分别修改，却忘记保持一致”的问题。如果为了查询性能在数据库中冗余保存总额，持久化层必须维护相应一致性。

再次，`submit()` 同时检查状态和明细，再改变订单状态。业务规则与状态转换集中在聚合根之内，而不是要求每个调用方各自记住检查条件。

最后，`OrderSubmitted` 只是领域内部记录的“订单已提交”事实，目前还没有发送任何 MQ 消息。事件怎样可靠地保存和发布，属于后面需要解决的基础设施问题。

可以直接为这个模型编写测试：

```python
from uuid import uuid4

order = Order(uuid4(), uuid4())
order.add_line(OrderLine("SKU-001", 2, Money(15000)))
assert order.total == Money(30000)

order.submit()
assert order.status == "PENDING_STOCK"
assert order.events == (OrderSubmitted(order.id),)

try:
    order.add_line(OrderLine("SKU-002", 1, Money(5000)))
except ValueError:
    pass
else:
    raise AssertionError("提交后不应允许修改明细")

order.confirm_stock()
assert order.status == "CONFIRMED"
```

这些代码只依赖 Python 标准库，可以在没有数据库、HTTP 服务和消息代理的情况下检查核心业务规则。这样做的价值在于，领域规则变更时，我们能够快速验证模型本身，而不必启动整个技术系统。

但模型测试通过，并不意味着生产系统的并发一致性已经得到保证。两个进程可能同时读取同一笔订单的旧状态，并分别执行不同的操作。如何避免后写入覆盖先写入，仍然需要持久化机制配合。

订单对象已经能保证自己的规则，但收到一个 HTTP 请求后，还要查询商品报价、加载聚合、保存结果。这些协调工作不能都塞回订单对象，否则领域模型又会依赖外部技术。

## 七、领域行为与用例编排

上面的 `Order` 知道订单应该如何维护自己的状态，却不知道怎样查询当前商品报价，也不知道使用 PostgreSQL 还是 MySQL 保存数据。

这是一种有意的限制。商品报价属于另一个业务能力，数据库连接属于基础设施。它们可以由应用服务负责协调。

应用服务（Application Service）面向完整的用例，例如“接收用户提交订单的请求”。它可以验证调用权限、获得必要的外部数据、创建或加载聚合、调用领域行为，并安排提交事务。真正决定“什么状态允许提交”的规则，仍由领域模型维护。

可以通过 `Protocol` 描述应用层需要的能力：

```python
from typing import Protocol

class PriceCatalog(Protocol):
    def price_for(self, sku: str) -> Money: ...

class OrderRepository(Protocol):
    def add(self, order: Order) -> None: ...
    def get(self, order_id: UUID) -> Order | None: ...
```

这里的 `PriceCatalog` 是订单应用所需要的报价能力，并不要求商品目录直接暴露自己的内部实体。实际实现可以使用本地同步的价格快照，也可以调用其他上下文的 API，前提是符合业务规定的价格时效与有效性要求。这里为了突出用例编排而使用同步接口；如果远程报价发生在异步 Web 应用中，接口与调用方也应采用异步 I/O，或者明确把同步调用移出事件循环线程。

应用层可以组织提交用例：

```python
from collections.abc import Sequence
from uuid import uuid4

@dataclass(frozen=True)
class RequestedLine:
    sku: str
    quantity: int

def submit_order(
    customer_id: UUID,
    requested: Sequence[RequestedLine],
    catalog: PriceCatalog,
    orders: OrderRepository,
) -> UUID:
    order = Order(uuid4(), customer_id)
    for item in requested:
        unit_price = catalog.price_for(item.sku)
        order.add_line(OrderLine(item.sku, item.quantity, unit_price))
    order.submit()
    orders.add(order)
    return order.id
```

这个函数只展示用例编排，尚未处理事务提交和领域事件可靠发布。因此它不能直接当作完整的生产级下单流程。下一节继续说明持久化与事务边界，领域事件的可靠发布则在后文单独讨论。

成交单价的来源还需要业务校验：它不应直接采用客户端提交的任意金额。应用层需要从可信的报价来源取得价格，并根据业务要求处理报价失效、价格版本和重新确认。领域对象负责维护订单自身的规则，但外部信息是否可信，通常需要在进入领域模型之前得到保证。

有些规则确实属于领域，却很难自然归属于一个实体或值对象。例如跨多个业务概念的复杂定价算法，或者一套根据仓库能力、地区和时效约束选择履约方案的规则。这时可以考虑领域服务（Domain Service）。

领域服务表达的是业务决策，应用服务表达的是用例流程。前者的名称通常来自业务语言，例如“计算最优分仓方案”；后者更接近“受理订单提交请求”。

这个区别不能仅凭是否调用 Repository 判断。领域服务可以依赖领域定义的查询能力，但如果其主要职责是开启数据库事务、发送 HTTP 请求和组装响应，它通常更接近应用层或基础设施协作代码。

另一方面，也不需要把所有业务算法都写成领域服务。金额求和很自然地属于订单聚合；复杂计算如果可由纯函数准确表达，也没有必要为了形式把它包装成拥有状态的类。

应用服务调用领域行为以后，改变还需要保存。纯 Python 对象与 SQLAlchemy ORM 在这一步相遇，也最容易让领域规则重新泄漏到数据库代码中。

## 八、模型的持久化与工作单元

第二篇已经介绍 Repository 封装数据访问。进入 DDD 后，它通常进一步承担“从存储中重建聚合、保存聚合”的责任。

对于订单上下文，调用方期望获取的是一个能够执行 `submit()` 或 `confirm_stock()` 的订单聚合，而不只是散落的数据库行。Repository 可以负责加载订单与其明细，并在保存时维护映射关系。

这不意味着必须为订单明细、金额值对象和每张表分别建立一个通用 CRUD Repository。若这些对象属于订单聚合，通常让订单仓储作为对外访问入口更符合边界。报表统计则可以走专门的只读查询，不必为了展示一张列表而重建所有聚合。

一种实现方法是让 SQLAlchemy ORM 类直接承载领域方法；另一种是使用普通 Python 对象表达领域模型，再通过 Mapper 在领域对象与 ORM 对象之间转换。

前者简单、映射成本低，但领域对象容易与加载状态、Session 生命周期和数据库字段结构绑在一起。后者隔离更明确，允许领域模型脱离数据库进行测试，代价是额外的映射和同步代码。

对于简单业务，可以让 ORM 对象承担少量业务行为。对于规则复杂、需要长期演化的核心领域，独立模型的收益可能更大。DDD 没有规定所有项目都必须坚持某一种映射方式。

要警惕的是把 ORM 对象仅仅作为数据容器，让一个巨大的 Service 用无数 `if` 负责修改所有状态。这种设计通常被称为贫血领域模型（Anemic Domain Model）。它不是语法错误，也并非所有事务脚本都不可取，但如果项目本来引入 DDD 是为了让复杂规则有明确的维护位置，那么只有 getter/setter 的实体就没有发挥领域模型的主要价值。

工作单元（Unit of Work，UoW）协调一组持久化操作，使它们按预期共同提交或回滚。SQLAlchemy 的 `Session` 本身已经包含许多工作单元机制；是否再封装一个 UoW 接口，取决于应用层是否需要隔离具体 ORM，并显式表达事务边界。

在第二篇的 FastAPI + SQLAlchemy 异步项目中，可以沿用下面这种写法：

```python
async with session.begin():
    order = await order_repo.get(order_id)
    if order is None:
        raise LookupError("订单不存在")

    order.confirm_stock()
    await order_repo.save(order)
```

这里的 `order_repo` 假定会通过相同的 `session` 执行持久化，并负责领域模型与存储模型之间的映射。`begin()` 成功退出时提交；出现异常时回滚。`save()` 的具体实现依赖前面选择的 ORM 映射方式，并不是 SQLAlchemy 自带的统一方法。

如果仓储操作自行 `commit()`，或者在上述事务中再用另一套独立的 Session 提交，事务边界就会被破坏。因此，事务应该由负责当前用例的外层协调者掌握，而不应该由各个 Repository 随意决定。

示例也假定进入 `session.begin()` 前没有在同一个 Session 中开始其他事务。SQLAlchemy 存在 autobegin 行为，已有活动事务时不能简单再开启一个同级事务。

模型内的状态检查有一个前提：当前对象代表数据库中的有效状态。出现并发请求后，不同进程可能同时持有旧版本，单靠 `order.submit()` 就无法保证最终写入正确。

## 九、并发条件下的聚合一致性

领域对象可以阻止单个进程中的非法状态转换，但无法单独解决多个请求同时修改同一条记录的问题。

假设两个 Worker 同时读取同一个 `PENDING_STOCK` 订单。一个收到库存确认事件，准备改成 `CONFIRMED`；另一个收到库存拒绝事件，准备改成 `REJECTED`。如果都以旧状态为基础分别保存，最终结果可能由最后写入者决定。

这就要求持久化层提供并发控制。常见方法包括行锁、乐观锁、带状态条件的更新，以及适当的事务隔离级别。

以乐观并发控制为例，可以为订单记录增加一个版本号。读取时得到版本 `version = 7`，提交修改时只允许更新原版本仍然为 7 的记录：

```sql
UPDATE orders
SET status = :new_status,
    version = version + 1
WHERE id = :order_id
  AND version = :expected_version;
```

如果受影响行数为 0，表示这个更新没有按预期发生，可能是记录不存在或版本已经变化。应用需要重新读取并根据当前状态决定重试、拒绝，或者要求人工处理，不能无条件把旧操作再执行一遍。

SQLAlchemy 2.0 也支持在 ORM 映射上设置 `version_id_col` 进行版本检查，但这种机制主要作用于 ORM 的逐对象 `flush()` 更新；直接执行批量 `UPDATE` 时不能假设映射器的版本校验会自动生效。

聚合定义的是领域上的一致性责任，数据库事务和并发控制负责在真实并发环境中落实这些约束。二者缺一不可。

即使订单持久化已经可靠，订单提交仍可能触发库存预留与后续通知。库存属于另一个职责边界，领域对象不能直接决定对方的数据库事务。

## 十、领域事件与跨上下文协作

当订单从草稿变为等待库存处理时，领域模型产生 `OrderSubmitted`。这个名称采用过去式，表达的是业务事实，而不是命令。

命令是“请占用库存”，可能成功也可能失败；事件是“订单已经提交”，说明某件事已经发生。二者的语义不同，接收方应如何处理也不同。

领域事件有助于让副作用显式化。例如，订单提交后需要触发库存预留，库存预留成功后再确认订单。订单聚合不需要在 `submit()` 方法中直接调用库存服务。它只负责自己的状态转换，并记录需要由外部协调的事实。

不过，把事件放进 `_events` 列表不等于可靠发布。这只是模型层的表达。领域事件可能由同一进程同步处理，也可能经过转换后形成跨上下文的集成事件（Integration Event）。是否需要通过 MQ，取决于部署边界与可靠性要求。

考虑以下流程：订单写入数据库并提交成功，然后向 RabbitMQ 发布消息，通知库存系统占用库存。

如果进程恰好在数据库提交后、消息发出前崩溃，订单已经处于待处理状态，库存方却永远不知道需要占用库存。反过来，若先发消息再提交数据库，也可能出现消息已经消费、订单事务却回滚的情况。

这就是双写问题。普通数据库事务不会自动覆盖独立的消息代理。

事务性 Outbox 是一种常见的解决方式。订单业务记录与一条待发布的消息记录，在同一个数据库事务中保存：

```python
async with session.begin():
    await order_repo.save(order)
    await outbox_repo.add(
        event_type="OrderSubmitted",
        aggregate_id=str(order.id),
        payload={"order_id": str(order.id)},
    )
```

这里的 `outbox_repo` 是概念接口，示例省略了表映射、序列化和错误处理，但关键要求是它与 `order_repo` 使用同一个数据库事务。之后由独立的发布程序读取已提交的 Outbox 记录，再向 MQ 发布。

Outbox 保证的是业务记录与“待发布消息”原子持久化，而不是消息恰好投递一次。发布成功后，如果程序在标记消息已发送之前崩溃，消息可能再次发送。因此，消费者仍应具备幂等处理能力，例如通过稳定的事件 ID 与数据库唯一约束记录已处理消息。

还要处理消息顺序、积压、重试、失败告警及 Outbox 表清理。对于同一个订单的连续状态事件，如果业务依赖顺序，单靠“消息最终会送达”仍然不够。

订单提交、库存预留、付款与物流履约往往分属不同的聚合，甚至不同的限界上下文。它们各自维护自己的业务不变量，整个交易流程却需要协调。

一种流程是：订单进入 `PENDING_STOCK`，库存方尝试预留；成功则返回库存已预留的事实，订单进入 `CONFIRMED`；失败则进入 `REJECTED`。这个过程中，用户可能短暂看见“处理中”。

这就是跨边界协作常见的最终一致性：不同上下文的状态不一定在同一瞬间更新，但系统通过可靠的命令、事件和失败处理，推动它们达到业务允许的最终结果。

当流程包含多个阶段、超时、取消和补偿时，可以考虑过程管理器（Process Manager）或 Saga 来显式追踪协作状态。例如付款失败后释放库存预留。补偿往往是一笔新的业务交易；一封已发送的邮件无法撤回，一次已完成的支付可能需要退款，而不是数据库回滚。

还有一种需要澄清的情况：如果业务明确要求“库存不够时，提交请求必须立即失败，且不允许出现待处理状态”，那么异步确认的方案就不符合需求。此时可以考虑在一个本地事务中完成必要的订单与库存更新，或者通过同步预留接口配合失败恢复机制协调。应当根据业务对一致性和响应时间的要求选择方案，而不是把“最终一致性”当成 DDD 的强制规则。

到这里，业务语言、模型边界、持久化和异步协作已经有了各自位置。项目目录可以沿着这些职责组织，但命名只有在代码遵守边界时才有意义。

## 十一、DDD 在 Python 项目中的组织

前面已经有 Router、Service、Repository 的分层概念，也有订单、库存、定价的业务边界。二者可以组合，而不必互相替代。

一个中等复杂度的单体后端，可以先按限界上下文或业务能力组织，再在各上下文内部划分接口、应用、领域和基础设施：

```text
app/
├── ordering/
│   ├── api/
│   │   ├── router.py
│   │   └── schemas.py
│   ├── application/
│   │   ├── commands.py
│   │   ├── services.py
│   │   └── ports.py
│   ├── domain/
│   │   ├── order.py
│   │   ├── money.py
│   │   └── events.py
│   └── infrastructure/
│       ├── orm.py
│       ├── mapper.py
│       └── repository.py
├── inventory/
│   ├── application/
│   ├── domain/
│   └── infrastructure/
└── catalog/
    ├── application/
    ├── domain/
    └── infrastructure/
```

这只是说明概念如何落地的一种目录组织方式。`ordering/domain/order.py` 不需要导入 FastAPI 的 `HTTPException`，也不应该为了修改订单状态而主动创建数据库连接。`ordering/api` 负责 HTTP 映射；`ordering/application` 负责提交订单、处理库存确认等用例；`ordering/infrastructure` 实现数据库、外部报价接口与消息发布相关的适配。

真实项目还需要决定应用如何组装这些依赖。Router 可以通过 FastAPI 的 `Depends` 获取应用服务，应用服务再通过构造参数得到 Repository、价格查询接口和 UoW。依赖对象的具体创建属于应用启动和基础设施组装，不必进入领域模型。

另外，DDD 的领域层并不要求拒绝一切第三方库。更重要的是避免业务规则被某个基础设施框架的生命周期和专用行为绑死。普通类型工具、时间与金额工具能否使用，需要按实际耦合程度判断。

MVC 主要讨论交互、表现和模型之间的组织关系；分层架构强调不同技术职责如何协作；DDD 关注如何理解复杂业务，以及模型在什么边界内有效。它们不是三个需要选一个的互斥方案。

在一个 FastAPI 单体里，可以同时使用业务上下文、Controller 式的 HTTP 入口和应用—领域—基础设施的分层。随着团队与系统扩大，再考虑让某个上下文独立部署，也并不违背 DDD。

微服务可能让上下文独立发布、扩容和演进，但也会引入远程调用、分布式数据一致性、版本兼容和运维成本。把所有 DDD 模块直接拆成微服务，往往会把原本局部的函数调用变成昂贵且容易失败的网络协作。

聚合适合保护写入时的业务约束，却未必适合复杂查询。例如后台订单列表可能需要联查客户、商品、库存和物流信息。如果为了查询列表而加载所有聚合再在 Python 中拼接，性能和代码都会变差。

可以为读取建立专用查询模型，直接使用 SQL 聚合与分页。这与命令查询职责分离（CQRS）的思想相近，但 DDD 不要求所有系统都部署两套数据库，也不要求所有读取都走事件构建的投影。

事件溯源（Event Sourcing）则是另一项独立选择：以事件序列作为状态的权威来源，通过重放事件重建当前状态。前面让 `Order` 暂存 `OrderSubmitted`，并不等于使用了事件溯源。普通订单表加领域事件，依然是一个完全成立的 DDD 实现。

DDD 提供了表达复杂业务的工具，也增加了建模和协作成本。回到项目最初的难题，才能判断投入是否值得。

## 十二、DDD 的适用范围

DDD 最值得投入的地方，是业务规则复杂、概念歧义多、状态转换频繁，而且不同业务职责会长期独立演化的系统。

这类项目的主要困难通常来自业务知识：开发人员需要反复确认某个动作是否合法，多个团队使用同一术语却有不同含义，某个状态需要依赖许多其他状态才能判断，或者每次修改业务规则都牵动大量代码。

在这样的环境里，通用语言帮助团队澄清含义；限界上下文帮助不同模型保留清晰边界；实体和值对象帮助表达业务概念；聚合集中维护不变量；应用服务、Repository 与工作单元则帮助把领域模型接入真实系统。

但一个简单的后台管理页面、稳定的 CRUD 接口，可能完全不需要独立领域模型、映射器、领域事件总线和多层接口抽象。直接使用 Pydantic、SQLAlchemy 和少量业务函数，也可以得到质量良好的系统。随着规则确实复杂起来，再逐步提炼领域对象和聚合，通常比一开始照抄完整目录模板更稳妥。

实际建模时，可以不断追问：**这里是哪条业务规则需要得到保护，为什么由这个对象或上下文负责，其他代码应该通过什么契约使用它？** 如果回答不了这三个问题，只是把 `models/` 改名为 `domain/`，再增加 `aggregate_root.py`、`domain_service.py`，代码的业务表达能力并不会自动提高。

DDD 也不能代替数据库一致性、消息可靠性、访问控制或性能设计。领域模型可以说明什么状态合法，但合法状态能否在多个并发请求和故障之间得到保证，还需要事务、锁、幂等与可靠集成机制配合。

前四篇文章从职责、依赖与抽象成本出发研究设计。DDD 将同样的问题进一步推进到业务知识本身：先弄清系统究竟在管理什么，再决定代码应当怎样组织。领域模型不是为了让代码看起来更像现实世界，而是为了让业务决定有准确的名字、清楚的归属，以及能够执行和验证的约束。

## 十三、参考资料

Eric Evans, *Domain-Driven Design: Tackling Complexity in the Heart of Software*, Addison-Wesley, 2003。DDD 的核心著作，系统介绍通用语言、实体、值对象、聚合与战略设计。

Vaughn Vernon, *Implementing Domain-Driven Design*, Addison-Wesley, 2013；*Domain-Driven Design Distilled*, Addison-Wesley, 2016。对限界上下文与聚合设计有更具体的阐述。

Martin Fowler, [Domain-Driven Design](https://martinfowler.com/bliki/DomainDrivenDesign.html)、[Bounded Context](https://martinfowler.com/bliki/BoundedContext.html)、[DDD Aggregate](https://martinfowler.com/bliki/DDD_Aggregate.html)、[Anemic Domain Model](https://martinfowler.com/bliki/AnemicDomainModel.html)。

Microsoft Learn, [Use Tactical DDD to Design Microservices](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/tactical-ddd)。讨论实体、值对象、聚合、领域服务及跨聚合协作。

Harry Percival and Bob Gregory, [Architecture Patterns with Python](https://www.cosmicpython.com/)。以 Python 展示领域建模、Repository、Unit of Work、聚合和消息驱动协作。

SQLAlchemy 2.0, [Configuring a Version Counter](https://docs.sqlalchemy.org/en/20/orm/versioning.html)。解释 ORM 版本列的工作方式及其适用边界。

AWS Prescriptive Guidance, [Transactional Outbox Pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)。解释数据库更新与消息发布的双写问题及 Outbox 方案。
