在开发一套 Python Web 服务时，我们通常会先安装 Python，再创建虚拟环境、安装依赖，最后启动应用。程序能否运行，取决于这些准备工作是否与开发时一致。

Python 依赖可以交给 `uv` 或 `pip` 管理，但系统动态库、操作系统工具、文件路径，以及一些依赖于 Linux 的运行行为，并不完全属于 Python 包管理器的职责。开发机能够正常启动的程序，放到另一台服务器上，仍可能因为系统环境不同而失败。

一种解决办法是把环境配置写成部署文档，要求每台服务器按照同样的步骤安装。可是文档描述的是操作过程，服务器上最终留下的状态还会受到旧软件、手动修改和安装顺序的影响。另一种办法是把应用所需的文件和运行配置组织成可分发的制品，让接收方尽量直接使用这个制品启动程序。

Docker 将后一种做法变成了一套标准化的开发与运行流程。但要理解它，最好先弄清楚：Docker 启动的容器，在 Linux 看来究竟是什么？

## 一、从一个普通的 Linux 进程说起

假设我们在服务器上运行：

```bash
python app.py
```

Shell 请求操作系统启动 Python 程序。Linux 为其创建进程，管理虚拟内存、文件描述符、线程、权限和调度状态。程序运行时要打开文件、建立网络连接、申请内存，最终都需要通过系统调用与内核交互。

这个 Python 进程并没有一个独立的操作系统。它使用宿主机的 Linux 内核，也通常直接看到宿主机当前的文件系统目录、进程和网络环境；它能实际访问什么，还受用户权限、挂载权限和其他安全机制约束。

如果同一台机器部署两套应用，而它们依赖不同的系统库版本，或者要求使用同一个固定端口，就可能发生环境与资源冲突。为它们分别创建 Python 虚拟环境，只能解决其中一部分问题：虚拟环境主要组织 Python 解释器及其包依赖，不能为进程提供独立的 Linux 网络栈、进程编号空间或系统文件视图。

Linux 本身已经具备隔离进程运行环境的能力。Namespace 可以让不同进程组看到不同的进程编号、挂载、网络等资源视图；cgroups 可以对一组进程实施资源统计和限制；文件系统挂载能够为程序准备独立的根目录。再结合权限、Capabilities、Seccomp 等安全机制，就可以让进程在一套受到约束的环境中运行。

Docker 所管理的 Linux 容器，正是建立在这些操作系统能力之上的。容器里运行的程序仍是 Linux 进程，仍由内核调度，也仍会执行系统调用。Docker 并没有为每个容器模拟一台完整计算机，或额外启动一个独立的 Linux 内核。

因此，“容器里有一个 Linux 系统”通常只是便于理解的说法。容器镜像可以带有 `/bin/sh`、`/etc`、`/usr` 以及某个 Linux 发行版的用户态程序和动态库；它们并不等于一个正在单独运行的 Linux 内核。

这条区别会贯穿整个 Docker 专题。

## 二、镜像、容器与仓库

Docker 将应用的交付和运行分成两个主要对象：镜像（Image）和容器（Container）。镜像用于提供运行所需的文件与配置；容器则是根据这些内容创建、可被启动和管理的运行实例。

一个镜像通常包含应用可执行文件、运行时、依赖库及文件系统内容，还包含默认工作目录、环境变量、启动命令等配置。它并非简单的压缩包。现代容器镜像通常按 OCI Image 规范组织，包括描述镜像内容的 Manifest、配置对象，以及承载文件系统变化的 Layer。不同镜像可以共享相同的只读内容层，从而减少重复传输和存储。

镜像一旦按其内容标识确定，其内容就不会在原位置被任意修改。如果重新构建得到不同内容，实际上会得到新的镜像制品。不过，给镜像起的标签可以重新指向其他内容，这一点需要与镜像本身的不可变性区分开。

例如：

```text
python:3.12-slim
```

这里的 `python` 是镜像仓库名称的一部分，`3.12-slim` 是标签（Tag）。省略镜像注册表地址时，Docker 通常会从 Docker Hub 的默认命名空间寻找相应镜像。标签是便于人阅读的引用，并不承诺永远指向同一份字节内容。如果要明确锁定某份已发布的镜像，可以按符合要求的 Digest 引用，例如 `镜像名@sha256:...`。镜像的内容标识、Manifest Digest 与具体平台的镜像配置 ID 也不应一概混为同一个值。

存放和分发镜像的服务称为 Registry，例如 Docker Hub 或企业自己的镜像注册表。Registry 提供推送与拉取镜像内容的接口；Repository 用于组织某组相关镜像，Tag 则是其中一个可变的引用。许多日常资料把 Registry 和 Repository 都简单翻译成“仓库”，阅读文档时应注意它们并不是同一层概念。

可以把三者的关系记成：镜像是交付制品，Registry 保存和分发制品，容器是根据镜像创建的运行实例。同一个镜像能够创建多个容器，每个容器有自己的状态和可写文件系统层；修改容器中的文件，不会直接修改原始镜像。

镜像解决了“程序及其依赖怎样交付”的问题。至于“谁读取镜像、准备隔离环境、真正启动进程”，还需要看 Docker Engine 的内部组件。

## 三、先运行一个容器

下面的命令面向已经安装 Docker Engine 的 Linux 环境。建议先执行：

```bash
docker version
docker context show
docker compose version
```

第一条命令可以查看客户端与服务端的版本信息。第二条命令显示当前使用的 Docker Context，帮助判断 CLI 实际连接的是哪个 Docker Engine。第三条检查后文多容器实验需要的 Compose 插件；安装 Docker Engine 并不一定同时安装该插件，本文需要使用支持 `depends_on.condition: service_healthy`、`up --wait` 和 `--wait-timeout` 的现代 Compose 版本。

如果 Docker Daemon 未运行，或者当前用户没有连接它的权限，访问 Engine 的命令可能失败；如果提示没有 `compose` 子命令，则需要按 Docker 官方安装文档安装 Compose 插件。此时应先检查安装与权限，不建议为了消除报错而随意修改 Docker Socket 的访问权限。

运行一个简单容器：

```bash
docker run --rm alpine:3.22 echo 'Hello from Docker'
```

如果本地尚未拥有所需的镜像，Docker 通常会先拉取。随后它根据镜像创建容器，在容器内执行 `echo`，将标准输出显示在当前终端。命令完成后，进程退出；`--rm` 要求 Docker 在容器退出时删除该容器。

注意，这条命令退出，并不意味着 Docker 出了故障。这个容器的主要进程只有一项短暂工作：输出一行文字。工作完成以后，进程自然终止。Docker 管理的是进程的生命周期，并不要求每个容器都持续运行。

我们再启动一个能够保留一段时间的容器：

```bash
docker run -d --name docker-study alpine:3.22 sleep 3600
```

`-d` 表示以分离模式运行，使 Docker CLI 不必一直占用当前终端等待进程结束。`--name` 为容器设置一个便于查找的名称。`alpine:3.22` 是镜像引用，`sleep 3600` 是本次启动时指定的命令，会覆盖该镜像的默认命令设置。这里不是在容器内先启动一个“操作系统”，再手工登录运行 `sleep`；`sleep` 本身就是这次容器的主要进程。

查看容器：

```bash
docker ps
docker inspect --format '{{.State.Status}} {{.State.Pid}}' docker-study
```

第一条命令列出运行中的容器。第二条读取 Docker 保存的容器状态和主进程 PID。对于本机原生 Linux Docker Engine，`.State.Pid` 通常是宿主机 PID Namespace 中可识别的进程编号。若命令显示 `running` 和一个正整数，说明容器对应的主进程已经启动。

进入容器中查看进程：

```bash
docker exec docker-study sh -c 'echo "shell PID: $$"; ps'
```

`docker exec` 会在已有容器的环境中启动一个额外进程。这与创建新容器不同。这里可以看到 `sleep` 和临时启动的 `sh`、`ps` 等进程。由于容器通常拥有独立的 PID Namespace，容器内看到的 PID 与宿主机 PID 可能不同。特别是容器里的 PID 1，一般对应这次启动时的主进程。

在原生 Linux Docker Engine 的宿主机上，还可以执行：

```bash
PID=$(docker inspect --format '{{.State.Pid}}' docker-study)
ps -p "$PID" -o pid,ppid,comm,args
```

如果能够从宿主机看到同一个 `sleep` 进程，就能直观地理解容器并没有脱离 Linux 进程模型。容器内外看到不同的 PID，是 Namespace 提供的进程编号视图所致。若 Docker CLI 实际连接的是远程 Engine，或者 Docker Desktop 内部的 Linux 虚拟机，这段宿主机 `ps` 就不能在当前终端所在的操作系统上直接对应到目标进程。

实验结束时，可以停止并删除容器：

```bash
docker stop docker-study
docker rm docker-study
```

`docker stop` 尝试让主进程正常退出，必要时再强制终止。`docker rm` 删除已停止的容器对象及与其绑定的可写层等资源；没有一并删除原始镜像，也不会默认删除所有外部持久化数据。

停止时的等待还与 PID 1 的特殊行为有关。在容器自己的 PID Namespace 中，作为 PID 1 运行的进程，对没有显式注册处理函数、默认动作本应结束进程的信号，可能不会按普通进程的方式退出。因此，本例的 `sleep` 在收到默认的 `SIGTERM` 后可能继续运行，直到 Docker 的停止等待时间耗尽，再被 `SIGKILL` 强制结束。需要正常收尾的应用应正确处理终止信号；必要时也可以通过 `--init` 引入负责转发信号和回收子进程的初始化进程。

## 四、`docker run` 的背后发生了什么

刚才只输入了一条命令，却完成了镜像获取、容器创建、进程启动以及标准输出连接。把这个过程理解成 Docker CLI 自己在后台运行了一次 `sleep`，会遗漏最重要的架构边界。

Docker Engine 采用客户端与服务端架构。`docker` 是常见的命令行客户端，`dockerd` 是处理 Docker Engine API 请求并管理容器、镜像、网络及存储对象的服务进程。两者可以运行在同一台机器，也可以通过受保护的远程连接通信。典型的本地 Linux Engine 通过 Unix Socket 暴露 API，CLI 将用户操作转换成 API 请求发送给 Daemon。

这意味着终端执行完 `docker run -d` 后，即使 Docker CLI 退出，容器也可以继续运行。控制终端与容器进程并没有必须保持的父子生命周期关系。

接下来还有两项值得区分的工作：高层的容器管理，以及将具体进程交给 Linux 内核运行。现代 Docker Engine 通常使用 `containerd` 管理容器运行相关的低层任务，包括镜像内容、快照、容器任务和运行时生命周期。真正创建容器进程时，常见的低层 OCI Runtime 是 `runc`。

在典型的 containerd Runtime v2 架构中，还有一个容易被教程略过的组件：`containerd-shim-runc-v2`。containerd 通过 Shim 管理容器任务，Shim 再按需要调用 `runc` 完成创建、启动等操作，并处理容器任务的 I/O 与退出状态等生命周期事务。`runc` 通常执行一次管理动作后便退出，不需要作为那个业务进程的长期父级控制进程驻留；持续运行的容器由 Shim 与 containerd 体系维护其状态。具体进程树和 Shim 复用方式会随运行时实现而变化，不能将其简化成永远固定的一对一关系。

可以按职责把这一过程理解为：

```text
用户输入 docker run
        │
        ▼
Docker CLI
        │ Docker Engine API
        ▼
dockerd
        │ 容器配置、网络等 Docker 对象管理
        ▼
containerd
        │ 内容、快照与任务生命周期
        ▼
containerd-shim-runc-v2
        │ 调用 OCI Runtime
        ▼
runc
        │ 配置 Namespace、挂载、权限、cgroups 等
        ▼
Linux 内核启动目标进程
        │
        ▼
容器中的 sleep / Python / Nginx ...
```

这张文字流程图表示组件之间的主要控制职责，不要求每项 Docker Engine API 都严格依次通过图中的每一个程序。镜像拉取、网络创建和存储挂载可能由不同组件、插件或子系统负责；运行期间也不会让每一条业务系统调用都重新经过 CLI、Daemon、containerd 和 runc。容器进程执行 `read()`、`write()`、`connect()` 等系统调用时，直接通过内核提供的接口工作。

`docker run` 还可以在概念上拆为 `docker create` 和 `docker start`。前者创建容器对象、准备配置及可写文件系统等资源，但不启动主要业务进程；后者让已创建的容器开始执行。Docker 的 CLI 文档明确区分了这两个操作。

```bash
docker create --name prepared alpine:3.22 sleep 3600
docker ps -a --filter name=prepared
docker start prepared
docker ps --filter name=prepared
docker stop prepared
docker rm prepared
```

在 `create` 之后，容器状态应当是 `created`；`start` 之后才会进入运行状态。这样就能解释为什么“镜像存在”“容器已经创建”和“容器正在运行”是三个不同事实。

## 五、从 OCI 标准到真正的进程

前面的调用链还隐藏着一个问题：`containerd` 怎样告诉 `runc`，应该启动什么程序、使用什么目录、创建哪些隔离环境？如果只能依赖 Docker 自己的一套私有约定，那么其他运行时就很难复用这套镜像与执行流程。

OCI（Open Container Initiative）为容器提供了互操作规范。其中，OCI Image Specification 规定镜像内容和分发制品的组织方式；OCI Runtime Specification 则规定容器运行配置与生命周期接口。二者处理的对象不同：镜像格式描述“可供运行的内容”，运行时规范描述“怎样准备并启动执行环境”。

OCI Runtime Bundle 通常包含根文件系统目录以及 `config.json`。运行配置会描述要执行的命令、工作目录、环境变量、挂载、Namespace、资源与安全约束等。下面是为了说明字段意义而缩减的片段，并不是可以直接交给 `runc` 的完整合法配置：

```json
{
  "ociVersion": "1.1.0",
  "root": { "path": "rootfs" },
  "process": {
    "terminal": false,
    "cwd": "/",
    "args": ["/bin/sleep", "3600"],
    "env": ["PATH=/usr/bin:/bin"]
  },
  "linux": {
    "namespaces": [
      { "type": "pid" },
      { "type": "mount" },
      { "type": "network" }
    ]
  }
}
```

`root.path` 指向供容器使用的根文件系统，`process.args` 定义要执行的程序与参数，`linux.namespaces` 指明需要建立哪些 Namespace。实际生成的配置还需要包含完整的挂载、权限、安全策略以及平台相关字段。OCI Runtime Specification 有精确定义，不能因为知道几个主要字段就声称能够手工创建一个生产容器。

`runc` 读取符合要求的 Bundle 和配置后，使用 Linux 内核能力建立执行环境，并启动目标程序。对于应用而言，它最终得到的是一组文件路径、环境变量、进程视图和可用资源。应用并不需要知道自己是由 `docker run`、containerd 的其他客户端，还是某个容器编排系统启动的。

标准化也解释了为什么 Docker 并不是 Linux 容器的唯一实现。Docker 提供开发、构建、分发、网络与管理体验；OCI Runtime 负责与标准约定的低层执行接口衔接；Linux 内核则提供真正的进程与隔离机制。这些层次可以独立演进。

## 六、容器的隔离来自哪里

再看刚才运行的 `sleep` 进程。它既能从宿主机的进程列表中被观察到，又能在容器内看到不同的 PID。这看似矛盾，实际上是进程所属的 Namespace 不同。

Linux Namespace 对特定类别的内核资源提供独立视图。例如，PID Namespace 影响进程编号与可见性；Mount Namespace 影响挂载点视图；Network Namespace 让进程拥有独立的网络接口、路由表等网络资源；UTS Namespace 可以隔离主机名；User Namespace 可以映射用户和组 ID。一个容器不必在所有 Namespace 类型上都与宿主机隔离：Docker 可以按配置共享部分 Namespace，因此隔离程度还取决于具体运行参数。

根文件系统则决定程序通过 `/` 看到哪些文件。容器里存在 `/usr/bin/python`，只是说明它的根文件系统包含这个可执行文件，并不表示宿主机一定安装了相同路径、相同版本的 Python。Docker 通常通过镜像层和一个容器可写层组合出容器需要的文件系统视图。这里的具体实现可能使用 overlayfs 等快照机制，也可能使用其他存储后端。Docker Engine 新版本的镜像存储实现已经出现变化，所以镜像分层的原理和某个固定磁盘目录结构应该分开理解。

cgroups 负责另一种限制：进程组可以使用多少 CPU 时间、内存以及其他受控制的资源。Namespace 主要处理资源视图和隔离，cgroups 主要处理资源统计与限制，两者并不相互替代。即使为容器分配了独立 PID Namespace，如果不限制资源，进程仍可能竞争宿主机 CPU 或内存。相反，只使用 cgroups 限制一个普通 Linux 进程，也不会让它自动得到独立的根目录或网络空间。

因此，容器不是一个单独的内核特性，而是多项机制协同形成的执行环境。这也解释了它的安全边界：隔离机制能够减少进程互相干扰的机会，却不能保证恶意程序绝对无法影响宿主机。容器与宿主机共享内核，内核漏洞、过高的 Capabilities、危险挂载以及访问 Docker API 的权限，都可能扩大风险。Docker 默认采取了部分安全约束，但不能把默认配置理解为适用于任意不可信工作负载的强隔离方案。

## 七、容器为什么不同于虚拟机

虚拟机通常由 Hypervisor 提供虚拟化的硬件环境，在其中启动一个具有自己内核的 Guest OS。容器则在宿主机内核提供的进程环境中运行，通过内核隔离机制获得相对独立的用户态视图。

两种方法解决的问题有交集，但成本结构不同。虚拟机通常需要为 Guest OS 提供额外的内核与系统运行环境，并通过虚拟化机制处理设备与资源；原生 Linux 容器不必为每个实例启动内核，所以创建和启动成本通常更低，多个容器也能够共享镜像的只读内容。

不过，“容器一定比虚拟机快”不是严格结论。应用性能还受到文件系统、网络路径、CPU 限额、虚拟化平台和宿主机负载的影响。虚拟机也可以通过模板、快照及精简系统快速启动，某些工作负载放在容器内仍会遭遇额外的存储或网络开销。启动成本与业务运行性能应当分开测量。

隔离强度也不能只看有没有单独的文件系统。虚拟机通常提供 Guest Kernel 与宿主机之间的额外隔离边界；普通 Linux 容器共享宿主机内核，风险模型不同。但虚拟机也依赖 Hypervisor 的安全性，不能声称其完全不存在逃逸风险。对于高风险、多租户或需要不同内核的工作负载，往往需要更加严格的隔离设计。

还有一个实际使用时经常造成困惑的现象：在 macOS、Windows 上使用 Docker Desktop 时，Linux 容器通常运行于平台提供的 Linux 虚拟化环境中，而非直接运行在 macOS 或 Windows 内核上。Docker Desktop for Linux 也采用自己的虚拟机。这并没有推翻“Linux 容器共享内核”的机制，只是它们共享的是虚拟机里的 Linux 内核。Docker CLI 位于桌面系统上，而实际的容器进程位于那个 Linux 环境中。

所以，谈论 Docker 的架构时，必须先说明使用的是原生 Linux Docker Engine，还是通过 Docker Desktop、远程 Engine 等方式访问容器。它们对应用层命令可以提供相似体验，底层进程位置和文件系统路径却可能不同。

## 八、容器的生命周期与数据边界

容器运行时存在两类状态：Docker 管理的容器对象状态，以及 Linux 内核中的进程状态。执行 `docker create` 可以生成一个尚未启动主要进程的容器对象；执行 `docker start` 后，进程开始运行；进程退出后，容器通常进入停止状态，但容器对象可以继续保留，直到被删除。

这也回答了一个常见疑问：为什么 `docker ps` 看不到刚运行完的容器，而 `docker ps -a` 仍可能看到？因为 `docker ps` 默认只列出正在运行的容器，`-a` 才会列出包括已停止容器在内的对象。使用 `--rm` 则要求 Docker 在退出后自动清理容器，因此不一定还能通过 `ps -a` 找到它。

容器的主进程是否退出，对生命周期尤其重要。如果容器主要进程是 `sleep`，`sleep` 结束后容器就会停止；如果主进程是 Web 服务器，该服务器意外崩溃，也通常意味着容器停止。容器可以包含多个进程，但并不因此自动拥有虚拟机那样的完整服务管理系统。为一个容器配置重启策略，最多能告诉 Docker 在某些条件下重新启动它，不能保证应用业务已经恢复健康。

文件状态也有单独的生命周期。容器从镜像创建时，通常会得到独立的可写层。容器停止后，如果对象仍被保留，可写层里的变更通常仍在；容器被删除后，这一层随之删除。镜像本身仍然存在，外部挂载的 Volume 或 Bind Mount 又有不同的保留规则。

因此，停止、删除、重建三个动作不能混用。部署 PostgreSQL、Redis 等需要保存数据的服务时，不能仅凭容器“还在运行”就断定数据已经持久化；也不能因为重新创建容器后某些文件不见了，就误以为镜像被修改了。容器文件系统与数据持久化会在本专题后续文章中专门展开。

## 九、用 Dockerfile 构建自己的应用镜像

前面的实验全部使用别人已经构建好的镜像。实际开发时，我们需要把自己的 Python 程序及依赖放进镜像。Dockerfile 就是描述这件事的构建文件。它按照声明的构建步骤，从一个基础镜像出发，生成新的镜像制品。Dockerfile 本身不会启动业务容器，真正创建和启动容器仍由 Docker Engine 完成。

先准备一个极小的 FastAPI 项目。文件结构如下：

```text
docker-study/
├── app.py
├── requirements.txt
├── Dockerfile
├── .dockerignore
└── compose.yaml
```

`app.py` 提供两个接口。`/health` 用来确认 Web 应用能够回应请求，`/database` 用来检查应用是否能连接 PostgreSQL。后一个接口将在 Compose 实验中使用。

```python
import os

import psycopg
from fastapi import FastAPI

app = FastAPI()


@app.get("/health")
def health():
    return {"status": "ok"}


@app.get("/database")
def database():
    with psycopg.connect(
        os.environ["DATABASE_URL"], connect_timeout=3
    ) as conn:
        with conn.cursor() as cursor:
            cursor.execute("SELECT current_database()")
            name = cursor.fetchone()[0]
    return {"database": name}
```

`requirements.txt` 记录应用需要安装的 Python 包。为了让示例便于理解，这里只约束主要版本范围；正式交付时还应该使用锁文件或完整的依赖版本约束，保证后续构建能够重现经过验证的依赖组合。

```text
fastapi>=0.115,<1
uvicorn>=0.30,<1
psycopg[binary]>=3.2,<4
```

接下来创建 `Dockerfile`：

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .

USER 10001
EXPOSE 8000

CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
```

这份文件的顺序并非随意排列。`FROM` 确定镜像的基础，因而我们不必手工打包 Python 解释器和它运行所需的全部系统文件。`WORKDIR` 设置后续指令使用的工作目录；目录不存在时，构建器会创建它。`COPY` 将构建上下文中的文件复制进镜像，`RUN` 在**构建阶段**执行命令并形成构建结果。最后的 `CMD` 记录容器创建后默认要执行的程序，它不会在 `docker build` 过程中启动 Web 服务器。

为什么先复制 `requirements.txt` 再安装依赖，最后才复制 `app.py`？因为镜像构建可以复用已有构建结果。只修改应用代码、没有改变依赖文件时，依赖安装步骤通常能够继续使用缓存；如果一开始就把全部项目复制进去，许多无关文件变化都可能影响后续缓存命中。缓存命中还受构建参数、父层及其他输入影响，不能单靠指令顺序推断必然复用。

`USER 10001` 使默认业务进程不以容器内 root 身份运行，减少不必要的权限；这里使用数字 UID，镜像内不一定存在对应的用户名。`EXPOSE 8000` 只是声明应用预期监听的端口，不会自动让宿主机外部访问该端口。`CMD` 使用 JSON 数组形式，使 Uvicorn 成为直接启动的程序；在正常的容器停止流程中，这有利于它接收终止信号。应用监听 `0.0.0.0`，表示接受容器网络空间内所有 IPv4 接口的连接。它和宿主机端口是否对外公开，依然是两回事。

Docker 构建时还需要一份 **Build Context（构建上下文）**。例如执行 `docker build ... .`，最后的 `.` 指定当前目录作为构建上下文。`COPY app.py .` 只能引用上下文允许访问的文件，并不能任意读取宿主机的整个文件系统。把项目的虚拟环境、Git 历史甚至密钥文件无意间放进上下文，会增加构建开销，也可能带来信息泄漏。因此还应创建 `.dockerignore`：

```text
.venv/
__pycache__/
*.pyc
.git/
.env
.pytest_cache/
```

在项目根目录执行：

```bash
docker build -t docker-study-api:0.1 .
docker image ls docker-study-api
```

`-t` 为构建结果赋予易读的名称和标签；它不是镜像的不可变内容标识。BuildKit 等构建组件读取 Dockerfile 和构建上下文，完成指令求解，输出可以由 Docker Engine 管理的镜像。构建日志中的阶段编号和缓存标记，可以用来观察哪些步骤真正执行、哪些步骤复用了已有结果。

随后启动应用：

```bash
docker run --rm \
  -p 127.0.0.1:8000:8000 \
  docker-study-api:0.1
```

在另一个终端访问：

```bash
curl http://127.0.0.1:8000/health
```

预期得到 `{"status":"ok"}`。此时尚未运行 PostgreSQL，也没有传入 `DATABASE_URL`，所以不要把 `/database` 的失败解释成容器网络一定存在问题。`-p` 的左侧是宿主机端口、右侧是容器端口；`127.0.0.1:` 将端口发布限制在宿主机回环地址，用于本机实验更合适。停止该命令后再进行后面的 Compose 实验，以免两个容器同时争用宿主机的 8000 端口。

至此，可以区分三个动作：`Dockerfile` 描述如何构建镜像，`docker build` 生成镜像，`docker run` 则根据镜像创建并运行容器。修改 `app.py` 不会自动更新已经构建好的镜像；需要重新构建，并用新镜像重新创建容器。详细的镜像层、缓存失效规则、多阶段构建与构建安全将在镜像专题中展开。

## 十、用 Docker Compose 管理多个容器

只有一个 Web 服务时，`docker run` 已经足够直观。加入 PostgreSQL 后，就要考虑如何同时管理数据库容器、应用容器、容器间网络、环境变量和持久化数据。如果全部通过命令行完成，配置散落在多个命令中，后续重建容易遗漏。

Docker Compose 使用声明式 YAML 文件描述**一组相互协作的服务**及其网络、存储配置，然后通过 `docker compose` 命令统一创建和管理。Compose 并没有取代 Docker Engine；它解析配置并调用底层引擎的构建和容器管理能力。现在推荐使用 Compose V2 的 `docker compose` 命令与 `compose.yaml` 文件格式，不需要照搬旧教程里的独立 `docker-compose` 可执行文件或旧版 `version:` 字段。

在项目根目录创建 `compose.yaml`：

```yaml
services:
  api:
    build: .
    ports:
      - "127.0.0.1:8000:8000"
    environment:
      DATABASE_URL: postgresql://demo:local_demo_password@db:5432/demo
    depends_on:
      db:
        condition: service_healthy
    healthcheck:
      test:
        - CMD
        - python
        - -c
        - "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=2).close()"
      interval: 5s
      timeout: 3s
      retries: 15

  db:
    image: postgres:18
    environment:
      POSTGRES_USER: demo
      POSTGRES_PASSWORD: local_demo_password
      POSTGRES_DB: demo
    volumes:
      - pgdata:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 15

volumes:
  pgdata:
```

这段 YAML 描述两个服务。`api` 的 `build: .` 让 Compose 使用当前项目目录中的 Dockerfile 构建应用镜像；`db` 则直接使用已经发布的 PostgreSQL 镜像。`services` 描述的是服务的**期望配置**，并不是某两个具体容器的永久 ID。Compose 会根据项目名、服务名和副本数量创建相应的容器，后续可以在配置变化时重新创建它们。

Compose 默认会为该项目创建网络，并让服务在网络中按照名称相互访问。对 `api` 而言，`db` 是可以在项目网络中解析的服务名，所以数据库连接地址使用 `db:5432`。这不是容器从自身的 `localhost` 访问另一个容器：每个容器通常有独立的网络空间，容器里的 `127.0.0.1` 指向它自己。这里没有为 PostgreSQL 配置 `ports`，因而没有主动将它的 5432 端口发布到宿主机；应用仍然可以通过 Compose 网络访问数据库。

`depends_on` 的 `service_healthy` 表示在启动 `api` 之前，Compose 先等待 `db` 通过所定义的健康检查。如果只写普通依赖关系，通常只能约束启动顺序，不能证明数据库已经准备好接受连接。但即使配置了健康检查，也不能保证数据库此后永远可用：网络断开、数据库重启或账号权限错误，都可能让后续 SQL 请求失败。因此应用仍需正确处理运行期间的连接异常。`pg_isready` 检查的是 PostgreSQL 是否响应连接就绪探测，不能替代完整的业务 SQL 验证。

数据库健康与 API 就绪也是两件事。`api` 的健康检查在容器内部使用 Python 标准库访问 `/health`，无需假定基础镜像里已经安装 `curl`。只有 Uvicorn 开始接受 HTTP 请求并返回成功响应，这项检查才会通过。不过 `/health` 没有执行数据库查询，因此它只验证 Web 应用的响应能力；数据库凭证和实际 SQL 是否可用，仍通过后面的 `/database` 接口验证。

数据库的 `volumes` 定义了一个命名卷 `pgdata`，挂载到 PostgreSQL 容器内的 `/var/lib/postgresql`。这里特意使用 PostgreSQL 18 对应的位置：官方镜像从 18 开始，将默认数据目录调整到 `/var/lib/postgresql/18/docker`，声明的 Volume 位置也改为 `/var/lib/postgresql`。对于 PostgreSQL 17 及更早版本，典型的挂载位置是 `/var/lib/postgresql/data`，不能不加区分地照搬。命名卷的数据生命周期与容器对象不同，删除或重新创建数据库容器时，卷可以继续保留。

上面的密码只供本机教学实验使用。把口令直接写在 Compose 文件中，不适合生产部署；环境变量本身也不构成强保密机制。正式环境应采用受控的凭证注入方案，并根据权限与威胁模型管理配置，不要将真实密码提交到代码仓库。

先检查配置，再启动应用：

```bash
docker compose config -q
docker compose up --build --wait --wait-timeout 120
docker compose ps
```

第一条命令解析并验证 Compose 配置；第二条根据配置构建应用镜像、准备网络和卷、创建并启动容器，然后等待服务达到运行或健康状态。`--wait` 隐含后台运行模式，本例两个服务都定义了健康检查，因此会等待两者通过检查，再成功返回；`--wait-timeout 120` 限制这一步就绪等待的时长，不代表整个镜像构建也必须在两分钟内完成。如果等待失败，应先查看状态和日志，再决定怎样处理。第三条命令显示服务状态。若需要查看日志，可以执行：

```bash
docker compose logs -f api
docker compose logs -f db
```

现在再次访问两个接口：

```bash
curl http://127.0.0.1:8000/health
curl http://127.0.0.1:8000/database
```

第二个接口在服务及数据库均正常时，应返回包含 `"database":"demo"` 的 JSON。这样就能看到 Compose 的实际作用：它没有把两套程序合并到一个进程，而是为两个独立容器建立了可通信的网络环境，并把需要的运行配置交给它们。

还可以验证数据是否真正与数据库容器分离。先通过 PostgreSQL 自带的 `psql` 创建一张简单的表，再写入一条记录：

```bash
docker compose exec db psql -U demo -d demo \
  -c "CREATE TABLE IF NOT EXISTS notes (id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY, content text NOT NULL);"

docker compose exec db psql -U demo -d demo \
  -c "INSERT INTO notes (content) VALUES ('persisted');"
```

然后删除这组服务的容器并重新启动：

```bash
docker compose down
docker compose up --wait --wait-timeout 120
docker compose exec db psql -U demo -d demo -c "SELECT * FROM notes;"
```

如果仍能读到刚才的 `persisted`，就说明数据保存在可复用的命名卷中，随容器重新创建而继续存在。默认的 `docker compose down` 会移除项目容器与网络，但不会移除已经声明的命名卷。相反，`docker compose down -v` 会一并删除 Compose 管理的相关卷，**其中的数据库数据会丢失**，不要在需要保留数据的环境中随意执行。

Dockerfile 和 Compose 在这里形成了清楚的分工：Dockerfile 负责将某个应用构建为镜像，Compose 负责描述一组服务怎样组合运行；Docker Engine 负责真正的镜像、网络、卷与容器操作。Compose 适合本地多容器开发，也可以用于一定规模的单机部署，但它本身不提供跨多台宿主机的自动迁移、分布式调度和完整高可用保障。容器网络、Volume 生命周期、健康检查与服务恢复，将在后面的专题进一步讨论。

## 十一、Docker 解决了什么，又没有解决什么

现在再回到最初的 Python 服务。我们希望把代码、Python 运行时和依赖一起交付，让另一台机器尽可能按照同样的方式启动它。Docker 镜像提供了可分发的文件与配置，Docker Engine 根据这些内容创建容器，再借助 Linux 内核运行实际进程。不同应用可以拥有相对独立的文件系统、进程和网络视图，部署过程因而更加可重复。

不过，镜像一致并不保证不同宿主机的所有行为完全一致。CPU 架构、Linux 内核及其功能、外部存储、DNS、网络策略、配置、时区、Secret 和数据库状态，都可能影响程序结果。一个只适用于 `linux/amd64` 的镜像也未必可以直接在 `linux/arm64` 主机上原生运行，除非提供对应平台的镜像或额外的模拟执行环境。

Docker 为用户定义的容器网络提供名称解析，前文 Compose 服务通过 `db` 找到数据库，就是一种基础服务发现。跨主机的服务发现、流量调度和故障恢复，则需要结合所用的编排系统与基础设施另行设计。数据库事务和业务幂等性也仍由应用及数据系统保证。Docker 能帮我们创建和管理进程运行环境，却不会自动让这些进程组成一个可靠的分布式系统。容器是否适合重新启动、停止时如何处理正在执行的请求、数据应该放在哪里，仍需要按照业务要求设计。

理解 Docker 最有效的方式，是始终把两个事实同时放在脑中：对开发者而言，它是一套镜像构建、交付与容器管理工具；对 Linux 内核而言，容器里的应用仍然是一组受到特定隔离与资源约束的进程。

至此，我们已经从 Linux 进程出发，经历了镜像构建、单容器启动和 Compose 多容器运行。下一篇将暂时放下 Docker 的高层命令，直接研究 Linux Namespace、cgroups 和 RootFS。我们会通过操作系统提供的工具观察：一个普通进程怎样获得新的资源视图，以及这些机制具体能隔离什么、不能隔离什么。
