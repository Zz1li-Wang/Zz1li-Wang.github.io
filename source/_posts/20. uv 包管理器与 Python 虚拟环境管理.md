Python 项目通常需要安装一些第三方库。最常见的方法是使用 `pip`，再用 `venv` 为每个项目建立独立的运行环境。

这套方法能够正常工作。不过，项目多了以后，还需要解决另外几件事：安装哪个 Python 版本、如何记录依赖、怎样让其他开发者安装相同的版本，以及怎样在 CI 和服务器上重建环境。

[uv](https://docs.astral.sh/uv/) 是一个用 Rust 编写的 Python 包与项目管理工具。它提供依赖安装、版本解析、虚拟环境管理、Python 安装和命令执行等功能，并且兼容不少常见的 `pip` 工作流。

本文先介绍虚拟环境的工作原理，再使用 uv 创建一个项目，逐步了解它的主要命令。示例以 CPython 3.12、uv 0.13 系列及 Linux/macOS 的终端命令为基础。uv 更新较快，部分初始化模板和默认行为在旧版本中有所不同。

## 一、Python 包安装在哪里

先看两个常用命令。

```bash
python --version
pip --version
```

`python` 用来启动解释器，`pip` 用来安装第三方包。虽然经常一起使用，但它们实际上是两个独立的可执行命令。

终端会按照 `PATH` 环境变量中的目录顺序寻找命令。电脑上如果安装了多个 Python，那么 `python` 和 `pip` 有可能来自不同的目录。

在 Linux 或 macOS 上，可以查看它们的实际位置。

```bash
which python
which pip
```

Windows 可以使用 `where python` 和 `where pip`。

因此，使用 pip 时有一种更稳妥的写法。

```bash
python -m pip install httpx
```

`-m` 参数让当前 Python 解释器执行指定模块。这样，`pip` 就由前面的 `python` 启动，安装目标与当前解释器保持一致，前提是这个解释器中已经安装了 pip。

第三方包一般安装到 Python 对应的 `site-packages` 目录。运行 `import httpx` 时，解释器会沿着模块搜索路径寻找它。这个搜索路径可以用下面的命令查看。

```bash
python -c "import sys; print('\n'.join(sys.path))"
```

如果两个项目共用同一个 Python 环境，它们也可能共用相同的第三方包。一个项目升级了依赖，另一个项目的运行结果就可能受到影响。

Python 为此提供了虚拟环境。

## 二、虚拟环境

Python 标准库自带 `venv` 模块，可以创建一个虚拟环境。

```bash
python -m venv .venv
```

执行后，当前目录会生成 `.venv`。在 Linux 和 macOS 上，它的结构大致如下。

```text
.venv/
├── bin/
│   ├── python
│   ├── pip
│   └── activate
├── lib/
│   └── python3.12/
│       └── site-packages/
└── pyvenv.cfg
```

Windows 的对应目录通常是 `Scripts` 和 `Lib\site-packages`。

`.venv/bin/python` 是这个虚拟环境的 Python 入口，`site-packages` 用来存放环境中的第三方包。创建环境时不需要复制一份完整的 Python 安装，虚拟环境通常会继续使用基础解释器的标准库。

其中，`pyvenv.cfg` 记录了基础 Python 的位置等信息。Python 启动后，会根据这些信息确定当前环境的安装路径和模块搜索路径。

可以直接观察解释器使用的路径。

```bash
.venv/bin/python -c "import sys; print(sys.prefix); print(sys.base_prefix)"
```

`sys.prefix` 是当前环境的前缀目录，`sys.base_prefix` 是基础 Python 的前缀目录。对于使用 `venv` 创建的环境，两者通常不同。

接着，激活虚拟环境。

```bash
source .venv/bin/activate
```

激活脚本会将 `.venv/bin` 放到当前 Shell 的 `PATH` 前面，并设置 `VIRTUAL_ENV` 等环境变量。此时执行 `python`，通常就会找到虚拟环境中的解释器。

```bash
which python
python -c "import sys; print(sys.prefix)"
```

退出环境使用 `deactivate`。

```bash
deactivate
```

实际上，激活只是让终端使用虚拟环境更加方便。即使没有激活，也可以直接运行它的 Python。

```bash
.venv/bin/python app.py
```

虚拟环境的隔离主要发生在 Python 包与命令入口层面。它不会隔离操作系统进程、网络或文件访问，因此不能代替容器或虚拟机。

`.venv` 也不适合作为项目交付文件。环境中的脚本可能包含解释器的绝对路径，部分依赖还包含与操作系统、CPU 架构及 Python ABI 相关的二进制文件。通常应该保存依赖声明，然后在目标机器上重新创建环境。

## 三、为什么使用 uv

假设我们准备为一个新项目安装 `httpx`，并把环境交给其他开发者使用。按照传统工作流，大致会执行下面的命令。

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install httpx
python -m pip freeze > requirements.txt
python -c "import httpx; print(httpx.__version__)"
```

这样可以运行程序，但 `requirements.txt` 是对当前环境的一次快照。它会把直接依赖与间接依赖放在一起。以后修改依赖时，需要开发者维护这个文件，并让新环境与它保持一致。

如果要分开管理依赖范围和锁定版本，还得引入其他工具。`venv`、`pip`、`pip-tools` 和 `pyenv` 可以组合完成这些工作，不过衔接由使用者负责。

uv 提供了另一种用法。

```bash
uv init --app --python 3.12 demo
cd demo
uv add httpx
uv run python -c "import httpx; print(httpx.__version__)"
```

这里的 `uv add` 会修改依赖声明、解析和锁定具体版本，并同步到项目虚拟环境。`uv run` 会在执行前检查环境是否与项目配置协调。

对于新成员或 CI，仓库中的声明与锁文件就足以说明应该安装哪些 Python 包，不需要复制某个人的 `.venv`。

这种工作流减少了几个文件之间的手工同步操作。uv 也能够直接安装 Python、为命令行工具创建隔离环境，以及管理包含多个包的代码仓库。项目中原本需要几个工具相互配合的事情，现在可以由同一个程序完成。

速度是另一个明显的吸引力。uv 的依赖解析器与安装器由 Rust 实现，能够复用下载和构建缓存，安装包时也会利用文件链接等机制减少重复复制。

官方基准测试中，一些场景明显快于 pip。不过速度取决于缓存是否命中、网络、包的大小和是否需要本地构建，不能把某个测试中的倍数当作所有项目的固定结果。后面会具体介绍缓存。

还有一点需要说明：锁定依赖、管理项目和隔离工具都已有其他成熟方案。uv 的优势是把这些能力结合起来，并提供较快的实现。项目本来已经采用稳定的工具链时，是否迁移仍然要考虑现有配置与团队成本。
## 四、安装 uv

uv 是独立的可执行程序，安装 uv 本身不要求预先安装 Python。

Linux 和 macOS 可以使用官方安装脚本。

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

安装完成后，检查版本。

```bash
uv --version
```

Windows 的安装方式，以及 Homebrew、pipx 等其他安装方法，可以查阅[官方安装文档](https://docs.astral.sh/uv/getting-started/installation/)。

uv 的命令分成几类。`uv python` 管理 Python 解释器，`uv venv` 创建虚拟环境，`uv pip` 提供与 pip 相近的安装接口。建立完整项目后，主要使用的是 `uv init`、`uv add`、`uv lock`、`uv sync` 和 `uv run`。

先用 uv 创建一个项目。

## 五、创建项目

执行下面的命令。

```bash
uv init --app --python 3.12 orders-api
cd orders-api
```

`--app` 表示创建应用项目，`--python 3.12` 指定项目使用的 Python 版本。`orders-api` 是目录名称。

在 uv 0.13 系列中，生成的主要文件如下。

```text
orders-api/
├── .python-version
├── README.md
├── pyproject.toml
└── src/
    └── orders_api/
        └── __init__.py
```

`src/orders_api/__init__.py` 里有一个简单的 `main()` 函数。生成的 `pyproject.toml` 还会配置一个同名命令入口，因此可以直接执行：

```bash
uv run orders-api
```

第一次运行时，uv 会根据项目配置寻找 Python，按需创建 `.venv`、生成 `uv.lock`，然后运行程序。默认模板会打印一条问候信息。

现在再看项目目录，会多出两个重要的内容。

```text
orders-api/
├── .venv/
├── uv.lock
├── pyproject.toml
├── .python-version
└── src/
```

`pyproject.toml` 是项目的配置与元数据文件。`uv.lock` 保存依赖解析结果。`.venv` 则是当前机器上实际安装的环境。

这些文件之间有明确的关系。uv 根据 `pyproject.toml` 中的依赖要求生成 `uv.lock`，然后按照锁文件把合适的包安装进 `.venv`。运行命令时，使用的是这个环境。

新版本的 `uv init` 默认会为应用配置构建系统和 `src` 目录；早于 uv 0.12 的版本默认模板不同。对于不需要安装自身为 Python 包的简单脚本项目，也可以使用 `uv init --no-package`，生成不带构建系统的项目。

## 六、安装与移除依赖

下面给项目安装 HTTP 客户端库 `httpx`。

```bash
uv add 'httpx>=0.28,<0.29'
```

命令执行完毕后，`pyproject.toml` 的依赖字段会增加一项。

```toml
[project]
requires-python = ">=3.12"
dependencies = [
    "httpx>=0.28,<0.29",
]
```

这段配置表示项目接受 `0.28` 系列的 `httpx`。uv 会查找符合要求的版本，同时解析 `httpx` 所依赖的其他包。

运行 `uv add` 时，uv 通常会连续完成依赖声明、锁文件更新和环境同步。安装完成后，可以直接运行代码。

```bash
uv run python -c "import httpx; print(httpx.__version__)"
```

以后不再需要 `httpx`，可以执行：

```bash
uv remove httpx
```

测试工具和代码检查工具一般只用于开发。uv 允许将它们放入依赖组。

```bash
uv add --dev pytest
uv add --group lint ruff
```

生成的配置类似下面这样，具体版本号由当时的解析结果决定。

```toml
[dependency-groups]
dev = ["pytest>=9"]
lint = ["ruff>=0.17"]
```

`dev` 是一个有默认行为的依赖组。通常执行 `uv sync` 或 `uv run` 时，uv 会包含这一组。其他组可以通过 `--group` 指定。

```bash
uv run pytest
uv run --group lint ruff check .
```

Python 包还有另一种可选依赖机制，写在 `[project.optional-dependencies]` 中。它主要用于发布给其他项目使用的额外功能，例如允许使用者安装 `some-package[postgres]`。依赖组主要服务于项目自身的开发、测试和维护，两种配置的用途不同。

## 七、依赖解析与锁文件

`pyproject.toml` 通常记录的是版本范围。例如，`httpx>=0.28,<0.29` 允许安装多个不同的补丁版本。

如果每次部署时都重新选择版本，那么不同日期创建的环境可能包含不同的依赖。为了解决这个问题，uv 使用 `uv.lock` 记录解析结果。

依赖解析需要同时满足所有包的要求。假设项目依赖 A 和 B，A 要求 `C>=1,<3`，B 要求 `C>=2,<4`，那么 C 必须满足两个范围的交集，即 `C>=2,<3`。如果 C 的某个版本又不支持当前 Python，解析器还需要排除它。

uv 会把直接依赖、间接依赖和它们之间的关系写入锁文件，同时记录不同 Python 版本、平台可能使用的条件分支。这也是 uv 所说的跨平台锁文件。同一份 `uv.lock` 可以包含不同环境适用的结果，安装时由 uv 选择对应的分支和分发文件。

生成锁文件的命令是：

```bash
uv lock
```

把锁文件中的依赖安装到本地环境，使用：

```bash
uv sync
```

`uv lock` 负责解析，`uv sync` 负责同步环境。后者默认进行精确同步，会删除当前环境中多余的包，使安装结果与本次选中的锁定依赖保持一致。

日常开发不需要每次手动执行这两个命令。`uv add` 会更新相关状态，`uv run` 默认也会在运行前检查锁文件和环境，并在需要时完成更新。

已经有锁文件后，新版本的发布不会自动导致项目升级。需要主动升级全部依赖，可以执行：

```bash
uv lock --upgrade
```

只升级某个包，可以执行：

```bash
uv lock --upgrade-package httpx
```

升级仍然受到 `pyproject.toml` 中版本范围的限制。上面的 `httpx<0.29` 不会因为加上 `--upgrade` 就允许安装 0.29。

这里还需要区分 `uv.lock` 与 `pip freeze`。`pip freeze` 主要列出某个环境当前安装的包和版本，而 `uv.lock` 来源于项目的依赖解析，保存更完整的依赖关系与环境条件。对于 uv 项目，应该让锁文件跟随源码一起提交到 Git。

锁文件能提高依赖安装的可复现程度，但仍然依赖包源可用、对应分发产物存在，以及目标机器具备必要的系统库和构建工具。锁定 Python 包版本不等于锁定整台机器。

## 八、运行程序

在传统工作流中，开发者经常先激活 `.venv`，再运行 `python` 或 `pytest`。uv 项目可以直接使用 `uv run`。

```bash
uv run python -c "import sys; print(sys.executable)"
uv run pytest
uv run orders-api
```

第一个命令会输出正在使用的 Python 路径。通常它会指向项目的 `.venv`。

`uv run` 的一个好处是，执行命令的人不需要依赖当前终端是否激活过虚拟环境。CI 和脚本同样可以明确地使用项目环境。

默认情况下，`uv sync` 会删除多余的第三方包，`uv run` 则采用非精确同步，一般不会清除额外包。如果希望运行前也进行精确同步，可以加上 `--exact`。

```bash
uv run --exact pytest
```

此外，`uv run` 可以为一次执行临时增加依赖。

```bash
uv run --with rich python -c 'from rich import print; print("[green]OK[/green]")'
```

这个命令适合临时试验。如果项目源代码长期依赖 `rich`，还是应该用 `uv add rich` 将它加入项目声明。

已经激活另一个虚拟环境时，uv 项目命令仍然会优先管理项目环境。确实需要使用当前激活环境，可以明确传入 `--active`。对于普通项目，让 uv 使用项目自己的 `.venv` 通常更容易维护。

## 九、管理 Python 版本

到这里，我们已经使用 `--python 3.12` 创建了项目。uv 也能够安装和查找 Python 解释器。

```bash
uv python install 3.12
uv python list --only-installed
uv python find 3.12
```

如果指定的 Python 不存在，uv 在默认配置下可以自动下载。它管理的 CPython 来自 Astral 的 `python-build-standalone` 可分发构建。uv 把自己安装的解释器称为 managed Python，其他来源的解释器称为 system Python，其中也包括 `pyenv` 等工具安装的版本。

项目目录中的 `.python-version` 可以指定 uv 默认请求哪个 Python 版本。

```bash
uv python pin 3.12
```

执行后，`.python-version` 通常包含一行：

```text
3.12
```

与它相关的还有 `pyproject.toml` 中的 `requires-python`。

```toml
[project]
requires-python = ">=3.12"
```

`.python-version` 用于选择日常使用的解释器，`requires-python` 用于声明项目支持的 Python 范围，并参与依赖解析。一个项目可以声明支持 Python 3.11 及以上，同时把本地开发的默认版本设为 3.12。

维护可发布的库时，需要特别注意 `requires-python` 的范围。写成 `>=3.12` 会允许未来的 Python 版本。如果项目只验证过有限的 Python 版本，就需要结合实际兼容性测试和发布计划来决定约束范围。

某些项目依赖系统定制的 Python 或特定编译选项，这时可以用 `--python` 指向已有解释器，并根据需要禁用自动下载。uv 提供统一的解释器管理接口，但并不要求所有项目都改用 uv 下载的 Python。

## 十、旧项目中的 uv pip

如果一个项目仍然使用 `requirements.txt`，不需要为了使用 uv 立刻迁移到 `pyproject.toml`。

先创建环境。

```bash
uv venv --python 3.12
```

然后安装依赖。

```bash
uv pip install -r requirements.txt
```

还可以直接安装指定的包。

```bash
uv pip install httpx
uv pip freeze
```

`uv pip` 提供了一套与 pip 相近的命令接口。它直接管理目标环境，不会因为安装了 `httpx` 就自动更新项目的 `pyproject.toml` 和 `uv.lock`。

对于需要从宽松约束生成固定版本文件的旧项目，可以使用：

```bash
uv pip compile requirements.in -o requirements.txt
uv pip sync requirements.txt
```

第一条命令解析依赖并输出文件，第二条命令按文件同步环境。这种工作流可以继续使用，只要团队明确哪份文件是依赖版本的权威来源即可。

uv 默认倾向于把包安装进虚拟环境。`uv pip install` 会使用已激活的虚拟环境，或者寻找当前目录及其父目录中的 `.venv`。如果确实要安装到非虚拟环境，可以明确指定解释器或使用 `--system`，但不建议随意修改操作系统管理的 Python。

还有一处容易忽略的差异：uv 不会读取 pip 专有的 `pip.conf` 或 `PIP_INDEX_URL`。使用私有包索引时，需要改用 uv 支持的配置方式，例如 `UV_INDEX_URL`，并检查认证和索引优先级设置。

## 十一、独立的命令行工具

`ruff`、`black` 之类的程序既可以成为项目开发依赖，也可以单独运行。

如果团队要求所有人使用相同的 Ruff 版本，应该把它加入项目依赖组，并通过 `uv run` 执行。

```bash
uv add --group lint ruff
uv run --group lint ruff check .
```

如果只是临时在某个目录检查代码，可以使用 `uvx`。

```bash
uvx ruff check .
```

`uvx` 是 `uv tool run` 的简写。uv 会为工具准备独立的环境，避免把工具依赖装进当前项目的 `.venv`。

对于经常使用的个人命令，也可以安装成长期可调用的工具。

```bash
uv tool install ruff
```

需要注意，直接使用未指定版本的 `uvx ruff`，不一定与项目锁文件中的 Ruff 相同。在 CI 中应固定工具版本，或者直接使用项目的依赖组。

## 十二、在团队和 CI 中使用 uv

开发环境中的 uv 会自动维护锁文件，这样使用比较方便。但 CI 通常应该按照仓库提交的结果运行，不希望测试过程中悄悄产生新的依赖解析结果。

可以先检查锁文件。

```bash
uv lock --check
```

也可以在同步环境时要求锁文件保持最新，并且不允许修改它。

```bash
uv sync --locked
```

`--locked` 的含义是：如果项目声明需要更新锁文件，命令就报错。测试时可以直接使用：

```bash
uv run --locked pytest
```

uv 还提供 `--frozen`，用于直接使用现有锁文件，不检查它与 `pyproject.toml` 是否同步。通常 CI 使用 `--locked` 更合适，因为它能够发现提交代码时漏掉的锁文件更新。

对于需要提前确认环境状态的场景，可以使用：

```bash
uv sync --check
```

部署时通常不需要安装测试和代码检查工具。对于已经配置构建系统的应用项目，可以在镜像构建阶段执行：

```bash
uv sync --locked --no-dev --no-editable
```

`--no-dev` 排除默认的开发依赖组，`--no-editable` 避免将项目以可编辑方式安装。随后可以使用 `.venv` 中的入口运行应用。实际部署还需要根据镜像结构、运行用户和系统依赖调整。

一般来说，Git 仓库应该保存 `pyproject.toml`、`uv.lock`，以及团队约定使用的 `.python-version`。`.venv` 应放进 `.gitignore`。

对于准备发布到 PyPI 的库，还要多考虑一步。库仓库中的 `uv.lock` 用于固定开发和测试环境，安装这个库的其他项目并不会直接采用该锁文件。使用者最终遵循的是库发布元数据中的依赖范围，因此库作者仍需测试所声明的兼容范围。

## 十三、缓存与环境重建

uv 的安装速度部分来自缓存机制。下载的包和构建产物可以在多个环境之间复用，条件允许时也可以使用硬链接或写时复制，减少重复下载和文件复制。

查看缓存目录可以执行：

```bash
uv cache dir
```

清理不再需要的缓存条目可以执行：

```bash
uv cache prune
```

缓存与 `.venv` 是两回事。缓存保存的是可复用的下载和构建产物，`.venv` 保存的是当前项目的实际安装结果。

如果项目环境出现异常，可以先确认 `pyproject.toml` 和 `uv.lock` 已经提交并且可信，然后删除项目的 `.venv`，重新同步。

```bash
rm -rf .venv
uv sync --locked
```

以上删除命令只适用于确认当前目录就是项目根目录的情况。Windows 需要使用对应的目录删除命令。

重新同步成功，说明 uv 能够从项目声明和锁文件重建 Python 环境。包源、构建工具链或系统动态库缺失时，重建仍然可能失败，这需要另外排查。

最后回顾一下几个最常用的命令。

```bash
uv init --app --python 3.12 orders-api  # 创建项目
uv add httpx                           # 添加运行依赖
uv add --dev pytest                    # 添加开发依赖
uv lock                                # 解析依赖
uv sync                                # 同步环境
uv run pytest                          # 运行命令
uv run --locked pytest                 # 使用已提交的锁文件测试
```

日常开发主要围绕这些命令进行。`pyproject.toml` 和 `uv.lock` 记录项目所需的依赖，`.venv` 可以随时在本机重新生成。理解它们的关系以后，uv 的其他命令也比较容易掌握。
