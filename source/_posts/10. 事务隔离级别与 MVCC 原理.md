假设数据库里有一条记录，余额为 100。事务 A 查询到了 100，还没有结束；事务 B 将余额改为 150 并提交。现在 A 再查询一次，应该得到 100，还是 150？

这件事没有脱离上下文的唯一答案。在 PostgreSQL 默认的 `READ COMMITTED` 下，A 通常会得到 150；在 `REPEATABLE READ` 下，它仍然会得到 100。

更有意思的是，B 的提交不需要等待 A 完成普通查询。两个事务可以在同一段时间内，对同一行数据形成不同的、各自合法的认识。

数据库不是把所有查询按顺序锁起来，也不是给每个事务复制一份完整数据库。PostgreSQL 通过多版本并发控制（Multi-Version Concurrency Control，MVCC），保留行的不同版本，并按读取者所处的事务快照判断哪个版本可见。

隔离级别则决定快照如何取得、可以使用多久，以及当并发写入发生冲突时应当如何处理。下文描述的是 PostgreSQL 18 的具体语义，同名隔离级别在其他数据库中不一定具有相同行为。

## 一、一次 UPDATE 为什么可能留下两个行版本

在抽象的关系模型里，我们认为某个主键对应一行数据。然而在 PostgreSQL 的堆表存储中，`UPDATE` 通常不是直接覆盖原有行版本的全部内容，而是创建一个新的行版本，并在旧版本的元信息中记录它已被更新。这样，旧版本就有机会继续服务于尚未结束的旧快照，而新版本可以服务于较新的快照。

每个行版本都有一些内部元信息，其中最重要的两个字段是 `xmin` 和 `xmax`。这里的 `xmin` 指创建该行版本的事务 ID；`xmax` 则可能记录删除或更新它的事务 ID。

这里使用“可能”，因为 `xmax` 也会被行锁等机制使用，不能简单地把它解释为“非零就表示此行已经删除”。真实可见性判断还要考虑标志位、事务状态、命令 ID、子事务等条件。

设某行原本为 `balance=100`，由已提交的事务 T10 创建。事务 T20 将其更新为 150。在便于理解的简化模型中，旧版本可以写成 `V1(100, xmin=T10, xmax=T20)`，新版本可以写成 `V2(150, xmin=T20, xmax=0)`。

如果 T20 尚未提交，其他事务一般仍能看到 V1，却不能看到 V2；如果 T20 已提交，之后取得的新快照通常看到 V2，而一个早于 T20 提交时刻取得的长期有效快照，仍可能看到 V1。

需要注意，这里的 T10、T20 是示意用的事务标识，不是时间戳，事务 ID 的大小也不能直接充当提交顺序。事务可能先取得较小的 ID，却比其他事务更晚提交。判断是否可见，不能只比较“哪个 ID 更小”，还必须知道相应事务在快照取得时是否已经完成，以及最终是提交还是回滚。

新版本也不一定永远沿着一条简单的物理链保存。PostgreSQL 有 Heap-Only Tuple（HOT）等更新优化，索引是否需要新条目、行版本如何在页内组织，与更新的列和页面剩余空间有关。本文只把“同一逻辑行可能有多个物理版本”当作理解隔离机制的起点，不把这种简化描述误认为精确的磁盘布局。

## 二、快照不是数据库文件的完整副本

如果每次读取都复制整个数据库，MVCC 就无法承受正常的业务负载。PostgreSQL 的快照不是数据页副本，它主要记录某一时刻事务活动范围的信息，读取时再结合行版本和事务提交状态进行判断。

PostgreSQL 提供了 `pg_current_snapshot()` 用于观察当前快照。其文本形式可以概括为 `xmin:xmax:xip_list`。

这里需要特别小心：**快照中的 `xmin`、`xmax`，和行版本中的同名系统列不是一回事。** 快照 `xmin` 是该快照所关注的最老活跃事务 ID 边界；快照 `xmax` 是上界，达到或超过这一上界的事务 ID 对该快照来说尚未完成；`xip_list` 记录取得快照时仍在进行中的顶层事务 ID。

因此，对于某个在快照上界以下的事务，如果它仍出现在进行中列表里，其写入不能仅因 ID 较早而对快照可见。如果它已经完成，还要根据提交或回滚状态决定结果。

自己事务先前的写入则存在特殊的“读己之写”规则，命令 ID 也参与同一事务内语句先后的可见性处理。子事务还有额外的父子关系判断，这与上一篇讨论的 `pg_subtrans` 相衔接。

可以在 PostgreSQL 中查看当前快照：

```sql
SELECT pg_current_snapshot();
```

这个函数输出的是当前时刻相关的事务可见性信息，不是“当前数据库第几个版本”的简单编号，也不能只凭输出字符串恢复某个时刻的全部业务数据。

`pg_visible_in_snapshot()` 能辅助判断顶层事务 ID 对指定快照的可见性，但官方明确指出，它不能直接用于判断子事务 ID。用这些接口观察原理是有价值的，生产业务不应该依赖系统列 `xmin` 的具体数值制定长期持久化协议。

快照提供了读取某段已提交历史的视角，但并发数据库还必须处理“写入正在发生”的情况。一个正在修改的行并不能凭“旧快照还能看到旧版本”就让所有写入者随意改动同一行。PostgreSQL 在 MVCC 之外仍使用行锁、表锁和事务冲突检测。MVCC 主要解释普通读取为何可以与写入并行；它从来不意味着数据库没有锁。

## 三、READ COMMITTED：每条语句重新看一次数据库

PostgreSQL 默认的隔离级别是 `READ COMMITTED`。对于不带 `FOR UPDATE` 或 `FOR SHARE` 的普通 `SELECT`，每条语句开始执行时会取得用于可见性判断的快照。查询不读取其他事务尚未提交的修改，却可以读取上一条语句之后新提交的结果。

这正是开头那次余额查询得到不同值的原因。事务 A 的第一次查询在事务 B 提交前取得快照，因此看到 100；B 提交后，A 的第二条查询取得新的快照，于是看到 150。两次查询属于同一个数据库事务，但使用了不同的读视角。

这与“事务里只有一份快照”的常见印象不同。只有更高隔离级别才会维持更稳定的事务级视角。SQL 标准把两次读取同一行、结果因其他事务的提交而改变称为**不可重复读**（nonrepeatable read）。

如果重复执行相同条件的查询，匹配行集合由于其他事务插入、删除或修改而变化，则称为**幻读**（phantom read）。在 PostgreSQL 的 `READ COMMITTED` 下，两种现象都可能发生。

虽然 SQL 标准还定义了 `READ UNCOMMITTED`（读未提交），但 PostgreSQL 并不提供真正允许普通查询读取其他事务未提交版本的这种模式。设置为 `READ UNCOMMITTED` 时，PostgreSQL 实际仍按 `READ COMMITTED` 工作。

因此，在 PostgreSQL 中不会因为显式选择“读未提交”就出现脏读。这是 PostgreSQL 的实现选择，而不是所有数据库的共同规则。

同样重要的是，`READ COMMITTED` 的 `UPDATE` 不能机械地理解成“严格按照语句开始时那一份快照修改”。如果目标行被其他事务并发修改，当前更新者可能等待对方完成。在对方提交之后，PostgreSQL 会针对更新后的行版本重新检查 `WHERE` 条件，符合条件才继续更新。

这就是为什么 `UPDATE account SET balance = balance + 1 WHERE id = 1` 与“先 `SELECT` 到 Python、计算新余额、再 `UPDATE balance = :old_value_plus_one`”不是等价的并发操作。后者可能用已经过时的应用层读值覆盖其他事务的结果。

还有一个更反直觉的细节：在 `READ COMMITTED` 下，`INSERT ... ON CONFLICT DO UPDATE` 可能作用于一条不在该语句常规读取快照中可见的冲突行。

这是唯一约束冲突处理和写入规则共同作用的结果。由此可见，快照可见性主要描述读取的一致性视角，不能替代对具体写入命令并发语义的分析。

## 四、REPEATABLE READ：固定快照之后，数据库如何处理更新冲突

PostgreSQL 的 `REPEATABLE READ` 通常为整个事务使用同一份快照。需要纠正一个常见说法：快照并非一定在执行 `BEGIN` 的瞬间取得，而是在该事务的第一条非事务控制语句开始时建立。

此后其他事务即使提交了新版本，也不会因为时间推进就改变当前事务的普通查询视角。当然，当前事务自己的修改仍应对自己可见。

这意味着 A 在第一次查询后，B 可以把余额从 100 更新为 150 并提交，而 A 再查仍然得到 100。旧数据之所以还存在，不是因为数据库向 A 发了一份对象缓存，而是因为 A 的快照仍需要旧行版本，PostgreSQL 不能在它结束之前随意清理该版本。

如果 A 不再只是读取，而是随后也要更新同一行，就不能一直假装 B 的提交没有发生。

PostgreSQL 的 `REPEATABLE READ` 遇到这种冲突时，若并发修改者已经提交，可能以 SQLSTATE `40001` 终止当前事务，提示并发更新导致无法序列化访问。应用需要重新开始整个事务，让新事务用更新后的数据库状态重新作出判断。

这体现了 MVCC 的两种职责之间的差别：让旧快照继续**读取**旧版本，不代表允许它在不处理冲突的情况下继续**写入**旧版本。读视角稳定与写入正确性是不同的问题。

PostgreSQL 的 `REPEATABLE READ` 比 SQL 标准对该级别要求的最低保证更强。

标准定义中的“可重复读”不必然排除所有幻读，而 PostgreSQL 在这一隔离级别下采用快照隔离（Snapshot Isolation），普通查询也不会出现标准意义上的幻读。不过，“两次查询结果不变”仍然不能推出“所有成功提交的事务结果都等价于某一种串行顺序”。

## 五、为什么没有脏读、没有幻读，仍然可能破坏业务约束

假设值班表要求始终至少有一名医生处于值班状态。初始有 A、B 两名医生，二者都在值班。两个事务分别打算让其中一名医生休息，业务逻辑相同：先查询当前值班人数，只要多于一人，就把自己负责的医生设为休息。

在 `REPEATABLE READ` 下，事务 T1 查询值班人数为 2；事务 T2 也查询到 2。T1 更新 A 的记录为不值班；T2 更新 B 的记录为不值班。因为两个事务修改的是不同的行，它们没有必然发生同一行上的写写冲突。结果二者都成功提交，值班人数变成 0。

这不是脏读，也不是不可重复读或幻读。每个事务一直看到自己的稳定快照，而且各自的 SQL 都可以顺利完成。错误出在两个事务基于同一个旧前提，修改了不同的记录，让一个跨记录的业务不变量最终被破坏。数据库理论把这种现象称为**写偏斜**（write skew）。

为什么它不可能等价于某种串行执行？如果先完整执行 T1，T2 在检查时就应看到仅剩一人值班，不能再让 B 休息；若先执行 T2，T1 同样不能让 A 休息。无论选哪个串行顺序，最终都应该至少有一人值班。而并发结果为零，说明它不具有可串行化语义。

这个反例也说明了事务一致性的真实边界。一个单独运行的事务能够维持规则，两个基于旧快照的事务并发运行却可能共同破坏规则。

数据库普通的 `CHECK (on_call IN (true, false))` 只能检查单行字段是否合法，不能自动理解“整个表必须至少有一行是 true”。如果业务需要跨行不变量，就必须让并发控制策略与这个规则相匹配。

## 六、SERIALIZABLE：不把所有事务排队，也能排除写偏斜

PostgreSQL 的 `SERIALIZABLE` 并不是把整个数据库变成“同一时间只准一个事务运行”。它使用 Serializable Snapshot Isolation（SSI），在快照隔离基础上跟踪可能导致串行化异常的读写依赖。

当某些依赖关系表明并发结果可能无法对应任何串行顺序时，数据库会使相关事务中的一个或多个失败，而不是让所有事务都提交。

回到值班问题。T1 读取了“B 仍然值班”的事实，T2 随后写入 B 的状态；从可串行化顺序看，这构成一个读写反依赖：T1 的读取结果要求它逻辑上先于 T2 的某次写入。

同理，T2 读到 A 仍在值班，而 T1 写入 A，也形成相反方向的依赖。两个方向构成循环，不能同时满足。SSI 不是仅靠这样一张简单的环形图直接执行检查，而是通过跟踪 `rw` 依赖和可能导致异常的危险结构，决定何时中止事务。

PostgreSQL 用于这种检测的谓词锁（predicate locking，`pg_locks` 中可见 `SIReadLock`）与普通排他行锁不同：它主要记录查询曾经依赖的读取范围，帮助后续写入发现冲突；它本身不阻塞其他事务对这些数据的写入，也不因此构成传统的锁等待死锁。

谓词锁可能以行、页或关系等粒度表达，执行计划和内存限制会影响其粒度。粒度变粗时，甚至可能增加并发冲突的误判与重试。

SSI 不是没有代价的免费正确性。它需要维护依赖关系和谓词锁，也可能中止本来执行了大量工作的事务。对于 SQLSTATE `40001`，必须重试**整个事务**，包括最初的查询和决定写哪些数据的业务判断，而不是只重试报错的那条 `UPDATE`。

如果只是局部重试，决策仍可能建立在已经被证明不合适的旧快照之上。上一篇的 SAVEPOINT 不应被当成这种错误的通用替代方案。

对于需要一份长期稳定报表、而又不想在报表执行过程中承担可串行化重试风险的场景，PostgreSQL 还支持 `SERIALIZABLE READ ONLY DEFERRABLE`。

它可以在开始读取前等待一个安全快照，之后只读事务就不必因为这些序列化异常被中止。代价是开始读取的等待时间可能变长。这再次表明，隔离的代价不只有锁等待，也包括快照获取和冲突检测的成本。

还有两个边界不能忽略。可串行化承诺的是成功提交事务的结果等价于某个串行执行顺序，并不保证事务一定成功、一定按启动顺序提交，也不等于自动实现数据库之外的消息、支付和文件操作的原子性。

PostgreSQL 的严格 Serializable 保证还取决于相关事务的使用方式；如果业务同时依赖其他较弱隔离级别的事务共同维护某个跨事务不变量，就不能未经分析地把整个系统视作严格可串行化。

## 七、在两个数据库会话中验证这些区别

下面使用 `psql` 的两个独立连接作为会话 A 和会话 B，避免 ORM identity map 或应用缓存影响观察。实验应在专用测试数据库中执行，保证没有第三方事务同时修改相关表。

先创建实验表。在一条不处于显式事务中的连接中执行：

```sql
CREATE TABLE IF NOT EXISTS blog_mvcc_account (
    id integer PRIMARY KEY,
    balance integer NOT NULL
);

INSERT INTO blog_mvcc_account (id, balance)
VALUES (1, 100)
ON CONFLICT (id) DO UPDATE SET balance = EXCLUDED.balance;
```

现在让会话 A 执行：

```sql
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT balance FROM blog_mvcc_account WHERE id = 1;
-- 预期：100
```

保持 A 的事务不结束，让会话 B 执行并提交：

```sql
BEGIN;
UPDATE blog_mvcc_account SET balance = 150 WHERE id = 1;
COMMIT;
```

回到会话 A：

```sql
SELECT balance FROM blog_mvcc_account WHERE id = 1;
-- 预期：150
COMMIT;
```

接下来在会话 B 中把余额重新设置为 100 并提交，然后把 A 的第一句改为 `BEGIN ISOLATION LEVEL REPEATABLE READ;`，重复相同的交错过程。此时 A 的第二次查询预期仍返回 100。

这里并不是演示连接池复用，而是验证两个隔离级别取得快照的时机不同；同一个会话 A 在一次事务期间保持同一条数据库连接。

写偏斜也可以用两个窗口复现，先创建值班表并重置数据：

```sql
CREATE TABLE IF NOT EXISTS blog_mvcc_duty (
    doctor text PRIMARY KEY,
    on_call boolean NOT NULL
);

INSERT INTO blog_mvcc_duty (doctor, on_call)
VALUES ('A', true), ('B', true)
ON CONFLICT (doctor) DO UPDATE SET on_call = EXCLUDED.on_call;
```

会话 A 与 B 各执行 `BEGIN ISOLATION LEVEL REPEATABLE READ;`，随后**都先执行**以下查询，确认结果为 2：

```sql
SELECT count(*) FROM blog_mvcc_duty WHERE on_call;
```

然后让 A 执行 `UPDATE blog_mvcc_duty SET on_call = false WHERE doctor = 'A';`，让 B 执行 `UPDATE blog_mvcc_duty SET on_call = false WHERE doctor = 'B';`，最后两个会话依次 `COMMIT`。

在其他会话没有介入的情况下，最终计数预期为 0。两个更新不命中同一行，因此这是写偏斜，而不是同一行的并发更新冲突。

在另一轮实验前重置两名医生为值班。把两个会话的隔离级别都改成 `SERIALIZABLE`，并保持“双方先查询、再各更新不同的行、最后提交”的顺序。

此时至少一个事务应以 SQLSTATE `40001` 失败，最终不应出现两人都成功休息的已提交结果。被中止的事务必须从头重试，并在新的快照下重新检查值班人数。如果在复现实验时未按这个顺序交错执行，就不能保证一定触发同样的冲突路径。

本轮审校使用 PostgreSQL 18.6 的两个独立连接实际复核了这些交错过程：`READ COMMITTED` 的两次读取依次得到 100、150，`REPEATABLE READ` 依次得到 100、100；写偏斜实验在 `REPEATABLE READ` 下两个事务都提交，最终值班人数为 0，而相同交错在 `SERIALIZABLE` 下有一个事务以 `40001` 失败，最终仍有一人值班。

## 八、MVCC 的代价：旧版本不能无限保留

多版本让读取不必总是等待写入，但那些不再属于最新状态的行版本仍然会占据存储空间。PostgreSQL 需要通过 `VACUUM` 清理对任何仍然需要的快照都已不可见的旧版本，并维护可供空间重用的状态。

不能把 `VACUUM` 简单理解成“把当前查询看不到的版本立即删除”，因为另一个事务可能持有更早的快照，仍然需要这些版本。

这就解释了为什么长事务可能导致表膨胀：它持续保留较旧的读取视角，可能推迟旧行版本的回收。其他因素，例如未处理的复制槽、热备反馈或长时间未完成的准备事务，也可能影响清理边界，具体需要结合部署配置排查。另一方面，长事务不一定产生大量死元组；它提供了保留旧版本的条件，实际膨胀还取决于并发更新、删除量和清理节奏。

可以使用 `pg_stat_activity` 观察长期活动事务，并查看 `backend_xmin`、`xact_start` 等字段；`pg_stat_all_tables` 的 `n_dead_tup` 则提供死元组数量的统计估计，而不是精确的物理计数。

诊断时要把事务持续时间、连接占用、更新频率和 VACUUM 状态放在一起分析，而不能看到一个长事务就断言它是所有存储问题的根源。

PostgreSQL 还必须防止事务 ID 回绕。堆元组记录的常规 XID 是有限宽度的，系统通过冻结足够老的事务信息，使长期存在的有效行版本不会因 ID 循环而被错误判断为未来版本。

自动清理不仅涉及回收空间，也承担着事务 ID 生命周期维护的职责。这部分与 MVCC 密切相关，但具体冻结阈值、可见性映射和反回绕机制已经形成独立的存储维护主题，不需要在隔离级别文章中逐项展开。

MVCC 本身也有适用边界。PostgreSQL 官方明确指出，`TRUNCATE` 和会重写表的某些 `ALTER TABLE` 形式并非完全 MVCC 安全；序列值也不遵循普通行版本的事务可见性与回滚规则。

常见的“查询不阻塞写入、写入不阻塞查询”，说的是普通 MVCC 读写关系，不能推广成任何 DDL、显式锁或所有命令都绝不互相等待。

## 九、如何选择隔离级别

看完内部机制后，隔离级别选择不应该再被简化为“级别越高越安全，所以全部设为最高”。`READ COMMITTED` 适合许多请求较短、更新目标明确的业务，但跨多条 SQL 的判断可能读到不同时间的状态。

`REPEATABLE READ` 提供稳定快照，适合需要一致读取视角的操作，却不能防止写偏斜等跨行不变量被破坏。`SERIALIZABLE` 提供更强的成功提交语义，但会引入冲突检测和完整事务重试的工程要求。

因此，真正的出发点是业务要维护什么不变量，以及这个不变量涉及哪些数据。唯一约束可以直接交给唯一索引；某一行余额不能跌破零，可能用一条条件更新就能表达；跨多行、跨条件范围的判断，才更需要分析隔离级别与锁定策略。

隔离级别、SQL 原子更新、数据库约束和显式锁并不是互相排斥的方案，后两篇将进一步讨论这些并发控制机制怎样组合使用。

最后还有一个经常被忽略的适用前提：不同数据库即使使用相同的隔离级别名称，也未必有完全一致的快照与冲突处理方式。

本文所说的 `REPEATABLE READ` 无幻读、Serializable 使用 SSI、`READ UNCOMMITTED` 实际按 `READ COMMITTED` 处理，都是 **PostgreSQL 的具体实现**，不能不加验证地套用到 MySQL 或其他数据库。

事务隔离的核心不是阻止并发，而是约束并发能够被观察和提交成什么结果。MVCC 解决了不同事务如何读取同一份不断变化的数据；快照的生命周期解释了不同隔离级别的读视角；冲突检测则决定稳定快照在写入时还能不能维持业务所要求的正确性。下一篇将从这些基础出发，讨论写入竞争、行锁和数据一致性问题。
