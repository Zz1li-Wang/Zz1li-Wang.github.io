两个事务都在正常执行 SQL，却突然有一个收到了 `deadlock detected` 错误。

它们并没有违反数据约束，也不是连接池耗尽。事务 A 已经修改了第一条记录，准备修改第二条；事务 B 则先修改了第二条，随后尝试修改第一条。结果 A 等 B 释放锁，B 又等 A 释放锁，谁都无法继续。

上一篇讨论悲观锁时，我们知道等待是数据库协调冲突的正常方式。但当等待关系形成闭环，继续等待就不再有意义。这种现象称为死锁（Deadlock）。

要理解死锁，不能只记住“加锁顺序不一致会死锁”。更重要的是弄清楚数据库在等待什么、为什么无法自行恢复、PostgreSQL 怎样发现闭环，以及业务代码应如何在事务失败后安全地重新执行。本文讨论 PostgreSQL 18 的锁管理与 SQLAlchemy 2.0.x 的异步事务处理。

## 一、普通锁等待为什么不等于死锁

先看一种很常见的等待。事务 A 更新一条记录后尚未提交，事务 B 也想更新同一行。由于两个写入操作的行级锁冲突，B 必须等待 A 结束事务。

只要 A 仍然能够继续执行并最终提交或回滚，这个等待就有机会解除。B 的执行可能变慢，但系统并没有因为这一次等待而陷入逻辑上的僵局。

死锁的区别在于，**持有资源的一方自己也在等待，而且等待关系形成了无法自行打破的循环**。

假设 A 已经锁住记录 1，B 已经锁住记录 2。接下来 A 请求记录 2，只能等 B；B 又请求记录 1，只能等 A。A 不结束事务，B 就不能继续；B 不结束事务，A 也不能继续。

这个例子中，任何一方都无法按原来的执行计划独立推进。继续延长等待时间并不会增加成功机会，必须有外部机制改变资源占有状态，例如放弃其中一个事务。

当然，“某条 SQL 等了很久”并不能证明发生了死锁。它可能只是被一个长事务阻塞，或者数据库正在执行耗时操作。**等待时间长短描述性能现象，等待依赖是否形成闭环才决定死锁是否成立。**

## 二、一次实际死锁如何形成

用两条数据就能复现这种情况。先在专用 PostgreSQL 测试数据库中创建表，并在没有其他测试事务运行时初始化两行记录。

```sql
CREATE TABLE IF NOT EXISTS blog_deadlock_demo (
    id integer PRIMARY KEY,
    value integer NOT NULL
);

INSERT INTO blog_deadlock_demo (id, value)
VALUES (1, 10), (2, 20)
ON CONFLICT (id) DO UPDATE SET value = EXCLUDED.value;
```

分别打开两个独立的 `psql` 连接，记为会话 A 和会话 B。先在 A 中开始事务，只修改记录 1。

```sql
-- 会话 A
BEGIN;
UPDATE blog_deadlock_demo SET value = value + 1 WHERE id = 1;
```

现在在 B 中开始另一个事务，只修改记录 2。

```sql
-- 会话 B
BEGIN;
UPDATE blog_deadlock_demo SET value = value + 1 WHERE id = 2;
```

到这里，两次 `UPDATE` 都可以执行成功。它们针对不同的行；虽然二者都在同一张表上持有 `ROW EXCLUSIVE` 表级锁，但这种表级锁模式彼此兼容。真正即将产生冲突的是行级修改。

回到 A，让它尝试修改记录 2。

```sql
-- 会话 A：此语句将等待会话 B
UPDATE blog_deadlock_demo SET value = value + 1 WHERE id = 2;
```

A 无法取得记录 2 的冲突行锁，因此进入等待。此时不要取消等待中的 SQL，而是切换到 B，尝试修改记录 1。

```sql
-- 会话 B：与会话 A 构成循环等待
UPDATE blog_deadlock_demo SET value = value + 1 WHERE id = 1;
```

现在两个事务互相等待。PostgreSQL 检测到死锁后，会使其中一个事务报错，典型 SQLSTATE 为 `40P01`，错误信息包含 `deadlock detected`。另一方则可能在受害事务释放锁之后继续执行。

不能预设一定是 A 或 B 报错。哪一个事务被中止取决于实际检测时机和锁管理状态，业务逻辑不得依赖所谓固定的“死锁牺牲者”。

结束实验时，收到死锁错误的会话应执行 `ROLLBACK` 清理其失败的显式事务块；另一会话在完成等待中的语句后，可按实验目的选择 `COMMIT` 或 `ROLLBACK`。若终端仍处于失败事务块内，不能直接继续执行普通 SQL。

如果重新运行实验，应先确认两个会话都已经退出前一轮事务，避免旧锁和旧数据影响结果。整个过程不需要显式调用 `SELECT ... FOR UPDATE`：普通 `UPDATE` 本身就会取得必要的行锁。

## 三、用等待关系图理解死锁的根本条件

我们可以把正在执行的事务抽象成节点，把等待关系画成有向边。假设事务 A 因为 B 持有冲突资源而不能继续，就画一条从 A 指向 B 的边，表示“A 等待 B”。

上一节的状态可以写成 `A → B` 和 `B → A`。这两条边形成一个有向环；如果涉及三个事务，也可能是 `A → B → C → A`。

在由这些事务和锁依赖构成的模型中，只要环上的每个事务都不能继续取得必要资源，就没有任何一个能够靠正常执行先释放资源。需要撤销某些请求、调整等待顺序，或者终止一个事务，才可能解除循环。

这里的等待环只是概念模型，不是说 PostgreSQL 只检查两条行锁边。真实锁管理中，等待者既可能被已经持有冲突锁的事务阻塞，也可能受锁等待队列中排在前面的不兼容请求影响。PostgreSQL 的 `pg_blocking_pids()` 也区分这两种阻塞来源。

因此，把死锁简化成“两个事务互相持有对方想要的两把锁”适合入门，但并不能覆盖共享锁、锁模式升级、等待队列和更多事务参与的复杂情况。

操作系统教材常用的“互斥、占有并等待、不可抢占、循环等待”可以辅助理解死锁形成的条件。对数据库开发更有用的落脚点则是：**让所有可能互相冲突的事务遵循可证明的一致资源获取规则，或在无法保证时正确处理事务中止。**

## 四、PostgreSQL 为什么不在每次等待时立即检查死锁

既然等待关系可以形成图，数据库为什么不在刚发现 B 被阻塞时立刻运行死锁检测？

因为绝大多数锁等待并不是死锁。持锁事务可能马上提交。若每发生一次短暂等待都做完整检测，会让大量正常竞争承担额外的锁管理成本。

PostgreSQL 采用延迟检查策略。`deadlock_timeout` 表示一个进程等待锁达到多久后，开始进行死锁检测。PostgreSQL 18 的默认值是 `1s`，不是“事务最多只能等待一秒”。

当等待超过这一阈值时，检测器会检查相关锁等待状态，判断是否存在死锁。如果不存在死锁，等待仍然可以继续；如果确实发现无法解除的循环，PostgreSQL 会中止参与其中的某个事务，让其他事务获得继续执行的机会。

这一实现还涉及一个重要细节：PostgreSQL 不仅会检查已持有冲突锁造成的硬阻塞，还会考虑锁等待队列中较早请求造成的软阻塞。硬阻塞不能靠调整队列消除；软阻塞则有机会通过改变等待顺序解除。

在 PostgreSQL 锁管理器的 `deadlock.c` 实现中，`FindLockCycle()` 沿等待依赖递归查找是否存在涉及当前等待者的环。如果环中存在可以调整的软依赖，`DeadLockCheck()` 会尝试重新安排相关锁的等待队列，并检查新的顺序是否仍然形成循环。

只有找不到可行的队列调整方案，才需要报告死锁并使一个事务失败。这个过程比前面的简化模型复杂，但核心仍然是寻找等待环、判断是否能够解除，然后恢复至少一部分事务的前进能力。

可以使用 `SHOW deadlock_timeout;` 查看当前配置。该参数的修改需要相应权限，通常不应为了让错误更快出现就直接在生产数据库大幅调小。

阈值过低意味着可能频繁执行昂贵的死锁检查；阈值过高则延迟真正死锁被发现的时间。它是在检测成本和故障响应速度之间做权衡，不是通过设置一个数值就能避免死锁。

## 五、死锁检测后究竟回滚了什么

当 PostgreSQL 判定死锁无法通过正常等待解除时，会选择一个参与事务报告错误，使该事务的执行失败。释放它所占有的事务性锁后，其他被阻塞的事务才可能继续。

这是一个必须区分的边界：被中止的不是“其中一条 SQL 的结果不算数，但这个事务此前做的修改仍自动保留”。在普通显式事务中，死锁错误使当前事务进入失败状态，先前尚未提交的工作不能继续被当作可提交成果。

假设 A 在取得记录 1 的锁时还修改了其他三张表。如果 A 因死锁失败，应用不能只补做那条报错的 `UPDATE`，再把此前的计算结果当作有效。正确恢复通常要求回滚失败事务，并从一个新的事务边界重新执行业务逻辑。

第三篇介绍的 SAVEPOINT 可以提供局部回滚边界，在特定设计下允许恢复某些错误。但这不能推出死锁都适合只回滚到保存点。死锁往往和此前的加锁顺序、读取结果及业务决策有关，只重新执行最后一条 SQL 可能再次进入相同等待关系，或者依据已经失效的状态作出决定。

从使用者角度看，PostgreSQL 报告 `40P01` 的意义是：**数据库为了恢复整体执行能力，拒绝了当前事务的一次执行尝试。** 它不意味着数据库内容已损坏，也不说明被中止的事务业务上永远不能成功。

不过，数据库只负责解除自己内部的死锁，不会重新调用你的 Python 函数。是否重试、重试几次、如何重新读取数据，都需要应用明确处理。

## 六、如何从数据库里找到阻塞关系

生产环境很难像实验一样在两个终端中逐句观察。更常见的现象是接口延迟上升、连接池被长时间占用，或日志中出现零星的 `40P01`。

排查时需要先分清当前是否还有阻塞关系，以及是否已经发生过死锁。一次死锁被处理后，受害事务释放了锁，环形等待可能已经消失。所以不能要求 `pg_locks` 在事故结束后仍然保留一张完整的死锁现场。

可以先观察 `pg_stat_activity` 和 `pg_blocking_pids()`：

```sql
SELECT
    w.pid AS waiting_pid,
    w.state AS waiting_state,
    w.wait_event_type,
    w.wait_event,
    now() - w.query_start AS waiting_query_age,
    b.pid AS blocking_pid,
    b.state AS blocking_state,
    now() - b.xact_start AS blocking_transaction_age,
    left(w.query, 120) AS waiting_sql,
    left(b.query, 120) AS blocking_sql
FROM pg_stat_activity AS w
JOIN LATERAL unnest(pg_blocking_pids(w.pid)) AS x(pid) ON true
LEFT JOIN pg_stat_activity AS b ON b.pid = x.pid
WHERE w.datname = current_database()
ORDER BY w.pid, b.pid;
```

查询结果中的 `waiting_pid` 指当前被阻塞的后端，`blocking_pid` 是 `pg_blocking_pids()` 报告的阻塞者。通过对应的事务开始时间和当前 SQL，可以进一步判断是不是某个很早就开始的事务占有资源。

需要注意，这个函数报告的不只是“已经持有一把冲突锁”的后端，也可能报告在等待队列中排在前面的不兼容请求；涉及并行查询或 prepared transaction 时，还可能出现重复 PID 或特殊值 `0`。上面的 `LEFT JOIN` 因此不保证每一行都能对应一条普通客户端会话。

上一章提到过，行级锁主要记录在行版本自身。一个事务等待另一事务结束时，`pg_locks` 中经常表现为 `transactionid` 等待，而不是稳定出现一条可直接映射到业务主键的 `tuple` 锁记录。不能因为没有查到 `tuple` 类型的等待就认定没有行锁竞争。

诊断时还可以查看某个数据库累计发生的死锁次数：

```sql
SELECT datname, deadlocks, stats_reset
FROM pg_stat_database
WHERE datname = current_database();
```

`deadlocks` 是自统计重置以来的累计计数，适合结合监控时间窗口观察趋势，但它不会告诉你每次死锁涉及哪条 SQL，也不能代替事故日志。因为检测和回滚可能很快完成，单次快照查询也不一定抓得到正在发生的环路。

## 七、日志为什么通常比事后查询更重要

PostgreSQL 发现死锁时会报告相关错误，并提供参与等待的进程、锁类型和 SQL 等诊断线索。应用异常日志中常能看到 `40P01`，但最有价值的上下文往往还在数据库服务端日志里。

为便于将数据库连接映射回应用请求，应配置适当的日志前缀或可追踪的 `application_name`。在应用层记录事务涉及的业务操作、关联 ID 和重试次数，也有助于把多条不同连接上的 SQL 还原为一次业务流程。

PostgreSQL 还提供 `log_lock_waits`，用于记录等待时间达到阈值的锁等待事件。它默认关闭，打开需要相应权限；其记录阈值与 `deadlock_timeout` 相关。因此，排查锁等待时可以在受控范围内临时调整日志配置，而不应把较低的检测阈值作为永久性能优化。

在诊断记录中，最重要的不是哪一行显示“正在等待”，而是还原事务此前已经持有哪些资源、下一步又申请了什么，以及不同代码路径为何采用了相反顺序。

有时表面上看到的是两个 `UPDATE` 之间的死锁，真实资源却来自外键检查、触发器、唯一性检查、显式 `LOCK TABLE` 或 advisory lock。只看最后一条报错语句，可能找不到最早形成不一致加锁顺序的地方。

同样不能把 `lock_timeout` 当作死锁检测。`lock_timeout` 是等待锁超过限定时间就报错，**无论等待是否形成死锁**；`statement_timeout` 则限制语句执行时间，其中可以包含锁等待。它们能够限制延迟，却不能证明已经修复了循环等待的根因。

## 八、最有效的预防办法：固定资源获取顺序

回到两条记录的实验，为什么 A 先锁记录 1、B 先锁记录 2 会形成死锁？因为两个事务对同一组资源采取了相反的获取顺序。

如果约定所有转账操作都按主键从小到大锁定账户，那么需要同时修改记录 1 和记录 2 的事务，都先申请记录 1，再申请记录 2。

当 A 已经持有记录 1 时，B 在第一步就需要等待。此时 B 尚未持有记录 2，所以 A 可以继续取得记录 2，完成工作后提交。B 随后获得记录 1，再按照相同顺序继续执行。

两个事务仍然可能发生锁等待，但不会仅因为它们对这两条记录采取相反顺序而形成前面那种闭环。这就是固定顺序真正发挥作用的地方：它不是让锁消失，而是限制等待依赖的方向。

在 Python 服务层可以先对将要访问的确定资源进行排序，再按顺序获取锁。例如对两个账户执行转账时，先得到 `sorted({source_id, target_id})`，然后在同一事务内依次执行 `SELECT ... FOR UPDATE`。

```python
from sqlalchemy import text

async def lock_accounts(conn, source_id: int, target_id: int) -> None:
    for account_id in sorted({source_id, target_id}):
        row = await conn.execute(
            text("SELECT id FROM accounts WHERE id = :id FOR UPDATE"),
            {"id": account_id},
        )
        if row.scalar_one_or_none() is None:
            raise ValueError(f"账户 {account_id} 不存在")
```

这里假设 `conn` 是外层事务管理的 `AsyncConnection`，并且 `accounts.id` 是主键。锁定完成后，实际的余额校验和转账更新仍必须在**同一个事务**中执行，且所有竞争的写入路径都要遵守同一规则。

如果要求非常严格地控制每一把锁的取得顺序，逐个按确定主键锁定比简单假设 `UPDATE ... WHERE id IN (...)` 会按业务列表顺序锁行更容易推理。SQL 执行计划、联结顺序、触发器等因素都可能让实际锁获取顺序与应用传入的参数顺序不一致。

固定顺序也不是“系统从此不会发生任何死锁”的保证。多个表、外键、隐式索引操作和不同锁模式可能引入额外资源；不同服务入口如果有一个绕过约定，仍然可能构成循环。对于同一对象需要升级锁模式的业务，还应尽可能一开始就申请最终需要的适当锁模式，避免两个事务都持有兼容弱锁后互相等待升级。

## 九、解决死锁不能只靠增加超时和重试次数

缩短事务有实际帮助。事务越短，持锁时间通常越少，竞争窗口也更小。把等待外部 HTTP、用户输入或其他不必要的工作放到持锁区间之外，能够减少不必要的长时间占用。

但缩短事务不等于从逻辑上排除死锁。即使两条事务都只执行几毫秒，只要存在相反的加锁顺序，它们仍然可能在恰好交错执行时形成循环。

增加连接池容量同样不能解决这个问题。它可以让更多请求进入数据库，但当这些请求竞争相同资源时，甚至可能增加同时参与冲突的事务数量。

对于结构性重复出现的死锁，真正应该修改的是加锁顺序、锁定范围、事务边界或数据更新方案。单条原子条件更新、唯一约束以及第六篇介绍的乐观版本检查，有时能够消除原本需要横跨多条 SQL 的锁协议，从而减少死锁机会。

不过不能把乐观锁理解成绝不会死锁。带版本条件的 `UPDATE` 仍使用数据库锁；涉及多个目标资源时，仍然可能形成相互等待。采用更高的隔离级别也不保证死锁消失，它主要改变可见性与异常检测语义。

## 十、Python 中如何正确识别死锁并重试

PostgreSQL 对死锁错误使用 SQLSTATE `40P01`。第六篇讨论的序列化失败是 `40001`。这两种错误都可能需要重新执行事务，但触发原因不同，不能只靠异常字符串中是否包含 `deadlock` 来识别。

SQLAlchemy 的异步接口会把数据库驱动异常包装成 DBAPI 相关异常。对于 `postgresql+asyncpg` 驱动，可以检查底层异常上的 `sqlstate` 属性；如果项目还支持其他驱动，需要按实际驱动的错误接口进行适配。

一个简化的事务重试封装如下：

```python
import asyncio
import random
from collections.abc import Awaitable, Callable
from typing import TypeVar

from sqlalchemy.exc import DBAPIError
from sqlalchemy.ext.asyncio import AsyncConnection, AsyncEngine

T = TypeVar("T")


async def run_transaction(
    engine: AsyncEngine,
    operation: Callable[[AsyncConnection], Awaitable[T]],
    max_attempts: int = 3,
) -> T:
    if max_attempts < 1:
        raise ValueError("max_attempts 必须大于零")

    for attempt in range(max_attempts):
        try:
            async with engine.begin() as conn:
                return await operation(conn)
        except DBAPIError as exc:
            sqlstate = getattr(exc.orig, "sqlstate", None)
            if sqlstate not in {"40P01", "40001"}:
                raise
            if attempt == max_attempts - 1:
                raise

            delay = min(0.05 * (2 ** attempt), 0.5)
            await asyncio.sleep(delay + random.uniform(0, 0.05))

    raise AssertionError("不可到达")
```

关键点不在于固定重试三次，而在于每次调用 `operation(conn)` 都处于一个**全新事务**中。`engine.begin()` 的上下文管理器会在异常退出时回滚；外层捕获发生在该事务作用域退出之后，因此不会试图用一个已经失败的事务继续执行 SQL。

这里的 `operation` 必须能在新的数据库状态下完整重新计算业务决定。例如一次转账需要重新读取余额、校验条件，再完成所有相关写入；不能沿用上次事务缓存的旧余额或已经生成但依赖旧状态的 SQL 参数。

退避和随机抖动只是降低立即再次相撞的概率，不保证下一次一定成功。对于持续出现的 `40P01`，应该把错误频率、涉及的 SQL 和等待关系记录下来，寻找结构性根因，而不是不断增加重试上限。

更严格地说，这个封装只适合**数据库内可安全重放的工作单元**。如果 `operation` 中已经给第三方支付平台发起扣款，数据库死锁回滚并不会撤销那次外部请求。事务重试与业务幂等、消息 Outbox 等机制需要共同设计。若发生的是提交成功但网络响应丢失的未知提交结果，也不能把它按普通 `40P01` 直接重试。

## 十一、用 asyncio 真正制造一次死锁

前面的双 `psql` 实验能直观地看到等待。我们还可以编写一个独立的 Python 程序，利用两个 `asyncio.Event` 保证两个事务先分别锁住不同行，再互相请求对方的行。

这里特意使用两个独立的数据库连接，而不是在同一个 `AsyncSession` 里启动两个协程。数据库死锁涉及多个事务之间的锁依赖，同一个 Session 的并发复用既不安全，也不符合这个实验的目标。

安装 `SQLAlchemy>=2.0,<2.1` 与 `asyncpg`，并配置指向**测试数据库**的 `DATABASE_URL`。表会在程序开始时创建并重置其两条测试记录。

```python
import asyncio
import os

from sqlalchemy import text
from sqlalchemy.exc import DBAPIError
from sqlalchemy.ext.asyncio import create_async_engine


async def main() -> None:
    engine = create_async_engine(os.environ["DATABASE_URL"])
    a_locked = asyncio.Event()
    b_locked = asyncio.Event()

    async def worker(name, first_id, second_id, mine, other):
        try:
            async with engine.begin() as conn:
                await conn.execute(
                    text("UPDATE blog_deadlock_demo "
                         "SET value = value + 1 WHERE id = :id"),
                    {"id": first_id},
                )
                mine.set()
                await other.wait()
                await conn.execute(
                    text("UPDATE blog_deadlock_demo "
                         "SET value = value + 1 WHERE id = :id"),
                    {"id": second_id},
                )
            print(f"{name}: 提交成功")
        except DBAPIError as exc:
            state = getattr(exc.orig, "sqlstate", None)
            if state == "40P01":
                print(f"{name}: 检测到死锁，事务已回滚")
            else:
                raise

    try:
        async with engine.begin() as conn:
            await conn.execute(text("""
                CREATE TABLE IF NOT EXISTS blog_deadlock_demo (
                    id integer PRIMARY KEY,
                    value integer NOT NULL
                )
            """))
            await conn.execute(text("""
                INSERT INTO blog_deadlock_demo VALUES (1, 10), (2, 20)
                ON CONFLICT (id) DO UPDATE SET value = EXCLUDED.value
            """))

        await asyncio.gather(
            worker("A", 1, 2, a_locked, b_locked),
            worker("B", 2, 1, b_locked, a_locked),
        )

        async with engine.connect() as conn:
            rows = await conn.execute(text(
                "SELECT id, value FROM blog_deadlock_demo ORDER BY id"
            ))
            print("最终记录:", rows.all())
    finally:
        await engine.dispose()


if __name__ == "__main__":
    asyncio.run(main())
```

两个任务都完成第一次 `UPDATE` 后，才允许彼此进入第二次写入。因此，在没有其他事务干扰、数据库使用正常锁管理规则的前提下，它们会形成循环等待。PostgreSQL 最终应报告一次死锁，另一个事务则有机会完成并提交。

程序没有为失败的一方自动重试，因此初始数据 `(1, 10)` 和 `(2, 20)` 在只有一个事务成功提交的情况下，最终应分别加 1。哪一个任务成功并不固定；若需要业务上两次操作都成功，就必须在捕获失败后按上一节的方法重新执行完整事务。

这段实验的同步事件仅用来制造稳定的交错顺序，不应成为业务代码中模拟数据库锁的方法。本轮审校已在 PostgreSQL 18.6、SQLAlchemy 2.0.54 与 `asyncpg` 0.32.0 上实际运行：一个事务收到 `40P01` 并回滚，另一个提交，最终两行分别从 10、20 变为 11、21。被选中的失败事务不具有固定性。

## 十二、死锁是数据库主动维护前进能力的一种失败处理

死锁并不说明数据库锁机制不可靠。恰恰相反，数据库通过阻止不兼容的操作同时修改共享状态，才有可能让事务遵守一致性要求。死锁是多条合法锁请求在特定交错顺序下形成的循环依赖。

PostgreSQL 的死锁检测保证系统能够发现这类循环并打破它，但不会保证每个事务都成功。它必须让其中某个事务失败，把后续恢复责任交还给应用。

从工程角度看，最有价值的预防措施是让所有业务路径按统一规则获取资源，并尽可能缩短事务的持锁范围。发生死锁时，则通过 `40P01`、数据库日志和阻塞关系恢复现场，并在业务允许的条件下重试完整事务。

这一篇也为整个数据库事务与并发控制专题画上句号。连接池决定有限的数据库连接如何被分配，事务决定修改的提交边界，MVCC 决定读取者能看见什么，锁与版本校验负责协调竞争，而死锁检测处理的是这些协调关系自身可能形成的循环。

它们共同服务于同一个目标：在多个请求同时访问数据时，让数据库执行结果仍然符合事先明确的业务规则。
