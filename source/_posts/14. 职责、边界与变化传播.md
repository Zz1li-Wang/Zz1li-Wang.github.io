软件项目刚开始时，修改需求通常比较直接。增加一个字段，调整一条判断，或者新增一个接口，开发人员往往能够很快找到需要修改的代码。

随着功能增加，情况会逐渐改变。订单优惠政策调整后，订单预览、创建流程和后台试算可能都需要检查。有时只改动一个判断，却会影响多个看起来互不相关的模块。开发人员不得不先弄清这些代码之间的关系，再决定从哪里下手。

代码越多，查找和理解所需的时间通常越长。但项目难以维护，往往还有更深一层的原因：一项设计决定被许多地方共同依赖，修改它就需要重新确认这些依赖是否仍然成立。

软件设计要处理的一个重要问题，就是如何组织这些决定及其依赖，使开发人员能够在有限的范围内理解程序，并尽可能将变化控制在相关的部分。

为什么代码会变得越来越复杂？

## 一、代码变复杂的原因
### 1. 复杂性来自代码之间的关系

假设两个系统都有十万行代码。第一个系统把价格计算规则交给一个明确的模块，其余功能通过约定好的接口取得计算结果。第二个系统则把价格判断分别写在接口、定时任务和后台管理代码里。

当业务稳定时，两者都可能正常运行。等到优惠规则发生变化，第一个系统有机会在一处完成调整；第二个系统则需要寻找所有实现过该规则的位置，并逐一确认它们是否一致。

差异并不体现在代码行数上，而在于代码之间共享了多少知识。模块 A 如果必须了解模块 B 的数据结构、执行顺序或业务判断，B 的这些决定就不再只属于 B。它们会成为两个模块之间的共同约束。

这种约束越多，理解一处代码时需要同时考虑的上下文就越大。即使最终只修改一个文件，开发人员也可能需要阅读很多文件才能确认改动是安全的。因此，维护成本既包括实际修改代码的成本，也包括定位、理解、验证以及回归测试的成本。

### 2. 变化的传播

变化传播既可能沿着明确的调用关系发生，也可能沿着不容易看见的业务约定发生。

一种情况是直接依赖。订单服务读取价格模块中的配置结构，并假定其中存在 `vip_rate` 字段。如果价格模块改变配置的表示方法，订单服务就可能需要跟着修改。

另一种情况没有直接调用。订单预览和后台试算分别写了一份优惠规则。两个模块之间没有 `import`，但它们必须对同一笔订单给出一致的优惠结果。业务规则一旦变化，两个地方都要调整。这也是一种耦合，只是依赖隐藏在业务语义中。

还有一些约束来自时间和状态。例如，一个模块必须先调用初始化函数，另一个模块才能正常工作；或者两个模块共同修改同一份可变数据。调用接口没有变化，也无法保证它们可以独立演化。

所以，检查依赖关系不能只看导入图。源代码能揭示一部分结构，业务规则、共享状态和执行顺序同样会决定变化的影响范围。

## 二、模块及其边界
要控制这些变化的传播范围，需要先理解模块化。
### 1. 模块化为什么有用

模块化（Modularity）是把系统组织成若干具有明确职责的部分，并为这些部分规定协作方式。

模块是一种设计上的划分。在 Python 项目中，它可以通过一个文件、一个包、一组类或多个相互配合的文件实现。文件是代码的物理组织单位，模块边界则取决于哪些知识由这一部分维护，以及其他部分能够依赖它的什么行为。

模块化带来的直接好处是缩小理解范围。调用价格模块的订单服务，只需要知道如何获得有效报价，以及报价结果代表什么。价格模块使用条件判断、规则表还是其他算法，原则上不必成为订单服务的知识。

这使开发人员有可能对系统进行局部推理（Local Reasoning）：理解某个模块及其公开约定，就能判断它在一定条件下的行为，而不用每次都读完整个系统。

但这种好处有一个前提。模块边界必须真正约束依赖。如果文件分开了，业务规则却仍然到处泄漏，代码目录看起来整齐，理解范围却没有缩小。

### 2. 内聚与耦合

人们常用内聚（Cohesion）和耦合（Coupling）描述模块结构。

内聚关注模块内部的内容为什么被放在一起。优惠资格、折扣金额和最终应付金额之间有紧密的业务联系，将它们组织在同一个定价职责下是合理的。发送通知、解析 Excel 和管理用户登录状态则很难用同一个职责解释。

内聚的高低无法根据函数数量简单判断。一个模块可以包含很多函数，却始终围绕同一组规则工作；一个只有几十行代码的模块，也可能混杂了几种毫不相关的职责。

耦合关注模块之间的依赖。订单服务需要调用定价功能，这种依赖本身没有问题。系统被拆成多个模块后，各部分仍然需要协作。更值得关注的是依赖的内容：订单服务究竟只依赖一个报价能力，还是同时依赖折扣参数、计算步骤、内部状态和配置格式？

后一种情况下，价格模块有更多内部决定已经成为外部约定。它们发生变化时，订单服务就更容易受到影响。

高内聚、低耦合可以作为设计目标，但这两个词还没有告诉我们应当怎样划分模块。把所有代码合并到一个文件，表面上可以消除文件之间的依赖，却只会把复杂关系藏在文件内部。把每个判断拆成独立类，则可能增加大量接口和跳转，同样不利于理解。

问题由此变得具体：模块究竟应该围绕什么来划分？

## 三、模块的划分

### 1. 分散维护的业务知识

假设系统规定，VIP 用户的订单满 200 元可以享受九折优惠。订单预览、订单创建和后台试算都需要按照当前规则计算应付金额。

项目早期，三个流程可能各自实现判断。业务没有变化时，这种写法很容易理解。等到优惠门槛调整，开发人员就需要修改三个地方。如果其中一处遗漏，同一笔订单可能在不同入口得到不同结果。

一种自然的改进是提取公共配置：

```python
from decimal import Decimal

VIP_THRESHOLD = Decimal("200.00")
VIP_DISCOUNT_RATE = Decimal("0.10")
```

不同流程读取这两个常量，自行判断资格并计算金额。现在如果只是把门槛从 200 元改成 300 元，修改常量就足够了。

这已经是有价值的改善，但模块边界仍然脆弱。调用方知道 VIP 资格由金额门槛决定，知道折扣使用一个固定比例，还知道应当由自己计算优惠金额。假如以后增加多档优惠、互斥规则或者新的计算顺序，调用方仍需调整。

集中配置解决了配置值重复维护的问题，却没有让价格计算的设计决定完全回到价格模块内部。

### 2. 将计算决定交给模块

可以把对外接口进一步调整为报价能力。下面假定系统只使用人民币，传入的金额已经验证为非负且精确到分，不考虑优惠叠加和税费；金额计算采用明确指定的四舍五入方式。

```python
from dataclasses import dataclass
from decimal import Decimal, ROUND_HALF_UP


@dataclass(frozen=True)
class PriceQuote:
    original: Decimal
    discount: Decimal
    payable: Decimal


def quote_price(amount: Decimal, level: str) -> PriceQuote:
    eligible = level == "VIP" and amount >= Decimal("200.00")
    rate = Decimal("0.10") if eligible else Decimal("0.00")
    discount = (amount * rate).quantize(
        Decimal("0.01"), rounding=ROUND_HALF_UP
    )
    return PriceQuote(
        original=amount,
        discount=discount,
        payable=amount - discount,
    )
```

调用方只需提供报价所必需的信息，并使用返回的结果：

```python
quote = quote_price(Decimal("300.00"), "VIP")
print(quote.payable)  # 270.00
```

优惠资格、折扣计算和本例采用的舍入策略都有了明确的维护位置。将来调整内部计算方式，只要报价接口及其行为约定保持不变，订单预览和创建流程就不必了解新的计算细节。

这一改动的价值超出了代码去重。价格模块现在拥有了对相关设计决定的解释权。调用方提出需求，模块依据自己维护的规则给出结果。

当然，价格模块仍可能需要读取数据库中的促销配置，或者与其他服务协作。这不影响它对外承担的报价职责。模块内部可以有复杂实现，重要的是这些复杂性有多少必须暴露给调用方。

### 3. 从案例回到模块划分依据

1972 年，David Parnas 在论文《On the Criteria To Be Used in Decomposing Systems into Modules》中研究了模块应按什么标准划分。他使用 KWIC（Key Word in Context）索引系统，对比了按照处理步骤组织程序与按照需要隐藏的设计决策组织程序的不同方案。

按处理步骤划分很直观：输入、加工、排序、输出，各有对应的部分。但是，当一个有关数据表示或处理方式的决定同时影响多个步骤时，这种划分未必能把变化限制在局部。

Parnas 提出的思路是，先识别那些困难的、或者可能发生变化的设计决定，再考虑如何让各个模块分别隐藏这些决定。这样，其他模块就不需要把这些决定作为自己实现的前提。

这里的“设计决定”不局限于业务规则。数据如何存储、采用什么算法、如何与外部系统交互，都可能成为需要隔离的决定。判断依据在于它是否应当由一个明确的模块负责，以及其他模块是否有必要知道它。

回到价格案例，优惠政策怎样解释、计算步骤怎样安排，正是调用方无需掌握的内部决定。由定价模块负责它们，才能使规则变化更有机会停留在定价模块内。

## 四、抽象、封装与信息隐藏

前面通过价格计算的例子，我们把原本分散在多个业务流程中的优惠规则，集中到了一个定价模块中。调用方只需要提供订单金额和客户等级，就能取得计算结果。

这种设计涉及软件开发中三个经常出现的概念：抽象（Abstraction）、封装（Encapsulation）和信息隐藏（Information Hiding）。

它们之间有密切的联系，但分别解决不同的问题。理解这些概念，还需要从程序如何组织数据、行为和对外接口说起。

### 1. 抽象：从具体实现中提取重要特征

抽象（Abstraction）是软件开发中非常基础的思维方式。

一个实际的软件功能往往包含大量细节，但使用这个功能的人通常不需要理解所有细节。因此，我们可以根据当前需要解决的问题，保留重要的特征和行为，暂时忽略无关的实现细节。

例如，订单价格计算涉及客户资格判断、折扣比例、金额舍入等多个步骤。但站在订单模块的角度，它真正关心的是：给定订单金额和客户信息，能够得到怎样的报价。

于是，我们可以把这些计算步骤抽象成一个报价操作：

```python
quote = quote_price(Decimal("300.00"), "VIP")
print(quote.payable)  # 270.00
```

调用方能够理解 `quote_price()` 的作用，也知道如何使用它返回的结果。至于函数内部通过条件判断还是规则表计算优惠，调用方没有必要了解。

这里发生了一次抽象：我们从具体的计算过程里，提取出了“根据订单信息取得报价”这项能力。

抽象的关键在于选择。哪些信息需要保留，取决于使用者的目的。对订单模块来说，优惠门槛可能是实现细节；对管理优惠政策的后台来说，优惠门槛可能恰恰是需要查看和修改的重要业务数据。

因此，抽象始终存在一定的观察角度。同一套实现可以在不同层次上形成不同的抽象。

抽象也不局限于面向对象编程。函数可以抽象一段计算过程，类可以抽象一组相关的状态和行为，模块可以抽象某项业务能力。它们的共同点是为复杂的实现提供一个更容易理解和使用的表示。

### 2. 封装：组织数据与行为

理解封装之前，需要先认识一个简单的问题：程序中的数据应该由谁负责维护？

假设我们使用一个类管理 VIP 优惠资格：

```python
from decimal import Decimal


class VipPolicy:
    def __init__(self):
        self._threshold = Decimal("200.00")

    def is_eligible(self, amount: Decimal, level: str) -> bool:
        return level == "VIP" and amount >= self._threshold
```

这个类有一个内部属性 `_threshold`，保存优惠门槛；还有一个方法 `is_eligible()`，负责判断订单是否符合优惠条件。

在没有这个类之前，门槛数据和资格判断可能由不同的代码分别管理。现在，相关的数据和行为被组织到了 `VipPolicy` 内部。

这就是封装（Encapsulation）的基本思想：将有关联的状态与操作组织在一个明确的边界中，并通过一定的访问方式管理它们。

使用者可以这样调用：

```python
policy = VipPolicy()

print(policy.is_eligible(Decimal("300.00"), "VIP"))  # True
```

我们不再需要让每个调用方分别读取门槛、检查用户等级和比较订单金额。资格判断由 `VipPolicy` 自己完成。

这样做还有另一个意义。如果以后修改优惠门槛，可以优先在负责维护它的类中调整，而无需让每个调用方重新解释优惠规则。

不过，封装并不意味着内部数据一定无法被外部访问。

在 Python 中，`_threshold` 前面的下划线是一种命名约定，表示这个属性通常被视为内部实现的一部分，不鼓励外部直接使用。

但下面的代码依然能够执行：

```python
policy._threshold = Decimal("500.00")
```

Python 的单下划线命名不会阻止这种操作。由此可见，将数据放进类中，并不自动保证这些数据受到严格保护。

封装提供了组织和管理数据与行为的边界，边界如何限制外部访问，还取决于语言机制和接口设计。

### 3. Getter 和 Setter：控制属性的访问

在面向对象编程中，我们经常会遇到 Getter 和 Setter。

Getter 是用于读取对象属性的方法，Setter 是用于设置对象属性的方法。它们通常被称为访问器（Accessor）和修改器（Mutator）。

假设我们希望允许外部读取和调整 VIP 优惠门槛，同时保证门槛必须大于零。

可以把前面的类改写为：

```python
from decimal import Decimal


class VipPolicy:
    def __init__(self):
        self._threshold = Decimal("200.00")

    def get_threshold(self) -> Decimal:
        return self._threshold

    def set_threshold(self, value: Decimal) -> None:
        if value <= 0:
            raise ValueError("优惠门槛必须大于零")

        self._threshold = value

    def is_eligible(self, amount: Decimal, level: str) -> bool:
        return level == "VIP" and amount >= self._threshold
```

现在，外部可以通过 `get_threshold()` 读取门槛，通过 `set_threshold()` 修改门槛。

```python
policy = VipPolicy()

print(policy.get_threshold())  # 200.00

policy.set_threshold(Decimal("300.00"))

print(policy.get_threshold())  # 300.00
```

如果调用方试图把门槛设置为负数，Setter 就会拒绝这次修改。

这样，对象可以通过自己的方法检查输入，并维护内部状态应当满足的约束。这类约束也称为不变量（Invariant）：在规定的有效状态下，对象必须始终满足的条件。

Getter 和 Setter 的价值，是为属性访问提供一个可以加入验证、转换或其他行为的入口。它们并不必然比直接访问属性更好。如果 Getter 只是原样返回属性，Setter 只是无条件赋值，那么额外的方法未必带来实际价值。

Python 还提供了 `@property`，可以用属性访问的语法调用 Getter 和 Setter。

上面的读写逻辑可以写成：

```python
from decimal import Decimal


class VipPolicy:
    def __init__(self):
        self._threshold = Decimal("200.00")

    @property
    def threshold(self) -> Decimal:
        return self._threshold

    @threshold.setter
    def threshold(self, value: Decimal) -> None:
        if value <= 0:
            raise ValueError("优惠门槛必须大于零")

        self._threshold = value
```

使用时看起来像直接访问属性：

```python
policy = VipPolicy()

print(policy.threshold)  # 调用 Getter

policy.threshold = Decimal("300.00")  # 调用 Setter
```

读取 `policy.threshold` 时，Python 会调用由 `@property` 定义的 Getter；执行赋值时，则会调用 `@threshold.setter` 定义的 Setter。

如果只定义 Getter，没有对应的 Setter，那么通过该属性名称执行赋值通常会抛出 `AttributeError`。

不过，这仍然不意味着对象的所有内部数据都无法被修改。前面提到的 `_threshold` 在 Python 中依然可以被直接访问。

更重要的是，Getter 和 Setter 控制的是访问方式，它们本身并不能保证模块的内部设计不会被其他代码依赖。

### 4. 信息隐藏：避免外部依赖内部设计

现在回到前面的价格计算问题。

假设优惠规则越来越复杂，我们决定把所有配置放进一个字典中：

```python
from decimal import Decimal


class PricePolicy:
    def __init__(self):
        self._config = {
            "vip_threshold": Decimal("200.00"),
            "vip_discount_rate": Decimal("0.10"),
        }

    def get_config(self) -> dict[str, Decimal]:
        return self._config
```

这里的 `_config` 是一个内部配置字典，保存了 VIP 优惠门槛和折扣比例。

类还提供了 `get_config()`，允许其他代码读取这份配置。这就是一个 Getter，只不过它返回的不再是单个数值，而是整个配置对象。

假设订单模块这样使用：

```python
policy = PricePolicy()

config = policy.get_config()

amount = Decimal("300.00")
level = "VIP"

eligible = (
    level == "VIP"
    and amount >= config["vip_threshold"]
)

rate = config["vip_discount_rate"] if eligible else Decimal("0.00")
payable = amount * (Decimal("1.00") - rate)
```

乍一看，这段代码已经使用了独立的类，内部配置也没有被调用方直接读取。外部通过 Getter 访问配置，似乎符合封装的要求。

但仔细观察会发现，订单模块仍然知道很多价格计算的内部细节。

它知道配置中存在 `vip_threshold` 和 `vip_discount_rate` 两个字段，知道 VIP 优惠通过金额门槛判断，也知道优惠金额需要乘以一个固定折扣比例。

这些知识已经进入了订单模块。

现在假设产品要求将原来的固定九折改成阶梯优惠。价格模块可能需要把原来的折扣率字段改成一个保存多档折扣的结构。

于是，订单模块就需要重新修改计算逻辑。其他读取了这份配置的模块也可能受到影响。

虽然价格配置已经被放进 `PricePolicy` 类中，但其内部数据结构和计算规则仍然成为调用方的依赖。

这就是“Getter 暴露了完整的内部配置结构”的含义。

还有一个更直接的问题。

在 Python 中，字典属于可变对象。上面的 `get_config()` 返回的是内部字典对象的引用，因此调用方可以通过这个引用修改同一份字典：

```python
policy = PricePolicy()

config = policy.get_config()

config["vip_discount_rate"] = Decimal("0.50")

print(policy.get_config()["vip_discount_rate"])  # 0.50
```

调用方没有经过 Setter，却改变了 `PricePolicy` 内部保存的折扣比例。

即使把 Getter 改成返回字典的副本，避免调用方直接修改原始字典，另一个问题依然存在：调用方仍然需要知道配置字段及其业务含义。

如果以后修改配置结构，调用方还是可能需要调整。

这里就需要引入信息隐藏（Information Hiding）。

信息隐藏关注的是：一个模块内部的哪些设计决定，不应该成为其他模块必须了解和依赖的知识。

在这个例子中，优惠门槛使用什么字段保存、优惠比例怎样组织、资格判断采用什么算法，都可以由价格模块自行维护。

订单模块需要的是根据当前适用规则得到正确报价的能力。

因此，我们可以让价格模块直接提供前面定义的 `quote_price()` 接口，由模块内部读取配置、判断优惠资格并计算结果。

调用方只需要：

```python
quote = quote_price(Decimal("300.00"), "VIP")

print(quote.payable)  # 270.00
```

以后，即使内部配置由字典变成数据库规则表，或者优惠算法发生变化，只要报价接口及其行为约定仍然成立，调用方就不需要理解这些变化。

这正是信息隐藏希望实现的效果。

信息隐藏的对象是设计决定，而不仅仅是变量。算法选择、数据表示、存储方式、内部状态以及其他可能变化的实现约定，都可能需要隐藏在明确的模块边界之后。

当然，并非所有配置信息都必须隐藏。如果某个后台功能本来就负责管理优惠门槛，那么读取、修改门槛就是它合理的业务需求。此时，可以专门提供查询或修改优惠政策的公开接口，并明确其参数与行为契约。

信息隐藏要求我们减少不必要的知识依赖，而不是禁止模块对外提供数据。

### 5. 三者之间的关系

通过前面的例子，可以进一步理解抽象、封装和信息隐藏之间的联系。

抽象首先帮助我们确定模块对外应该提供什么能力。对于定价模块，我们可以选择将复杂的计算过程表现为一次报价操作，让调用方围绕报价这个业务概念进行协作。

封装则帮助我们把价格计算需要的数据与操作组织在一起，由明确的模块负责维护它们。访问控制、属性验证和内部状态管理，都可以通过封装边界实现。

信息隐藏关注这个边界是否真正隔离了内部的设计决定。如果调用方依然必须知道折扣配置的结构和计算步骤，那么即使程序使用了类、私有命名和 Getter，也未必达到了预期的信息隐藏效果。

三者并非互不相关的独立技术。一个设计良好的模块，往往通过抽象确定公开能力，通过封装组织内部实现，再依据信息隐藏原则减少实现细节向外部传播。

但信息隐藏还存在一个必须明确的边界：模块对外的接口本身就是一种依赖。

以 `quote_price()` 为例，调用方依赖函数接受什么参数、返回什么结果，以及金额单位、计算精度和失败行为等约定。这些内容共同组成了接口契约（Interface Contract）。

契约必须足够明确，调用方才能正确使用模块。

如果将来定价功能增加多币种支持，原来的 `Decimal` 金额可能需要替换为包含币种信息的金额对象。此时，接口契约本身可能需要改变，调用方自然也可能需要调整。

因此，信息隐藏无法消除所有变化传播，它能做的是让内部实现变化尽可能不影响对外契约，并使公共契约的变化具有明确的影响范围。

至于应该公开什么、隐藏什么，还需要根据模块承担的职责和调用方的实际需求判断。这也是为什么仅仅使用类、接口或某种设计模式，并不能自动得到良好的软件设计。

## 五、依赖关系与变化的范围

模块之间建立协作后，依赖便不可避免。设计需要关心的是依赖指向哪里，以及依赖所涉及的知识是否稳定。

假设订单服务调用 `quote_price()`，价格模块把内部的条件判断替换为规则表查询。只要公开契约不变，订单服务理论上无需修改。它依赖的是报价结果的语义，而非获得结果的过程。

如果订单服务直接读取价格模块的内部折扣配置，那么配置的结构就进入了订单服务的知识范围。价格模块调整实现时，必须额外考虑这个调用方。依赖仍然只有一条，但它承载了更多容易变化的细节。

还有一种更隐蔽的情况：两个模块直接共享一份可变对象，或者要求调用按特定顺序发生。即便函数签名保持不变，状态表示和执行时序的变化也可能导致错误。因此，审查依赖时，除了源代码引用，还要看数据所有权、状态变更和时序约定。

依赖过于复杂时，还可能出现循环。订单模块调用价格模块，价格模块又反过来导入订单服务，会使双方更难独立理解和初始化。循环依赖值得检查，但是否需要拆除，以及怎样拆除，仍要看两者承担的职责；消除一条导入语句并不一定消除实际的业务耦合。

衡量设计质量也不能只统计一次修改涉及多少文件。如果公共报价契约改变，订单服务需要更新是合理的；如果内部折扣算法调整，却要求多个无关流程一起改动，就需要检查模块边界是否泄漏了实现知识。

减少变化传播的目的，是让受影响的部分与真正发生变化的职责尽量一致。

## 六、模块化的限度
模块化也会带来新的问题。
### 1. 未来的变化无法完全预测

按照变化考虑模块边界，似乎要求设计者预知未来。但实际开发中，业务方向、使用方式和外部环境都可能变化，任何划分都只建立在当前能够掌握的信息之上。

已有需求、业务不变量、修改记录和团队对领域的理解，可以为划分提供依据。例如，优惠资格与折扣计算需要共同保证报价正确，通常适合处在一个清楚的定价职责之内。订单通知则受到渠道、模板、投递失败处理等因素影响，具有不同的变化来源。

不过，不能只凭“经常一起修改”就合并模块。同一需求可能同时涉及接口、数据库和页面，它们在一次提交中出现，并不说明它们应该由同一个模块维护。还要追问这些代码为何一起变化，是否共同维持某个业务约束，以及能否在不破坏对外契约的前提下独立演化。

同样，名义上属于一个领域的规则，也未必永远需要放在一起。优惠资格可能由营销政策决定，金额舍入可能由财务约定决定。定价模块可以统一对外提供报价，但内部是否继续拆分，应由各项规则的职责和变化关系决定。

### 2. 隔离变化也有成本

每增加一道模块边界，就需要维护新的接口、约定和依赖关系。开发人员可能需要在更多文件之间跳转，测试中也可能增加替身和组装工作。过多的间接层会延长理解代码的路径。

如果一项规则简单、稳定，只在一个地方使用，把它拆成数个抽象类和策略对象，未必能节约维护成本。另一方面，把订单、库存、支付和通知都堆在一个模块中，也会让不同的变化原因相互干扰。

模块设计实际上是在权衡两种成本：当前组织抽象与协作的成本，以及未来修改时需要理解和调整的成本。高层次的设计原则有助于识别风险，却无法替代具体的业务判断。

还需要注意，正确复用的前提是语义相同。订单预览可以根据当前规则重新报价，已经成立的历史订单通常应保留当时确定的交易金额。两者都涉及价格，但不能因此让历史报表每次都调用当前优惠规则重算。否则，规则升级可能改变过去的财务事实。

好的模块边界必须建立在对业务含义的理解上。仅凭相似的代码形状决定复用，有时会把本来不同的职责错误地绑在一起。

## 七、从模块设计到软件架构

到这里，我们可以重新理解软件设计的工作。

面对一个持续变化的系统，开发人员需要识别有哪些重要的决定，哪些决定彼此关联，哪些可以独立变化，以及其他部分需要通过什么约定使用它们。模块划分将这些决定安排到不同的职责边界，依赖关系则描述边界之间如何协作。

当这些安排扩展到整个系统，形成相对稳定的职责分工、依赖方向和协作机制时，就进入了软件架构讨论的范围。

一个系统可以按订单、定价、库存等业务能力组织模块，同时采用 Controller、Service、Repository 等分层方式安排代码。两者观察的是不同维度：业务模块关注规则的归属，分层关注不同技术职责之间的协作。它们可以共同存在，但实际效果仍取决于代码是否遵守边界。

因此，架构图和目录结构只是设计的表达方式。真正影响维护成本的，是代码中谁拥有某项知识，谁必须依赖它，以及该知识变化后需要重新确认多大的范围。

软件设计无法阻止需求变化，也无法让所有模块彼此独立。它能够争取的是局部理解和局部修改的机会：让每项重要决定尽可能有清晰的归属，让必要的协作通过明确的契约发生，并对增加抽象所付出的成本保持判断。

下一篇将讨论 MVC 与分层架构，继续研究后端程序如何组织不同职责，以及不同层次之间的依赖应当怎样建立。
