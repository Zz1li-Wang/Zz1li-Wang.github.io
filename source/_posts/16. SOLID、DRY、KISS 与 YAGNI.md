前两篇从需求变化出发，讨论了模块化和分层架构。订单创建的 HTTP 入口、业务处理和数据访问已经可以分开，但系统仍有可能变得难以修改：一个 `OrderService` 容纳越来越多的政策，Repository 对外暴露大量专用操作，为了应对想象中的扩展而设计的接口也越来越多。

问题已经不在于是否分了层，而在于这些边界为什么这样划、什么值得抽象，以及代码之间应该形成怎样的依赖。SOLID、DRY、KISS 和 YAGNI 经常被放在一张原则清单上讲解，其实它们针对的是相互牵连的几类设计成本。

继续从订单定价出发，可以看到这些原则如何在一次次需求变化中出现，也可以看到它们为什么不能不加判断地同时执行。

## 一、订单定价规则逐渐增加

假设订单系统最初只有一条优惠政策：VIP 用户购买金额满 200 元，可以享受九折。金额以人民币分为单位保存，计算时用整数避免二进制浮点数带来的精度问题。

```python

def discount_cents(amount_cents: int, level: str) -> int:
    if level == "VIP" and amount_cents >= 20_000:
        return (amount_cents + 5) // 10
    return 0
```

这里暂时约定传入金额是非负整数。`(amount_cents + 5) // 10` 在这个前提下实现了百分之十优惠金额按“半分向上”取整到分。例如原价 200.05 元，优惠金额为 20.01 元。其他货币及舍入规则需要另外约定。

这段代码只有一种变化来源：当前优惠政策。需求明确，计算方法简单，使用独立函数已经足够。此时为它建立抽象基类、策略注册中心和配置驱动的规则引擎，未必有实际收益。

后来，产品提出了第二种活动：普通用户也可以参加“满 400 元减 60 元”，但每笔订单只使用一种指定的活动，不叠加优惠。再后来，运营希望由后台切换当前活动；财务则要求调整报表中优惠金额的展示方式。

原来的函数可能开始增加活动类型判断。如果开发人员顺手把报表格式、优惠配置读取甚至数据库保存都放进一个 `PricingService`，代码仍然可以运行，但不同类型的修改已经集中到同一个位置。

运营继续调整优惠活动的同时，财务又要求修改报表格式，通知部门希望更换邮件模板。它们可能出现在同一个下单流程中，却有不同的维护原因。单一职责原则首先关心这种差异。

## 二、单一职责原则与变化来源

单一职责原则（Single Responsibility Principle，SRP）是 SOLID 中的第一个原则。它经常被简化为“一个类只做一件事”。这个解释过于模糊，因为“一件事”可以是一次金额计算，也可以是完成整笔订单交易。

Robert C. Martin 使用过“一个模块应该只有一个变化原因”的表述，后来又将变化原因与提出需求的业务角色或利益相关方联系起来。其目的在于帮助我们辨认：哪些代码由于同一类业务责任而需要共同维护，哪些代码因不同的责任而分别变化。

假设某个 `OrderManager` 同时计算折扣、生成财务报表和发送订单邮件。营销人员调整优惠规则、财务人员改变报表口径、运营人员更换邮件模板，都可能要求修改这个类。

这三个需求涉及不同的职责。它们偶尔在同一个业务流程中发生，并不足以构成放在同一个模块内的理由。如果修改优惠时顺带影响邮件发送，意味着原本可以隔离的变化已经相互牵连。

一种合理的组织方式，是让定价模块解释优惠政策，让报表模块负责统计口径，让通知模块负责投递规则。订单创建用例可以调用它们，但无需拥有所有内部决定。

这里的业务角色帮助辨别需求来源，不能机械映射成公司的组织架构。同一位产品经理可能提出多种相互独立的需求；不同部门也可能共同维护同一项业务约束。判断仍要回到代码承担的业务含义。

创建订单需要校验购买数量、获取商品价格、计算优惠、扣减库存和保存订单。若这些步骤共同完成一次不可分割的业务操作，应用服务组织它们是正常的。我们不需要为了满足“只做一件事”，给每个步骤建立一个只有一个方法的类。

区别在于组织流程和拥有规则。订单应用服务可以决定何时调用定价模块，却不必自己维护 VIP 的计算细节；它可以要求扣减库存，却不必自己拼接库存更新的 SQL。

模块边界的粒度取决于抽象层次。在应用层，“创建订单”可以是一项职责；在定价模块内部，“解释优惠政策”又可以是一项更具体的职责。单一职责原则无法脱离业务语义，单纯通过函数数量来执行。

职责划开后，优惠规则本身还会继续增加。即便它只由定价模块维护，这个模块也可能在每次增加活动时反复修改同一段大型条件分支。开闭原则针对的就是这样的扩展压力。

## 三、开闭原则与规则扩展

当营销活动不断增加时，优惠计算可能逐渐变成以下形式：

```python

def discount_cents(amount_cents: int, level: str, campaign: str) -> int:
    if campaign == "VIP_10":
        return (amount_cents + 5) // 10 if level == "VIP" and amount_cents >= 20_000 else 0
    if campaign == "FULL_60":
        return 6_000 if amount_cents >= 40_000 else 0
    return 0
```

代码中每增加一种活动，就可能增加一个分支。如果只有两三种活动，而且变化很少，这种实现依然清晰。真正需要重新设计的信号，是新增活动已成为反复发生的需求，多个调用位置开始维护同类分支，或者修改旧分支时频繁影响其他活动。

开闭原则（Open/Closed Principle，OCP）可以用来考虑这种情况。Bertrand Meyer 对它的早期论述是模块应当能够扩展，又能够作为稳定单元供其他模块使用。后来，这一思想常被表述为“对扩展开放，对修改关闭”。

“关闭”不能理解为禁止修改既有源码。修复错误、修改原有业务规则、调整已经过时的抽象，都可能需要修改代码。更实际的目标是：**当某一类变化可以预见且反复发生时，尽量通过既定扩展方式增加新行为，减少对稳定代码的反复修改。**

继续使用前面的订单案例，假设已确定不同活动都遵循一个共同约定：输入当前订单信息，返回本次活动的优惠金额。每笔订单只选择一种优惠活动。

Python 可以用 `Protocol` 表达这种接口。下面的代码把数据契约、计算入口和两种具体政策放在一起，便于比较：

```python
from dataclasses import dataclass
from typing import Protocol

@dataclass(frozen=True)
class QuoteInput:
    amount_cents: int
    level: str

class DiscountRule(Protocol):
    def discount_cents(self, data: QuoteInput) -> int: ...

class VipDiscount:
    def discount_cents(self, data: QuoteInput) -> int:
        if data.level == "VIP" and data.amount_cents >= 20_000:
            return (data.amount_cents + 5) // 10
        return 0

class FullReduction:
    def discount_cents(self, data: QuoteInput) -> int:
        if data.amount_cents >= 40_000:
            return 6_000
        return 0

@dataclass(frozen=True)
class PriceQuote:
    discount_cents: int
    payable_cents: int

def quote_price(data: QuoteInput, rule: DiscountRule) -> PriceQuote:
    if data.amount_cents < 0:
        raise ValueError("金额不能为负数")

    discount = rule.discount_cents(data)
    if not 0 <= discount <= data.amount_cents:
        raise ValueError("优惠金额不符合约定")

    return PriceQuote(
        discount_cents=discount,
        payable_cents=data.amount_cents - discount,
    )
```

使用时由调用方选择本次报价采用的优惠规则：

```python

data = QuoteInput(amount_cents=50_000, level="NORMAL")
quote = quote_price(data, FullReduction())
print(quote.payable_cents)  # 44000
```

这次变化的关键是 `quote_price()` 不再负责判断活动的具体类型。未来增加第三种规则，只要实现同样的行为契约，报价流程就可能保持不变。

不过，系统依然需要在某处选择并创建具体规则。后台切换活动可能涉及数据库配置和规则装配，新增策略也可能要求修改装配代码。开闭原则并不意味着增加功能时整个系统一个旧文件都不能修改；它希望保护的是已经稳定、没有必要随新规则改变的那部分逻辑。

这段设计有一个容易被忽视的前提：我们已经知道活动种类会独立变化，并且它们确实能够遵守相同的计算契约。

如果未来要求多种优惠叠加、设置互斥优先级，或者需要跨订单累计金额，问题就可能超出单条 `DiscountRule` 的表达能力。我们也许需要修改报价输入、增加组合规则，甚至重新设计定价过程。

原先稳定的契约可能无法表达全新的业务概念。需要修改时应调整它；开闭原则所保护的是已经识别出来的一类扩展，而未来出现的新维度会推动抽象继续演化。提前猜测全部变化只会把不确定性固化进今天的结构。

把不同算法改成可替换对象后，一个新的约束随之出现：它们是否真的能在同一调用位置安全工作？只看方法名称和类型注解，还不能回答这个问题。

## 四、里氏替换原则与行为契约

前面的 `quote_price()` 接受 `VipDiscount` 和 `FullReduction`。新策略加入以后，表面上拥有相同方法，实际运行却可能破坏原先的行为约定。

里氏替换原则（Liskov Substitution Principle，LSP）来源于 Barbara Liskov 对数据抽象和子类型的研究，后来与 Jeannette Wing 对行为子类型作了更形式化的讨论。其核心要求是：在程序依赖某种类型的地方，使用符合该类型契约的子类型，不应破坏程序原本可以依赖的正确性性质。

我们约定 `DiscountRule.discount_cents()` 接受合法的非负订单金额。当订单不符合活动条件时，返回 0；当符合条件时，返回介于 0 和订单金额之间的优惠值。

现在有人新增了一种活动，却做了以下实现：

```python

class StrictFullReduction:
    def discount_cents(self, data: QuoteInput) -> int:
        if data.amount_cents < 40_000:
            raise ValueError("未达到活动门槛")
        return 6_000
```

这个类拥有要求的方法，也能通过某些结构化类型检查。但对于金额为 300 元的有效报价输入，它抛出了异常。原本的报价流程允许订单不满足优惠条件，并预期得到 0 元优惠；替换后，这个原本合法的调用失败了。

问题不在于不同策略算出了不同金额，而在于新实现擅自收紧了调用条件。符合原来契约的使用者，无法再安全使用替换后的实现。

正确做法是让未达到门槛的活动返回 0，除非业务本来就要求将“不符合活动条件”定义为错误，并明确把这种情况写进所有实现共同遵守的契约。

类型注解可以说明参数与返回值的形状，但行为契约还涉及更多内容。

前置条件（Precondition）规定调用者必须满足什么条件。假设接口允许所有非负金额，具体实现就不应再要求金额至少为 400 元才允许调用。后置条件（Postcondition）规定操作成功后保证什么结果。在我们的例子中，优惠金额需要处在 0 到原价之间。对象不变量（Invariant）则描述有效对象在其生命周期中必须维持的约束。

从行为子类型的角度看，替换实现一般不能任意加强前置条件或削弱后置保证，还应尊重原有不变量及其他可观察的行为要求。异常、状态修改和副作用也可能属于契约的一部分。

例如，一个仓储接口约定 `get()` 查不到对象时返回 `None`，新实现却直接抛出异常；或者原接口保证一次保存调用不会自行提交事务，替换实现却在内部执行 `commit()`。即使方法签名完全相同，它们也可能破坏调用方已经依赖的行为。

Python 的 `Protocol` 可以通过结构化类型检查帮助判断某个对象是否具备所需的方法和类型形状，但类型检查器通常无法证明“优惠金额不会超过原价”这样的业务语义。因此，还需要通过明确的契约、测试和设计审查保证可替换性。

里氏替换原则也不限于继承体系。在采用鸭子类型和依赖注入的 Python 项目中，只要代码需要把不同实现作为同一种能力使用，就必须考虑行为是否真正兼容。

可替换性要求共同约定，但约定的内容也不能无限增长。随着定价模块既服务订单，又支持后台配置，使用者可能只需要其中很小一部分能力。接口隔离原则在这里发挥作用。

## 五、接口隔离原则与依赖范围

随着业务增长，定价模块可能对外提供很多功能：计算报价、查询活动配置、修改优惠门槛、导出活动报表。把它们放在同一个类中，有时符合管理上的便利，但使用者并不一定需要全部能力。

接口隔离原则（Interface Segregation Principle，ISP）强调，使用者不应被迫依赖自己并不使用的接口能力。

假设订单创建只需要报价功能，而后台管理系统需要修改活动。若两者都依赖一个包含十几个方法的 `PricingManager` 接口，那么接口的变化就有机会影响本来不相关的调用方。测试时也可能需要准备远超实际使用范围的替身对象。

可以根据使用者真正需要的能力定义接口：

```python
from typing import Protocol

class PriceQuoter(Protocol):
    def quote(self, data: QuoteInput) -> PriceQuote: ...

class PolicyAdmin(Protocol):
    def set_threshold(self, campaign: str, amount_cents: int) -> None: ...
```

订单创建依赖 `PriceQuoter`，后台配置管理依赖 `PolicyAdmin`。同一个实现类可以同时满足两个接口，也可以分别由不同组件提供。接口隔离要求的是缩小使用者的依赖面，不一定要求把实现拆成两个类或部署成两个服务。

这也解释了为什么通用接口未必越完整越好。一个声称适用于所有数据源的 Repository，如果强制每个实现都提供批量删除、事务提交、复杂分页和全文检索，那么只需要按 ID 读取数据的调用方也被绑到了这些额外约定上。

当然，不需要为每个函数建立一个独立接口。当一组操作确实属于同一种使用需求，并且通常一起演化时，保持在同一个契约内更容易理解。接口隔离同样要看职责关系，而不是机械地把方法拆得越细越好。

接口可以按使用者的需求分开，接着还要安排它们与具体实现之间的源代码关系。订单用例是否必须导入 SQLAlchemy 仓储，决定了业务层对基础设施了解多少。

## 六、依赖倒置原则与业务核心

第二篇里，订单应用服务调用 Repository，Repository 使用 SQLAlchemy 访问数据库。这样的调用路径已经分离了代码位置，但仍然可以继续追问：应用服务是否必须知道具体的 Repository 类，才能执行创建订单？

假设服务在内部直接构造 `SqlAlchemyOrderRepository`，甚至自行创建数据库 Session。此时想在测试中替换存储实现，或者让同一个用例用于其他数据访问环境，都可能需要修改服务代码。

依赖倒置原则（Dependency Inversion Principle，DIP）关注的是这种源代码依赖关系。Robert C. Martin 的经典表述强调，高层策略与低层实现都应该依赖抽象，抽象不应依赖实现细节。

这里的高层与低层指职责和抽象程度，不等于目录位置或代码执行顺序。创建订单的业务用例属于相对高层的政策；SQLAlchemy 查询、数据库驱动和连接细节属于较低层的技术实现。

下面只保留依赖关系，不重复第二篇已经讨论过的 Session 生命周期、库存扣减与事务实现：

```python
from typing import Protocol

class OrderWriter(Protocol):
    async def save(self, payable_cents: int) -> int: ...

class OrderService:
    def __init__(self, quoter: PriceQuoter, orders: OrderWriter):
        self.quoter = quoter
        self.orders = orders

    async def create(self, data: QuoteInput) -> int:
        quote = self.quoter.quote(data)
        return await self.orders.save(quote.payable_cents)
```

这里的 `OrderService` 只说明自己需要哪些能力。实际运行时，应用的组装位置可以传入具体的定价器和 SQLAlchemy 仓储。测试时也可以传入满足相同契约的替身。

一个重要细节是，依赖倒置不会消除运行时调用。`OrderService` 执行时仍然可能调用 SQLAlchemy 仓储，数据库仍然接收 SQL。改变的是源代码对实现细节的依赖：业务模块不需要导入和构造某个具体数据库实现。

抽象接口可以放在应用层或专门的端口模块中，由基础设施实现它。对于复杂项目，这种组织方式有助于让业务模块保持相对独立。但 Python 并不要求一定定义 `Protocol` 才能进行依赖注入；构造函数接收已有对象，本身也可以实现运行时替换。`Protocol` 主要使所需能力更清楚，并支持静态检查。

还要注意，上面的代码只是解释依赖方向的片段，省略了数量、库存、订单实体及事务。真实创建订单用例仍要保证多个数据库操作处于适当的事务边界。让接口看起来干净，并不能代替数据一致性的设计。

依赖注入（Dependency Injection，DI）是把某个对象需要的依赖从外部传入，而不是让它在内部自行创建。构造函数参数就是最简单的一种形式，并不要求使用容器或框架。

依赖倒置则是关于模块应当依赖哪一层约定的设计原则。两者经常一起出现，但不是同一个概念。把一个具体的 `SqlAlchemyOrderRepository` 实例通过构造函数传给服务，已经使用了依赖注入；如果服务的源码依然显式依赖该具体类的专有接口，那么依赖倒置可能仍然有限。

反过来，为每个函数建立接口也不会自动得到良好的架构。如果接口只是照搬 ORM 的所有方法，业务模块仍可能依赖大量数据库语义。抽象是否有效，最终取决于它是否表达了业务真正需要的能力。

前面几项原则主要处理对象之间的职责与依赖。还有一类问题可能根本没有调用关系：两个模块独立维护同一项业务规则，需求变化时必须手动同步。DRY 要求我们从知识的归属看待这种重复。

## 七、DRY 与业务知识的唯一来源

SOLID 主要讨论职责、扩展、替换和依赖。DRY（Don't Repeat Yourself）从另一个角度讨论维护成本：一项知识如果在系统中有多个独立表示，那么这项知识变化时，开发人员就必须保持它们同步。

Andy Hunt 和 Dave Thomas 在《The Pragmatic Programmer》中强调的是知识应具有单一、明确、权威的表示。这里的“知识”可以是业务规则、数据定义或某项系统约定，不限于重复的几行代码。

第一篇文章中，订单预览、订单创建和后台试算分别实现 VIP 优惠规则，这就是同一份业务知识在多个地方重复维护。只要它们应该依据同一条政策计算，就应当让它们共享一个权威规则来源，避免优惠门槛只更新其中一处。

但两段看起来相同的代码，并不一定代表同一份知识。假设营销活动的优惠比例恰好是百分之十，另一个独立的渠道手续费率也恰好是百分之十。它们可能都写成 `amount * 0.1`，却由不同的业务主体管理，也可能在不同时间独立变化。

如果仅仅因为数字和计算表达式相同，就将它们绑定到同一个 `DEFAULT_RATE`，以后优惠率调整就可能意外改变手续费。机械提取公共函数，有时反而制造了本来不存在的耦合。

判断是否需要消除重复，要追问这两段实现是否代表同一项规则、是否拥有相同的变化原因，以及谁对正确性负责。代码形状是线索，业务语义才是依据。

实际系统可能为了查询性能保存冗余数据，也可能把权威规则生成成前端和后端各自需要的格式。这样的设计并不必然违反 DRY。

关键是要区分权威来源与派生副本，并规定它们如何同步。例如，订单确认时保存成交单价和优惠金额，是为了记录交易当时的事实；当前优惠政策即使变化，也不应该覆盖历史成交金额。它们在数值上可能曾经相同，业务含义却已经不同。

同样，前端可以做即时价格预览，但正式下单时仍应由服务端按有效规则验证或重新计算，不能把可由客户端任意提交的金额当作权威成交价格。

DRY 的作用是减少知识不一致带来的维护风险。它并不保证把所有相似实现收拢到一个函数，就一定能够得到更好的设计。

把重复知识收拢，并为变化建立扩展接口，往往会让设计越来越完整。然而每一个新的抽象也有维护成本，因此还需要另一组原则来限制这种扩张。

## 八、KISS 与抽象的理解成本

KISS 常被概括为 Keep It Simple, Stupid，在软件开发中用来提醒我们避免不必要的复杂性。它没有规定某种具体技术结构，更接近一条设计判断准则。

前面的优惠计算，可以只有一段条件判断，也可以通过策略对象、规则接口和装配机制完成。哪一种更简单，要结合真实需求判断。

如果系统只有一种优惠，短小的函数往往更容易阅读、修改和测试。引入五六个类，虽然能够展示完整的模式，却使阅读者必须跨越多个文件才能理解一次计算。

如果系统已有十多种独立活动，每周都会新增策略，而且多个入口都需要统一计算，那么将规则拆成独立实现、统一调用契约，反而可能降低长期复杂度。此时，代码行数增加了，但不同变化之间的牵连减少了。

所以，简单不能只用行数或类的数量来衡量。开发人员需要关心完成一个需求时必须同时理解多少概念、追踪多少依赖、确认多少隐含约定。一个非常短却依赖全局可变状态的函数，可能比稍长但输入输出明确的函数更难维护。

KISS 要求我们选择能够满足当前约束、又容易解释的方案。抽象、设计模式和框架都可能帮助降低复杂度，也可能无端增加复杂度。它们应当为真实问题服务。

现有需求已经足够复杂时，我们仍需考虑未来。但“将来可能扩展”无法直接证明今天应该提前实现所有扩展机制。YAGNI 讨论的正是做决定的时机。

## 九、YAGNI 与延迟设计

YAGNI 是 You Aren't Gonna Need It 的缩写，通常与极限编程（Extreme Programming，XP）的简单设计和增量设计实践联系在一起。它提醒开发人员，不要因为某项功能将来“可能会需要”，就在今天完成它。

假设系统现在只有 VIP 九折优惠。团队预计未来可能出现阶梯优惠、优惠券叠加、会员积分抵扣、跨店铺促销和跨币种结算，于是决定首先开发一个通用规则引擎，支持动态表达式、插件装载、规则优先级和远程配置。

这些能力听起来都有合理用途，但如果需求尚未明确，实现它们就需要现在支付开发、测试、理解、升级和维护的成本。更重要的是，未来真正出现的规则未必符合今天的猜测。一个过早建立的抽象，可能反过来限制后续设计。

业务变化尚不明确时，保持设计可理解、测试充分、修改成本可控，可以让团队在获得更多信息后再决定如何扩展。

如果第二种独立优惠活动真正出现，我们就有了比较具体的变化需求，可以判断提取共同契约是否值得。若增加第三、第四种活动的频率很高，再考虑策略装配或规则注册机制，就有了更充分的证据。

延迟设计决定，并不意味着必须等到代码已经严重失控才重构。合理的方式是让当前实现保持清晰，依靠测试和模块边界降低后续修改的风险，然后随着需求逐步演化。

Martin Fowler 对 YAGNI 的讨论也强调，推迟推测性功能的价值不仅体现在节省最初的编码时间，还体现在避免为这些功能持续承担维护和修改成本。

YAGNI 不能成为忽略已知约束的理由。订单创建需要保证库存与订单记录的一致性，这属于当前业务正确性；用户密码需要安全存储，这是当前安全要求；如果接口明确存在重试场景，必要的幂等处理也可能是当前需求的一部分。

与之不同，提前实现尚未要求的“全渠道、全币种、任意优惠组合引擎”，属于推测性功能。判断是否应当提前建设，需要考虑需求的确定程度、未来补建的代价、系统的风险以及设计是否容易调整。

对于数据迁移、不可逆的外部协议和高成本基础设施决策，适当的前瞻性设计可能具有明显价值。YAGNI 是反对没有充分依据的提前实现，并不要求完全忽略已经能够识别的长期风险。

现在再把这些原则放回同一个订单系统，就能看到它们可能给出不同方向的建议。设计决策需要结合变化的确定程度和维护成本，而不宜把原则当成必须逐条勾选的清单。

## 十、原则在实际设计中的取舍

经过前面的分析，可以看到这些原则之间存在联系，也存在需要权衡的地方。

单一职责要求我们识别变化原因，为不同知识找到合适的归属；开闭原则希望已经明确的变化类型能够通过扩展获得支持；里氏替换原则保证这些扩展能够遵守共同的行为约定；接口隔离限制调用方对无关能力的依赖；依赖倒置则进一步安排高层业务政策与具体技术实现之间的源代码关系。

DRY 从知识一致性出发，提醒我们避免让同一条规则分散到多个维护位置。KISS 和 YAGNI 则约束上述设计活动本身的成本，防止为了追求抽象、复用或未来扩展而建立缺少实际依据的结构。

它们并不总会给出完全相同的建议。

开闭原则可能鼓励提前设置扩展接口，YAGNI 则要求确认扩展需求是否真实存在。两者可以通过识别稳定的变化点来协调：有反复出现的扩展需求，便值得形成共同契约；只有模糊猜测时，先保留简单实现通常更合理。

DRY 可能促使我们合并相似的代码，单一职责原则却提醒我们检查这些代码是否受不同业务原因驱动。当两个流程只是暂时相似、未来可能独立变化时，保留局部重复有时比制造错误的公共抽象更安全。

依赖倒置可以隔离数据库和外部服务的具体实现，但如果一个小工具只调用一个稳定的库，为每个 API 加上自定义 Protocol 和工厂，可能违背 KISS 所强调的必要简单。

回到实际开发，逐条检查“是否满足 SOLID”并不能告诉我们哪一种结构更好。更有效的检查方法，是观察一次确定的业务变化：哪些文件必须修改，哪些接口受到影响，是否出现了无关模块的连锁修改；再检查为限制这些变化新增的抽象，是否值得它们带来的理解与维护成本。

软件设计没有一套脱离上下文的最优结构。原则帮助我们建立判断依据，却不能替代对当前业务、变化来源和工程约束的理解。

从第一篇的模块边界，到第二篇的后端分层，再到本篇的设计原则，我们已经能够解释许多常见的重构选择。接下来讨论具体设计模式时，应该把重点放在模式解决了什么真实问题、引入了哪些新约束，以及什么情况下使用它会使设计更复杂。
