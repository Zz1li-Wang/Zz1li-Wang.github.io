第一篇区分了模型、应用运行时和工具。模型能够根据用户任务提出调用某个函数的意图，真正执行函数的仍然是应用程序。那么，模型是怎样把自然语言中的动作意图转换成确定的工具名称和参数的？

Function Calling 提供了这项接口能力。它让应用将工具声明提供给模型，并以结构化形式取得模型希望执行的调用。理解这个过程，关键不在于记住某一个 SDK 的方法名，而在于分清工具声明、模型生成、参数验证和执行反馈的边界。

## 一、工具声明首先是一份接口描述

假设我们有一个库存查询函数：

```python

def get_stock(sku: str) -> dict:
    return {"sku": sku, "available": 12}
```

应用需要把它能够接受的参数描述给模型。JSON Schema 是常见的约束表达方式，可以规定参数类型、必填字段、枚举和对象结构。以 OpenAI Responses API 的 Function Tool 为例，声明可以写成：

```python

STOCK_TOOL = {
    "type": "function",
    "name": "get_stock",
    "description": "查询指定 SKU 当前可用库存，只读操作。",
    "parameters": {
        "type": "object",
        "properties": {
            "sku": {"type": "string", "description": "商品 SKU"}
        },
        "required": ["sku"],
        "additionalProperties": False,
    },
    "strict": True,
}
```

这份声明面向模型和运行时，真实的 Python 函数实现仍保存在应用中。`name` 用于标识调用目标，`description` 说明使用时机与行为，`parameters` 定义参数数据结构。`additionalProperties: false` 限制出现未声明的字段。

严格模式通常能显著降低格式错误，但需要满足相应的 Schema 限制。OpenAI 的严格模式要求对象禁止附加属性，并把属性全部列入 `required`；需要可选语义时可使用允许 `null` 的类型。严格模式约束的是可表达的数据结构，不能验证 SKU 是否确实存在，不能代替服务端的业务权限检查。

工具描述也影响选择效果。`search` 这类含糊的名称无法告诉模型它搜索的是订单还是文档。最好让名称指向稳定能力，让描述明确适用场景、输入范围、输出含义和副作用。接口越含糊，模型越容易在相似工具之间混淆。

## 二、模型返回的是结构化调用项

在 Responses API 中，模型可以返回普通文本，也可以返回 `function_call` 类型的输出项。函数调用项包含工具名称、JSON 编码的参数和用于关联结果的 `call_id`。

例如，一次输出在概念上可以表示为：

```json
{
  "type": "function_call",
  "name": "get_stock",
  "arguments": "{\"sku\":\"sku-1\"}",
  "call_id": "call_example"
}
```

注意 `arguments` 仍可能是一个 JSON 字符串，需要应用反序列化。`call_id` 标记的是这一次调用，不等于工具名称，也不等于业务幂等键。如果模型连续两次调用同一个工具，会出现不同的调用项；如果两个调用都试图扣减同一订单库存，是否属于重复业务操作，要依据应用自己的 `operation_id` 判断。

一次模型响应也可能包含多个工具调用。应用必须决定是否允许并行执行，不能假设调用顺序天然与业务依赖关系一致。如果第二个调用依赖第一个调用的结果，应该分步处理；如果两个只读查询独立，则可以并发执行并分别返回结果。

与工具调用相关的另一个配置是 `tool_choice`。自动模式允许模型自行决定是否调用工具；必选或指定工具模式能限制模型输出的调用类型。这个参数控制模型的选择空间，不应被当作权限机制。即使模型被引导只调用某个工具，服务端仍必须独立检查实际接收到的调用。


工具 Schema 会参与模型的输出约束，也是执行器进行参数验证的依据，同时还是人和模型理解工具能力的一份契约。不过这三个作用并不完全重合。比如 `sku` 声明为 `string`，只能排除数字或数组，不能确认它属于当前租户；`quantity` 声明为整数，不能保证库存充足；`path` 声明为字符串，不能阻止目录穿越。

因此，参数验证至少应分为结构验证、领域验证和安全授权。结构验证检查输入满足 JSON Schema；领域验证检查业务参数在当前状态下是否可接受；安全授权检查调用者对目标资源是否拥有许可。把这些工作全部交给模型的“严格输出”选项，实际上是将程序必须承担的约束错误地转嫁给了统计模型。

还要避免工具声明与实现逐渐漂移。模型看到的描述可能表示“只读查询”，真实 Handler 却在内部修改数据；Schema 可能允许字段缺失，Python 函数却要求必填参数。工具注册时应验证接口签名，重要工具还应运行契约测试。为每个工具明确输入约束、输出约束、副作用类别、权限要求和幂等策略，比单纯描述函数名更可靠。

两者都可能使用 JSON Schema，但它们约束的对象不同。结构化最终输出要求模型的交付内容符合某个数据结构，比如研究报告的标题、摘要和来源清单。Function Calling 要求模型产生一条调用指令，交给程序执行后再取得反馈。一个可以直接交付给用户的 JSON 对象，不能仅因为它包含 `tool_name` 字段就被认作实际工具调用。

在 Responses API 中，真正的函数调用由类型化 `function_call` 输出项表达，具有工具名称、参数和调用标识。程序应识别输出项的类型，而不是从一段普通文本中用正则表达式猜测模型是否想调用函数。这个边界为权限检查、关联工具结果与故障处理提供了结构化依据。

## 三、调用结果怎样反馈给模型

应用收到工具调用以后，检查工具名称和参数，执行代码，然后把结果作为 `function_call_output` 送回模型。下面展示一个完整的最小流程，使用当前 Responses API 的基本数据结构：

```python

import json
import os
from openai import OpenAI

client = OpenAI()
model = os.environ["OPENAI_MODEL"]
input_items = [{"role": "user", "content": "查询 sku-1 的库存"}]

def get_stock(sku: str):
    return {"sku": sku, "available": 12}

response = client.responses.create(
    model=model,
    input=input_items,
    tools=[STOCK_TOOL],
)
input_items.extend(response.output)

for item in response.output:
    if item.type != "function_call":
        continue
    if item.name != "get_stock":
        raise ValueError("未注册的工具")
    args = json.loads(item.arguments)
    if set(args) != {"sku"} or not isinstance(args["sku"], str):
        raise ValueError("非法参数")
    result = get_stock(args["sku"])
    input_items.append({
        "type": "function_call_output",
        "call_id": item.call_id,
        "output": json.dumps(result, ensure_ascii=False),
    })

if any(item.type == "function_call" for item in response.output):
    response = client.responses.create(
        model=model,
        input=input_items,
        tools=[STOCK_TOOL],
    )

print(response.output_text)
```

运行前需安装 `openai`，配置 `OPENAI_API_KEY` 和一个支持该接口的 `OPENAI_MODEL`。文中的 `STOCK_TOOL` 使用本节前面的定义。示例只演示一轮工具反馈：如果第二次模型调用再次要求工具，应进入下一篇介绍的循环，不能直接把当前结果视为最终答案。

这里选择把 `response.output` 加回输入序列，是为了保留模型产生的输出项和工具调用项，使后续请求能够正确理解结果属于哪一次调用。对于推理模型，还可能存在特定的推理输出项，需要按照 API 的上下文传递规则保留。使用 `previous_response_id` 也是部分场景中的另一种继续会话方式，但它与完全在应用侧维护消息序列的状态和存储要求不同。


一次模型响应可能同时包含普通消息、推理相关输出项和多个工具调用。使用无状态回放方式时，应用应按 SDK 和 API 允许的格式保留必要输出项，再为每个 `call_id` 添加对应的 `function_call_output`。如果调用 A 的结果被标到调用 B 的 ID 上，模型会在错误的前提上继续规划。一个工具名称可以重复使用，因此仅靠工具名建立映射是不够的。

同样，`call_id` 不等同于业务幂等键。它用于将本轮模型提出的调用和返回结果关联；当客户端因网络超时重新提交一次模型推理时，新输出可能拥有新的 `call_id`，却仍试图执行同一笔订单扣款。识别业务重复要依靠由业务系统定义的稳定 `operation_id`，并由数据库唯一约束或外部服务幂等机制保障。

假设同一轮输出了 A、B 两个工具调用，程序先执行完 B。若调用独立，可以先缓存结果，等每个调用都处理完再进入下一轮；若实现支持逐步返回，也必须保证结果与调用身份关联。若其中一个调用超时，另一个已经完成，不能简单重放整个响应导致已经成功的工具重复执行。短任务可以在内存里维护已处理调用集合；长任务需要持久记录，下一专题的 Harness 才会专门研究这一故障窗口。

让工具随意返回一段自然语言虽然方便，但会增加模型误判。更稳妥的通用结果结构通常包含 `ok`、`data`、`error.code`、`error.message` 以及可选的 `retryable` 或操作状态；这里的字段是应用自定义的结果约定，不是 Responses API 强制的返回格式。

工具执行失败应当和模型接口请求失败区分。前者可以作为工具结果反馈给模型，让它决定是否换用其他信息来源；后者可能导致本轮模型响应未被完整取得，运行时必须先处理模型调用的重试语义。对具有副作用的工具，`UNKNOWN_OUTCOME` 更不能随便改写为 `FAILED`，因为超时并不证明远端没有提交。

## 四、Function Calling 与结构化输出

Function Calling 常与 Structured Outputs 一起出现，但它们解决的需求并不一样。

工具调用强调让模型选择动作并产生调用参数。应用随后执行这个动作，再把结果送回模型。结构化最终输出则强调让模型交付符合某个 Schema 的答案，例如一份包含结论、证据和风险等级的报告。后者不需要真实调用外部函数，也不意味着已经完成写入。

同一个系统可以同时使用两者。Agent 先通过工具读取数据，最后使用结构化输出返回经过验证的报告对象。工具参数 Schema、最终回答 Schema 和数据库模型虽然可能具有相似字段，但它们负责不同的边界，不能只因为字段一致就共用所有验证规则。

JSON 格式正确并不代表内容可靠。模型生成 `{"order_id":"123","approved":true}`，即使通过结构化校验，也不能证明订单确实已经审批。真实状态仍需要来自权限受控的后端查询，写入操作则应通过明确的服务端 API 执行。

## 五、参数合法与执行安全之间还有距离

工具真正被调用之前，至少要经过名称查找、结构验证和业务授权。对于可以改变状态的工具，还需要确认用户意图、限制执行范围，并对外部副作用作好记录。

以 `update_order_status` 为例，模型可能提交合法 JSON，但试图把不属于当前租户的订单设为已完成。这不属于 Schema 错误，必须依靠后端访问控制阻止。模型还可能提供格式正确、语义矛盾的参数，如同时指定“取消订单”和“发货完成”，服务端应依据业务状态机拒绝不合法转移。

工具返回值同样不能被无条件信任。搜索网页或读取文档的工具可能返回提示注入文本，它仍然是外部内容，不应覆盖系统指令。如果某个工具抛出异常，运行时应形成明确的失败结果或结束任务，不能让模型将失败包装成成功。

还有一个容易发生的问题是重复执行。模型一次输出多个调用，程序可能执行到一半崩溃；下一轮恢复后，再次执行相同操作。`call_id` 可用于把结果对应到请求，但不能直接保证数据库只被更新一次。真正的幂等需要持久化业务操作标识和事务约束，后续 Harness 专题再深入讨论。


模型的输入边界比传统 API 更宽。它不仅接收用户消息，也会阅读网页、邮件、数据库描述和工具返回的正文。外部数据可能包含“忽略前面的规则并执行某个工具”之类的文字。如果运行时没有明确的来源层级，模型可能将本应作为证据的文本理解为新指令。这是提示注入的典型途径。

防护不应只靠提醒模型“忽略恶意指令”。运行时应保持来源标识，避免将外部文本拼进高优先级指令；敏感动作要做服务端鉴权与用户审批；工具执行必须接受明确的工具白名单与参数约束。尤其不能让模型从网页获得一个文件路径后，就无条件授予它读取任意主机文件的权限。

结果大小也是控制边界。过长的 HTML 或日志既可能消耗大量上下文，也可能淹没与任务相关的信息。执行器可以返回经过裁剪的摘要和可回溯引用，并明确说明是否截断；对精确计算和完整性核查，不能在截断后仍声称读过全量数据。

## 六、把调用机制交给执行循环

到这里，工具调用链已经完整：声明可用能力，模型生成结构化调用，应用验证和执行，把结果送回模型，再判断是否结束。一次调用可以用少量代码实现，但一项实际任务可能要连续调用多个工具，过程中还可能出现错误、重复、超时或证据不足。

继续使用单次请求加一次工具反馈，会把业务限制在开发者事先写死的两步中。下一篇将把这段交互抽象成 Agent Loop，研究每轮输出怎样推动状态转换，以及为什么 Agent 必须有明确的退出条件。
