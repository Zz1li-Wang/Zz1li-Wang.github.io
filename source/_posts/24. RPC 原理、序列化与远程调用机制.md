上一篇讨论了 Socket、TCP 和 HTTP 的职责。网络能够把字节从一个进程传给另一个进程，HTTP 还能为这些字节提供请求、响应和状态语义。然而，订单服务真正希望完成的操作是 `inventory.reserve(order_id, sku, quantity)`。它关心库存是否预留成功，并不希望每次都自己编写 URL、解析响应体、处理协议细节。

RPC（Remote Procedure Call，远程过程调用）由此产生。它让调用方通过一个明确的接口发起远程操作，由客户端与服务端的通信组件负责把方法、参数和结果转换为网络消息。RPC 的外观可以接近普通函数调用，但调用过程跨越了进程和故障边界。理解它，需要沿着一次真实的远程调用，看清每一层究竟做了什么。

## 一、一次远程调用的完整过程

设想订单服务需要调用库存服务的 `Reserve` 方法。客户端在代码中构造请求对象，然后执行 `await stub.Reserve(request)`。`stub` 是客户端代理，通常由接口描述文件生成，或者由框架运行时构造。调用 `Reserve()` 并不会直接跳转到库存服务的 Python 函数，它先进入客户端 RPC 运行时。

运行时需要识别目标服务和方法，使用约定的序列化格式将参数编码为字节，并按照传输协议封装请求。接下来，它取得到目标服务的连接，发出请求，并等待响应。服务端协议层解析收到的数据，根据服务名和方法名找到对应的处理函数，把参数还原成服务端语言能够使用的对象，再调用业务实现。业务返回后，服务端执行相反方向的编码，客户端收到响应并解码，最终把结果交还给原来的调用者。

```text
订单业务代码
    ↓ 调用 Reserve(request)
客户端 Stub / RPC 运行时
    ↓ 参数编码、确定目标和方法
传输层与网络
    ↓ 请求字节
服务端 RPC 运行时
    ↓ 解码、方法分发、参数校验
库存业务实现
    ↓ 返回结果或错误
服务端编码 → 网络传输 → 客户端解码
    ↓
订单业务代码得到结果
```

这条链路中包含了两个不同的接口。对调用方来说，`Reserve(request)` 是程序中的调用接口；在网络上传输时，它对应一个双方能够共同理解的协议。前者服务于代码组织，后者规定跨语言、跨进程的兼容方式。RPC 框架把两者衔接起来，却不能消除网络故障。

与普通函数调用相比，远程调用还要经过队列等待、网络传输、服务端调度、序列化和反序列化。参数大小、连接状态以及对方是否繁忙，都会影响调用耗时。因此，不能把进程内的细粒度函数接口原样搬到网络上。一个原本需要连续执行 `get_stock()`、`get_reserved()`、`set_reserved()` 的本地流程，拆分后更适合收敛为具有完整业务语义的 `Reserve` 操作，让库存服务在自己的事务中维护库存约束。

## 二、接口契约如何被两端共同理解

两个进程不能依赖彼此的 Python 对象地址或类定义来传递参数。即使双方都使用 Python，不同的代码版本也可能对字段名称、默认值或错误含义产生不同理解。跨语言以后，类型表示和编码差异更加明显。

RPC 因而需要接口契约（Contract）。契约至少应说明服务名称、方法名称、请求与响应的数据结构，以及调用失败时如何表示错误。有些框架使用 IDL（Interface Definition Language）来描述契约，并为不同语言生成客户端代理和服务端接口；另一些框架可以基于代码声明、注解或者运行时约定工作。

以库存预留为例，契约可以规定请求包含 `order_id`、`sku` 和 `quantity`，成功响应包含 `reservation_id` 与预留结果。这里真正需要长期稳定的是字段的业务含义：`quantity` 是本次请求预留的数量，还是订单希望达到的最终预留数量？重复发送相同 `order_id` 是否属于同一逻辑操作？库存不足与网络故障应当返回不同的结果还是不同的错误？这些问题无法由字段类型自动回答。

接口还需要考虑演化。客户端和服务端往往不能在同一时刻升级。新服务端添加字段后，旧客户端可能仍只认识原来的字段；某个原有字段被重命名或改变含义，则可能让双方在协议解析成功的情况下执行错误业务。契约设计既要考虑数据结构兼容，也要考虑业务语义兼容。

代码生成能够减少手写适配代码的重复劳动，却不意味着业务兼容性由工具自动保障。生成的 Stub 知道如何编码和调用某个方法，不知道修改库存预留规则是否会破坏现有订单流程。

## 三、序列化究竟解决了什么

序列化是按照约定的格式，把结构化数据转换成可以存储或传输的表示；反序列化则在另一端重建对应的数据结构。常见方案包括 JSON、Protocol Buffers、MessagePack 等。RPC 不必绑定某一种序列化格式，具体选择取决于框架、语言生态与协议要求。

JSON 易于阅读和调试，具有广泛的语言支持，但数字表示、字段缺失和类型约束需要双方明确约定。举例说，JSON 中的数字并不天然对应 Python 的 `int`、JavaScript 的 `number` 和数据库的 `DECIMAL` 中同一个精确类型。对金额、超大整数和时间值而言，协议设计必须明确精度与表示规则。

Protocol Buffers 则通过结构化的消息定义进行二进制编码。以常见的 proto3 为例：

```proto
syntax = "proto3";

message ReserveRequest {
  string order_id = 1;
  string sku = 2;
  int32 quantity = 3;
}
```

字段后面的 `1`、`2`、`3` 是字段编号。二进制线格式依靠字段编号及线类型识别数据，通常不直接传输字段名称。对于整数，Protobuf 常使用 Varint 等编码方式，较小的非负整数可以用较少字节表示。`int32`、`sint32` 的负数编码成本不同，也说明“采用二进制格式”并不足以推断某个字段的实际空间开销。

字段编号一旦投入使用，就属于协议的一部分。随意交换 `order_id` 和 `sku` 的字段编号，即使类型都仍是字符串，也会让旧版本客户端把两项数据解释错位。删除字段后通常应把原编号标记为 `reserved`，避免以后重复使用；添加新字段通常属于二进制线格式安全的演化，但应用逻辑能否兼容还取决于新字段是否被错误地当成必填条件。

需要区分序列化、压缩和加密。序列化负责数据的表示与重建；压缩减少数据量，是否有收益取决于内容及算法；TLS 等机制负责传输加密和身份验证。Protobuf 数据较难直接阅读，并不意味着它天然具备保密能力。将它用于不受信任的网络时，仍须采取适当的安全措施。

## 四、方法分发与错误返回

客户端把请求送到服务端之后，服务端需要知道调用哪一个处理函数。RPC 协议会使用某种方法标识，可能是服务名加方法名，也可能是由框架定义的其他标识。运行时根据注册表或生成代码，将请求交给对应的处理器。

处理器执行的过程与普通业务函数相似，但它的输入来自外部。服务端需要限制消息大小，验证字段，进行鉴权，并对异常建立稳定的返回约定。不能因为通信发生在内网，就认为请求一定来自可信代码，也不能将数据库异常栈直接作为远程错误返回。

错误至少存在三个层面。网络层可能连接失败、超时或中断；协议层可能无法解析消息，或者找不到指定方法；业务层则可能明确拒绝库存预留，例如商品不存在或可用库存不足。将它们全部变成 `False` 会抹去重要差异，调用方也无法据此判断应该修正参数、查询状态，还是尝试重试。

RPC 框架通常规定一组状态码或者错误结构，但业务错误怎样映射到这些状态，仍由接口设计决定。比如把库存不足作为正常的业务响应，还是作为一个特定的业务错误，两种方式都可能成立，关键在于整个系统使用一致的约定。另一方面，服务器内部异常不应暴露内部实现细节，可以通过稳定错误码与服务端日志保留足够的诊断信息。

还要注意错误发生的时间。客户端在网络中断后看到“调用失败”，并不能据此断定业务处理函数没有运行。即使服务端成功完成操作并编码了响应，也可能在发送响应的最后一步失去连接。RPC 框架返回的传输错误描述的是客户端观察到的结果，不等于业务事务的最终状态。

## 五、RPC 与 HTTP API 的关系

“RPC”和“HTTP”常被放在一起比较，其实两者的分类依据不同。RPC 描述远程调用的编程和交互模型，HTTP 是应用层通信协议。RPC 可以通过 HTTP 传输，常见的 HTTP API 也完全可以采用面向动作的 RPC 风格。

例如 `POST /inventory/reservations` 通过 HTTP 请求预留库存。调用方可以自己使用 HTTP 客户端构造 JSON，也可以通过生成的客户端代理完成请求构造、参数编码和错误转换。后者体现了 RPC 的调用体验，但底层仍可能使用 HTTP。

所谓 REST API 又属于不同的概念层面。REST 是一组架构约束，关注资源、统一接口、表示和无状态交互等原则。一个使用 JSON 和 HTTP 的接口不一定严格符合 REST；一个 RPC 系统使用 HTTP/2，也不意味着它自动具备 REST 的资源语义。gRPC 的典型实现就是基于 HTTP/2 来承载远程方法调用。

因此，在选型时不宜只比较“RPC 和 HTTP 哪个性能更高”。更有意义的问题是：接口是否面向外部开放，调用双方是否能共享契约文件，是否需要跨语言代码生成，是否有浏览器直接调用的要求，是否需要双向流，团队是否具备相应的网关和调试工具。序列化格式、HTTP 版本、网络距离与业务处理耗时都会影响性能，框架名称本身不能决定所有结果。

## 六、调用模型与流式通信

最熟悉的 RPC 形式是一问一答：客户端发送一个请求，服务端返回一个响应。这通常称为 Unary RPC，适用于库存预留、查询订单和计算报价等操作。

另一类需求会产生连续的数据。服务端可能持续返回任务进度；客户端可能连续上传一组数据；实时协作则可能需要双方独立发送消息。支持流式调用的 RPC 框架一般把这些模式区分为服务端流、客户端流和双向流。

流式调用的重点不只是减少重复建立连接。它改变了消息的生命周期：一个调用内部可能包含多条消息，需要分别处理发送和接收进度、流量控制、取消以及调用结束状态。双向流允许双方独立读写，也不要求交替一问一答。对于没有流式需求的业务，为使用新技术而引入长期存活的流，可能只会增加状态管理和故障恢复成本。

长时间运行的流还不能与持久消息队列混为一谈。流连接断开以后，框架不一定为应用保留尚未处理的业务消息，更不天然提供消费确认与持久化重放。是否需要断线恢复、业务序号和历史重放，必须在协议或上层存储中专门设计。

## 七、远程调用的边界应当怎样设计

理解了 RPC 的实现过程，就可以重新审视服务接口的粒度。远程调用存在固定开销和失败概率，许多本地函数之间的协作在网络上会变得昂贵。接口应该优先表达完整业务动作，让所属服务维护自己的状态和约束，而不是暴露数据库的每一个读写步骤。

对库存服务而言，`Reserve` 应一次性完成检查、并发控制和预留记录更新；订单服务不应该先远程读取库存数量，再依据这个过时的数值发起另一次扣减。后者既增加网络往返，也在检查与修改之间引入竞争窗口。

服务接口还应明确调用方能依赖的保证。它是否允许重复请求？相同操作标识重复提交会返回原结果还是拒绝？一次超时之后能否查询操作状态？哪些错误属于明确拒绝，哪些属于结果尚不确定？这些承诺应当出现在接口契约和测试中，而不是留给调用者猜测。

对于高频读取场景，也可能需要批量接口、读模型或缓存，避免远程逐条查询。批量操作同样要定义部分失败的语义。把多个小操作组合成一个调用，可以减少网络开销，但也可能放大单次请求大小、服务端占用时间和错误恢复难度，不能无限合并。

最后还需要考虑观测。网络链路跨越多个进程，单个异常栈只能说明局部发生了什么。请求标识、业务操作标识、Trace ID、方法耗时、返回状态和依赖服务信息，能够帮助我们将不同节点的执行记录关联起来。传递这些标识通常依靠 RPC 的 Metadata 或 HTTP 首部，它们也应遵守权限与隐私约束。

## 八、理解 RPC 后再看 gRPC

RPC 的关键组成部分已经明确：双方共同认可接口契约，客户端代理把方法调用编码为消息，传输层完成发送，服务端根据方法标识完成分发，结果与错误再沿相反方向返回。框架能够自动完成不少重复工作，但业务语义、事务边界和失败恢复仍然需要开发者设计。

下一篇选择 gRPC 作为具体实现，主要因为它把接口描述、代码生成、Protobuf 编码和 HTTP/2 传输组织成了一套成熟的开发工具。届时可以把本篇的调用链对应到 `.proto`、Stub、Channel、服务端处理器和 gRPC Status，看清抽象概念怎样变成可以运行的程序。
