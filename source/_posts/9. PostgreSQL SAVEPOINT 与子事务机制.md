上一篇讨论了事务为什么能够整体提交或回滚。但在实际开发中，有时我们并不希望一次局部失败就放弃整个事务。

假设一笔批量入库操作已经成功写入前几条记录，随后遇到一条违反唯一约束的数据。业务允许跳过这条重复记录，继续处理后面的数据，但要求所有**被接受**的记录仍然作为一个整体提交。

如果直接捕获 SQL 异常然后继续执行，PostgreSQL 往往会拒绝后续 SQL；如果执行 `ROLLBACK`，此前已经写入的合法记录也会一起被撤销。

我们真正需要的，是一种介于“忽略异常”和“撤销整个事务”之间的能力：保留一个事务的外层边界，只撤销其中一小段操作。PostgreSQL 的 `SAVEPOINT` 正是为此存在的。

不过，理解它不能只停留在“设置保存点，然后回滚到保存点”，因为其背后涉及事务失败状态、子事务层级、事务 ID，以及 ORM 如何管理内存中尚未提交的对象。本文以 PostgreSQL 18 为准，ORM 示例使用 SQLAlchemy 2.0.x 与 `asyncpg`。

## 一、为什么捕获异常还不够

先在用于实验的数据库中建一张独立的表：

```sql
CREATE TABLE blog_savepoint_demo (
    id integer PRIMARY KEY,
    note text NOT NULL
);
```

这张表要求 `id` 唯一。以下示例都在专用测试数据库中执行；首次创建表后可以连续运行，重新实验时应先按需清空测试表。现在开启事务，先插入一条记录，再尝试插入相同主键。

```sql
BEGIN;

INSERT INTO blog_savepoint_demo VALUES (1, 'first');
INSERT INTO blog_savepoint_demo VALUES (1, 'duplicate');

SELECT * FROM blog_savepoint_demo;

ROLLBACK;  -- 清理失败事务，方便后续实验
```

第二条 `INSERT` 会触发唯一约束错误，SQLSTATE 为 `23505`。但紧接着执行的 `SELECT` 不会像平常那样正常读取数据，而会收到 `25P02`，其含义是当前事务已经处于失败状态。

对 PostgreSQL 而言，某条语句执行失败与“应用层已经处理了这个异常”是两回事。即使 Python 的 `try/except` 捕获了异常，也不会自动修改服务器端的事务状态。

在一个没有可用保存点的显式事务块里，通常只能执行完整的 `ROLLBACK` 来恢复可正常执行 SQL 的状态。若此时发送 `COMMIT`，PostgreSQL 也不会把此前成功执行的修改提交，而是结束这个失败事务并按回滚处理。

这种设计有其必要性。假如某条语句违反了约束，数据库无法推断应用是想忽略这条记录、修复它后重试，还是放弃所有已经完成的修改。让事务进入失败状态，迫使调用方明确选择恢复边界，比悄悄继续执行更安全。

问题在于，普通事务只有一个总的恢复边界。为了能够在中途恢复，我们必须事先声明局部边界。这就是保存点的作用。

## 二、SAVEPOINT 怎样把一次失败限制在局部

在事务中，`SAVEPOINT` 记录一个可以回退的边界。执行 `ROLLBACK TO SAVEPOINT` 时，边界之后尚未保留的修改被撤销，但边界之前的修改以及外层事务仍然存在。

```sql
BEGIN;

INSERT INTO blog_savepoint_demo VALUES (1, 'first');

SAVEPOINT item_sp;
INSERT INTO blog_savepoint_demo VALUES (2, 'temporary');
INSERT INTO blog_savepoint_demo VALUES (2, 'duplicate');  -- 23505

ROLLBACK TO SAVEPOINT item_sp;

INSERT INTO blog_savepoint_demo VALUES (3, 'after-error');
RELEASE SAVEPOINT item_sp;

COMMIT;
```

在初始表为空、没有其他客户端参与的条件下，最后留下 `id=1` 和 `id=3`，而不是 `id=2`。保存点之前的第一条 `INSERT` 仍属于外层事务。

保存点之后，既有成功的 `INSERT`，也有失败的 `INSERT`；执行 `ROLLBACK TO` 时，这一段都被放弃，随后外层事务又可以继续执行新的语句。

注意，恢复动作必须是 `ROLLBACK TO SAVEPOINT`。当保存点后的操作已导致当前事务进入失败状态时，不能靠 `RELEASE SAVEPOINT` 绕过错误。`RELEASE` 是保留局部修改并移除保存点的操作，不负责把一个已经失败的子事务恢复为可用状态。

再看 SQL 的三个基本动作，它们的含义并不对称。`SAVEPOINT s` 建立恢复位置；`ROLLBACK TO SAVEPOINT s` 撤销该位置之后的操作，并使后续语句能够继续；`RELEASE SAVEPOINT s` 放弃这个恢复位置，把尚未回滚的局部成果并入外层事务。

这里的“并入”是逻辑上的，并不是写入最终提交结果。即使执行了 `RELEASE`，只要最外层还没有 `COMMIT`，这些修改就仍然可能因外层 `ROLLBACK` 而全部丢失。

## 三、子事务不是可以独立提交的小事务

PostgreSQL 并不只是保存一份数据快照，等需要回滚时把整份快照恢复。它在事务处理器内部建立了**子事务**（subtransaction，通常缩写为 subxact），用于组织局部事务状态。

每个保存点都可以形成一个新的子事务层级；子事务之内还可以再次建立保存点。最外层事务是父节点，局部操作位于其下的子节点，因而形成一棵层级树。这个结构解释了为什么某一层可以被放弃，而它之前的工作仍然保留。

```sql
BEGIN;
INSERT INTO blog_savepoint_demo VALUES (10, 'outer');

SAVEPOINT s1;
INSERT INTO blog_savepoint_demo VALUES (11, 'inside-s1');

SAVEPOINT s2;
INSERT INTO blog_savepoint_demo VALUES (12, 'inside-s2');
RELEASE SAVEPOINT s2;

ROLLBACK TO SAVEPOINT s1;
COMMIT;
```

假设这几个主键尚不存在，最终只有 `id=10` 留下。`RELEASE s2` 只是让 `s2` 的修改进入 `s1` 所在的父级范围，并没有使 `id=12` 独立持久化。随后回滚到 `s1`，`id=11` 和 `id=12` 一起被撤销。

PostgreSQL 还允许多个保存点使用相同名称。新定义的同名保存点会遮蔽更早的那个，直到较新的保存点被释放，旧保存点才重新可访问。因此，保存点名称更像当前嵌套结构中可定位的标签，而不是整个事务内永远唯一的标识。

这里有个容易忽略的细节：执行 `ROLLBACK TO SAVEPOINT s1` 后，`s1` **仍然存在**，并不是自动消失。PostgreSQL 会撤销该层级当前的子事务，并在相同层级开始新的子事务，因此之后还可以再次回滚到 `s1`。

但在 `s1` 之后创建的更内层保存点会被销毁。相反，`RELEASE SAVEPOINT s1` 会释放它及其之后仍处于活动状态的保存点，使它们不再可供回滚。释放与回滚对保存点自身的处理并不相同。

这种子事务不是一条新的数据库连接，也不是另起一个可以与父事务并行提交的独立事务。它们共享同一外层事务的生命周期；父事务最终回滚，所有已释放但尚未随父事务提交的子事务修改都要回滚。即使内部子事务已经“成功结束”，它也不具有脱离父事务的持久化保证。

## 四、PostgreSQL 怎样记住子事务的归属和结果

如果每个子事务都只有一个简单的 Python 式作用域，那么关闭一个作用域似乎就能撤销其中的操作。但 PostgreSQL 需要解决更底层的问题：子事务可能已经对真实数据页作出修改，还可能创建新的行版本或持有锁。之后的查询必须知道这些修改究竟属于哪个事务分支，以及那个分支的最终结果是什么。

PostgreSQL 使用事务 ID 和事务状态来协助完成判断。最外层事务在真正需要常规写事务 ID 时获得 XID；只读事务不必仅因执行了 `BEGIN` 就分配一个常规 XID。子事务同样不是一建立就必然消耗持久的子事务 ID。

一个子事务需要写入数据库时，可以分配自己的 subxid；系统还会确保它的父级，包括顶层事务，具有所需的常规事务 ID，并且父级 XID 早于子级 subxid。

PostgreSQL 在 `pg_subtrans` 中保存子事务 ID 到其直接父事务 ID 的关系，用以追溯子事务所属的顶层事务。事务提交状态则由 `pg_xact` 等机制维护。

**子事务已完成与最外层事务已提交，是两个不同判断。** 一个成功结束的子事务可以处于依赖父事务最终结果的状态；只有顶层事务最终提交，它的有效子事务结果才随之被认定为提交。如果顶层事务回滚，这些子事务即使曾成功释放，也不能独立成为有效的已提交结果。

局部回滚也不意味着数据库一定会逐行执行与原 SQL 相反的操作。它与上一篇讲过的事务回滚原则一致：数据库根据事务层级、状态以及 MVCC 可见性处理已取消分支的修改，必要的物理清理由后续机制完成。一个被放弃的子事务可能已经写过 WAL 或修改过缓冲区中的页，但其修改不能因“已经发生过物理写入”就变成有效提交结果。

理解这层父子关系后，`RELEASE SAVEPOINT` 就不再显得像“小型 COMMIT”。它的实质是结束局部恢复范围并保留其成果，使成果继续受父事务控制。真正决定这批修改能否对外作为已提交结果出现的，仍然是最外层事务的最终结束方式。

## 五、回滚后资源状态会发生什么变化

局部回滚除了影响数据，还会影响事务期间获得的锁。PostgreSQL 的规则是，某个保存点之后取得的事务性锁，通常会在回滚到这个保存点时释放；保存点之前已经取得的锁不会因为后来回滚了一段操作就全部消失。如果保存点后的操作升级了先前的锁，回滚应恢复并保留之前已经持有的锁状态，而不是把原本的锁也丢掉。

这意味着 SAVEPOINT 不只是一个错误恢复工具，有时也会影响锁的持续时间。但不能反过来认为保存点一定能够解除任何锁等待。回滚不到尚未结束的外层事务之前时，外层事务仍然可能持有早期获得的行锁或表锁；回滚后继续执行的语句也可以再次获取新锁。锁的冲突规则和死锁问题，分别留给第五篇与第七篇。

此外，“恢复到保存点”也不能解释成整个外部世界倒流。PostgreSQL 序列函数 `nextval()` 已经取走的值，不会因保存点回滚而归还。

对于游标，回滚可能关闭在保存点内创建的游标，但不会把此前游标在保存点内执行 `FETCH` 所移动的位置自动恢复。数据库以外已经发送的请求、日志或消息，更不会由 PostgreSQL 替应用撤销。

这些限制都来自同一个原则：SAVEPOINT 只能管理 PostgreSQL 自身具备相应事务回滚语义的状态。它不是任意程序操作的通用撤销机制。

## 六、在存储过程里，异常处理为什么也涉及子事务

在 PL/pgSQL 中，带 `EXCEPTION` 处理器的 `BEGIN ... END` 代码块同样可以形成子事务。发生错误时，处理器能够在撤销该块中数据库修改之后继续工作，而不是必然放弃整个外层事务。

```sql
DO $$
BEGIN
    INSERT INTO blog_savepoint_demo VALUES (20, 'before-block');

    BEGIN
        INSERT INTO blog_savepoint_demo VALUES (21, 'inside-block');
        INSERT INTO blog_savepoint_demo VALUES (21, 'duplicate');
    EXCEPTION WHEN unique_violation THEN
        RAISE NOTICE 'duplicate ignored';
    END;

    INSERT INTO blog_savepoint_demo VALUES (22, 'after-block');
END
$$;
```

在表中尚无相同主键、且 `DO` 语句正常完成的条件下，这个块不会留下 `id=21`，但会留下 `id=20` 和 `id=22`。这是因为 `EXCEPTION` 撤销了发生错误的内部块的数据修改，而没有撤销它之前的外层工作。

PL/pgSQL 的局部变量则具有不同语义：当异常被处理时，变量可能保留异常发生时已被赋予的值，不能把数据库回滚理解成所有过程变量一并恢复。

但是，没有必要把每个 PL/pgSQL 代码块都理解成子事务：这里起关键作用的是带 `EXCEPTION` 子句的块。官方文档也明确说明这种块的进入与退出有额外开销。

PL/pgSQL 函数内部不能直接像普通 SQL 客户端那样随意执行 `SAVEPOINT`、`ROLLBACK TO`、`RELEASE`；在过程语言中通常使用异常块表达这种局部恢复需求。

更重要的是，捕获 `unique_violation` 不一定意味着“恰好是我们预期的那一条唯一约束发生冲突”。触发器或其他唯一索引也可能产生同类异常。

对于单纯的插入冲突处理，PostgreSQL 通常提供更直接的 `INSERT ... ON CONFLICT`，没有必要刻意制造错误，再付出子事务恢复的成本。子事务适用于确实需要把一组操作作为局部整体尝试、又允许放弃这一组操作的情况。

## 七、SQLAlchemy 的 begin_nested() 究竟做了什么

SQLAlchemy 2.0 在 ORM 层通过 `Session.begin_nested()` 和异步版本 `AsyncSession.begin_nested()` 管理 SAVEPOINT。它们返回的嵌套事务对象负责控制局部回滚或释放保存点；外层 Session 仍然管理最外层事务。

这里需要特别区分两个 API：在 SQLAlchemy 2.0 中，`session.commit()` 提交的是**最外层事务**，不会因为当前存在保存点就自动变成 `RELEASE SAVEPOINT`。

要结束局部保存点，应使用 `begin_nested()` 返回的事务对象，或者使用 `async with session.begin_nested()` 的上下文管理器。后者正常退出时释放保存点，异常退出时回滚到保存点。

下面是一段可以单独运行的异步 ORM 实验。它使用独立的测试表，以便观察保存点之前、之内和之后的对象分别会怎样处理。

先安装依赖，并提供数据库连接地址：

```bash
python -m pip install 'SQLAlchemy>=2.0,<2.1' asyncpg
export DATABASE_URL='postgresql+asyncpg://appuser:password@127.0.0.1:5432/appdb'
```

```python
import asyncio
import os

from sqlalchemy import Integer, String, select, text
from sqlalchemy.exc import IntegrityError
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column


class Base(DeclarativeBase):
    pass


class Record(Base):
    __tablename__ = "blog_savepoint_orm"

    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    note: Mapped[str] = mapped_column(String(100), nullable=False)


async def main() -> None:
    engine = create_async_engine(os.environ["DATABASE_URL"])
    make_session = async_sessionmaker(engine, autoflush=False)

    try:
        # 仅用于独立实验：清空这张专用测试表。
        async with engine.begin() as conn:
            await conn.run_sync(Base.metadata.create_all)
            await conn.execute(text("DELETE FROM blog_savepoint_orm"))

        async with make_session.begin() as session:
            session.add(Record(id=1, note="outer-before"))

            try:
                async with session.begin_nested():
                    session.add(Record(id=2, note="inside"))
                    session.add(Record(id=2, note="duplicate"))
            except IntegrityError:
                print("局部写入失败，保存点已回滚")

            session.add(Record(id=3, note="outer-after"))

        async with make_session() as session:
            result = await session.execute(
                select(Record.id, Record.note).order_by(Record.id)
            )
            print(result.all())
    finally:
        await engine.dispose()


if __name__ == "__main__":
    asyncio.run(main())
```

在没有其他客户端干扰、测试表允许写入的情况下，结果应包含 `id=1` 和 `id=3`，不包含 `id=2`。本轮审校已在 PostgreSQL 18.6、SQLAlchemy 2.0.54 与 `asyncpg` 0.32.0 上实际运行这段程序，得到 `[(1, 'outer-before'), (3, 'outer-after')]`。

这段程序有两个不明显但非常关键的机制。

第一个是 **`begin_nested()` 会先无条件 flush 当前 Session 已经积累的待处理 ORM 状态**，即使构造 `async_sessionmaker` 时设置了 `autoflush=False` 也是如此。

因此，`Record(id=1)` 在真正建立局部保存点前就会被写入外层数据库事务；局部失败时它不会随 `id=2` 一起回滚。如果业务希望某个对象也属于局部回滚范围，就必须把产生或修改它的操作放进 `begin_nested()` 的作用域中，而不是提前放在外面。

第二个是，保存点回滚不仅需要恢复数据库中的事务状态，也必须让 ORM 内存状态保持一致。SQLAlchemy 会处理保存点范围内发生变化的对象状态；对于已存在而在保存点内被修改的对象，回滚后相关属性通常会被标记为过期，待重新访问时从数据库刷新，而没有被修改的对象状态可以保留。

这与简单执行原生 SQL 不同，因为 ORM 还维护 identity map 和 Unit of Work。对于异步 ORM，过期属性的后续加载仍可能涉及隐式数据库 I/O，实际访问时应遵循异步加载的约束。

异常捕获位置也不能随意调整。上面的 `try/except` 包住了整个 `async with session.begin_nested()`，从而让上下文管理器先执行必要的保存点回滚，再由外层处理异常。

如果在 `begin_nested()` 内部直接捕获 `IntegrityError`、不重新抛出也不显式回滚，可能让上下文管理器误以为代码块已成功结束，进而尝试释放仍处于失败状态的保存点。遇到数据库错误后，优先让嵌套事务上下文完成回滚，再决定是否跳过该条数据。

还有一点不能忽略：如果某次错误发生在 **建立保存点之前的自动 flush**，它就不受这个新保存点保护。调用者需要确保局部易失败的变更不会提前积累在外层 Session 中。这也是 `begin_nested()` 的 flush 规则为何不仅是实现细节，而会直接影响业务正确性。

## 八、SAVEPOINT 为什么不能当作廉价的任意重试机制

保存点确实增加了恢复的灵活性，但它不是零成本操作。每次建立、释放或回滚保存点，都涉及数据库命令以及子事务状态管理；一旦发生修改，还可能涉及 subxid 分配、父子关系记录与相关事务状态处理。

PostgreSQL 为后端进程缓存有限数量的活动子事务 ID。官方文档指出，每个后端最多缓存 64 个仍然打开的 subxid；超过后，事务状态查询可能需要额外访问 `pg_subtrans`，产生明显的管理开销。

这里的 64 不是“每个事务最多只能使用 64 个保存点”的硬限制，也不能简单理解为“循环使用 65 次保存点必定性能骤降”。文档讨论的是仍然打开、尚未回滚或释放的子事务 ID；而且只读保存点并不必然分配 subxid。真正的影响取决于嵌套深度、写入行为、是否及时结束子事务以及负载情况。

保存点也没有缩短外层事务的总寿命。即使每条数据都放进单独的保存点，如果最外层事务持续很久，外层取得的锁、长事务相关资源以及连接占用仍然可能一直存在。

把几万条记录放进一个大事务，再为每条记录创建保存点，不一定比把工作合理地分成若干独立事务更合适。是否必须整体提交，是首先需要确定的业务约束；如果不要求整个批次同时成功，分批提交往往更容易控制失败范围和资源占用，但也会改变原有的原子性边界。

SAVEPOINT 也不适合被当成所有并发错误的统一补救措施。发生序列化失败、死锁、连接中断或者未知提交结果时，是否需要重试整个外层事务，要按错误类型和实际事务状态判断。

特别是序列化失败，数据库所否定的可能是整个事务所依据的并发执行结果，局部重做某条 SQL 未必能够恢复正确性。不能看到 `ROLLBACK TO` 可以让事务继续，就推导出任何错误都只需要重试子事务。

## 九、工程上应该怎样选择局部回滚边界

保存点适合的情况，是一个外层事务中存在**允许失败的局部操作**，并且该局部操作的失败不应改变此前已经完成的合法工作。外层事务负责最终原子提交，内层保存点负责尝试性操作的回退。两个边界承担不同职责，不能互相替代。

在 Repository 和 Service 分层中，尤其应当避免 Repository 自行调用 `session.commit()`。

如果 Service 计划统一提交多个数据修改，但其中某个 Repository 提前结束了外层事务，保存点再也无法为此前的操作提供回滚能力。通常由应用服务决定事务边界，并在确实需要局部容错的内部环节使用 `begin_nested()`，更容易维持清楚的控制关系。

还应先问一个更根本的问题：局部失败是否真的需要通过异常实现？如果只是避免插入某条重复数据，`ON CONFLICT DO NOTHING` 或 `ON CONFLICT DO UPDATE` 往往能够直接表达意图，减少不必要的异常和子事务开销。

只有当一段操作具有多条 SQL 的共同成败关系，或者需要捕获一种能够被安全地局部放弃的错误时，保存点才体现出它的价值。

到这里可以重新回答开头的问题：PostgreSQL 发生 SQL 错误后不会仅因应用捕获异常就继续运行，因为服务器端事务已进入失败状态。

SAVEPOINT 的作用，是提前创建更小的事务恢复边界；`ROLLBACK TO` 结束失败的子事务并在保存点层级重新开始，使外层事务得以继续。`RELEASE` 则保留局部成果，但最终提交权仍然属于最外层事务。

下一篇讨论事务隔离级别与 MVCC。子事务已经让我们看到，数据库必须判断一条行版本修改属于哪个事务分支、该分支最终是否有效。接下来要解决的问题是：**即使事务全部正常提交，不同事务为什么仍可能在同一时刻看到不同的数据版本？**
