上一篇文章介绍了 Python 的 `async/await`、协程对象、Task、Future 和事件循环。

我们已经知道，`asyncio.create_task()` 可以将协程包装为 Task，并交给事件循环调度。多个 Task 可以在等待 I/O 时交替执行，从而实现并发。

但是，创建任务只是异步编程的开始。

假设一个 Web 接口需要同时查询用户信息、订单记录和账户余额。我们可以创建三个 Task，让数据库请求并发执行。

如果三个任务全部成功，自然没有什么问题。

但如果其中一个查询失败了呢？另外两个任务是否还应该继续？如果接口已经超时，正在执行的任务能否停止？如果请求已经结束，还有没有任务在后台运行？

这些问题涉及异步任务的生命周期、调度、取消与异常处理。

它们也是异步程序与普通同步程序之间，一个容易被忽略的区别：**任务一旦能够独立执行，我们就必须考虑由谁负责管理它，以及它最终应该如何结束。**

## 一、从协程对象到 Task

我们先回顾一个简单的例子。

```python
import asyncio


async def work():
    print("开始执行")
    await asyncio.sleep(1)
    print("执行结束")


async def main():
    task = asyncio.create_task(work())
    await task


asyncio.run(main())
```

程序首先调用 `work()`，创建协程对象。

接着，`asyncio.create_task()` 将协程包装成 Task，并安排它在当前事件循环中执行。

当 `main()` 执行 `await task` 时，如果任务尚未完成，`main()` 就会暂停，等待任务结束。

看起来整个过程很简单，但这里已经涉及两个相互独立的执行过程。

一个是 `main()` 对应的 Task，另一个是 `work()` 对应的 Task。

它们都由事件循环管理，但有各自的执行状态。

### 1. Task 的生命周期

Task 并不是创建以后就立即执行到结束。

在典型的 `asyncio` 运行过程中，一个 Task 可能处于等待调度、正在执行、等待异步操作，以及执行结束等阶段。

当 Task 被创建后，事件循环会安排它执行。

当它获得执行机会时，就开始驱动对应的协程。

如果协程执行到某个尚未完成的 Future，Task 就会暂停，等待这个 Future 完成。

Future 完成以后，相关回调会将 Task 重新安排到事件循环中，使它继续执行。

协程最终返回结果或者抛出异常时，Task 也会进入终态。

这里需要区分两类状态。

我们可以从调度过程的角度，将任务理解为就绪、运行中和等待中。

但从 `asyncio.Task` 对外提供的状态接口来看，更重要的是它是否已经完成，以及最终是正常返回、发生异常还是被取消。

这些调度阶段并不是 `asyncio.Task` 暴露的一套完整、固定的公开状态枚举。

例如：

```python
task.done()
task.cancelled()
```

`done()` 用于判断任务是否已经结束。正常返回、因异常结束或者被取消，都属于已经完成。

`cancelled()` 则只有在任务最终以取消状态结束时才会返回 `True`。

所以，一个任务已经结束，并不代表它一定执行成功。

### 2. create_task() 以后会立即执行吗？

默认情况下，`asyncio.create_task()` 会将任务安排到事件循环中，等待后续调度。

这意味着，调用 `create_task()` 后，通常会先继续执行当前 Task 的代码，等当前 Task 让出控制权，新创建的 Task 才获得执行机会。

不过，这并不是所有版本和配置下都成立的绝对规律。

从 Python 3.12 开始，`asyncio` 提供了 eager task factory 等机制；从 Python 3.14 开始，`create_task()` 也支持 `eager_start` 参数。

启用立即执行模式后，新建 Task 可以在创建期间就开始执行协程，直到第一次真正阻塞，甚至直接执行完成。

因此，不能依赖 `create_task()` 与后续语句之间的细微执行顺序，来保证业务逻辑的正确性。

如果两个任务之间存在先后依赖，应该通过明确的等待、事件或者其他同步机制建立关系，而不是依靠对调度顺序的猜测。

### 3. 创建 Task 不等于等待 Task

还有一个重要问题。

```python
asyncio.create_task(work())
```

这行代码只是创建并安排一个任务，并没有等待它完成。

如果当前函数随后返回，那么新任务可能仍在运行。

这种写法有时被称为 Fire-and-forget，也就是启动任务后不再等待其结果。

但在 Python 中，这并不是可靠的后台任务管理方式。

首先，`asyncio` 官方文档要求开发者为独立创建的 Task 保存适当的强引用，避免任务在执行过程中因为引用管理问题而被意外回收。

其次，如果任务发生异常，却没有任何地方获取异常结果，就可能出现：

```text
Task exception was never retrieved
```

更重要的是，如果这个任务属于某个业务请求，却在请求结束后继续运行，那么它的生命周期就脱离了原本的业务边界。

这会让异常处理、资源释放和服务关闭过程变得难以管理。

因此，对于有明确归属的一组任务，应该尽量让它们的生命周期受到调用方管理。

## 二、如何等待多个异步任务？

前面已经介绍过 `await task`。

但实际程序经常需要同时等待多个 Task，而且不同场景对等待结果的要求并不相同。

有时候，我们希望等所有任务完成。

有时候，只需要最先返回的结果。

还有时候，我们希望在规定时间内取得已经完成的部分结果，剩余任务则继续运行或者被主动取消。

Python 为此提供了几种不同的等待机制。

### 1. gather()：并发执行并汇总结果

最常见的是 `asyncio.gather()`。

```python
import asyncio


async def query(name, delay):
    await asyncio.sleep(delay)
    return f"{name} 查询完成"


async def main():
    results = await asyncio.gather(
        query("用户", 2),
        query("订单", 1),
        query("余额", 3),
    )

    print(results)


asyncio.run(main())
```

这三个查询的等待时间分别为两秒、一秒和三秒。

由于它们可以并发执行，整体耗时通常接近三秒，而不是六秒。

还有一个细节：`gather()` 返回结果的顺序，与传入任务的顺序一致，而不是任务实际完成的顺序。

即使订单查询最先完成，最终结果仍然按照用户、订单、余额排列。

为什么？

因为 `gather()` 的设计目标是将多个可等待对象的结果汇总起来，并保持调用方指定的结果位置关系。

需要注意，`gather()` 本身不限制并发数量。如果需要限制同时访问数据库或外部 API 的任务数量，还需要连接池、`asyncio.Semaphore` 等机制。

### 2. wait()：关注任务是否完成

`asyncio.wait()` 的侧重点有所不同。

它返回两个集合，一个保存已经完成的任务，另一个保存尚未完成的任务。

```python
import asyncio


async def query(delay):
    await asyncio.sleep(delay)
    return delay


async def main():
    tasks = {
        asyncio.create_task(query(1)),
        asyncio.create_task(query(3)),
    }

    done, pending = await asyncio.wait(
        tasks,
        timeout=2,
    )

    print("已完成:", len(done))
    print("未完成:", len(pending))

    for task in pending:
        task.cancel()

    await asyncio.gather(
        *pending,
        return_exceptions=True,
    )


asyncio.run(main())
```

程序等待两秒后，通常会得到一个已完成任务和一个未完成任务。

与 `gather()` 不同，`wait()` 并不直接返回任务的业务结果。调用方需要从已经完成的 Task 中读取结果或异常。

它还可以通过 `return_when` 参数决定返回条件。

例如，`FIRST_COMPLETED` 表示有任务结束就可以返回，`FIRST_EXCEPTION` 表示有任务因异常结束时可以提前返回，`ALL_COMPLETED` 则要求全部任务结束。

需要注意，`wait()` 的超时只会结束当前等待，不会自动取消剩余任务。

因此，上面的代码需要主动取消 `pending` 中的 Task，并等待它们完成取消清理。

另外，从 Python 3.11 开始，不能直接向 `wait()` 传递普通协程对象，而应该传递 Task 或 Future 等受支持的对象。

### 3. as_completed()：按照完成顺序处理结果

有时候，我们并不想等所有任务结束后才处理结果。

例如，一个程序同时请求多个外部服务，希望哪个服务先返回，就先处理哪个服务的数据。

这时可以使用 `asyncio.as_completed()`。

```python
import asyncio


async def query(name, delay):
    await asyncio.sleep(delay)
    return name


async def main():
    tasks = [
        asyncio.create_task(query("A", 3)),
        asyncio.create_task(query("B", 1)),
        asyncio.create_task(query("C", 2)),
    ]

    async for task in asyncio.as_completed(tasks):
        result = await task
        print(result)


asyncio.run(main())
```

在 Python 3.13 及之后版本中，可以像这样使用异步迭代。

程序通常依次输出 B、C、A。

这说明任务的执行顺序与结果处理顺序可以分开。

`gather()` 更适合需要收集全部结果的情况，`wait()` 更适合关注一组任务的完成状态，而 `as_completed()` 则适合按照实际完成顺序逐个处理结果。

但需要注意，`as_completed()` 不会因为一个任务已经完成，就自动取消其他任务。

如果调用方决定不再等待剩余结果，仍然需要明确处理未完成任务的后续生命周期。

## 三、为什么异步任务需要取消机制？

普通同步函数执行时，调用者通常需要等函数返回才能继续执行。

异步任务则不同。

我们可以创建一个 Task，让它独立运行，并在某个时间点决定不再需要它。

例如，一个用户发起请求后，服务端开始执行数据库查询。但在查询结束之前，业务操作被取消了。

如果查询结果已经没有任何使用价值，继续消耗资源就可能是不必要的。

这时，我们希望通知对应的 Task 停止执行。

`asyncio` 提供了 `Task.cancel()` 方法。

但是，**取消任务并不是强制杀死线程，也不是立即停止协程。**

它更接近一种协作式的停止请求。

### 1. cancel() 实际做了什么？

先看一个例子。

```python
import asyncio


async def worker():
    try:
        print("任务开始")
        await asyncio.sleep(10)
        print("任务正常结束")
    except asyncio.CancelledError:
        print("收到取消请求")
        raise
    finally:
        print("执行清理逻辑")


async def main():
    task = asyncio.create_task(worker())

    await asyncio.sleep(0)

    task.cancel()

    try:
        await task
    except asyncio.CancelledError:
        print("任务已取消")

    print("取消状态:", task.cancelled())


asyncio.run(main())
```

运行结果通常是：

```text
任务开始
收到取消请求
执行清理逻辑
任务已取消
取消状态: True
```

我们分析一下这个过程。

首先，事件循环安排 `worker()` 开始执行。

当 `worker()` 执行到 `await asyncio.sleep(10)` 时，它进入异步等待状态。

随后，`main()` 调用 `task.cancel()`。

这并不是直接销毁 Task，而是请求取消它。

在 Task 下一次得到处理机会时，`asyncio` 会尝试向其协程注入 `CancelledError` 异常。

在这个例子中，`worker()` 捕获异常，执行清理逻辑，然后重新抛出异常。

最终，Task 以取消状态结束。

所以，取消机制依赖于协程对异常和执行状态的处理。

### 2. 为什么 cancel() 不保证立即结束？

假设一个协程正在执行大量同步计算：

```python
async def calculate():
    total = 0

    for i in range(100_000_000):
        total += i

    return total
```

这个函数没有任何可以正常让出执行权的异步等待操作。

在普通的单线程事件循环中，当它开始执行以后，其他 Task 就无法及时运行。

因此，另一个同属此事件循环的 Task 甚至可能暂时没有机会调用 `cancel()`。

即使取消请求已经从其他线程被安全地提交给事件循环，也不能直接中断当前正在执行的 Python 计算。

取消必须等待运行时有机会处理相应请求。

所以，`cancel()` 不是操作系统提供的强制抢占机制。

如果要处理耗时的 CPU 计算任务，应该考虑把计算放到独立进程或其他合适的执行资源中，而不是指望协程取消能够随时打断计算。

### 3. 取消请求不等于取消成功

一个 Task 收到 `CancelledError` 后，可以执行异常处理逻辑。

如果协程捕获了这个异常，却不再将它抛出，那么任务可能继续运行，甚至最终正常返回。

也就是说，调用 `cancel()` 只是发出取消请求，并不保证任务一定进入最终取消状态。

这也是为什么 `cancel()` 返回 `True` 不等于 `task.cancelled()` 一定为 `True`。

前者说明取消请求已被接受，后者说明任务最终确实以取消状态结束。

这个区别在工程实践中十分重要。

例如，某个任务可能已经接收到取消请求，但仍然需要释放数据库连接或者完成必要的资源清理。

调用方如果希望确认任务真正结束，就应该在发出取消请求之后继续等待它，而不是简单地调用一次 `cancel()` 就认为清理已经完成。

## 四、CancelledError 为什么比较特殊？

Python 使用异常机制传递异步任务的取消请求。

但 `CancelledError` 与普通业务异常有一个重要区别。

从 Python 3.8 开始，`asyncio.CancelledError` 直接继承自 `BaseException`，而不是普通的 `Exception`。

因此：

```python
try:
    await some_operation()
except Exception:
    print("发生错误")
```

这里的 `except Exception` 通常不会捕获 `asyncio.CancelledError`。

这是一个有意设计的行为。

因为取消不一定代表任务执行失败。

它可能是调用方主动要求停止任务，也可能是超时、任务组关闭等控制流程的一部分。

如果把取消当成普通异常随意捕获，就可能破坏异步程序的生命周期管理。

### 1. 为什么不应该吞掉取消异常？

考虑下面的代码：

```python
async def worker():
    try:
        await asyncio.sleep(10)
    except asyncio.CancelledError:
        print("忽略取消")
        return "success"
```

即使外部请求取消这个 Task，它仍然可能返回 `"success"`。

此时任务并没有以取消状态结束。

对于调用方而言，任务的取消语义已经改变了。

更麻烦的是，`asyncio.TaskGroup` 和 `asyncio.timeout()` 等机制内部也依赖取消来协调任务。

如果底层协程随意吞掉 `CancelledError`，就可能使这些高级机制无法按照预期工作。

因此，最稳妥的做法是让取消异常继续向上传播。

如果确实需要捕获它，通常应该在完成清理后重新抛出。

```python
async def worker():
    try:
        await do_work()
    except asyncio.CancelledError:
        await cleanup()
        raise
```

这里的 `raise` 用于将原来的取消异常继续向上传递。

不过，如果清理本身也可能抛出异常，还需要单独考虑清理失败时应该如何处理。

### 2. finally 是资源清理的重要位置

如果任务无论正常结束、出现业务异常还是被取消，都需要释放某个资源，那么 `finally` 通常更合适。

```python
async def worker():
    resource = await acquire_resource()

    try:
        await use_resource(resource)
    finally:
        await release_resource(resource)
```

无论 `use_resource()` 正常返回还是因为异常退出，程序都会尝试进入 `finally` 执行资源释放逻辑。

但这也不是绝对保证。

如果进程被强制终止，或者清理阶段再次发生异常、再次收到取消请求，资源释放仍然可能未能完整执行。

因此，对于数据库连接、事务和外部资源，优先使用已经正确实现生命周期管理的异步上下文管理器，通常比手工组织多个清理步骤更可靠。

需要特别注意，任务取消不等于数据库事务已经回滚，也不等于外部 API 调用没有产生副作用。

这些行为取决于数据库驱动、事务管理器和下游服务的实际实现。

## 五、超时控制与任务取消

取消机制还有一个非常重要的使用场景：超时。

假设程序需要调用外部 API。

如果对方一直没有返回结果，我们不可能无限等待。

于是，程序需要设置一个时间限制。

Python 的 `asyncio` 提供了 `wait_for()` 和 `timeout()` 等机制。

虽然它们的使用方式不同，但都与取消机制密切相关。

### 1. wait_for() 如何控制超时？

```python
import asyncio


async def request():
    await asyncio.sleep(5)
    return "success"


async def main():
    try:
        result = await asyncio.wait_for(
            request(),
            timeout=1,
        )
        print(result)
    except TimeoutError:
        print("请求超时")


asyncio.run(main())
```

程序通常会在大约一秒钟后输出：

```text
请求超时
```

`wait_for()` 会等待指定的可等待对象。

如果超过时间限制，它会尝试取消正在等待的操作，并在相应取消处理完成后抛出 `TimeoutError`。

这里有一个容易误解的地方。

设置 `timeout=1` 并不意味着整个函数一定会在严格的一秒钟内返回。

如果被等待的任务需要执行取消清理，或者不能及时响应取消，那么 `wait_for()` 的实际等待时间可能超过一秒。

因此，超时首先是一种限制等待时间的控制策略，而不是能够无条件终止底层操作的硬性执行期限。

### 2. timeout() 与 wait_for() 有什么区别？

从 Python 3.11 开始，还可以使用 `asyncio.timeout()`。

```python
import asyncio


async def main():
    try:
        async with asyncio.timeout(1):
            await asyncio.sleep(5)
    except TimeoutError:
        print("操作超时")


asyncio.run(main())
```

与 `wait_for()` 不同，`timeout()` 是异步上下文管理器。

它限制的是整个代码块所处的等待范围。

在超时时，`timeout()` 会请求取消当前 Task，并在退出上下文时处理相应的取消异常，将由自身超时引起的取消转换为 `TimeoutError`。

所以，`TimeoutError` 通常需要在 `async with` 外部捕获。

这两种方式的区别在于取消作用的对象。

`wait_for()` 主要围绕某个被等待的操作建立超时控制。

`timeout()` 则为当前 Task 中的一段执行过程建立超时范围。

这在 Web 开发中非常有价值。

例如，一个请求需要连续进行多次数据库查询。如果希望整个业务操作的等待时间受到统一限制，可以使用 `timeout()` 包裹相关执行过程，而不是只给每一次查询分别设置独立超时。

### 3. 超时以后，后台工作一定停止了吗？

不一定。

如果底层操作能够正确响应取消，并在必要的清理之后退出，那么超时可以结束相应的异步工作。

但如果任务将同步函数交给线程池执行：

```python
await asyncio.to_thread(blocking_operation)
```

那么取消正在等待结果的 Task，并不意味着工作线程中的 `blocking_operation()` 会被强制停止。

工作线程可能仍然继续执行，直到同步函数自行返回。

同样，如果程序已经向外部系统发送了请求，取消本地的等待任务，也不代表外部系统一定停止处理这个请求。

所以，在工程上必须区分三个概念：不再等待某个结果、取消本地异步任务，以及终止真实的底层操作。

它们不一定同时发生。

## 六、异步任务的异常是如何传播的？

取消只是 Task 的一种结束方式。

另一种常见情况是任务执行时发生异常。

在普通同步调用中，如果函数抛出异常，异常会沿着当前调用栈向上传播。

Task 则可以独立于创建它的函数运行。

因此，一个异步任务发生异常，并不意味着异常会立即出现在创建它的那一行代码。

### 1. Task 会保存异常

考虑下面的程序：

```python
import asyncio


async def worker():
    await asyncio.sleep(1)
    raise ValueError("任务执行失败")


async def main():
    task = asyncio.create_task(worker())

    try:
        await task
    except ValueError as exc:
        print("捕获异常:", exc)


asyncio.run(main())
```

`worker()` 抛出 `ValueError` 后，对应的 Task 以异常状态结束。

当 `main()` 执行 `await task` 时，这个异常会重新传播到等待它的调用方。

因此，Task 不只是负责调度协程，也负责保存任务的最终结果或者异常。

对于已经结束的 Task，我们可以使用：

```python
task.result()
task.exception()
```

`result()` 会返回正常执行的结果；如果任务因异常结束，则重新抛出该异常。

`exception()` 可以取得任务保存的异常对象；对于正常完成的 Task，它返回 `None`。

但如果 Task 已被取消，调用这些方法会抛出 `CancelledError`。如果 Task 尚未完成，则会抛出 `InvalidStateError`。

因此，使用这些接口时，需要明确任务当前的状态。

### 2. 为什么会出现未处理的 Task 异常？

假设我们创建了一个 Task，却没有等待它，也没有取得异常。

```python
asyncio.create_task(worker())
```

如果 `worker()` 最终抛出异常，就可能出现：

```text
Task exception was never retrieved
```

这是因为任务异常虽然已经被 Task 保存，却没有被调用方正常处理。

`asyncio` 会在相关时机报告这种未取回的异常。具体日志出现时间可能受到对象生命周期和事件循环关闭过程影响。

这与同步函数直接向调用者抛出异常的行为不同。

所以，在工程实践中，创建一个独立 Task，就意味着需要决定由谁负责观察它的最终状态。

如果某个任务的结果对调用方有意义，就应该等待并处理它。

如果它属于长期运行的后台任务，则需要明确的后台任务管理器负责保存引用、处理异常、停止任务以及关闭资源。

否则，异常可能被延迟发现，甚至在业务层面悄悄失去处理机会。

### 3. gather() 遇到异常会怎样？

这是异步编程中比较容易写错的地方。

默认情况下：

```python
await asyncio.gather(
    task_a(),
    task_b(),
    task_c(),
)
```

如果某个任务首先抛出普通异常，`gather()` 会将异常传播给等待它的调用方。

但是，**默认情况下，其他尚未完成的任务不会因为这个异常而自动取消。**

这与很多人的直觉不同。

假设任务 A 查询失败，而任务 B 和任务 C 仍在访问外部系统。调用方可能已经捕获 A 的异常，但 B、C 依然能够继续执行。

如果业务要求其中一个任务失败后，其他任务也必须停止，那么仅仅使用默认的 `gather()` 并不能满足要求。

`gather()` 还提供 `return_exceptions=True` 参数。

```python
results = await asyncio.gather(
    task_a(),
    task_b(),
    return_exceptions=True,
)
```

这时，普通任务异常会作为结果列表中的元素返回，而不是立即向外抛出。

这种方式适合希望尽可能收集多个任务结果，并分别处理成功与失败的场景。

但它也要求调用方认真检查每个结果，不能把异常对象当成成功数据。

另外，如果取消的是 `gather()` 自身，它会向尚未完成的子任务传播取消请求。如果只是其中一个子 Task 被取消，默认情况下不会连带取消其他子任务。

这些行为差异说明，异常传播和取消传播是两个相关但不同的问题。

## 七、TaskGroup 与结构化并发

现在我们遇到了一个问题。

如果一段业务逻辑需要创建多个子任务，调用方不但要等待它们，还需要处理它们的异常和取消状态。

任务数量越多，手工管理的复杂度就越高。

如果任务之间还有嵌套关系，就更加困难。

为了解决这类问题，Python 3.11 引入了 `asyncio.TaskGroup`。

它体现了一种重要的并发设计思想：结构化并发（Structured Concurrency）。

### 1. 什么是结构化并发？

结构化并发的核心思想是，让并发任务的生命周期具有明确的代码结构和归属关系。

普通的 `create_task()` 可以在函数执行过程中创建一个独立任务。这个任务可能在函数返回后继续运行。

结构化并发则希望一组子任务受到共同的作用域管理。

当程序离开这个作用域时，相关任务应该已经完成，或者已经按照约定处理了取消和异常。

这与普通函数调用具有相似的结构化特点。

一个函数调用内部的执行过程，原则上应该能够通过明确的返回或异常传播来管理，而不是不断留下调用方不知道是否结束的后台工作。

`TaskGroup` 就是这种思想在 `asyncio` 中的实现之一。

### 2. TaskGroup 是如何工作的？

先看一个简单示例。

```python
import asyncio


async def query(name, delay):
    await asyncio.sleep(delay)
    return f"{name} 查询完成"


async def main():
    async with asyncio.TaskGroup() as group:
        user_task = group.create_task(
            query("用户", 1)
        )
        order_task = group.create_task(
            query("订单", 2)
        )

    print(user_task.result())
    print(order_task.result())


asyncio.run(main())
```

这里通过 `async with` 创建了一个任务组。

所有通过 `group.create_task()` 添加的任务，都归这个任务组管理。

当程序准备离开 `async with` 代码块时，TaskGroup 会等待其中的任务结束。

只有当任务组完成相应的生命周期管理以后，程序才会继续执行后面的代码。

因此，我们不需要对每个 Task 单独编写 `await` 才能确保任务组在离开作用域前处理完它们。

这就为一组并发任务建立了明确的管理边界。

### 3. 如果一个任务失败，会发生什么？

这是 TaskGroup 相比默认 `gather()` 更重要的区别。

假设一个任务查询失败，而其他任务仍然在执行。

```python
import asyncio


async def query_user():
    await asyncio.sleep(0.5)
    raise ValueError("用户查询失败")


async def query_orders():
    try:
        await asyncio.sleep(10)
        return "订单查询完成"
    finally:
        print("订单任务清理")


async def main():
    try:
        async with asyncio.TaskGroup() as group:
            group.create_task(query_user())
            group.create_task(query_orders())
    except* ValueError as exc:
        print("捕获任务组异常:", exc)


asyncio.run(main())
```

这里的用户查询在半秒后抛出异常，而订单查询原本需要等待十秒钟。

当 TaskGroup 发现一个成员任务因为普通异常而失败时，会向其他尚未完成的成员任务发送取消请求。

订单任务收到取消后，进入 `finally` 执行清理逻辑。

随后，TaskGroup 等待剩余任务完成退出过程，并将需要报告的异常向外传播。

这意味着，任务组不是简单地“谁报错就立即退出”。

它首先要处理整个任务组的生命周期，确保相关成员已经结束，然后才向调用方报告失败。

当然，如果某个子任务不响应取消，或者清理过程长期阻塞，TaskGroup 也可能需要等待很久。

结构化并发提供的是明确的生命周期管理语义，而不是强制中断任何代码的能力。

### 4. 为什么需要 ExceptionGroup？

前面的代码使用了一个之前比较少见的语法：

```python
except* ValueError as exc:
```

这里的 `except*` 用于处理异常组（Exception Group）。

为什么需要异常组？

因为多个并发任务可能几乎同时失败。

如果任务 A 抛出了 `ValueError`，任务 B 又抛出了 `RuntimeError`，那么调用方可能需要知道两个异常，而不是只看到其中一个。

Python 3.11 引入的 `ExceptionGroup` 和 `except*`，允许将多个异常作为一组传播，并按照异常类型分别处理。

TaskGroup 在处理多个子任务失败时，就可能将这些异常组织为 `ExceptionGroup` 或 `BaseExceptionGroup`。

需要注意，普通的任务取消通常不会像业务异常那样被收集进任务组的异常组中。

另外，`KeyboardInterrupt` 和 `SystemExit` 等特殊异常有专门的传播规则，不能简单地理解为所有异常都会统一包装成 `ExceptionGroup`。

对于一般业务开发，最重要的是认识到：并发任务可能同时失败，因此错误不一定只有一个。

### 5. TaskGroup 是否应该完全替代 gather()？

并不需要。

`gather()` 更侧重并发执行多个可等待对象，并按照传入顺序汇总结果。

TaskGroup 更侧重让一组有关联的任务具有共同的生命周期和故障处理边界。

如果业务要求多个子任务共同完成一项操作，并且一个任务失败后其他任务也应该停止，那么 TaskGroup 通常更符合要求。

如果业务需要收集各个任务的成功或失败结果，允许部分任务失败后其他任务继续执行，那么 `gather(return_exceptions=True)` 可能更加直接。

因此，两者并不是简单的新旧替代关系。

它们提供了不同的异常传播和任务管理语义。

另外，从 Python 3.15 开始，TaskGroup 还新增了 `cancel()` 方法，用于主动结束整个任务组的生命周期。这个接口不能直接用于较早的 Python 版本。

## 八、取消会传播到哪些任务？

介绍了 `gather()` 和 TaskGroup 后，还需要澄清一个问题。

如果任务 A 正在等待任务 B，这时取消任务 A，任务 B 是否也会被取消？

答案取决于具体的等待关系和所使用的 API。

对于普通的：

```python
await task_b
```

如果任务 A 因取消而终止当前等待，取消请求通常会传播到它正在等待的 Task 或 Future。

但如果调用方需要在自己被取消以后，仍然允许某个被等待的任务继续运行，就可以考虑使用 `asyncio.shield()`。

```python
task = asyncio.create_task(
    important_operation()
)

result = await asyncio.shield(task)
```

在这种情况下，如果当前等待者受到外部取消，`shield()` 可以阻止这个取消请求仅仅因为当前等待关系而传递给内部 Task。

但当前等待者本身仍然会收到 `CancelledError`。

也就是说，`shield()` 保护的是内部任务免受这一条取消传播路径的影响，而不是让调用方免于取消。

而且，如果内部 Task 因其他原因受到取消，`shield()` 也不能阻止。

因此，`shield()` 并不是一个让任务绝对安全的保护机制。

如果我们确实需要让某个任务在调用方取消之后继续运行，就必须同时考虑它的引用保存、完成结果、异常处理和服务关闭时的资源回收。

否则，屏蔽取消只是把任务从当前等待关系中分离出来，并没有真正解决生命周期管理问题。

## 九、这些机制在 Web 开发中有什么意义？

现在，我们可以重新考虑文章开头的 Web 接口场景。

假设一个接口需要并发查询用户、订单和账户信息。

在最简单的情况下，我们可以通过 `gather()` 并发执行查询，降低多个独立 I/O 操作串行等待造成的延迟。

但如果三个查询共同决定一个完整的响应，其中任意一个失败都意味着请求无法成功，那么 TaskGroup 可能更适合管理这组查询。

它能够在成员任务发生普通异常后，取消其他尚未完成的任务，并等待它们完成退出过程。

如果整个请求还有明确的耗时要求，则可以使用 `asyncio.timeout()` 给相关业务操作设置统一的超时范围。

这样，任务创建、异常传播和超时控制就可以形成比较完整的执行边界。

不过，真正的 Web 系统比这些示例复杂得多。

### 1. 客户端断开连接是否会取消接口任务？

不一定。

客户端断开连接、ASGI 服务器收到断开事件，以及应用层协程被取消，是三个不同的事情。

服务器可以感知连接断开，但是否进一步取消正在执行的请求处理任务，取决于服务器、Web 框架以及具体请求处理方式。

因此，不能假设客户端一断开连接，FastAPI 的路由函数就一定立即收到 `CancelledError`。

对于长时间运行的请求、流式响应和需要主动中止的操作，通常还需要考虑框架实际提供的断开检测和取消机制。

### 2. 请求被取消后，数据库操作一定停止了吗？

同样不一定。

一个协程可能已经向数据库发送 SQL。

此后，即使 Python 侧的 Task 被取消，数据库服务器也可能仍然在执行之前收到的语句。

数据库驱动是否会发送协议层面的取消请求、连接是否还能复用，以及事务如何回滚，都需要结合具体驱动和数据库行为判断。

因此，异步 Task 的取消状态，不能直接作为数据库操作已终止或事务已回滚的证明。

如果业务涉及修改数据、发送消息或者调用外部支付服务，还需要考虑事务、幂等性和操作结果不确定的问题。

尤其是操作已经提交到外部系统，但本地任务尚未收到成功响应时，取消本地任务也无法撤销已经发生的业务副作用。

### 3. 后台任务应该如何管理？

对于确实需要脱离当前 HTTP 请求继续执行的任务，应该有明确的生命周期所有者。

短时间、允许随进程终止而停止的本地任务，可以由应用级任务管理器跟踪，并在服务关闭时进行清理。

如果任务必须跨进程重启继续执行，或者要求可靠重试和持久化状态，那么仅仅使用 `asyncio.create_task()` 就不够了。

因为 Task 的执行状态默认保存在当前 Python 进程的内存中。进程退出以后，它不会自动恢复。

这类任务通常需要引入持久化存储、消息队列或者独立的后台 Worker。

因此，需要区分进程内异步并发与可靠后台任务系统。

`asyncio` 负责在当前运行环境中组织异步执行，但不自动提供持久化、分布式调度和故障恢复能力。

## 十、小结

前两篇文章解决了协程和事件循环如何实现并发的问题。

这一篇进一步讨论了任务创建以后，整个执行过程应该怎样受到管理。

Task 不只是一个能够被事件循环调度的协程包装对象，它还保存着任务的完成状态、返回结果和异常。

`gather()`、`wait()` 和 `as_completed()` 提供了不同的等待方式，使程序能够根据实际需求收集结果、观察任务状态或者按完成顺序处理数据。

任务取消则是一种协作式机制。`cancel()` 通过请求注入 `CancelledError`，让协程有机会停止执行并清理资源，但并不保证底层操作被立即终止。

超时机制建立在取消等运行时机制之上，也不能简单地理解为强制中断执行。

对于具有共同业务目标的一组任务，TaskGroup 提供了结构化并发能力，让任务的创建、等待、取消和异常传播具有明确的生命周期边界。

回过头看，异步编程真正复杂的地方，并不只是如何让多个任务同时推进。

**更重要的是，当这些任务不再按照单一的同步调用栈执行时，程序必须重新建立清晰的生命周期、错误传播和资源管理规则。**

这也是为什么一个异步程序即使能够正常运行，也不一定意味着它已经具有可靠的异常和取消处理能力。

接下来的文章，我们会从协程和事件循环回到 Web 服务本身，研究一次 HTTP 请求从网络连接进入服务器，到路由匹配、接口执行和响应返回，究竟经历了怎样的过程。
