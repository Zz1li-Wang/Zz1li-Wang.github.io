程序员每天都要使用终端。安装依赖、运行测试、查看 Git 状态、登录服务器，最后总会回到一个命令行窗口。

既然如此，一个很自然的想法就是：能不能把更多开发工作放进终端？编辑代码、搜索文件、管理项目、切换 Git 分支，都在同一个界面完成。

我现在使用的主力组合是 WezTerm、Zsh、Tmux 和 Neovim，再加上 fzf、ripgrep、fd、zoxide、Yazi、Lazygit 等命令行工具。这套环境不一定适合所有人，但是它有一个很明显的优点：每个工具只解决一件事，彼此又可以组合。

终端开发也不是为了拒绝图形界面。浏览器、数据库客户端、抓包工具，当然可以继续使用 GUI。它真正解决的问题，是把高频的开发操作放进一个统一、可重复、能够远程使用的工作流。

本文先谈终端开发的好处，然后介绍一套我比较推荐的技术栈。最后再补充几个配置时经常遇到的问题。

## 一、什么是终端开发

很多人听到“终端开发”，想到的是黑色窗口、满屏命令和很高的学习成本。

其实没有那么复杂。所谓终端开发，就是把终端作为主要工作区。代码编辑器、Shell、Git、文件搜索和项目进程都运行在这个工作区中。

一套典型环境是下面这样。

```text
WezTerm
└── Zsh
    └── Tmux
        ├── Neovim：编辑代码
        ├── Shell：运行测试
        ├── Shell：启动开发服务器
        └── Lazygit / Yazi：管理 Git 和文件
```

WezTerm 负责显示文字和接收按键，Zsh 负责执行命令，Tmux 管理窗口和会话，Neovim 负责编辑代码。其他 CLI 工具按需加入。

这些工具不是同一种东西，也不是互相替代。终端模拟器换成 Kitty，Shell 仍然可以用 Zsh；编辑器换成 Vim，Tmux 仍然可以保留。整个环境像搭积木，哪一层不合适，就单独替换哪一层。

这正是终端工具栈的第一个特点：它没有一个必须全部接受的“大套件”。

## 二、工作不会被应用窗口切碎

图形化开发环境的问题，不是功能不够，而是功能经常分散在不同窗口。

写代码在编辑器，运行服务在终端，查看提交在 Git 客户端，登录服务器又要打开另一个终端。每个应用都有自己的标签、快捷键和工作目录。来回切换几次，很容易忘记当前窗口对应哪个项目。

Tmux 可以把一个项目的进程放在同一个 session 中。

```bash
tmux new-session -A -s myblog
```

上面的命令会创建一个名为 `myblog` 的会话。如果它已经存在，就直接进入。

进入以后，我通常会保留几个窗口。

```text
1:nvim    编辑代码
2:shell   执行命令和测试
3:server  运行开发服务器
4:log     查看日志
```

它们共享同一个项目上下文，又是彼此独立的进程。测试失败时切到编辑器修改，保存后切回来重新运行，不需要寻找窗口，也不需要重复进入目录。

终端开发带来的速度，并不只是“键盘比鼠标快”。更重要的是工作上下文没有频繁中断。手还在键盘上，当前目录、虚拟环境、日志和代码也都在眼前。

## 三、命令可以组合，操作可以复用

命令行工具通常都有清楚的输入和输出。一个命令的结果，可以直接交给另一个命令处理。

比如，`fd` 负责寻找文件，`fzf` 负责交互选择，`bat` 负责显示预览。Ubuntu 中的 `bat` 命令名是 `batcat`，所以下面的示例使用这个名字。

```bash
fd --type f | fzf --preview 'batcat --color=always --style=numbers {}'
```

这条命令会列出当前目录中的文件。移动光标时，右侧显示文件内容；按下回车，就把选中的路径输出出来。

再把结果交给 Neovim，就得到一个简单的文件选择器。

```zsh
fe() {
  local file
  file=$(fd --type f | fzf --preview 'batcat --color=always --style=numbers {}') || return
  nvim -- "$file"
}
```

这就是终端工具最吸引我的地方。`fd` 不需要知道什么是编辑器，`fzf` 不需要知道候选项是不是文件，Neovim 也不负责遍历目录。三个工具按照标准输入和标准输出连接起来，就得到一个新功能。

很多日常操作都会经历类似的过程。

```text
先输入一条命令
    ↓
从历史记录中再次使用
    ↓
写成 Shell 函数
    ↓
稳定以后做成脚本
```

GUI 中的一次点击往往很难复用。命令行则天然会留下命令、参数和退出状态。只要一项操作开始重复，就有机会把它变成自动化流程。

## 四、本地和远程可以使用同一种方式

终端环境特别适合 SSH 和 WSL。

```bash
ssh dev@example.com
```

登录远端以后，Shell、Tmux、Neovim 和大多数 CLI 的操作方式都没有变化。服务器不需要运行完整桌面，也不需要传输整个图形界面。

如果网络中断，远端 Tmux 中的进程仍然可以继续运行。重新登录后，再连接原来的 session。

```bash
tmux attach-session -t work
```

这对于编译、训练任务、日志观察和远程编辑很有用。笔记本合盖或者 SSH 暂时掉线，不会直接结束正在运行的程序。

Windows 用户也可以通过 WSL 获得完整的 Linux 开发环境。Windows 上运行 WezTerm，里面直接进入 WSL，再使用与服务器相同的 Zsh、Tmux 和 Neovim。这样一来，本地开发和远端服务器之间的差异会小很多。

当然，配置文件和已安装的软件仍然属于各自机器。终端开发提供的是相似的操作方式，不是自动把所有环境变成同一台电脑。

## 五、我推荐的工具栈

如果只推荐一套组合，我会选择下面这些工具。

| 位置 | 推荐工具 | 主要用途 |
| --- | --- | --- |
| 终端模拟器 | [WezTerm](https://wezterm.org/) | 字体、颜色、键盘输入、WSL 入口 |
| Shell | [Zsh](https://www.zsh.org/) | 命令执行、历史、补全和交互操作 |
| 会话管理 | [Tmux](https://github.com/tmux/tmux) | 窗口、分屏、远程会话持久化 |
| 编辑器 | [Neovim](https://neovim.io/) | 代码编辑、LSP、语法树和插件扩展 |
| 模糊选择 | [fzf](https://github.com/junegunn/fzf) | 从文件、历史、目录和项目中快速选择 |
| 搜索 | [ripgrep](https://github.com/BurntSushi/ripgrep)、[fd](https://github.com/sharkdp/fd) | 搜索文件内容和文件路径 |
| 目录跳转 | [zoxide](https://github.com/ajeetdsouza/zoxide) | 根据使用频率快速进入目录 |
| 终端界面 | [Yazi](https://yazi-rs.github.io/)、[Lazygit](https://github.com/jesseduffield/lazygit) | 文件管理和 Git 操作 |

这里没有列出几十个插件。先把主干搭起来，比一开始复制一份庞大的 dotfiles 更重要。

终端模拟器可以换成 Kitty、Alacritty 或 Ghostty，Shell 可以换成 Fish，编辑器也可以继续使用 VS Code。真正值得保留的是工具之间的连接方式，而不是某一个具体品牌。

## 六、安装基础工具

Ubuntu 和 WSL 可以先安装发行版仓库中的基础工具。

```bash
sudo apt update
sudo apt install -y zsh tmux fzf ripgrep fd-find bat jq zoxide
```

Ubuntu 为了避免命令名冲突，把 `fd` 和 `bat` 安装成了 `fdfind` 和 `batcat`。可以直接使用这两个名字，也可以在 `~/.local/bin` 中建立自己的符号链接。

```bash
mkdir -p "$HOME/.local/bin"
command -v fd >/dev/null || ln -s "$(command -v fdfind)" "$HOME/.local/bin/fd"
command -v bat >/dev/null || ln -s "$(command -v batcat)" "$HOME/.local/bin/bat"
```

如果目标文件已经存在，`ln` 会拒绝覆盖。先检查它指向哪里，不要为了省一步就使用 `ln -sf` 覆盖现有命令。还要确认 `~/.local/bin` 已经在 `PATH` 中。

Neovim、WezTerm、Yazi 和 Lazygit 更新较快，发行版仓库中的版本可能明显落后。建议按照各自官网安装当前稳定版。本文最后给出的配置仓库也提供了 Ubuntu/WSL 依赖安装和版本检查脚本。

一开始不必把表格中的工具全部装齐。Zsh、Tmux、fzf、ripgrep 和 fd 已经足够体验主要工作流。

## 七、终端模拟器：WezTerm

终端模拟器就是打开后显示命令行的那个图形程序。它不是 Shell，也不负责解释 `cd`、`git` 这些命令。

我推荐 WezTerm，主要有三个原因。

第一，它可以运行在 Windows、macOS 和 Linux 上。第二，它使用 Lua 配置，按键、字体和启动方式都可以放进版本控制。第三，它对 WSL 有直接支持，Windows 用户可以把某个 WSL 发行版设为默认入口。

WezTerm 的配置文件是 Lua。下面是一份很小的配置。

```lua
local wezterm = require("wezterm")
local config = wezterm.config_builder()

config.font = wezterm.font("JetBrainsMono Nerd Font")
config.font_size = 12
config.hide_tab_bar_if_only_one_tab = true
config.scrollback_lines = 10000

return config
```

Nerd Font 不是必须的，但是很多提示符和 Neovim 插件会使用其中的图标。字体必须安装在真正负责绘制界面的系统中。比如，WezTerm 运行在 Windows 上，就要把字体安装到 Windows，而不是只安装在 WSL 里。

如果希望 Windows 版 WezTerm 启动后直接进入 Ubuntu WSL，可以增加下面一行。

```lua
config.default_domain = "WSL:Ubuntu"
```

发行版名称不是 `Ubuntu` 时，需要换成实际名称。

WezTerm 自带标签页和分屏，Tmux 也有这些功能。两套都用，很快就会出现重复快捷键。我通常把 WezTerm 当作显示层，把项目窗口和分屏交给 Tmux。不开 Tmux 时，再临时使用 WezTerm 自带的 pane。

## 八、Shell：Zsh

Shell 接收输入的命令，再启动对应程序。Bash、Zsh 和 Fish 都属于 Shell。

如果希望开箱即用，我会推荐 Fish。它默认就有语法高亮、自动建议和友好的补全，几乎不配置也很好用。

但是，Fish 的语法与传统的 `sh`、Bash 不完全兼容。网上的安装脚本、服务器环境和团队文档，大多仍然以 Bash 或 Zsh 为例。我的选择是把 Zsh 作为交互 Shell，脚本则根据需要明确写成 Bash 或 POSIX `sh`。

安装 Zsh 后，可以先手动启动。

```bash
zsh
```

确认补全、环境变量和开发工具都正常，再考虑设置成默认 Shell。

```bash
chsh -s "$(command -v zsh)"
```

Zsh 本身已经带有强大的补全系统。最小配置可以从历史记录和补全开始。

```zsh
HISTFILE="$HOME/.zsh_history"
HISTSIZE=100000
SAVEHIST=100000

setopt INC_APPEND_HISTORY
setopt HIST_IGNORE_ALL_DUPS
setopt HIST_FIND_NO_DUPS

autoload -Uz compinit
compinit
```

然后再加入几个真正有用的增强。

`zsh-autosuggestions` 会根据历史记录，在光标后面显示灰色建议；`fast-syntax-highlighting` 会根据命令是否有效改变颜色；`fzf-tab` 会把补全候选交给 fzf；`zsh-history-substring-search` 可以按照已经输入的内容搜索历史。

这些功能组合起来以后，很多命令不再需要从头输入。输入几个字符，再使用方向键、`Tab` 或右方向键即可完成。

插件管理器不是必需品。插件少时可以直接加载，插件多了再选择 Zinit、Antidote 等管理器。不要先装一整套框架，再花时间寻找某个行为到底来自哪里。

新版本 fzf 可以直接生成 Zsh 集成脚本。

```zsh
source <(fzf --zsh)
```

如果发行版自带的 fzf 版本较旧，可以加载它随软件包提供的 `key-bindings.zsh` 和 `completion.zsh`。zoxide 也需要在 Shell 启动时初始化。

```zsh
eval "$(zoxide init zsh)"
```

完成以后，`Ctrl-r`、`Ctrl-t`、`Alt-c`、`z` 和 `zi` 才会成为日常工作流的一部分。

## 九、会话管理：Tmux

Tmux 是终端复用器。它可以在一个终端中创建多个 window 和 pane，还可以让这些进程脱离当前终端继续运行。

第一次使用时，只需要记住四条命令。

```bash
# 创建名为 work 的会话
tmux new-session -s work

# 查看已有会话
tmux list-sessions

# 重新进入会话
tmux attach-session -t work

# 存在就进入，不存在就创建
tmux new-session -A -s work
```

Tmux 默认前缀键是 `Ctrl-b`。先按前缀，再按其他键，执行 Tmux 操作。

```text
Ctrl-b c    新建 window
Ctrl-b %    左右分屏
Ctrl-b "    上下分屏
Ctrl-b d    退出当前客户端，会话继续运行
```

配置文件通常是 `~/.tmux.conf` 或 `~/.config/tmux/tmux.conf`。下面几项就足够开始使用。

```tmux
set -g mouse on
set -g history-limit 50000
set -g default-terminal "tmux-256color"

bind '"' split-window -v -c "#{pane_current_path}"
bind % split-window -h -c "#{pane_current_path}"
bind c new-window -c "#{pane_current_path}"
```

后三行让新 pane 和 window 继承当前目录。否则，每次分屏后都可能回到默认目录。

用熟以后，可以加入 `tmux-sessionizer`。它的思路很简单：扫描常用项目目录，用 fzf 选中一个项目，再创建或进入对应的 Tmux session。

```bash
project=$(fd --type d --max-depth 2 . "$HOME/study" "$HOME/work" | fzf) || exit
session=$(basename "$project" | tr '.:' '__')
tmux new-session -A -s "$session" -c "$project"
```

这段代码正好展示了终端工具如何组合：`fd` 找项目，`fzf` 选择项目，Tmux 打开工作区。

## 十、编辑器：Neovim

Neovim 是一个基于终端的模态编辑器。普通模式负责移动和执行操作，插入模式负责输入文字，可视模式负责选择内容。

它的学习成本主要来自“模式”，不是配置。刚开始先学下面几项就够了。

```text
i          进入插入模式
Esc        回到普通模式
h j k l    左、下、上、右移动
w / b      向前、向后按单词移动
dd         删除一行
yy         复制一行
p          粘贴
u          撤销
:w         保存
:q         退出
```

熟悉这些操作后，再学习文本对象、搜索、宏和寄存器。不要第一天就背完整快捷键表。

现代 Neovim 已经不只是一个文本编辑器。它内置 LSP 客户端，可以连接 Pyright、gopls、rust-analyzer 等语言服务器；Tree-sitter 提供更准确的语法解析；插件可以补上文件搜索、自动补全、Git、调试和文件管理。

我比较推荐下面这组插件方向。

| 功能 | 选择 |
| --- | --- |
| 插件管理 | lazy.nvim |
| 语法解析 | nvim-treesitter |
| 语言服务 | Neovim LSP、nvim-lspconfig、Mason |
| 模糊搜索 | fzf-lua 或 Telescope |
| 文件浏览 | Oil.nvim、Yazi.nvim |
| 诊断列表 | Trouble.nvim |
| Git | gitsigns.nvim、Neogit 或 Lazygit |

这不是必须全部安装的清单。最先需要的是 LSP、搜索和补全，其他功能遇到需求再加。

插件也不是越多越好。Neovim 配置最容易出现的问题，就是同一个功能由两三个插件同时提供。两个格式化器保存时一起运行，两个补全引擎争抢菜单，多个文件管理器又占用同一组快捷键。每加入一个插件，最好能说清楚它解决了什么问题。

遇到异常时，可以先用干净模式启动。

```bash
nvim --clean
```

如果干净模式正常，问题通常在个人配置或插件中。进入正常 Neovim 后，还可以运行下面的命令。

```vim
:checkhealth
```

它会检查剪贴板、LSP、Tree-sitter、外部工具等常见依赖。

## 十一、模糊选择：fzf

fzf 是整套工具栈中很关键的一环。

它的功能只有一个：读取一组候选，让用户模糊搜索，然后输出选中的内容。

```bash
printf '%s\n' apple banana orange | fzf
```

运行以后，输入几个字符，就可以从三项中选择一项。

候选不一定是文件。它可以是 Shell 历史、Git 分支、进程、目录、Tmux pane，甚至是一组自己生成的字符串。

fzf 的 Zsh 集成提供了几个很实用的快捷键。

```text
Ctrl-r    搜索命令历史
Ctrl-t    搜索文件，并把路径插入当前命令
Alt-c     搜索目录并进入
```

这三个快捷键会明显减少重复输入。尤其是 `Ctrl-r`，以前运行过的长命令，输入一两个关键词就能找回来。

在我的配置中，`Tab` 补全也会进入 fzf 界面。Git 分支、命令参数和文件路径都可以边输入边筛选，候选较多时比反复按 `Tab` 更直观。

## 十二、搜索和跳转：ripgrep、fd、zoxide

`ripgrep` 的命令名是 `rg`，用来搜索文件内容。

```bash
rg 'create_user' src tests
```

它默认递归搜索，并且会遵守 `.gitignore`，因此很适合代码仓库。

显示匹配行的前后内容，可以使用 `-C`。

```bash
rg -C 3 'create_user' src
```

只列出包含匹配内容的文件，可以使用 `-l`。

```bash
rg -l 'TODO'
```

`fd` 用来搜索文件名和目录名。

```bash
# 查找所有 Lua 文件
fd --extension lua

# 只查找目录
fd --type d 'project'

# 包含隐藏文件，但排除 .git
fd --hidden --exclude .git
```

`rg` 搜内容，`fd` 搜路径，分工很清楚。它们都可以把结果交给 fzf。

`zoxide` 解决的是另一个高频问题：进入一个很长的目录。

```bash
cd ~/study/projects/python/MyBlog
```

使用一段时间以后，zoxide 会记住经常访问的目录。以后只需要输入其中一部分。

```bash
z MyBlog
```

如果存在多个结果，可以交互选择。

```bash
zi
```

它会调用 fzf 显示候选目录。这里又出现了同样的组合方式：zoxide 负责记录和排序目录，fzf 负责选择。

## 十三、终端界面：Yazi 和 Lazygit

命令行并不意味着所有操作都要背参数。TUI，也就是终端用户界面，可以在终端里提供面板、列表和快捷键。

Yazi 是文件管理器。

```bash
yazi
```

它适合浏览目录、预览文件、批量选择和移动文件。需要快速理解陌生目录时，Yazi 比连续执行很多次 `ls` 更方便。

Neovim 用户还可以通过 Yazi.nvim 从编辑器中打开它。选择文件后直接回到当前编辑会话，不必另开一个图形文件管理器。

Lazygit 是 Git 的终端界面。

```bash
lazygit
```

它可以查看文件差异、分块暂存、切换分支、处理 rebase 和浏览提交记录。我尤其喜欢它的分块暂存：可以从一个文件中只选择这次提交真正需要的几行。

不过，使用 Lazygit 之前还是应该理解 `git status`、`git add`、`git commit`、`git switch` 和 `git rebase`。TUI 帮助我们更快地执行操作，不能替代对 Git 状态的理解。

## 十四、一套完整的日常工作流

把前面的工具连起来，一次开始工作的过程可以很短。

先跳到项目目录。

```bash
z MyBlog
```

然后使用项目选择器进入 Tmux session。

```bash
ts
```

这里的 `ts` 是我给 `tmux-sessionizer` 设置的别名。它会用 fzf 选择项目，再进入对应会话。

第一个 window 打开 Neovim。

```bash
nvim .
```

第二个 window 运行测试，第三个 window 启动服务。需要查找代码时，在 Neovim 中使用 fzf-lua，或者直接在 Shell 中运行 `rg`。需要处理 Git 时，打开 Lazygit。需要浏览大量文件时，打开 Yazi。

离开电脑前，从 Tmux detach。第二天重新进入同一个 session，编辑器、服务和日志仍然保持原来的布局。

这个流程真正方便的地方，是项目变成了一个可以随时离开和重新进入的工作区，而不只是硬盘上的一个目录。

## 十五、不要一次换掉所有工具

终端开发的学习曲线确实存在。Shell、Tmux 和 Neovim 各有一套快捷键，如果同时学习，很容易把时间全花在配置上。

比较舒服的顺序是先换终端模拟器和 Shell。等命令历史、补全和目录跳转已经顺手，再加入 fzf、rg、fd 和 zoxide。

下一步学习 Tmux，只使用 session、window、pane 和 detach。最后再把 Neovim 作为主编辑器。在这段时间里，VS Code 或 JetBrains IDE 完全可以继续保留。

还有一个实用原则：先使用默认键位，再决定哪些键真的需要修改。别人 dotfiles 中的快捷键来自他的键盘、系统和习惯，完整照搬以后往往更难记。

配置也应该跟着实际问题增长。第一次启动很慢，再分析 Shell 插件；颜色真的不对，再研究 `TERM`；语言服务器找不到，再检查 `PATH`。没有遇到的问题，不需要提前加入十行“兼容配置”。

## 十六、几个常见问题

终端开发看起来只有一个窗口，背后却有好几层。

```text
终端模拟器 → Shell → Tmux → Neovim → LSP、格式化器和其他 CLI
```

按键、颜色和环境变量会沿着这条链路传递。出现问题时，从外向内检查通常最快。

Tmux 内颜色异常，先比较内外的 `TERM`。

```bash
printf 'TERM=%s\n' "$TERM"
infocmp "$TERM" >/dev/null
```

Tmux 外部的 `TERM` 应描述真实终端，Tmux 内部通常是 `tmux-256color`。不要在 `.zshrc` 中无条件写死 `TERM=xterm-256color`，否则只是让所有程序拿到一份不一定真实的能力说明。

Neovim 找不到语言服务器或格式化器，先检查它实际看到的可执行文件。

```vim
:lua print(vim.fn.exepath('pyright-langserver'))
:checkhealth vim.lsp
```

Neovim 内置的是 LSP 客户端，不会因此自动拥有 Pyright、gopls 等语言服务器。它们仍然需要单独安装，并且在启动 Neovim 时已经位于 `PATH` 中。

如果问题只出现在运行很久的 Tmux 中，可能是 Tmux session 还保留着旧环境。可以分别查看全局环境和当前 session 环境。

```bash
tmux show-environment -g PATH
tmux show-environment PATH
```

已经运行的 Shell 和 Neovim 不会自动获得后来修改的环境变量。新建一个 pane 正常、旧 pane 仍然异常，通常就是这个原因。

某个组合键只在 Tmux 中失效，可以先运行 `cat`，按下该键，比较 Tmux 内外收到的字符。终端按键最终会编码成字符序列，终端模拟器、Tmux 和应用必须对这些序列有相同理解。

Shell 启动很慢，可以先测量。

```zsh
time zsh -i -c exit
```

常见原因是每次启动都运行版本管理器、重新生成补全或者同步加载太多插件。先找到真正耗时的部分，再决定是否缓存或延迟加载。
