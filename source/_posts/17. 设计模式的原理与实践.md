前三篇文章先后讨论了职责与边界、MVC 与分层架构，以及 SOLID、KISS、DRY、YAGNI。我们已经知道，软件设计需要减少不必要的依赖，让不同的变化有明确的归属。但在实际开发中，仅仅理解这些原则还不够。遇到第三方接口不兼容、计算规则频繁变化，或者一段流程必须允许别人扩展时，代码应该怎样组织？

这些问题往往有一些重复出现的结构。1994 年出版的《Design Patterns: Elements of Reusable Object-Oriented Software》，总结了 23 种常见的面向对象设计模式。它们通常分为创建型、结构型和行为型三组。创建型关注对象怎样产生，结构型关注对象怎样组合，行为型关注职责与协作怎样安排。

设计模式不是框架，也不是一段可以直接复制的标准代码。它描述的是特定条件下反复出现的设计问题，以及一种经过实践的解决思路。理解模式时，最值得弄清楚的是原有实现为什么遇到困难，新结构如何改变依赖关系，以及这种改变带来了什么成本。

下面仍以 Python 后端业务为主要背景，穿插订单、定价、支付、报表和文件处理等场景。代码使用 Python 3.12 及以上版本的标准库；各示例独立，不需要拼接成同一个项目。为了说明对象协作，会省略与模式无关的数据库连接、HTTP 接口和部署代码。

## 一、设计模式

设计模式的出现，源于一些反复发生的对象创建、组合与协作问题。
### 1. 从条件分支到对象协作

假设订单系统支持不同的折扣政策。最初只有 VIP 九折，直接写一个 `if` 就能解决问题。后来陆续增加满减和会员积分抵扣，计算函数开始根据活动类型选择不同算法。

此时有两种选择。一种是继续维护条件分支，另一种是把不同规则放进独立的实现中，再由报价流程调用它们。后一种组织方式就是策略模式的典型用途。

但是，策略模式并不能让计算自动变得正确，也不保证代码一定更简单。如果只有一个稳定的优惠规则，独立函数通常更合适；如果活动种类经常增加，而且具有共同的计算契约，策略对象或可调用函数才可能减少修改成本。

同样的判断适用于其他模式。使用模式的理由应当来自真实的变化压力，而不是因为项目还没有某种模式。

### 2. 设计模式与架构模式的关系

前三篇讨论的分层架构安排的是系统级职责。它可以规定 API 层负责请求与响应，应用服务负责业务用例，仓储负责数据访问。

设计模式通常关注更局部的协作。例如，应用服务通过策略模式选择定价算法，通过适配器访问外部支付系统，通过观察者或事件分发机制通知其他组件。它们可以同时存在于分层架构中。

这两种设计尺度不能相互代替。把订单模块写成十几个策略类，并不会自动得到合理的事务边界；建立了 Controller、Service、Repository 目录，也不会自动解决外部 SDK 与业务接口不兼容的问题。

## 二、创建型模式：对象应该怎样产生

程序通常通过调用类来创建实例。如果调用方不仅需要使用某种能力，还必须了解实例属于哪个具体类、初始化需要哪些参数、相关对象如何配套，创建过程本身就可能成为依赖来源。创建型模式主要处理这些问题。

### 1. 工厂方法：由谁决定创建哪个对象

订单通知可能通过邮件或短信发送。假如通知流程直接构造具体发送器，新增渠道时就要检查通知流程如何初始化它。

最简单的改进，是用一个普通函数集中创建对象：

```python
class EmailSender:
    def send(self, text: str) -> str:
        return f"邮件：{text}"


class SmsSender:
    def send(self, text: str) -> str:
        return f"短信：{text}"


def make_sender(channel: str):
    providers = {"email": EmailSender, "sms": SmsSender}
    try:
        return providers[channel]()
    except KeyError as exc:
        raise ValueError(f"不支持的通知渠道：{channel}") from exc


print(make_sender("email").send("订单已发货"))
```

这种写法通常称为**简单工厂**。它很实用，但严格来说，不等同于 GoF 的工厂方法（Factory Method）。简单工厂将类型选择集中到一个函数；经典工厂方法让基类定义通用流程，由子类决定流程中需要创建的具体对象。

```python
from abc import ABC, abstractmethod
from typing import Protocol


class Sender(Protocol):
    def send(self, text: str) -> str: ...


class EmailSender:
    def send(self, text: str) -> str:
        return f"邮件：{text}"


class SmsSender:
    def send(self, text: str) -> str:
        return f"短信：{text}"


class NotificationJob(ABC):
    def run(self, text: str) -> str:
        sender = self.create_sender()
        return sender.send(text)

    @abstractmethod
    def create_sender(self) -> Sender:
        raise NotImplementedError


class EmailJob(NotificationJob):
    def create_sender(self) -> Sender:
        return EmailSender()


class SmsJob(NotificationJob):
    def create_sender(self) -> Sender:
        return SmsSender()


print(EmailJob().run("订单已发货"))
```

`NotificationJob.run()` 固定了执行流程，但不知道具体发送器如何创建。子类通过覆盖 `create_sender()` 决定产品类型。新增一种通知任务，可以新增子类而保留通用流程。

这也说明工厂方法适合怎样的情况：一个可继承的通用流程需要创建对象，而具体产品取决于子类。如果只需要根据配置字符串选择一种发送器，普通函数或字典注册表往往比创建完整的继承体系更清晰。

### 2. 抽象工厂：创建一组必须配套的对象

工厂方法通常讨论某类对象的创建。抽象工厂（Abstract Factory）进一步处理“一组相关对象怎样一起创建”的问题。

设想文件系统模块支持本地存储和对象存储。上传器负责保存文件，链接生成器负责生成与该存储系统相匹配的访问地址。如果调用方随意组合本地上传器和对象存储链接生成器，可能得到无效的访问地址。

可以让一个工厂同时提供同一存储方案下的两种能力：

```python
from typing import Protocol


class Uploader(Protocol):
    def put(self, name: str) -> str: ...


class LinkBuilder(Protocol):
    def link(self, key: str) -> str: ...


class StorageFactory(Protocol):
    def uploader(self) -> Uploader: ...
    def links(self) -> LinkBuilder: ...


class LocalUploader:
    def put(self, name: str) -> str:
        return f"files/{name}"


class LocalLinks:
    def link(self, key: str) -> str:
        return f"/static/{key}"


class CloudUploader:
    def put(self, name: str) -> str:
        return f"objects/{name}"


class CloudLinks:
    def link(self, key: str) -> str:
        return f"https://storage.example/{key}"


class LocalFactory:
    def uploader(self) -> Uploader:
        return LocalUploader()

    def links(self) -> LinkBuilder:
        return LocalLinks()


class CloudFactory:
    def uploader(self) -> Uploader:
        return CloudUploader()

    def links(self) -> LinkBuilder:
        return CloudLinks()


def upload_and_link(factory: StorageFactory, name: str) -> str:
    key = factory.uploader().put(name)
    return factory.links().link(key)


print(upload_and_link(LocalFactory(), "report.pdf"))
```

示例中的 `put()` 只是模拟生成存储键，并没有真正写入文件。需要关注的是工厂与产品的关系：调用方选择一次存储方案，之后得到的上传器和链接生成器属于同一组实现。

抽象工厂的收益是减少产品族混用，也方便整体替换技术方案。代价是引入了额外接口，而且如果以后增加第三类必须配套的产品，每个具体工厂都可能需要扩展。所以它适合确实存在多组产品、且组内对象必须相互兼容的场景。

### 3. 建造者：复杂对象分步骤构造

对象的构造参数很多时，直接调用构造函数容易出现含义不清和约束遗漏的问题。建造者（Builder）把构造过程组织成一系列明确的步骤，最后再生成完整对象。

例如，导出任务有格式、是否压缩、字段选择等选项，我们希望在任务真正创建之前验证这些组合是否有效。

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class ExportJob:
    format: str
    fields: tuple[str, ...]
    compressed: bool


class ExportJobBuilder:
    def __init__(self):
        self._format = "csv"
        self._fields: list[str] = []
        self._compressed = False

    def format(self, value: str) -> "ExportJobBuilder":
        self._format = value
        return self

    def fields(self, *names: str) -> "ExportJobBuilder":
        self._fields = list(names)
        return self

    def compress(self) -> "ExportJobBuilder":
        self._compressed = True
        return self

    def build(self) -> ExportJob:
        if self._format not in {"csv", "json"}:
            raise ValueError("不支持的导出格式")
        if not self._fields:
            raise ValueError("至少需要一个导出字段")
        return ExportJob(
            format=self._format,
            fields=tuple(self._fields),
            compressed=self._compressed,
        )


job = (ExportJobBuilder()
       .format("json")
       .fields("order_id", "amount")
       .compress()
       .build())
print(job)
```

构造过程使用可变的 Builder，完成后返回不可变的 `ExportJob`。它让复杂配置分步骤形成，并把最终校验集中到 `build()` 中。

但是，Python 支持关键字参数、带默认值的 `dataclass` 和 Pydantic 校验。对于只有少量参数的数据对象，直接实例化通常足够。经典建造者的更完整形式还可以让同一组构造步骤生成不同表示，示例只展示了最常见的分步构造需求。

### 4. 原型：从已有对象复制出新对象

有时新对象与一个现成对象几乎相同，只需要修改少数配置。原型模式（Prototype）通过复制已有对象进行创建，避免重新描述完整构造过程。

Python 已经提供 `copy.copy()` 和 `copy.deepcopy()`：

```python
from copy import deepcopy


template = {
    "name": "默认导出任务",
    "options": {"columns": ["order_id", "amount"]},
}

job = deepcopy(template)
job["name"] = "财务导出"
job["options"]["columns"].append("tax")

print(template["options"]["columns"])  # ['order_id', 'amount']
print(job["options"]["columns"])       # ['order_id', 'amount', 'tax']
```

普通浅拷贝只复制外层容器，内部列表等可变对象仍可能共享；深拷贝会递归复制可以复制的内部对象。不过，数据库 Session、网络连接、锁、文件句柄等资源通常不适合直接深拷贝。使用原型前，需要明确哪些状态应当共享，哪些状态必须独立。

### 5. 单例：唯一对象的作用域在哪里

单例模式（Singleton）希望在某个作用域内确保一个类只有一个实例，并提供统一访问方式。日志配置、进程内缓存或者应用级组件初始化时，经常有人考虑它。

Python 不一定需要自定义 `__new__` 或元类来实现这类需求。若只想在当前进程中复用一份不可变配置，可以使用带缓存的工厂函数：

```python
from dataclasses import dataclass
from functools import lru_cache


@dataclass(frozen=True)
class Settings:
    service_name: str


@lru_cache(maxsize=1)
def get_settings() -> Settings:
    return Settings(service_name="order-service")


assert get_settings() is get_settings()
```

这段代码展示了缓存重用，并不保证整个分布式系统只有一个实例。多个 Worker 进程有各自的内存和缓存；缓存被清除后也可以创建新对象；在并发首次调用时，`lru_cache` 还可能使被包装函数执行多次。

因此，需要先明确“唯一”的范围。如果要求系统中只有一个任务调度执行者，进程内单例完全不够，往往需要数据库、租约或协调服务提供跨进程约束。若只是让多个组件共享一个服务实例，通过应用启动时创建对象、再用依赖注入分发，通常更容易测试，也更容易控制生命周期。

## 三、结构型模式：对象应该怎样组合

创建对象之后，还需要把它们连接起来。结构型模式关注接口不兼容、功能组合、子系统过于复杂，以及访问对象需要附加控制等问题。

### 1. 适配器：让不同接口能够协作

假设订单系统使用统一的支付接口，要求输入金额单位为分，输出平台交易编号。某个旧支付 SDK 接收的却是元，并返回一个带有特殊字段名称的字典。

如果业务服务直接依赖 SDK 的字段和单位，未来更换支付渠道就会影响订单代码。适配器模式（Adapter）把外部接口转换为内部期望的接口：

```python
from decimal import Decimal
from typing import Protocol


class PaymentGateway(Protocol):
    def charge(self, amount_cents: int) -> str: ...


class LegacyPaySDK:
    def debit(self, amount_yuan: str) -> dict[str, object]:
        return {"success": True, "trade_no": "T-1001"}


class LegacyPayAdapter:
    def __init__(self, sdk: LegacyPaySDK):
        self.sdk = sdk

    def charge(self, amount_cents: int) -> str:
        if amount_cents <= 0:
            raise ValueError("支付金额必须大于零")
        yuan = Decimal(amount_cents) / Decimal(100)
        response = self.sdk.debit(f"{yuan:.2f}")
        if response.get("success") is not True:
            raise RuntimeError("支付失败")
        trade_no = response.get("trade_no")
        if not isinstance(trade_no, str):
            raise RuntimeError("支付结果缺少交易编号")
        return trade_no


def pay_order(gateway: PaymentGateway, amount_cents: int) -> str:
    return gateway.charge(amount_cents)


print(pay_order(LegacyPayAdapter(LegacyPaySDK()), 12345))
```

适配器承担了单位换算、字段解析和错误转换。调用方只知道 `PaymentGateway` 的约定，不必了解旧 SDK 的返回结构。

真实支付还需要处理超时、未知结果、幂等键和回调确认。适配器只解决接口差异，不能通过一层包装自动解决支付一致性。如果内部接口无法表达外部服务的某种重要状态，应当修订契约，而不是强行把不同语义映射成同一个成功或失败值。

### 2. 装饰器：不改原对象，叠加额外行为

订单定价需要记录计算日志，但我们不希望修改每一种优惠策略的实现。装饰器模式（Decorator）通过一个拥有相同接口的包装对象，在调用前后增加行为。

```python
from typing import Protocol


class Quoter(Protocol):
    def quote(self, amount_cents: int) -> int: ...


class OriginalQuoter:
    def quote(self, amount_cents: int) -> int:
        return amount_cents


class LoggingQuoter:
    def __init__(self, wrapped: Quoter):
        self.wrapped = wrapped

    def quote(self, amount_cents: int) -> int:
        result = self.wrapped.quote(amount_cents)
        print(f"报价：{amount_cents} -> {result}")
        return result


quoter: Quoter = LoggingQuoter(OriginalQuoter())
print(quoter.quote(30_000))
```

包装对象和被包装对象拥有相同的 `quote()` 能力，因此对调用方来说可以互相替换。多个装饰器还可以套在一起，分别承担日志、指标或缓存等职责。

Python 中的 `@decorator` 语法也经常用于包装函数，它与 GoF 装饰器模式具有相近的思想，但并非所有使用 `@` 的语法都属于该模式。例如，`@property` 主要参与属性描述符的定义。函数装饰器通常还需要使用 `functools.wraps` 保留原函数的相关元信息。

叠加功能也存在成本。装饰顺序可能影响行为，缓存包装在权限检查外层或内层就可能带来完全不同的安全语义。对于简单的一次性功能，直接调用函数通常比建立多层包装对象更容易理解。

### 3. 外观：给复杂子系统提供一个简洁入口

导出报表可能需要读取记录、转换格式并保存文件。调用方如果每次都自行协调这些步骤，就必须知道整个子系统的调用顺序。

外观模式（Facade）提供一个面向常见使用需求的入口，把内部子系统的协作封装起来：

```python
class ReportReader:
    def read(self) -> list[int]:
        return [100, 200, 300]


class ReportFormatter:
    def format(self, numbers: list[int]) -> str:
        return "\n".join(str(n) for n in numbers)


class ReportStorage:
    def save(self, content: str) -> str:
        return f"report-{len(content)}.txt"


class ReportFacade:
    def __init__(self):
        self.reader = ReportReader()
        self.formatter = ReportFormatter()
        self.storage = ReportStorage()

    def export(self) -> str:
        data = self.reader.read()
        content = self.formatter.format(data)
        return self.storage.save(content)


print(ReportFacade().export())
```

调用方现在只需要 `export()`，不必掌握报表内部每一步。外观对象没有取代原来的子系统，只是提供了一条更简单的访问路径。高级调用方如果确实需要更细的能力，仍然可以直接使用底层接口。

这与应用服务有一定相似性：二者都可能协调多个组件。区别主要在设计意图。外观强调简化复杂子系统的使用界面；应用服务还要表达业务用例及其事务责任。实际项目可以由同一个类承担两者，但不能因为存在一个 `Facade` 就默认已经处理了事务和失败恢复。

### 4. 代理：在访问目标对象时增加控制

代理模式（Proxy）也通过包装对象工作，但它的重点是控制对目标对象的访问。访问控制、延迟加载、远程对象调用和缓存，都可以通过代理实现。

例如，下载文档前需要确认调用者有权限：

```python
from typing import Protocol


class DocumentStore(Protocol):
    def read(self, doc_id: str) -> str: ...


class MemoryDocumentStore:
    def read(self, doc_id: str) -> str:
        return f"文档内容：{doc_id}"


class AuthorizedStore:
    def __init__(self, target: DocumentStore, allowed_ids: set[str]):
        self.target = target
        self.allowed_ids = allowed_ids

    def read(self, doc_id: str) -> str:
        if doc_id not in self.allowed_ids:
            raise PermissionError("无权读取此文档")
        return self.target.read(doc_id)


store: DocumentStore = AuthorizedStore(MemoryDocumentStore(), {"doc-1"})
print(store.read("doc-1"))
```

装饰器与代理的代码形式可能很相似，都采用包装和委托。它们的区别主要在意图：装饰器面向功能叠加，代理面向访问控制或访问方式的替代。

示例权限集合只是为了表现机制。真实权限检查需要使用可信的用户身份和授权数据，并确保其他调用路径不能绕过这层检查。仅在某一个包装类中增加校验，不足以建立完整的安全边界。

### 5. 组合：让树形结构具有统一操作

文件夹可以包含文件，也可以包含其他文件夹。若调用方需要分别判断叶子节点和容器节点，递归处理代码就会到处出现类型判断。

组合模式（Composite）让叶子和组合对象提供共同的操作，并让组合对象把操作递归委托给子节点。

```python
from dataclasses import dataclass, field
from typing import Protocol


class Node(Protocol):
    def size(self) -> int: ...


@dataclass
class File:
    bytes: int

    def size(self) -> int:
        return self.bytes


@dataclass
class Folder:
    children: list[Node] = field(default_factory=list)

    def size(self) -> int:
        return sum(child.size() for child in self.children)


root = Folder([File(100), Folder([File(20), File(30)])])
print(root.size())  # 150
```

调用方无需关心节点究竟是文件还是文件夹，只要执行 `size()`。这种结构适合目录树、组织结构、表达式树和文档节点。

统一接口也有边界。文件与文件夹并不拥有完全相同的能力，比如添加子节点只对文件夹有意义。如果强行让所有节点实现 `add_child()`，叶子节点可能只能抛出异常，反而破坏接口的清晰性。示例只抽象了双方都能够正确提供的 `size()`。真实树结构还应防止意外形成循环引用，否则递归遍历可能无法终止。

### 6. 桥接：将两个独立变化维度拆开

通知消息有普通通知和紧急通知两种类型，也支持邮件、短信两种渠道。如果每种组合都创建一个类，就可能出现 `NormalEmailNotification`、`UrgentEmailNotification`、`NormalSmsNotification` 等类。消息类型和渠道继续增加时，组合数量会持续增长。

桥接模式（Bridge）通过组合，把两个能够独立变化的维度分开：

```python
from typing import Protocol


class Channel(Protocol):
    def send(self, text: str) -> str: ...


class EmailChannel:
    def send(self, text: str) -> str:
        return f"EMAIL: {text}"


class SmsChannel:
    def send(self, text: str) -> str:
        return f"SMS: {text}"


class Notification:
    def __init__(self, channel: Channel):
        self.channel = channel

    def content(self, text: str) -> str:
        return text

    def notify(self, text: str) -> str:
        return self.channel.send(self.content(text))


class UrgentNotification(Notification):
    def content(self, text: str) -> str:
        return f"[紧急] {text}"


print(UrgentNotification(SmsChannel()).notify("库存告警"))
```

通知类型决定内容如何表达，渠道决定如何发送。两个维度通过 `Channel` 契约连接，可以相对独立地扩展。

桥接与策略都有“持有一个接口对象”的形式。策略侧重在同一上下文中替换算法；桥接侧重把两个独立演化的抽象维度拆开。实践中无需仅凭类图判断模式名称，更重要的是是否确实存在这两个变化方向。

### 7. 享元：共享大量重复的不可变数据

如果一份文档有数十万个节点，每个节点都保存相同的字体、颜色和行高配置，可能造成不必要的内存占用。享元模式（Flyweight）让多个对象共享可以复用的内部状态。

```python
from dataclasses import dataclass
from functools import lru_cache


@dataclass(frozen=True)
class TextStyle:
    font: str
    size: int
    color: str


@lru_cache(maxsize=128)
def style_for(kind: str) -> TextStyle:
    if kind == "title":
        return TextStyle("Sans", 20, "black")
    return TextStyle("Sans", 12, "gray")


@dataclass
class TextNode:
    content: str
    style: TextStyle


first = TextNode("标题一", style_for("title"))
second = TextNode("标题二", style_for("title"))
assert first.style is second.style
```

这里共享的是不可变的 `TextStyle`，每个节点仍然保存自己的文本。享元常把可以共享的固有状态与每次使用时独有的外部状态分开。

如果数据量很小，共享机制可能比节省的内存更昂贵。对于可变状态，随意共享还可能让一个对象的修改影响其他对象。实际使用时应结合内存分析决定是否需要这种优化。

## 四、行为型模式：算法与对象应该怎样协作

创建型解决实例的产生，结构型解决实例的组合。行为型模式则进一步考虑：多个对象之间应该怎样分配职责，如何选择算法，怎样处理事件，以及如何组织一段允许变化的流程。

### 1. 策略：把可替换的算法交给不同实现

第三篇已经使用过定价规则的例子。策略模式（Strategy）可以把它理解为一种更一般的设计：上下文保持相同的工作目标，具体算法由一个满足契约的对象或函数提供。

在 Python 中，算法未必需要包装成只有一个方法的类。函数本身就可以作为策略：

```python
from collections.abc import Callable


def vip_discount(amount_cents: int) -> int:
    return (amount_cents + 5) // 10 if amount_cents >= 20_000 else 0


def full_reduction(amount_cents: int) -> int:
    return 6_000 if amount_cents >= 40_000 else 0


def quote(amount_cents: int, rule: Callable[[int], int]) -> int:
    if amount_cents < 0:
        raise ValueError("金额不能为负")
    discount = rule(amount_cents)
    if not 0 <= discount <= amount_cents:
        raise ValueError("优惠金额越界")
    return amount_cents - discount


print(quote(50_000, vip_discount))    # 45000
print(quote(50_000, full_reduction))  # 44000
```

`quote()` 只关心策略接受订单金额并返回合法的优惠值。新算法可以独立实现，报价流程不必新增活动类型判断。

策略的关键是替换算法。由谁选择策略是另一个问题，可以通过配置、工厂或调用方决定。如果所有算法其实只有一两行、数量稳定，直接使用条件分支可能更容易理解。若策略需要维护状态、多个协作方法或复杂依赖，再考虑 `Protocol` 或专门的策略类。

### 2. 状态：同一个操作在不同状态下有不同规则

策略模式与状态模式（State）的代码结构有时很像，都会把行为委托给另一个对象。不过，状态模式的变化通常由对象自身的生命周期驱动。

订单在草稿状态可以支付或取消，支付后不能再次支付，已取消订单不能再支付。若状态增多，每种操作内部可能都出现大量状态判断。

下面让状态对象决定操作是否合法，以及操作结束后进入什么状态：

```python
from typing import Protocol


class OrderState(Protocol):
    def pay(self, order: "Order") -> None: ...
    def cancel(self, order: "Order") -> None: ...


class Draft:
    def pay(self, order: "Order") -> None:
        order.state = Paid()

    def cancel(self, order: "Order") -> None:
        order.state = Canceled()


class Paid:
    def pay(self, order: "Order") -> None:
        raise ValueError("订单不能重复支付")

    def cancel(self, order: "Order") -> None:
        raise ValueError("已支付订单需走退款流程")


class Canceled:
    def pay(self, order: "Order") -> None:
        raise ValueError("已取消订单不能支付")

    def cancel(self, order: "Order") -> None:
        raise ValueError("订单已经取消")


class Order:
    def __init__(self):
        self.state: OrderState = Draft()

    def pay(self) -> None:
        self.state.pay(self)

    def cancel(self) -> None:
        self.state.cancel(self)


order = Order()
order.pay()
print(type(order.state).__name__)  # Paid
```

订单对象把操作委托给当前状态，状态实现负责决定下一步。这使不同状态的行为可以分别维护，并把状态转换规则明确表达出来。

但状态模式也不是状态机的唯一实现。对于只有几个状态和简单转换规则的系统，使用 `Enum` 配合一张转换表，通常更短且更容易检查。复杂订单还可能涉及数据库持久化、并发更新和外部支付事实；仅在内存中切换状态对象不能保证数据库中的状态一致性。状态模式解决的是行为组织问题，不是事务一致性问题。

### 3. 观察者：一个事件发生后通知多个关注者

创建订单后，可能需要刷新报表、记录审计信息、发送提醒。如果订单模块直接调用所有后续组件，就必须知道每个关注者的存在。未来增加一个订阅行为，还要修改订单模块。

观察者模式（Observer）让事件发生方维护一个订阅关系，在状态变化或事件发生时通知订阅者。下面用同步回调说明基本机制：

```python
from collections.abc import Callable
from dataclasses import dataclass


@dataclass(frozen=True)
class OrderCreated:
    order_id: int


class EventPublisher:
    def __init__(self):
        self._subscribers: list[Callable[[OrderCreated], None]] = []

    def subscribe(self, callback: Callable[[OrderCreated], None]) -> None:
        self._subscribers.append(callback)

    def publish(self, event: OrderCreated) -> None:
        for callback in tuple(self._subscribers):
            callback(event)


def record_audit(event: OrderCreated) -> None:
    print(f"审计记录：{event.order_id}")


def send_notice(event: OrderCreated) -> None:
    print(f"发送通知：{event.order_id}")


publisher = EventPublisher()
publisher.subscribe(record_audit)
publisher.subscribe(send_notice)
publisher.publish(OrderCreated(order_id=101))
```

发布者只知道应当通知订阅者，不再需要写死每一种后续处理逻辑。订阅者可以独立增加；如果系统还需要动态取消订阅，则应继续提供相应的取消接口，并处理回调身份与并发修改问题。

这个例子是**进程内同步通知**，不等于可靠消息队列。某个回调抛出异常时，后面的回调可能不执行；进程崩溃后，尚未通知的订阅者不会自动恢复。若业务要求数据库事务提交后可靠发布事件，就要进一步考虑事务性 Outbox、MQ、重试和幂等消费。观察者提供了一种依赖解耦方式，不提供跨进程持久化和至少一次投递保证。

### 4. 职责链：让请求依次经过多个处理者

一个 API 请求可能需要先检查身份，再检查请求频率，最后执行实际业务。把所有检查写进一个巨大函数，后续调整检查顺序或增加规则都会影响这个函数。

职责链模式（Chain of Responsibility）把处理者连成一条链。每个处理者可以处理、拒绝，或者将请求交给后继处理者。

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Request:
    authenticated: bool
    quota_remaining: int


class Handler:
    def __init__(self, next_handler: "Handler | None" = None):
        self.next_handler = next_handler

    def handle(self, request: Request) -> str:
        if self.next_handler is None:
            raise RuntimeError("没有处理者接收请求")
        return self.next_handler.handle(request)


class AuthHandler(Handler):
    def handle(self, request: Request) -> str:
        if not request.authenticated:
            raise PermissionError("身份验证失败")
        return super().handle(request)


class QuotaHandler(Handler):
    def handle(self, request: Request) -> str:
        if request.quota_remaining <= 0:
            raise ValueError("请求额度不足")
        return super().handle(request)


class BusinessHandler(Handler):
    def handle(self, request: Request) -> str:
        return "请求已处理"


pipeline = AuthHandler(QuotaHandler(BusinessHandler()))
print(pipeline.handle(Request(True, 3)))
```

这种结构与 Web 中间件、校验流水线很接近。职责链存在两类常见语义：有的请求在某个处理者处理成功后便停止传播，有的请求必须依次通过全部处理者。上面的代码属于后者，前两个处理者完成检查后继续传递。

链式处理带来的风险是执行路径不容易直接看见，还可能出现请求无人处理、异常被错误吞掉、处理顺序影响结果等问题。因此，需要明确终止条件、错误语义和可观测性，而不能只因为处理步骤较多就一定拆成链。

### 5. 命令：把一次操作变成可以传递的数据或对象

普通方法调用通常在调用发生时立即执行。但有些操作需要先被记录下来，稍后再执行；还有些操作要进入队列、支持重试或保留审计记录。

命令模式（Command）把一次操作及其所需参数表示为独立对象，再交给执行者处理。下面使用消息对象与处理器分离的写法：

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class CancelOrder:
    order_id: int
    reason: str


class OrderRepository:
    def cancel(self, order_id: int, reason: str) -> None:
        print(f"取消订单 {order_id}：{reason}")


class CancelOrderHandler:
    def __init__(self, repository: OrderRepository):
        self.repository = repository

    def handle(self, command: CancelOrder) -> None:
        self.repository.cancel(command.order_id, command.reason)


command = CancelOrder(order_id=101, reason="用户申请取消")
handler = CancelOrderHandler(OrderRepository())
handler.handle(command)
```

命令对象描述“希望执行什么操作”，处理器决定“怎样执行”。与直接调用仓储方法相比，这种组织方式便于在执行前做统一授权、记录、排队和分发。经典 GoF 命令对象也可以自行持有接收者并提供 `execute()`；上面的写法更适合把命令序列化为消息的场景。

不过，创建命令对象不会自动带来幂等性、撤销能力或可靠投递。重复执行取消命令是否安全，需要业务规则保证；命令进入真正的 MQ 后，还需要处理投递确认、消费失败和重试。撤销一条已经对外发送或支付成功的命令，通常也不是简单执行反向函数就能完成。

### 6. 模板方法：固定流程，开放部分步骤

在文件导入场景中，CSV、JSON 等文件的读取方式不同，但导入流程都可能包含解析、标准化、验证和保存。

模板方法模式（Template Method）在基类中固定整体流程，并把少数可变化的步骤交给子类实现。

```python
from abc import ABC, abstractmethod
import csv
import io
import json


class Importer(ABC):
    def run(self, text: str) -> list[str]:
        names = self.parse(text)
        cleaned = [name.strip() for name in names]
        return [name for name in cleaned if name]

    @abstractmethod
    def parse(self, text: str) -> list[str]:
        raise NotImplementedError


class CsvImporter(Importer):
    def parse(self, text: str) -> list[str]:
        rows = csv.DictReader(io.StringIO(text))
        return [row["name"] for row in rows]


class JsonImporter(Importer):
    def parse(self, text: str) -> list[str]:
        return [row["name"] for row in json.loads(text)]


print(CsvImporter().run("name\n Alice \n Bob \n"))
print(JsonImporter().run('[{"name":" Alice "}]'))
```

公共的标准化步骤只维护一次，具体文件格式负责自己的解析逻辑。这种结构适合一段流程的骨架稳定、只有部分步骤变化的情况。

模板方法主要通过继承实现扩展。与策略模式相比，它把可扩展步骤固定在基类和子类的关系中；策略则可以在运行时组合和替换算法。如果文件解析器需要动态注册或者不同步骤有多个独立变化维度，使用组合的处理流水线可能更灵活。

### 7. 迭代器：遍历数据时隐藏访问方式

调用方经常需要逐条处理记录，但数据可能来自列表、树结构或分页 API。迭代器模式（Iterator）把遍历状态和获取下一项的方式封装起来，让使用者通过统一的迭代接口读取元素。

Python 已经把这一思想内置在 `for`、`iter()`、`next()` 和生成器中。访问分页接口时，可以用生成器隐藏分页过程：

```python
from collections.abc import Callable, Iterator


def iter_orders(
    fetch_page: Callable[[str | None], tuple[list[int], str | None]],
) -> Iterator[int]:
    cursor: str | None = None
    while True:
        items, next_cursor = fetch_page(cursor)
        yield from items
        if next_cursor is None:
            break
        cursor = next_cursor


def fake_page(cursor: str | None) -> tuple[list[int], str | None]:
    if cursor is None:
        return [101, 102], "page-2"
    return [103], None


print(list(iter_orders(fake_page)))  # [101, 102, 103]
```

调用方只需要迭代订单编号，而不用自己维护游标与分页请求。生成器按需获取后续数据，不需要先把所有分页结果放进内存。

生产环境仍然要处理网络失败、重复游标、分页过程中数据变化和资源清理等问题。Python 语言已经提供完整的迭代协议，因此通常没有必要为了实现迭代器模式，再创建模仿 Java `hasNext()`、`next()` 的接口体系。

### 8. 中介者：集中管理多个对象的交互

如果多个组件彼此直接调用，关系很快会变复杂。例如，订单状态变化后可能影响支付按钮、取消按钮、操作日志和提示区域。每个组件直接知道其他所有组件，新增一个组件时可能需要修改大量交互代码。

中介者模式（Mediator）设置一个协调者，让组件把交互意图交给它，再由它决定怎样通知其他参与者。一个简单的消息聊天室可以展示这种结构：

```python
class ChatRoom:
    def __init__(self):
        self.members: dict[str, "Member"] = {}

    def join(self, member: "Member") -> None:
        self.members[member.name] = member

    def send(self, sender: str, receiver: str, text: str) -> None:
        self.members[receiver].receive(sender, text)


class Member:
    def __init__(self, name: str, room: ChatRoom):
        self.name = name
        self.room = room
        room.join(self)

    def send(self, receiver: str, text: str) -> None:
        self.room.send(self.name, receiver, text)

    def receive(self, sender: str, text: str) -> None:
        print(f"{self.name} 收到 {sender}：{text}")


room = ChatRoom()
a = Member("A", room)
b = Member("B", room)
a.send("B", "你好")
```

成员不持有彼此的引用，只知道协调者。中介者适合确实存在大量交互关系、又需要集中维护协调规则的情况。

但中介者也可能演变成新的巨型对象。倘若所有业务流程都塞进一个 `Manager` 或 `Coordinator`，只是把原来分散的复杂性集中到了一个地方。中介者有助于降低参与者之间的直接依赖，仍然需要明确自己的职责边界。

### 9. 备忘录：保存和恢复对象状态

文本编辑器的撤销功能，通常需要在修改前保存某个状态，以便将来恢复。备忘录模式（Memento）让对象可以保存自己的状态快照，而恢复方不必了解内部状态怎样表示。

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Snapshot:
    text: str


class Editor:
    def __init__(self):
        self._text = ""

    def write(self, text: str) -> None:
        self._text += text

    def snapshot(self) -> Snapshot:
        return Snapshot(self._text)

    def restore(self, snapshot: Snapshot) -> None:
        self._text = snapshot.text

    @property
    def text(self) -> str:
        return self._text


editor = Editor()
editor.write("第一版")
previous = editor.snapshot()
editor.write(" 第二版")
editor.restore(previous)
print(editor.text)  # 第一版
```

快照记录的是某个时点的状态。对复杂对象来说，复制完整对象可能很昂贵，甚至会包含数据库连接等不应复制的资源。实际系统可以只保存必要的状态、采用增量差异，或者使用事件记录重新计算状态。

备忘录并不等同于数据库事务回滚。事务回滚依赖数据库的事务机制，而应用层撤销可能跨越多次已提交操作，涉及外部副作用时尤其需要单独设计。

### 10. 访问者：给稳定的数据结构增加新的操作

假设系统拥有一棵表达式树，节点类型有数字和加法。除了计算表达式的值，我们还希望以后对同一棵树做格式化、分析或静态检查。

如果每增加一种操作，都必须修改所有节点类，就会让数据结构与操作不断耦合。访问者模式（Visitor）把针对各类节点的操作组织在一个独立的访问者中。

```python
from dataclasses import dataclass
from typing import Protocol, TypeVar


T = TypeVar("T")


class Visitor(Protocol[T]):
    def number(self, node: "Number") -> T: ...
    def add(self, node: "Add") -> T: ...


@dataclass(frozen=True)
class Number:
    value: int

    def accept(self, visitor: Visitor[T]) -> T:
        return visitor.number(self)


@dataclass(frozen=True)
class Add:
    left: "Number | Add"
    right: "Number | Add"

    def accept(self, visitor: Visitor[T]) -> T:
        return visitor.add(self)


class Evaluator:
    def number(self, node: Number) -> int:
        return node.value

    def add(self, node: Add) -> int:
        return node.left.accept(self) + node.right.accept(self)


expression = Add(Number(2), Add(Number(3), Number(4)))
print(expression.accept(Evaluator()))  # 9
```

节点的 `accept()` 根据自身的具体类型调用访问者中相应的方法。这样，新增另一种针对既有节点的操作，可以定义新的访问者，而不需要把该操作写进每一个节点类。

代价同样明确：如果经常新增节点类型，比如乘法、比较、函数调用，每个访问者都可能需要扩展新方法。因此，访问者更适合节点类型相对稳定、而针对这些节点的操作频繁增加的情况。

在现代 Python 中，某些表达式树处理也可以通过 `match`、普通函数或内置 `ast.NodeVisitor` 实现。是否需要自己建立完整访问者体系，应以具体扩展需求为依据。

### 11. 解释器：把一套小型规则表示成可执行结构

如果用户需要配置“VIP 且订单金额达到 200 元”这样的条件，系统可以把规则表示为数据，再由程序解释它的含义。解释器模式（Interpreter）围绕一套语言的语法结构，为不同表达式定义解释行为。

```python
from dataclasses import dataclass
from typing import Protocol


@dataclass(frozen=True)
class Context:
    level: str
    amount_cents: int


class Expression(Protocol):
    def evaluate(self, context: Context) -> bool: ...


@dataclass(frozen=True)
class IsVip:
    def evaluate(self, context: Context) -> bool:
        return context.level == "VIP"


@dataclass(frozen=True)
class AmountAtLeast:
    threshold: int

    def evaluate(self, context: Context) -> bool:
        return context.amount_cents >= self.threshold


@dataclass(frozen=True)
class And:
    left: Expression
    right: Expression

    def evaluate(self, context: Context) -> bool:
        return self.left.evaluate(context) and self.right.evaluate(context)


rule = And(IsVip(), AmountAtLeast(20_000))
print(rule.evaluate(Context("VIP", 30_000)))  # True
```

这里的 `IsVip`、`AmountAtLeast` 和 `And` 构成了一种极简规则语言。表达式可以通过组合形成更复杂的条件。

但这个示例只实现了表达式的内存表示与求值，没有实现将用户输入文本解析成表达式树的语法分析器。真实规则语言还需要考虑语法、类型检查、错误提示、表达式规模以及执行资源限制。尤其不能因为需要动态规则，就直接对用户输入调用 Python 的 `eval()`。

当规则语言很简单时，结构化 JSON 条件或普通配置可能足够；表达式不断增长后，也可以采用成熟的解析器或规则引擎。解释器模式适合确实要定义和执行一套语言的场景，不应把普通的 `if` 判断都改造成解释器。

## 五、相似模式的区分和选择技巧

学完这些模式后，很容易发现不同模式的代码结构高度相似。例如，适配器、装饰器和代理都可以持有另一个对象并转发方法；策略、状态和桥接都可能通过组合接口实现变化；工厂方法、抽象工厂和建造者都涉及创建对象。

仅凭“是否存在一个接口”“是否有一个包装类”来判断模式，往往无法得到可靠结论。模式真正的区别在它所解决的问题。

适配器的目标是转换不兼容接口；装饰器为已有行为附加额外职责；代理控制访问目标的过程。策略使算法可以替换，状态使对象在不同生命周期阶段表现不同，桥接则分开两个独立变化的维度。工厂方法将创建决定交给可扩展的子类，抽象工厂协调一组相关产品的创建，建造者强调复杂对象的构造步骤。

还要区分模式所解决的问题和框架已经提供的能力。Python 的函数是一等对象，很多单方法策略可以直接用函数。生成器已经实现了大部分日常迭代需求。标准库的 `copy`、`functools`、`abc`、`typing.Protocol` 和 `ast` 也为若干模式提供了成熟的语言机制。若现有机制足以表达意图，再额外建立一套仿照其他语言的类层次，通常不会改善设计。

一个实用的设计顺序是：先说明当前代码遇到的实际限制，再识别变化的来源，最后评估某种模式是否能够让这类变化更局部。需要关注新增接口、包装层、对象生命周期和测试成本，也需要考虑团队能否在不读遍整个项目的情况下理解这套协作结构。

有时最好的做法是保留条件分支。对于两个稳定且简单的算法，一个明确的 `if` 可能比一套策略注册中心更容易维护。类似地，为一个完全确定的流程建立抽象工厂，或者给每次函数调用都包装命令对象，可能只会增加代码数量和间接依赖。

模式还不能代替业务正确性。状态模式不会自动阻止数据库并发写入，观察者不会自动保证事件可靠投递，命令模式不会自动带来幂等处理，代理也不会自动形成完整的安全边界。使用模式前后，这些问题都必须由相应的数据库、消息与权限机制来保证。

## 六、从模式回到软件设计

前三篇文章建立了一条判断主线：让重要的设计决定拥有明确的职责归属，让其他模块只依赖必要且稳定的契约，并对额外抽象的成本保持警惕。

设计模式只是把这条主线落实到一些反复出现的问题中。创建型模式帮助我们管理对象创建时的依赖；结构型模式帮助我们连接不同接口、组合能力以及控制访问；行为型模式帮助我们安排算法、状态变化和对象之间的通信。

它们并没有规定一个项目必须包含多少个模式。真正有价值的设计，是在一个需求发生变化时，开发人员知道应当修改哪里，也能解释为什么其他部分不需要跟着变化。

设计模式值得学习，但不值得为了使用而使用。识别问题、理解依赖与行为契约，始终比准确说出模式名称更重要。

下一篇将进一步讨论领域驱动设计（DDD）与复杂业务系统的组织方式，研究当单个模块的边界不足以表达业务规则时，怎样通过领域模型、聚合和应用层协作管理复杂性。
