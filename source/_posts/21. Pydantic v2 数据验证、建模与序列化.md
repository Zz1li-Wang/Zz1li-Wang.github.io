Python 很容易处理字典。对于简单的数据，读取一个字段、转换类型，再判断取值范围，几行代码就能完成。

不过，Web 接口收到的请求通常比一个字典复杂。一个订单可能包含客户编号、多个商品、配送方式和备注。数据从 JSON 进入 Python 后，字段可能缺失，类型可能不符合预期，列表里的某一项还可能包含错误。

如果每个接口都自行解析这些数据，重复代码会越来越多。业务函数也很难知道自己拿到的是已经处理好的对象，还是未经检查的原始字典。

[Pydantic](https://docs.pydantic.dev/) 用来处理这件事。开发者通过 Python 类型注解描述数据结构，Pydantic 根据这些声明进行转换和验证，并提供把对象输出为字典、JSON 和 JSON Schema 的方法。FastAPI 的请求体验证也大量使用了它。

本文使用 Pydantic v2，逐步建立一个订单模型。下面示例以 Python 3.12 和 Pydantic v2 的 API 为基础，代码中的类型转换、默认值和序列化行为与 v1 有一些区别。

先安装依赖。

```bash
python -m pip install 'pydantic>=2,<3'
```

## 一、基本用法

先从一个只有两个字段的模型开始。

```python
from pydantic import BaseModel


class OrderItem(BaseModel):
    sku: str
    quantity: int


item = OrderItem(sku="book-001", quantity="2")

print(item)
print(type(item.quantity))
```

输出类似下面这样。

```text
sku='book-001' quantity=2
<class 'int'>
```

`OrderItem` 继承自 `BaseModel`。类中的类型注解告诉 Pydantic，`sku` 应当是字符串，`quantity` 应当是整数。

创建实例时，我们故意把 `quantity` 写成字符串 `"2"`。Pydantic 接受了这个输入，并把它转换为整数 `2`。因此，业务代码读取 `item.quantity` 时，拿到的是经过处理的值。

普通 Python 类型注解没有这个效果。下面的函数虽然声明了整数参数，运行时仍然可以收到字符串。

```python
def double(quantity: int) -> int:
    return quantity * 2


print(double("2"))  # 22
```

类型注解主要提供静态信息；Python 不会因此在每次函数调用时自动校验参数。`dataclass` 和 `TypedDict` 也不会默认把输入字符串转换为整数。

Pydantic 在模型创建时执行运行时验证，因而适合放在 HTTP 请求、消息队列、配置文件等外部数据进入程序的位置。

除了调用构造器，还可以把完整字典交给 `model_validate()`。

```python
payload = {"sku": "book-001", "quantity": "2"}
item = OrderItem.model_validate(payload)
```

两种写法都使用模型的验证规则。本文后面主要使用 `model_validate()`，这样更容易看出数据是从外部输入进入模型的。

这里有一个容易被忽略的细节：Pydantic 的验证不意味着输入必须原本就符合注解。默认情况下，它会在规则允许时进行类型转换。验证成功所保证的是得到的模型值符合约束，不能据此判断调用方最初发送的是什么类型。

## 二、字段约束

只有类型还不够。订单数量必须大于零，商品编号不能是空字符串，金额还需要限制精度。

Pydantic 使用 `Field()` 描述这些约束。

```python
from decimal import Decimal

from pydantic import BaseModel, Field


class OrderItem(BaseModel):
    sku: str = Field(min_length=1, max_length=64)
    quantity: int = Field(gt=0)
    unit_price: Decimal = Field(
        gt=0,
        max_digits=12,
        decimal_places=2,
    )
```

`min_length` 和 `max_length` 限制字符串长度，`gt=0` 表示必须大于零。`Decimal` 适合表达需要十进制精度的金额；`max_digits` 限制有效十进制数字总数，`decimal_places` 限制小数位数。

现在传入一份数据。

```python
item = OrderItem.model_validate({
    "sku": "book-001",
    "quantity": "2",
    "unit_price": "39.90",
})

print(item.quantity)                 # 2
print(item.unit_price)               # 39.90
print(type(item.unit_price))         # <class 'decimal.Decimal'>
```

字符串形式的数字分别转换为 `int` 和 `Decimal`。这里把金额写成字符串，是为了让十进制表示在进入 `Decimal` 之前不经过 JSON 浮点数的近似表示。对于金额接口，采用字符串金额或整数最小货币单位，都比依赖二进制浮点数更容易保持约定清楚。

如果将数量改为零，模型创建会失败。

```python
OrderItem.model_validate({
    "sku": "book-001",
    "quantity": 0,
    "unit_price": "39.90",
})
```

Pydantic 会抛出 `ValidationError`，其中包含 `quantity` 不满足大于零约束的信息。稍后会介绍怎样读取错误详情。

同一种约束需要在多个字段中使用时，可以通过 `Annotated` 给类型附加元数据。

```python
from typing import Annotated

PositiveQuantity = Annotated[int, Field(gt=0)]


class InventoryChange(BaseModel):
    quantities: list[PositiveQuantity] = Field(min_length=1)
```

这里有两层约束。`list[PositiveQuantity]` 要求列表中每个元素都能通过正整数验证，外面的 `Field(min_length=1)` 则要求列表至少包含一项。

常见的取值范围、字符串长度和容器大小，可以优先使用 `Field()`。它们不仅参与运行时验证，还会出现在能够表达这些约束的 JSON Schema 中。

## 三、必填字段与默认值

先看下面的模型。

```python
class OrderNote(BaseModel):
    title: str
    description: str | None
    note: str | None = None
    status: str = "pending"
```

`title` 没有默认值，所以必须提供。`description` 允许为 `None`，但仍然是必填字段。如果不传 `description`，验证会失败。

`note` 有默认值 `None`，因此可以省略。`status` 也可以省略，缺失时会使用 `"pending"`。

```python
order = OrderNote.model_validate({
    "title": "新订单",
    "description": None,
})

print(order.note)    # None
print(order.status)  # pending
```

这与部分开发者熟悉的 Pydantic v1 行为不同。v2 中，`str | None` 只表示取值允许包含 `None`；如果希望字段可以不传，还需要明确写出默认值。

有默认值也不意味着默认值一定会接受同样的验证。Pydantic 默认假定模型作者提供的默认值可信，因此不会验证它。

```python
class RetryPolicy(BaseModel):
    retries: int = "3"


policy = RetryPolicy()
print(type(policy.retries))  # <class 'str'>
```

这里实例属性仍然可能是字符串。需要检查默认值时，可以启用 `validate_default`。

```python
class RetryPolicy(BaseModel):
    retries: int = Field(default="3", validate_default=True)


policy = RetryPolicy()
print(policy.retries)       # 3
print(type(policy.retries)) # <class 'int'>
```

默认值如果需要在每次创建对象时动态生成，应使用 `default_factory`，例如为请求生成随机标识或创建当前时间。不要把需要每次重新计算的表达式直接写成类定义时求值的默认值。

## 四、嵌套模型

订单中通常不止一个商品。可以在前面的 `OrderItem` 基础上建立订单模型。

```python
from uuid import UUID

from pydantic import BaseModel, Field


class OrderCreate(BaseModel):
    customer_id: UUID
    items: list[OrderItem] = Field(min_length=1)
    note: str | None = None
```

`customer_id` 使用 `UUID`，`items` 使用 `list[OrderItem]`。Pydantic 不仅检查 `items` 是否是列表，还会根据 `OrderItem` 的定义处理每一个元素。

```python
payload = {
    "customer_id": "12345678-1234-5678-1234-567812345678",
    "items": [
        {
            "sku": "book-001",
            "quantity": "2",
            "unit_price": "39.90",
        }
    ],
}

order = OrderCreate.model_validate(payload)

print(type(order.customer_id))  # <class 'uuid.UUID'>
print(type(order.items[0]))     # <class '__main__.OrderItem'>
print(order.items[0].quantity)  # 2
```

原始输入是嵌套字典，验证后的 `order.items[0]` 却是 `OrderItem` 实例。访问字段时可以使用 `order.items[0].quantity`，不必在每一层处理字典键。

如果第二个商品的数量错误，Pydantic 会把错误位置记录为 `items`、下标 `1` 和字段 `quantity`。这使框架能够指出一个复杂 JSON 中具体哪个位置不符合要求。

不过，并非所有字典都需要建成模型。结构长期稳定、有明确约束的对象适合使用 `BaseModel`；对于键集合确实动态的元数据，带有键和值类型约束的 `dict` 有时更合适。

## 五、额外字段与字段别名

下面给请求增加一个未声明的字段。

```python
payload["debug"] = True
order = OrderCreate.model_validate(payload)
print(order.model_dump())
```

默认情况下，Pydantic 会忽略没有定义的字段。因此，`debug` 不会出现在模型输出中。这种行为有利于兼容上游增加的新字段，但也可能掩盖调用方的拼写错误。

如果接口希望严格限定请求结构，可以使用 `ConfigDict`。

```python
from pydantic import ConfigDict


class OrderCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")

    customer_id: UUID
    items: list[OrderItem] = Field(min_length=1)
    note: str | None = None
```

这时，传入 `debug` 会得到 `extra_forbidden` 错误。`extra` 还有 `ignore` 和 `allow` 两种设置，分别表示忽略和保留额外字段。

对写入接口来说，拒绝未声明字段通常更容易及时发现协议错误；读取第三方 API 响应时，如果上游允许增加字段，忽略额外字段可能更实用。应该按照数据边界的兼容要求选择。

外部 JSON 还有一个常见问题：字段名可能采用 camelCase，而 Python 习惯使用 snake_case。例如请求发送 `customerId`，程序希望使用 `customer_id`。

```python
from pydantic import Field


class OrderCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")

    customer_id: UUID = Field(
        validation_alias="customerId",
        serialization_alias="customerId",
    )
    items: list[OrderItem] = Field(min_length=1)
    note: str | None = None
```

`validation_alias` 指定读取输入时使用的名称，`serialization_alias` 指定输出时使用的名称。模型内部的属性仍叫 `customer_id`。

```python
order = OrderCreate.model_validate({
    "customerId": "12345678-1234-5678-1234-567812345678",
    "items": [{
        "sku": "book-001",
        "quantity": 2,
        "unit_price": "39.90",
    }],
})

print(order.customer_id)
print(order.model_dump(by_alias=True).keys())
```

这里 `by_alias=True` 让输出采用 `customerId`。如果还希望输入同时接受 Python 属性名 `customer_id`，可以在模型配置中设置 `validate_by_name=True`；具体要不要开放这种别名，取决于外部接口契约。

## 六、联合类型

订单还可能有不同的履约方式。配送订单需要地址，自提订单需要门店编号。

先定义两个模型。

```python
from typing import Annotated, Literal


class Delivery(BaseModel):
    kind: Literal["delivery"]
    address: str = Field(min_length=1)


class Pickup(BaseModel):
    kind: Literal["pickup"]
    store_id: UUID
```

`Literal` 将 `kind` 限定为指定字符串。然后把它们组成联合类型。

```python
Fulfillment = Annotated[
    Delivery | Pickup,
    Field(discriminator="kind"),
]
```

现在可以把订单中的 `fulfillment` 声明为 `Fulfillment`。

```python
class OrderCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")

    customer_id: UUID = Field(
        validation_alias="customerId",
        serialization_alias="customerId",
    )
    items: list[OrderItem] = Field(min_length=1)
    fulfillment: Fulfillment
    note: str | None = None
```

验证下面的输入时，Pydantic 会根据 `kind` 的值选择 `Delivery` 模型。

```python
payload = {
    "customerId": "12345678-1234-5678-1234-567812345678",
    "items": [{
        "sku": "book-001",
        "quantity": "2",
        "unit_price": "39.90",
    }],
    "fulfillment": {
        "kind": "delivery",
        "address": "Shanghai",
    },
}

order = OrderCreate.model_validate(payload)
print(type(order.fulfillment))  # <class '__main__.Delivery'>
```

普通的 `Delivery | Pickup` 也可以验证联合类型，但 Pydantic 需要根据各分支的规则判断哪个模型更匹配。v2 的默认 smart union 策略可能在小版本中调整匹配细节。

对于有明确类型标记的业务数据，`discriminator` 更直接。一个固定字段决定使用哪个模型，验证错误也更容易定位。生成 JSON Schema 时，这个判别关系还可以成为接口文档的一部分。

## 七、自定义验证器

`Field()` 能表达单个字段的常见约束。有些规则需要编写 Python 代码，例如去掉备注两端的空格，或者检查订单中不能出现重复商品编号。

这时可以使用验证器。

```python
from typing import Self
from pydantic import field_validator, model_validator


class OrderCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")

    customer_id: UUID = Field(
        validation_alias="customerId",
        serialization_alias="customerId",
    )
    items: list[OrderItem] = Field(min_length=1)
    fulfillment: Fulfillment
    note: str | None = None

    @field_validator("note")
    @classmethod
    def normalize_note(cls, value: str | None) -> str | None:
        if value is None:
            return None
        return value.strip() or None

    @model_validator(mode="after")
    def check_duplicate_skus(self) -> Self:
        skus = [item.sku for item in self.items]
        if len(skus) != len(set(skus)):
            raise ValueError("订单项中的 SKU 不能重复")
        return self
```

`@field_validator` 默认在字段完成类型验证之后运行，也就是 `mode="after"`。这个例子中，验证器收到的已经是 `str` 或 `None`，可以直接处理字符串。

验证器需要返回处理后的值。如果忘记 `return`，字段最终可能变成 `None`，造成后续验证或业务逻辑错误。

如果需要先兼容某种旧格式，再交给 Pydantic 处理，可以使用 `mode="before"`。这时函数收到的是尚未完成类型转换的原始输入，可能是字符串、列表、字典，也可能是其他 Python 对象，因此需要自己判断类型。

Pydantic v2 还提供 plain 和 wrap 验证器。plain 可以接管字段验证，跳过后续内部验证；wrap 则通过一个 handler 决定如何调用或包裹默认验证流程。这些模式适合需要特殊控制验证过程的情况，普通业务约束通常从 after 验证器开始就够了。

重复商品编号是另一种规则。它需要查看整个订单的 `items`，因此在同一个模型里增加了 `@model_validator(mode="after")`。模型级 after 验证器运行时，各个字段已经完成验证，可以直接读取 `self.items`，最后返回 `self`。如果订单包含两个相同的 SKU，函数会抛出 `ValueError`，由 Pydantic 整理为验证错误。

需要注意，字段验证器可以访问的其他字段受到字段定义顺序影响。如果规则必须同时依赖多个字段，模型级验证器通常更清楚。

验证器适合处理只由当前输入决定的规则。库存是否足够、客户有没有权限下单、订单是否已经支付，都需要数据库或其他外部状态。这些检查应该由业务服务在适当的事务和权限上下文中完成。把数据库查询和网络调用塞进模型验证器，会使对象创建产生隐含 I/O，也会让测试和复用变得困难。

自定义验证器通常用 `ValueError` 表示数据不满足规则。不要使用 `assert` 作为生产校验，因为 Python 在优化模式下可能移除断言。另外，Pydantic v2 不会自动把验证器中的 `TypeError` 包装为 `ValidationError`；这有助于暴露验证器本身的编程错误。

## 八、验证错误

Pydantic 验证失败时，会抛出 `ValidationError`。这个异常除了提供可阅读的错误文本，还可以返回结构化的错误列表。

```python
from pydantic import ValidationError

bad_payload = {
    "customerId": "not-a-uuid",
    "items": [{
        "sku": "",
        "quantity": 0,
        "unit_price": "free",
    }],
    "fulfillment": {
        "kind": "delivery",
    },
    "unknown": True,
}

try:
    OrderCreate.model_validate(bad_payload)
except ValidationError as exc:
    for error in exc.errors():
        print(error["loc"], error["type"])
```

在定义了 `extra="forbid"`、使用判别联合的模型中，主要错误位置大致如下。

```text
('customerId',) uuid_parsing
('items', 0, 'sku') string_too_short
('items', 0, 'quantity') greater_than
('items', 0, 'unit_price') decimal_parsing
('fulfillment', 'delivery', 'address') missing
('unknown',) extra_forbidden
```

`loc` 表示错误在数据中的位置，`type` 是可供程序判断的错误代码，`msg` 则是面向人的错误说明。错误项还可能带有原始输入和额外上下文。

对于 Web API，可以使用 `loc` 把错误对应到具体表单字段，再把内部错误转换为统一的 HTTP 响应。程序逻辑不应依赖英文 `msg` 的具体措辞；它可能随版本或本地化方式变化。

如果把异常写入日志，也要注意原始输入可能包含密码、令牌等敏感内容。结构化错误便于处理，但不能不经筛选就全部记录。

## 九、类型转换与严格模式

前面的例子中，字符串 `"2"` 被转换为了整数。Pydantic 默认使用宽松验证模式，即按照目标类型规定的规则接受部分可以转换的输入。

这种行为适用于 HTTP 查询参数和环境变量。它们通常以字符串的形式传递，即使逻辑上表示的是整数、布尔值或日期。

不过，有些内部命令要求调用方必须已经提供正确的 Python 类型。这时可以启用严格模式。

```python
class StrictCommand(BaseModel):
    model_config = ConfigDict(strict=True)

    retries: int
    enabled: bool


StrictCommand.model_validate({
    "retries": 3,
    "enabled": True,
})
```

如果把 `retries` 改为字符串 `"3"`，或把 `enabled` 改为字符串 `"true"`，Python 模式下的严格验证会拒绝它们。除了模型级配置，也可以使用字段级的 `Field(strict=True)`，或在调用 `model_validate()` 时传入 `strict=True`。

严格模式还有一个重要细节：Python 输入与 JSON 输入不完全相同。

```python
from datetime import date


class Event(BaseModel):
    id: UUID
    day: date
    count: int
```

从 Python 字典验证时，严格模式一般要求 `id` 和 `day` 已经是对应的 Python 对象。

```python
Event.model_validate({
    "id": "12345678-1234-5678-1234-567812345678",
    "day": "2026-10-15",
    "count": 1,
}, strict=True)  # UUID 和 date 字符串会导致错误
```

但 JSON 没有 UUID 和日期类型。通过 `model_validate_json()` 使用严格模式时，Pydantic 对这些类型允许特定的字符串表示。

```python
raw_json = '''{
  "id": "12345678-1234-5678-1234-567812345678",
  "day": "2026-10-15",
  "count": 1
}'''

Event.model_validate_json(raw_json, strict=True)
```

这段 JSON 可以通过验证。严格模式控制的是在当前输入模式下允许哪些转换，不能简单理解成所有类型都绝对禁止字符串形式。

遇到边界值时，还应该查阅官方的 [Conversion Table](https://docs.pydantic.dev/latest/concepts/conversion_table/)。宽松模式不是任意强制类型转换，例如带有非零小数部分的浮点数也不能无条件变成整数。

## 十、读取不同来源的数据

目前使用的是 `model_validate()`，它接收 Python 对象。如果拿到的是原始 JSON 字符串或字节，可以使用：

```python
order = OrderCreate.model_validate_json(raw_order_json)
```

`model_validate_json()` 同时完成 JSON 解析和模型验证，不需要先手动执行 `json.loads()`。此外，它使用 JSON 模式，因此严格验证时的规则可能与 Python 模式不同。

如果数据来自一个普通对象或 ORM 实例，可以配置 `from_attributes=True`，让 Pydantic 从对象属性读取字段。

```python
class UserRead(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    name: str


user = UserRead.model_validate(orm_user)
```

这个设置只改变字段的读取方式。它不会负责打开数据库 Session、预加载关联对象或者控制事务。对于 SQLAlchemy ORM，访问属性可能触发延迟加载；如果对象已经脱离 Session，或者异步 ORM 在错误的上下文中触发了隐式 I/O，验证仍然可能失败。

有时需要验证的并不是一个具名模型，而是单独的 `list[OrderItem]`。可以使用 `TypeAdapter`。

```python
from pydantic import TypeAdapter

items_adapter = TypeAdapter(list[OrderItem])

items = items_adapter.validate_python([{
    "sku": "book-001",
    "quantity": "2",
    "unit_price": "39.90",
}])
```

验证后，`items` 是包含 `OrderItem` 实例的列表。`TypeAdapter` 也提供 JSON 验证、序列化和 JSON Schema 生成功能。

适配器会为目标类型准备验证 schema。高频循环中最好创建一次并复用，不必每次处理数据都重新创建相同类型的适配器。

## 十一、序列化

到这里，我们把外部数据转换成了 Python 对象。接口返回响应时，还需要把模型重新转换为适合传输的数据。

Pydantic 提供 `model_dump()` 和 `model_dump_json()`。

```python
python_data = order.model_dump()
json_data = order.model_dump(mode="json")
json_text = order.model_dump_json()
```

默认的 `model_dump()` 返回 Python 字典，并递归处理嵌套模型。不过，UUID、`Decimal`、日期等值可以继续保持 Python 对象，因此结果不一定能直接交给标准库的 `json.dumps()`。

`model_dump(mode="json")` 同样返回 Python 字典，但会把不能直接用 JSON 表达的对象转换成兼容的表示。例如 UUID 和 `Decimal` 通常会变成字符串。

`model_dump_json()` 则直接返回 JSON 字符串。这三种输出的用途不同，调用时应该先明确接收方需要的是 Python 数据还是 JSON 文本。

如果模型配置了别名，可以在序列化时传入 `by_alias=True`。

```python
order.model_dump(mode="json", by_alias=True)
```

这样输出的键可以使用外部协议中的 `customerId`。如果只需要部分字段，还可以使用 `include` 或 `exclude`。

```python
order.model_dump(
    include={"customer_id", "items"},
    mode="json",
)
```

部分更新接口更需要注意“没有提供字段”与“明确提供空值”的区别。

```python
from typing import Literal


class OrderPatch(BaseModel):
    note: str | None = None
    status: Literal["pending", "paid"] | None = None


patch = OrderPatch.model_validate({"note": None})

print(patch.model_fields_set)                # {'note'}
print(patch.model_dump(exclude_unset=True))  # {'note': None}
```

输入只设置了 `note`，并且明确要求把它设为 `None`。`status` 没有出现，虽然它的默认值同样是 `None`，却不应该被当成一次更新请求。`exclude_unset=True` 正好可以保留这个区别。

不过，`model_fields_set` 反映的是当前模型状态。模型创建后再给某个字段赋值，该字段也会被认为已经设置。它不是原始请求的永久快照。

需要特殊输出格式时，可以使用 `@field_serializer` 或 `@model_serializer`。例如 API 规定日期必须采用某种格式，可以在序列化阶段统一转换。序列化器不会改变模型内部的值，因此应把输入校验与输出协议分别处理。

Pydantic v2 还有一个值得注意的默认行为。假设字段注解为 `User`，但实际保存的是带有 `password` 的 `UserLogin` 子类对象。

```python
class User(BaseModel):
    name: str


class UserLogin(User):
    password: str


class Response(BaseModel):
    user: User


response = Response(
    user=UserLogin(name="alice", password="secret")
)

print(response.model_dump())
# {'user': {'name': 'alice'}}
```

外层按照声明的 `User` 类型序列化，默认不会带出子类额外声明的 `password`。如果确实要根据运行时具体类型输出所有字段，可以使用 `SerializeAsAny` 或 `serialize_as_any=True`，但要事先确认不会意外输出敏感信息。

## 十二、验证后的对象还会变化吗

正常验证完成后，模型中的数据满足当时的约束。但 `BaseModel` 默认是可变的，而且给字段重新赋值通常不会再次执行验证。

```python
class UserAge(BaseModel):
    age: int


user = UserAge(age=20)
user.age = "unknown"
print(user.age)  # unknown
```

为了在属性赋值时验证，可以使用 `validate_assignment=True`。

```python
class UserAge(BaseModel):
    model_config = ConfigDict(validate_assignment=True)
    age: int
```

此时，把字符串 `"unknown"` 赋给 `age` 会失败。需要阻止普通属性重新赋值时，可以使用 `frozen=True`。

但是，这两种配置都不等于递归保护整棵对象图。字段里如果包含可以原地修改的列表或字典，直接修改其中的元素不一定触发模型级验证；`frozen=True` 也不会自动深度冻结它们。

另外，Pydantic 提供一些有意绕过验证的接口。

```python
copy = user.model_copy(update={"age": "unknown"})
```

`model_copy(update=...)` 不验证 `update` 中的新值。它假定调用者传入的更新数据可信。

`model_construct()` 更直接，它允许不执行完整验证就创建模型。这样既不会自动转换 UUID 字符串，也不会把嵌套字典递归转换成模型实例。只有已经在可信路径完成验证的数据，才适合考虑这种接口。

即使再次调用 `model_validate()`，传入的如果本身就是同类模型实例，默认也可能被视为已经验证过。需要对已有实例重新验证，可以研究 `revalidate_instances` 配置。

因此，Pydantic 的类型保证依赖于正常验证流程和后续使用方式。绕过验证、修改可变对象后，不能继续假设模型会永远保持合法。

## 十三、JSON Schema 与内部实现

Pydantic 不只用模型执行验证，还可以从模型定义生成 JSON Schema。

```python
schema = OrderCreate.model_json_schema()
```

生成结果包含字段类型、必填要求、数值约束、嵌套模型和联合类型的描述。FastAPI 等框架可以利用它生成 OpenAPI 文档，使客户端知道请求和响应应采用什么结构。

输入验证与输出序列化可能使用不同的别名、字段规则和自定义逻辑。因此，Pydantic 允许分别生成两种模式的 schema。

```python
input_schema = OrderCreate.model_json_schema(mode="validation")
output_schema = OrderCreate.model_json_schema(mode="serialization")
```

JSON Schema 也有表达能力的限制。`quantity > 0` 可以转成标准数值约束，但自定义验证器里“订单中的 SKU 不允许重复”这样的 Python 规则，通常不能完整地自动投影为通用 JSON Schema。客户端通过 Schema 检查，并不能保证服务端所有验证都会成功。

Pydantic v2 的运行机制可以再往下看一层。定义模型时，Pydantic 收集类型注解、字段约束、配置和验证器，建立一份内部的 core schema。实际验证和序列化的核心工作由 `pydantic-core` 执行，其中主要部分用 Rust 编写。

```text
模型定义、字段约束、验证器
            ↓
        Core Schema
            ↓
    pydantic-core 执行
       ↙          ↘
  输入验证        输出序列化
```

这套设计使重复执行同一种验证不需要每次重新解释所有字段定义，也是 Pydantic v2 相比 v1 的一项重要实现变化。不过，自定义 Python 验证器仍然需要执行 Python 代码，涉及数据库或网络的操作也不会因为使用了 Pydantic 而变快。

## 十四、在项目中怎样使用

对于一个 Web 应用，通常可以分别定义创建请求、部分更新和读取响应的模型，例如 `OrderCreate`、`OrderPatch` 与 `OrderRead`。

创建请求需要验证客户、商品及配送信息，但不应该要求调用方提供数据库 ID 和创建时间。读取响应则可能包含订单编号、状态和创建时间。数据库 ORM 模型还涉及持久化字段、关联加载和 Session 生命周期。这几种对象的用途不同，没必要强行合并为一个类。

业务服务可以在入口处接收验证后的数据，再根据数据库状态、权限和业务事务处理订单。对于简单的应用，直接使用 Pydantic 模型作为应用层输入 DTO 并没有问题；对于约束复杂的领域模型，可以在边界完成验证后，再转换为相应的领域对象。

如果输入来自不同来源，同样需要确定何处建立验证边界。HTTP 请求、消息队列、文件导入和第三方 API 响应都可能携带未经验证的数据。从数据库重新读出、跨进程传递或者经过不可信代码修改后，也可能需要再次验证。没有必要机械地在每一层重复调用 `model_validate()`。

还有两个迁移细节。Pydantic v2 将应用配置管理所用的 `BaseSettings` 移到了独立的 `pydantic-settings` 包。环境变量和 `.env` 文件具有自己的来源优先级与加载生命周期，不建议用普通请求模型顺带承担整套配置管理。

从 v1 升级时，常见方法名称也发生了变化。

```text
dict()          → model_dump()
json()          → model_dump_json()
parse_obj()     → model_validate()
construct()     → model_construct()
copy()          → model_copy()
```

此外，`orm_mode` 改为 `from_attributes`，旧式 `@validator` 和 `@root_validator` 应迁移到相应的新验证器接口。不过，迁移不能只替换方法名。必填字段、类型转换、默认值、联合类型和子类序列化等行为都有变化，最好使用实际输入和预期 JSON 输出重新执行测试。

## 十五、结语

Pydantic 适合处理程序边界处的数据。通过 `BaseModel` 和类型注解，可以把原始字典或 JSON 转成具有稳定字段类型的 Python 对象；`Field()` 和验证器负责补充约束；`ValidationError` 让失败位置可供程序处理；序列化接口则把对象转成外部协议需要的格式。

使用时需要记住，模型验证成功只说明经过这次验证得到的数据满足了当时的规则。默认类型转换会改变输入表示，模型可以被后续代码修改，自定义验证器也不能取代数据库事务和权限检查。

对于多数项目，从简单的 `BaseModel`、`Field()`、嵌套模型和 `model_dump()` 开始就可以解决大量问题。遇到跨字段规则、复杂联合类型或特殊输出协议时，再引入相应机制。模型越清楚，程序里需要反复处理原始字典的地方就越少。
