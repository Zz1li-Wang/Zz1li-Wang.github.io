上一篇文章讨论了模块化、内聚、耦合和信息隐藏。我们希望将容易变化的设计决定安排在明确的职责边界内，让其他模块通过稳定的契约使用它们。

但这个目标还没有回答一个实际问题：一个后端项目往往包含 HTTP 接口、业务规则、数据库操作和外部服务调用，这些代码究竟应该如何组织？

刚开始写 FastAPI 时，把所有内容写进路由函数十分方便。接口接收请求，读取数据库，检查条件，保存结果，再返回响应。几十行代码就能完成一个功能。

业务稍微复杂一些，问题就出现了。创建订单需要计算价格、扣减库存和保存记录；后台管理系统也要创建订单；定时任务可能需要取消超时订单；未来还可能由消息消费者触发同样的操作。如果这些流程各自维护业务规则，上一篇文章讨论的变化传播便会再次出现。

MVC 与分层架构都与职责分离有关，但它们的出发点、适用场景和具体结构并不完全相同。理解它们，需要从各自要解决的问题说起。

## 一、示例：差劲的代码

### 1. 从路由函数开始

下面是一段简化的订单创建代码。为了突出结构，假定请求参数已经完成基本校验，商品价格以分为单位存储。

```python
@router.post("/orders")
async def create_order(data: OrderCreate, session: AsyncSession = Depends(get_session)):
    product = await session.get(Product, data.product_id)
    if product is None:
        raise HTTPException(404, "商品不存在")

    amount = product.price_cents * data.quantity
    discount = (amount + 5) // 10 if data.level == "VIP" and amount >= 20000 else 0

    if product.stock < data.quantity:
        raise HTTPException(409, "库存不足")

    product.stock -= data.quantity
    order = Order(product_id=product.id, quantity=data.quantity,
                  payable_cents=amount - discount)
    session.add(order)
    await session.commit()
    return {"order_id": order.id}
```

这段代码能表达创建订单的主要步骤，却把几种不同性质的决定放在了一起。`HTTPException` 和路由装饰器属于 HTTP 协议；优惠计算属于定价规则；库存检查属于业务约束；`session.get()`、`session.add()` 和 `commit()` 则涉及数据库访问与事务。

当优惠门槛调整时，需要修改接口实现。新增一个批量创建入口时，需要重新组织相同的业务步骤。更换存储方式时，接口里的数据库代码也会受到影响。

此外，这段代码还存在并发问题。先读取 `stock` 再执行 `product.stock -= quantity`，在并发事务下可能发生超卖或更新丢失，具体表现取决于数据库及事务隔离行为。仅仅把这些语句搬到另一个文件，并不能消除问题。

我们需要先把不同的变化原因辨认出来，再考虑让谁负责维护它们。

### 2. 入口、业务与存储具有不同的变化原因

HTTP 接口可能因为 URL、认证方式、请求格式或错误码而变化。业务规则可能因为销售政策、库存约束或订单状态流转而变化。数据库访问可能因为索引、查询方式、表结构或存储技术而变化。

这些变化有时同时发生，但并不总是同时发生。让每一类决定都有相对明确的归属，就可以减少无关修改之间的牵连。

由此产生了两种常见的组织思路。一种重点研究用户界面如何与业务模型协作，即 MVC；另一种把应用按职责划分为若干层次，即分层架构。

## 二、MVC

要理解 MVC 在现代 Web 项目中的含义，需要先回到它最初试图解决的界面协作问题。
### 1. 从图形界面到 Model、View、Controller

MVC 是 Model–View–Controller 的缩写，起源于 Smalltalk 图形用户界面的设计实践，通常追溯到 Trygve Reenskaug 在 20 世纪 70 年代末的工作。

在图形界面中，同一份应用状态可能被多个窗口或控件展示。用户点击按钮、拖动元素或者输入内容，界面需要处理操作，业务状态也可能随之改变。如果负责显示的代码同时维护全部业务规则，那么更改界面布局就容易影响业务逻辑，增加一种显示方式也可能迫使开发者复制同一组规则。

MVC 试图把这些责任区分开。Model 表示应用关心的状态及其相关行为；View 负责将状态呈现给用户；Controller 处理用户输入，并根据交互语义协调相应动作。

在经典 Smalltalk MVC 中，View 可以观察 Model 的变化并更新显示，Controller 主要解释来自输入设备的事件。Model、View 和 Controller 的关系并不是所有场景下都遵循“Controller 调用 Model，再调用 View”的单一路径。它们可以有各自的协作方式，具体取决于界面框架和 MVC 的实现形式。

MVC 中影响最深远的思想，是将表现相关的代码与业务状态及规则分开。业务模型不必知道自己被显示成表格还是图形，不同视图也可以在共同的模型之上工作。

### 2. Web 框架中的 MVC

Web 应用与早期桌面图形界面不同。传统服务端 Web 程序需要处理一次 HTTP 请求，执行操作，再生成 HTML 响应。很多框架因此把请求入口称为 Controller，把模板称为 View，把持久化对象或业务部分称为 Model。

这种称呼十分普遍，但它与经典 MVC 并不完全等价。请求处理器通常按一次请求的生命周期工作，浏览器与服务器之间也不会直接共享一个可以通知视图更新的内存对象。现代前端还可能独立负责渲染，后端只返回 JSON。

例如，FastAPI 中的路由函数负责接收 HTTP 请求、执行参数校验后的处理逻辑并返回响应。我们可以把它视为一种控制器式的入口，但 FastAPI 并没有要求使用传统 MVC 的三部分结构。

对于只提供 JSON API 的后端，响应模型和序列化代码属于对外表现的一部分，却不能简单认定为经典 MVC 中的 View。业务领域中的 Model 也不等于某个 SQLAlchemy ORM 类；ORM 映射对象主要描述 Python 对象与数据库表之间如何对应，它是否承担业务行为，取决于具体设计。

因而，看到项目里有 `models/`、`views/` 和 `controllers/` 三个目录，并不足以判断它是否有效地实现了职责分离。名称沿用了 MVC，代码中真正的依赖关系仍需要单独检查。

### 3. MVC 与后端分层关注不同维度

如果把 MVC 的三个名称直接对应为 `Controller → Service → Repository`，会得到一个看似整齐却不准确的解释。Service 不是 MVC 中的 View，Repository 也不是 MVC 中的 Model。

MVC 主要讨论界面交互、表现与应用状态的关系。分层架构则可以覆盖整个应用，包括接口适配、业务处理、数据访问以及其他基础设施。

一个 Web 系统可以在表现部分使用 MVC，同时在服务端采用分层结构。两者可以组合，也可以分别存在，不是相互排斥的架构选项。

## 三、分层架构

理解了 MVC 的关注范围以后，可以继续考察后端项目中的分层架构。
### 1. 层次是对职责和依赖的约束

分层架构（Layered Architecture）将系统中的不同职责组织成若干逻辑层，每一层对外提供某类能力，并通过明确的接口使用其他层的能力。

在许多企业应用中，一种经典划分是表现层、领域或业务逻辑层、数据源层。表现层负责用户交互或 API 协议，业务逻辑层解释业务规则，数据源层负责数据库及其他持久化细节。

在 Python Web 项目中，经常看到更具体的 `Router → Service → Repository`。可以粗略理解为：Router 负责 HTTP 入口，Service 负责一个业务用例，Repository 负责数据访问。不过，这只是常见实现，并不是分层架构的完整定义，更不是必须使用的唯一目录结构。

“层”首先是逻辑概念。三个层完全可以运行在同一个 Python 进程中，共用一个代码仓库和数据库。把它们拆成不同目录不会自动变成微服务，把它们部署到不同机器也不能自动保证职责合理。

这里还要区分层与部署中的 Tier。Layer 侧重代码职责和逻辑依赖；Tier 通常描述运行或部署上的物理划分。所谓三层架构有时指逻辑分层，有时指浏览器、应用服务器和数据库三个部署层次，具体含义必须结合上下文判断。

### 2. 请求的执行顺序与代码依赖

一次创建订单的请求可能按如下顺序执行：HTTP 请求到达 Router；Router 将业务输入交给 Service；Service 查询商品、计算报价、扣减库存并创建订单；Repository 通过 ORM 操作数据库；结果最终被转换成 HTTP 响应。

这描述的是运行时的调用路径。静态依赖还要看各模块在源代码中引用了什么。如果 Service 直接导入 `HTTPException`，就意味着业务用例知道了 HTTP 错误的表达方式。若希望同一个业务用例被命令行或消息消费者复用，这种依赖会造成障碍。

反过来，Router 知道如何调用创建订单的 Service，是一种合理依赖。它需要明确业务能力的名称、参数及返回结果，但不需要知道库存采用什么 SQL 更新语句。

分层架构通常鼓励依赖具有清晰方向，但不必强制每一次调用都经过所有层。一个简单的只读查询未必需要经过复杂的领域模型；一个纯计算函数也不应为了遵循目录结构而先访问 Repository。设计目标是控制知识依赖，具体的调用路径可以根据职责调整。

### 3. 依赖的方向为什么重要

假设我们以后为订单系统增加 MCP 工具或消息消费者。如果创建订单的完整逻辑位于 HTTP Router 中，新入口为了复用它，就可能需要伪造 HTTP 请求、调用路由函数，或者复制代码。

如果有一个不依赖 HTTP 的创建订单用例，新的入口可以直接调用它。这样 HTTP、定时任务和消息处理成为不同的输入适配方式，业务操作保持相同。

这反映了分层的重要价值：变化频繁的技术入口不应迫使核心业务规则跟着变化。规则越具有独立的表达形式，就越容易在不同使用场景下复用和测试。

不过，代码层面的依赖反转、接口抽象和端口适配器还可以继续深入。此处先建立职责分离的基础，后续讨论设计原则和 DDD 时，再研究如何让业务核心完全不依赖具体基础设施。

## 四、Router、Service 和 Repository

### 1. Router 处理与 HTTP 有关的事情

路由层负责将 HTTP 世界中的请求转换为应用可以理解的输入，再把应用结果转换为 HTTP 响应。它通常需要处理路径、方法、认证授权的接入、请求参数和响应格式、状态码与异常映射等问题。

例如，商品不存在时返回 404，库存不足时返回 409。这些是接口层对业务结果的表达方式。同一个业务错误在命令行程序中可能表现为终端提示，在消息消费者中则可能对应重试或死信处理。

因此，Service 抛出 `ProductNotFound`、`InsufficientStock` 等具有业务含义的异常，Router 再映射为 `HTTPException`，通常比直接在 Service 中抛出 HTTP 异常更容易复用。

输入校验也存在层次区别。`quantity` 在 HTTP 请求中必须是整数、且大于零，可以由 Pydantic 先行拒绝非法请求；但“不允许购买超过现有库存的数量”依赖数据库中的当前业务状态，必须在业务操作中保证。只依靠请求模型的校验无法维护并发条件下的数据一致性。

### 2. Service 表达一个可以执行的业务用例

Service 一词在不同项目中含义差别很大。这里指应用服务，也就是提供“创建订单”“取消订单”“确认收货”等业务操作的边界。

一个创建订单的用例需要确定操作顺序：验证输入，读取商品，根据当前规则计算价格，扣减库存，生成订单，并在成功时提交事务。它涉及多个对象和数据操作，需要一个地方负责组织这些步骤。

Service 可以包含简单的业务判断，但不意味着全部业务规则都应该堆放在一个庞大的 `OrderService` 类中。优惠计算如果能够独立表达，就可以交给定价函数或定价模块；复杂订单状态转换可以由领域对象负责。应用服务负责用例的组织以及事务边界，领域规则则根据复杂程度安排在合适的位置。

Martin Fowler 对 Service Layer 的描述也强调它作为应用操作边界的作用：多个外部入口可以通过同一个服务层调用应用能力，并由它协调业务处理。对于更复杂的领域模型，Service Layer 可以保持较薄，将业务规则交给领域对象，而不必把所有计算都塞进服务方法。

### 3. Repository 管理持久化访问

Repository 通常被译为仓储。它向上层提供读取和保存业务数据的操作，并将 SQL、ORM 查询表达式等数据访问细节集中管理。

例如，Service 需要取得商品，可以调用 `product_repo.get(product_id)`；需要扣减库存，可以调用 `product_repo.decrease_stock(product_id, quantity)`。Service 由此不必自己组织 `select()`、`update()` 语句。

这种职责划分不是要求每个 ORM 表都创建一个拥有 `add()`、`get()`、`update()`、`delete()` 的通用 Repository。对于简单项目，SQLAlchemy 已经提供了丰富的数据映射与查询能力，机械包裹一层同名 CRUD 方法，可能只会增加代码跳转。

Repository 真正有价值的场景，是数据访问具有可复用的查询语义，或者持久化细节需要独立管理。在复杂领域模型中，经典 Repository 模式还强调像访问对象集合一样访问领域对象，以隔离数据库映射细节。很多项目将“封装 SQLAlchemy 查询的类”也称为 Repository，但它未必完全实现了这一经典模式。

Repository 一般不应在每次 `add()` 或 `update()` 后自行提交事务。否则，一个业务用例跨越多个仓储操作时，先完成的数据库修改可能已经提交，后续失败也无法整体回滚。

### 4. ORM Model、Schema 和领域模型

Python 项目里经常出现多个名称相近的 Model。它们虽然都描述数据，却分别服务于不同目的。

Pydantic Schema 或 DTO 可以定义请求与响应的数据契约，负责类型转换和必要的输入约束。SQLAlchemy ORM Model 定义对象与数据库表之间的映射，包括列、主外键和关联。领域模型则表达业务概念、状态和行为，不必与数据库表具有一一对应关系。

简单系统可以直接让 ORM 对象承载部分业务行为，避免为了纯粹的形式分离而增加大量映射代码。复杂系统若需要严格隔离持久化机制，则可以使用独立领域对象和映射器。选择哪种方式，应当取决于领域逻辑的复杂度、依赖稳定性及映射成本。

更重要的是，不要把请求 Schema 直接当成数据库表结构的替身，也不要把数据库所有字段都原样暴露给外部。接口、持久化和业务语义变化的原因并不完全相同。

## 五、一个完整的分层示例

前面讨论的职责可以放进一个简化项目中。这个例子使用 FastAPI、Pydantic v2、SQLAlchemy 2.0 的异步接口和 SQLite。为了便于本地运行，启动时自动建表并准备一条测试商品。实际项目应使用数据库迁移工具管理表结构。

这里以人民币“分”为金额单位，避免用浮点数表示金额。VIP 订单满 200 元享受九折，优惠金额按四舍五入取整到分。商品库存不能为负，一次创建订单需要同时完成库存扣减和订单保存。

项目结构如下：

```text
app/
├── __init__.py
├── main.py
├── db.py
├── models.py
├── repositories.py
├── service.py
└── api.py
```

### 1. 数据库会话和持久化模型

在 `db.py` 中创建数据库引擎与会话工厂。`get_session()` 用于为 HTTP 请求提供一个独立的 `AsyncSession`，并在使用结束后关闭它。

```python
# app/db.py
from collections.abc import AsyncIterator

from sqlalchemy.ext.asyncio import (
    AsyncSession, async_sessionmaker, create_async_engine,
)
from sqlalchemy.orm import DeclarativeBase


class Base(DeclarativeBase):
    pass


engine = create_async_engine("sqlite+aiosqlite:///./demo.db")
SessionFactory = async_sessionmaker(engine, expire_on_commit=False)


async def get_session() -> AsyncIterator[AsyncSession]:
    async with SessionFactory() as session:
        yield session
```

在 `models.py` 中定义商品和订单表。数据库约束是业务校验之外的又一道保护，它可以阻止库存被持久化为负数，但本身并不替代订单创建流程中的条件更新。

```python
# app/models.py
from sqlalchemy import CheckConstraint, ForeignKey
from sqlalchemy.orm import Mapped, mapped_column

from .db import Base


class Product(Base):
    __tablename__ = "products"
    __table_args__ = (
        CheckConstraint("price_cents >= 0"),
        CheckConstraint("stock >= 0"),
    )

    id: Mapped[int] = mapped_column(primary_key=True)
    price_cents: Mapped[int]
    stock: Mapped[int]


class Order(Base):
    __tablename__ = "orders"

    id: Mapped[int] = mapped_column(primary_key=True)
    product_id: Mapped[int] = mapped_column(ForeignKey("products.id"))
    quantity: Mapped[int]
    unit_price_cents: Mapped[int]
    discount_cents: Mapped[int]
    payable_cents: Mapped[int]
```

### 2. Repository 不决定何时提交

仓储负责数据库访问，使用同一个传入的 Session。库存扣减采用带条件的单条 `UPDATE`，只有当前库存足够时才更新成功。

```python
# app/repositories.py
from sqlalchemy import update
from sqlalchemy.ext.asyncio import AsyncSession

from .models import Order, Product


class ProductRepository:
    def __init__(self, session: AsyncSession):
        self.session = session

    async def get(self, product_id: int) -> Product | None:
        return await self.session.get(Product, product_id)

    async def decrease_stock(self, product_id: int, quantity: int) -> bool:
        statement = (
            update(Product)
            .where(Product.id == product_id, Product.stock >= quantity)
            .values(stock=Product.stock - quantity)
        )
        result = await self.session.execute(statement)
        return result.rowcount == 1


class OrderRepository:
    def __init__(self, session: AsyncSession):
        self.session = session

    async def add(self, order: Order) -> None:
        self.session.add(order)
        await self.session.flush()
```

`flush()` 会把当前待执行的数据库操作发送到数据库，使自增主键等结果在事务内部可用，但它不会提交事务。仓储因此可以完成数据访问任务，而把最终提交或回滚的决定留给负责整个用例的代码。

### 3. Service 组织业务操作

在 `service.py` 中，业务异常不依赖 HTTP。价格计算写成独立的纯函数，创建订单则由应用服务组织。

```python
# app/service.py
from dataclasses import dataclass
from sqlalchemy.ext.asyncio import AsyncSession

from .models import Order
from .repositories import OrderRepository, ProductRepository


class ProductNotFound(Exception):
    pass


class InsufficientStock(Exception):
    pass


@dataclass(frozen=True)
class OrderResult:
    order_id: int
    payable_cents: int


def calculate_discount(amount_cents: int, level: str) -> int:
    if level == "VIP" and amount_cents >= 20_000:
        return (amount_cents + 5) // 10
    return 0


class OrderService:
    def __init__(self, session: AsyncSession):
        self.session = session
        self.products = ProductRepository(session)
        self.orders = OrderRepository(session)

    async def create(self, product_id: int, quantity: int, level: str) -> OrderResult:
        if quantity <= 0 or level not in {"VIP", "NORMAL"}:
            raise ValueError("订单参数无效")

        async with self.session.begin():
            product = await self.products.get(product_id)
            if product is None:
                raise ProductNotFound()

            amount = product.price_cents * quantity
            discount = calculate_discount(amount, level)

            if not await self.products.decrease_stock(product_id, quantity):
                raise InsufficientStock()

            order = Order(
                product_id=product_id,
                quantity=quantity,
                unit_price_cents=product.price_cents,
                discount_cents=discount,
                payable_cents=amount - discount,
            )
            await self.orders.add(order)
            return OrderResult(order.id, order.payable_cents)
```

这里需要关注的地方是 `async with self.session.begin()`。它包围了读取商品、扣减库存和创建订单的过程。正常退出时事务提交，抛出异常时事务回滚。因此，扣减库存成功但创建订单失败，不会留下已经提交的库存变化。

库存操作使用条件更新，也避免了单纯“先查库存、再按读到的旧值写回”所带来的典型并发风险。但商品价格的并发修改、重复请求的幂等性和订单生命周期管理，仍然需要额外的业务策略。这个例子只覆盖单商品订单创建所需的基本一致性。

### 4. Router 负责转换 HTTP 请求和响应

HTTP 层可以专注于输入输出以及业务错误到 HTTP 状态码的映射。

```python
# app/api.py
from typing import Annotated, Literal

from fastapi import APIRouter, Depends, HTTPException
from pydantic import BaseModel, Field
from sqlalchemy.ext.asyncio import AsyncSession

from .db import get_session
from .service import (
    InsufficientStock, OrderService, ProductNotFound,
)


router = APIRouter()


class OrderCreate(BaseModel):
    product_id: int = Field(gt=0)
    quantity: int = Field(gt=0)
    level: Literal["VIP", "NORMAL"]


class OrderCreated(BaseModel):
    order_id: int
    payable_cents: int


@router.post("/orders", response_model=OrderCreated, status_code=201)
async def create_order(
    data: OrderCreate,
    session: Annotated[AsyncSession, Depends(get_session)],
) -> OrderCreated:
    try:
        result = await OrderService(session).create(
            data.product_id, data.quantity, data.level
        )
    except ProductNotFound as exc:
        raise HTTPException(404, "商品不存在") from exc
    except InsufficientStock as exc:
        raise HTTPException(409, "库存不足") from exc

    return OrderCreated(
        order_id=result.order_id,
        payable_cents=result.payable_cents,
    )
```

如果创建订单失败，Router 可以选择如何对外表达错误，但它并不负责决定库存扣减和订单保存的事务顺序。Service 也不需要知道最终是否返回 JSON。

### 5. 组装应用并运行

最后，在 `main.py` 中组装接口，并准备一条价值 300 元、库存为 10 的测试商品。

```python
# app/main.py
from contextlib import asynccontextmanager

from fastapi import FastAPI

from .api import router
from .db import Base, SessionFactory, engine
from .models import Product


@asynccontextmanager
async def lifespan(app: FastAPI):
    async with engine.begin() as connection:
        await connection.run_sync(Base.metadata.create_all)

    async with SessionFactory() as session:
        async with session.begin():
            if await session.get(Product, 1) is None:
                session.add(Product(id=1, price_cents=30_000, stock=10))

    yield
    await engine.dispose()


app = FastAPI(lifespan=lifespan)
app.include_router(router)
```

安装依赖并启动服务：

```bash
python -m pip install 'fastapi' 'uvicorn' 'SQLAlchemy>=2.0,<2.1' 'aiosqlite'
uvicorn app.main:app --reload
```

发送订单请求：

```bash
curl -X POST 'http://127.0.0.1:8000/orders' \
  -H 'Content-Type: application/json' \
  -d '{"product_id":1,"quantity":1,"level":"VIP"}'
```

首次成功创建时，应得到类似 `{"order_id":1,"payable_cents":27000}` 的响应。这个请求所经过的代码路径是确定的：Router 完成 HTTP 数据转换，Service 组织创建订单的步骤，Repository 负责执行数据库操作，SQLAlchemy Session 将相关操作放在同一个数据库事务中。

示例使用 SQLite 是为了降低本地运行门槛。需要在正式项目中处理多用户高并发、隔离级别、价格快照、幂等性及性能时，应结合所选数据库（如 PostgreSQL）重新验证一致性方案。演示中的启动建表与测试数据初始化也应该替换为迁移和独立的数据准备流程。

## 六、事务与业务操作边界

### 1. Session 的生命周期和事务边界是两回事

前面的代码中，FastAPI 依赖函数为请求创建并关闭 Session，Service 则使用 `session.begin()` 确定事务的提交或回滚范围。两者承担不同职责。

SQLAlchemy 的 Session 是 ORM 工作状态和数据库交互的管理单元。它能够追踪对象变更、执行查询、协调 flush 和事务。创建 Session 并不等于立即完成一次数据库提交，关闭 Session 也不应该被当成“业务成功”的信号。

把 Session 的生命周期设置为一次 HTTP 请求，是 Web 项目中常见的便利做法，但不是强制规则。如果一个请求包含多个需要独立提交的业务操作，事务范围就未必与整个请求相同；如果一次业务操作来自后台任务，它也应该能够在没有 HTTP 请求的情况下管理会话和事务。

值得注意的是，默认行为下 SQLAlchemy Session 可能通过 autobegin 在首次需要时自动开始事务。因此，如果在 `session.begin()` 之前已经使用同一个 Session 执行了查询，再进入显式 `begin()`，可能遇到“事务已经开始”的错误。示例将所有数据库访问都放在显式事务块内部，避免了这一问题。

### 2. 为什么 Repository 不宜自行 commit

假设订单创建需要两个数据库更新：先扣库存，再写订单。如果 `ProductRepository.decrease_stock()` 自行提交，随后 `OrderRepository.add()` 因数据库约束失败，库存变更已经持久化。即使后一个操作执行回滚，也无法撤销前一个已提交的事务。

由负责整个业务用例的一方掌握事务范围，可以将多个仓储操作纳入同一个原子提交单元。这也是工作单元（Unit of Work）思想与分层应用常见的结合点。

但事务边界不一定永远由某个名叫 Service 的类直接操作。项目也可以引入单独的 Unit of Work 对象，由应用服务使用它来协调多个仓储。关键在于业务操作必须有明确且一致的提交责任，而不是某个固定的代码位置。

### 3. 数据库事务不能自动覆盖外部系统

如果订单创建还需要发送邮件、调用支付网关或发布 MQ 消息，情况会复杂得多。普通数据库事务只能保证其覆盖的数据库操作按照该数据库的事务语义提交或回滚，并不能自动撤销已经发送的邮件或外部 HTTP 请求。

如果在数据库提交前调用外部系统，数据库随后回滚可能造成外部副作用已经发生；如果先提交数据库再发送消息，进程在两者之间崩溃，又可能造成消息丢失。

因此，分层只是为这些操作安排职责，无法单独解决跨系统一致性。可靠事件发布可能需要事务性 Outbox、消息重试和幂等处理；复杂的跨系统流程可能需要补偿操作或其他协调机制。这些机制值得在后续事务与消息队列专题中展开，但它们属于一致性问题，不能靠多加一个 Service 或 Repository 自动获得。

## 七、分层后的思考

### 1. 不能让 Service 变成新的巨型模块

路由变薄之后，常见的下一步是把原来写在 Router 中的代码整体搬进 `OrderService`。项目表面上有了层次，但订单创建、取消、审核、导出和各种规则都集中在一个类里。新的需求最终还是需要不断修改它。

这说明层次划分与业务模块划分是两件事。Router、Service、Repository 主要区分技术职责；订单、价格、库存则区分业务职责。一个项目既可以按业务模块组织目录，也可以在各业务模块内使用分层结构。

随着系统增长，可以把定价规则安排在价格模块，把库存约束放在库存相关的业务组件中，把创建订单的步骤留给订单用例协调。这样不仅入口与存储分离，业务内部的变化来源也得到了进一步区分。

### 2. 应用服务与领域规则如何配合

对于简单业务，应用服务直接执行几条业务判断并无不可。复杂性增加之后，把所有规则写成流程化的 `if` 判断会变得难以维护，尤其是状态转换、不变量和多项规则需要保持一致时。

这时可以采用更明确的领域对象或领域服务。例如，订单是否允许取消属于订单生命周期的规则，可能由订单对象的行为维护；计算优惠属于定价规则，可以交给定价组件；创建订单所需要的查询、调用和事务组织，则仍由应用服务负责。

不应把“Service 不能写业务逻辑”当成放之四海而皆准的规定。所谓应用服务、领域服务与事务脚本，是不同设计方法中的术语。一个规模很小的系统可以使用事务脚本式服务完成业务操作；当业务模型足够复杂时，再将规则转移到更有表达力的领域模型中。

设计是否合理，需要看规则是否有明确归属，以及修改某一项规则时是否必须穿过无关模块，而不是简单统计 Service 的代码行数。

### 3. 查询路径不必照搬写入路径

创建订单涉及数据修改、业务不变量和事务，设计时需要格外注意一致性。后台列表查询则主要关注过滤、关联、排序和分页。如果为了遵守统一结构，要求所有查询必须先创建领域对象，再由 Service 一层层转换，可能带来不必要的内存消耗和代码复杂度。

一些系统会让只读查询直接通过专门的 Query Service 或查询 Repository 返回面向展示的数据结构，而写入流程保留完整的业务约束。这并不意味着放弃分层，而是承认读写操作的关注点不同。

尤其是分页、聚合报表和多表检索，经常需要数据库直接完成过滤与聚合。如果 Repository 的抽象迫使程序先加载全部记录，再在 Python 中筛选，就说明抽象正在妨碍正确而高效的数据访问。

## 八、如何判断这样的分层是否值得

判断一次重构是否改善了设计，可以回到上一篇文章提出的变化传播问题。

如果把 REST API 改成由 MCP 工具调用，是否需要重新实现订单优惠与扣库存？如果数据库查询从简单主键查找改成更复杂的 SQL，HTTP 层是否必须跟着修改？如果优惠规则发生变化，创建订单、订单预览和后台试算是否仍然各自维护条件判断？

这些问题比检查目录是否包含 `api/`、`service/` 和 `repository/` 更有意义。

测试也能暴露边界是否清晰。定价规则可以通过纯函数测试验证门槛、边界金额和舍入约定；应用服务可以用真实数据库或明确约定的仓储替身验证创建流程；HTTP 测试则重点检查参数校验、状态码、响应结构和异常映射。

不过，可测试性不能作为唯一标准。为了方便 Mock 而给每一个简单函数增加接口和类，会带来额外维护成本。尤其是在 SQLAlchemy 已经提供 Session、映射和查询能力的情况下，完全重复其功能的抽象未必值得保留。

小项目可以直接采用 Router 加少量业务函数，在有明确重复查询或复杂业务流程时再引入 Service 和 Repository。持续增长的业务系统则更有理由及早区分 HTTP 入口、用例协调与持久化责任。合理的分层程度取决于变化频率、团队规模、业务复杂度及预期寿命。

因此，MVC 和分层架构提供的是职责组织的方法，而不是能够照搬的目录模板。它们的共同价值，是通过划定边界减少无关知识之间的依赖。一个设计是否成功，最终要看真实需求发生变化时，修改能否相对集中，调用方是否能够依赖明确的契约，以及新增抽象带来的成本是否得到补偿。

下一篇将进一步讨论 SOLID、KISS、DRY 和 YAGNI。这些原则经常被当成独立的编码规范，实际上它们与前两篇讨论的职责、依赖、变化和抽象成本有直接关系。理解了分层为什么存在，才能更具体地判断什么时候应该提取接口、减少重复，或者停止增加设计层次。
